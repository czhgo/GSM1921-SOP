## 上下文丢失后制度推断陷阱（原 KNOWN_PITFALLS §4 + insights §6.5）

**原则**：上下文丢失后，不得自行推断制度安排，必须读取 CLAUDE.md 和对应 guides 确认。

**判例**：赋权关系链修正了三轮——第一轮遗漏了组织委员的专班赋权，第二轮混淆了只读视图的继承关系（历史设计：管理者只读继承管理模式/成员只读独立视图，2026-08-05 权限重构后已废弃），第三轮才与 COMMISSIONER_FRAMEWORK.md 对齐。

**纠正**：遇到权限/角色/制度相关问题时，先读取对应 guides 文件确认，再动手修改代码。

**反面论证**：为什么不每次都读取所有 guides？因为 token 有限，按需读取更高效。判断标准：涉及角色/权限/制度 → 必须读取对应 guide。

**判例补充（原 insights §6.5，与上判例同事件合并）**：赋权链三轮修正的每一轮错误都源于对制度理解的偏差，而非技术错误——制度文件中已明确的规则必须在代码中精确实现；CLAUDE.md 是最高制度母本，写代码前先读 CLAUDE.md。

## 党小组轮值过度推定事件——"听起来合理"不是制度依据（原 insights §6.1）

**判例**：CLAUDE.md ASCII 决策示意图中，主题党日的承办方被写为"承办: 党小组轮值"。纠正：主题党日从未被制度规定为党小组轮值，正确表述是"承办: 按需指定党小组"。

**根因**：AI 在缺乏明确制度依据的情况下，基于「轮值即公平」的惯性思维做出了过度推定。

**教训**：任何涉及制度安排的表述，必须有母本溯源。"听起来合理"不是制度依据。与上文「上下文丢失后制度推断陷阱」同族（AI 自行推断制度）——但本判例不依赖"上下文丢失"触发，AI 在正常工作中同样可能以惯性思维过度推定制度，故独立成节；两者的纠正一致：涉及制度先读母本（CLAUDE.md/guides）确认。

## 上下文丢失教训（原 KNOWN_PITFALLS §8）

> **本节为 CLAUDE.md 甲部冷层（H90 外部权威源索引）外移归位**。保留原 10 条原则级提醒，供 Agent 在上下文丢失后按需读取，避免重复犯错。

1. **文件修改必须验证持久化**：Edit工具可能报告成功但未写入磁盘，关键文件修改后必须用Python验证
2. **一改具改必须全仓搜索确认零残留**：不能只改"最明显的几处"
3. **临时文件用完即删**：零容忍.bak/.py遗留，可复用工具归入.tools/
4. **不得自行推断制度安排**：涉及权限/角色/制度时，先读guides确认
5. **经验沉淀写入前检查定位**：确认内容与目标文件定位匹配
6. **选择最合适的工具**：MCP工具 > LLM推理 > Python脚本（仅批量操作）
7. **终端命令禁止写入含中文的文件内容**：PowerShell默认编码可能损坏UTF-8文件。禁止使用`[System.IO.File]::WriteAllText`或`Set-Content`等命令写入含中文的文件。文件写入必须使用Edit/Write工具，终端仅用于读取验证（`Select-String`、`Get-Content`等）
8. **对话回退后必须审计仓库实际状态**：回退可能导致部分文件回退、部分未回退的不一致。恢复后必须用Grep/Read检查关键文件的实际内容，以磁盘为准更新乙部
9. **Read 工具可能返回缓存内容**：Read 工具对 CLAUDE.md 等大文件可能返回与磁盘不一致的缓存内容，与 Edit 工具的"虚假成功"叠加形成误判。验证文件修改必须用 Python `open()` 读回确认，不得仅依赖 Read 工具
10. **决策中阐述的重要原则必须检查是否写入 guides/Harness**（论断 P-018，2026-08-09 自论断汇编迁出）：当决策中阐述的原则超越本次决策、具有长期指导意义时，必须：(a) 写入决策日志；(b) 检查是否需要写入 guides 的对应文件；(c) 若原则具有全局约束力，写入 Harness 对应章节。不得仅记录决策结果而不沉淀原则
11. **同区域连续 Edit 相互覆盖**：对同一文件同一区域连续/并行编辑时，后一次 Edit 可能把前一次改写"还原"为原文。每次编辑后必须用 Read 复核该区域实际状态，不依赖 Edit 的返回输出（详见 §14）

## 对话总结虚假完成陷阱（原 KNOWN_PITFALLS §9）

**原则**：接续会话开始新工作前，必须用 Grep 验证前序会话的"对话总结"描述与实际代码状态一致，不得仅凭总结描述就认为某项修改已完成。

**判例**：T94 权限系统第 4 轮成果补强时，前序会话的对话总结声称"11 个 entry 已添加 storageKey 参数"，但接续会话 Grep 验证发现实际只有 6 个 entry 添加了 storageKey，5 个 entry（party-disc/party-org/party-secretary/ws-prop-commissioner/ws-disc-commissioner）完全未添加；另有 2 个 entry（ws-deep/ws-leader）虽有 storageKey 但 activate 仍为硬编码未改为 activeTab。总共 7 处遗漏。

**根因**：AI 在生成长会话的对话总结时，可能基于"应该完成"的预期而非"实际完成"的证据描述工作成果。特别是在多轮工具调用、多文件修改的长会话中，AI 可能将"计划中的修改"误记为"已执行的修改"。这与 §1 的"Edit 虚假成功"不同——§1 是工具返回值与磁盘状态不符，本节是 AI 总结描述与磁盘状态不符。

**纠正（验证策略）**：

| 场景 | 验证方式 |
|---|---|
| 接续会话开始前 | Grep 验证前序总结声称的"已修改文件清单"与代码实际状态一致 |
| 会话结束前 | verification-before-completion（Grep 零残留 + GetDiagnostics） |
| 对话总结生成时 | "已修改文件清单"必须附 Grep 验证证据，不得仅描述"已添加/已修改" |

**为什么必须 Grep 验证而非信任总结？** 因为总结是 AI 生成的内容，可能包含"应该完成"的预期描述。Grep 是对磁盘状态的直接查询，不受 AI 记忆影响。信任总结等同于信任一个可能基于错误前提的描述。

**为什么不是"每次会话都重新审计所有文件"？** 因为接续会话只需验证"前序总结声称的修改清单"，不需要全仓库审计。判断标准：前序总结提到的每个"已修改文件"都应用 Grep 验证关键标识符是否存在。

**为什么不是"Edit 失败"问题？** 因为如果 Edit 工具报告失败，前序会话会立即重试或换用 Write。本次问题是 Edit 可能成功执行了部分修改（tab-bar.js 组件改造），但 entry 调用方的修改（添加 storageKey 参数）未执行——AI 在总结时将"计划"误记为"已完成"。这是 AI 认知层面的问题，不是工具执行层面的问题。

**与 §1 的区别**：§1 是"Edit 报告成功但磁盘未持久化"（工具层面），纠正措施是改用 Write。§9 是"AI 总结声称完成但磁盘未执行"（认知层面），纠正措施是 Grep 验证。两者可能叠加——Edit 虚假成功 + AI 总结虚假完成，但根因不同，纠正措施也不同。

**生效条件**：仅适用于"接续会话"场景——前序会话留下对话总结，接续会话基于总结继续工作。同一会话内不适用（因为 AI 清楚知道自己刚做了什么）。

**防范措施三层**：
1. 会话内：每次"完成一批修改"后立即运行 Grep 验证，不等到会话结束
2. 会话末：verification-before-completion（Grep 零残留 + GetDiagnostics）作为强制出口
3. 接续会话首：Grep 验证前序总结声称的修改清单与代码实际状态一致后再开始新工作

## 上下文丢失与交接协议（原 insights §3.1）

**四重丢失场景**：

| 场景    | 触发条件            | 影响            |
| ----- | --------------- | ------------- |
| 会话重启  | 上下文窗口满 / IDE 重启 | 全部任务进度、设计决策丢失 |
| 长任务中断 | 对话超出上下文窗口容量     | 前半段上下文丢失      |
| 跨日继续  | 用户隔天继续工作        | 无法知道上次断点      |
| 方向变更  | 用户在会话中改变需求方向    | 旧方向与新方向混淆     |

**会话交接协议**：每次会话结束前，必须捕获当前任务清单及完成状态、本会话修改的文件列表、关键设计决策、下一步待办、未解决的阻塞项。

**为什么不能"下次再回忆"？** 因为 AI 每次会话都是"失忆"的。没有书面交接，下次会话只能从零开始推断——而推断的准确率远低于书面记录。本篇各节（制度推断陷阱/对话总结虚假完成陷阱）的判例即交接缺位的后果实例。

## 减负审查标准（原 insights §2.1）

每一项产出物必须通过三重检验，任一不通过即视为"伪需求"：

| 验证   | 问题                | 不通过后果       |
| ---- | ----------------- | ----------- |
| 硬性要求 | 上级是否有明文规定？        | 无制度依据 → 伪需求 |
| 无重叠  | 是否已有其他产出物覆盖？      | 冗余 → 合并或删除  |
| 防真空  | 删除后是否造成工作断点或归档缺失？ | 结构性需求 → 保留  |

党务层的产出物审查可独立于党建层进行——奥卡姆剃刀可以更精准地切割。

**为什么不做"保留一切以防万一"？** 因为保留一切等于不筛选——"万一"的可能性无限，而注意力是有限的。每一项"看起来存在"的产出物都会被纳入管理者的工作预期，伪需求占据的是注意成本，而非存储空间。防真空检验已经划定了"结构性需求必须保留"的边界，"保留一切"是在边界内的过度保守。

**生效条件**：任何新增产出物/待办/上下文条目前的取舍审查；与下节「工作上下文只留当前」配套执行。

## 工作上下文只留当前——完成即归档（原 insights §2.2）

工作上下文文件只保留未来待办与待决策，已完成工作归入归档日志——每次上下文加载都是成本，历史信息不应白白消耗注意成本；"保留约束"不等于"保留全文"，上下文只需知道结论，约束细节归日志。项目落地：CLAUDE.md H50.1 乙部任务生命周期。

## 三种决策状态的语义区分（原 insights §2.5）

在待决策事项管理机制中，三种状态有明确的语义边界：

| 状态         | 语义                  | 判断性质 | 生命周期        |
| ---------- | ------------------- | ---- | ----------- |
| **待决策**    | 决策人尚未选择方向            | 未决策  | 停留在待决策池，等待判断 |
| **搁置**     | 决策人已决定"现在不做"，保留未来可能性 | 时机判断 | 退出待决策池，记录决策日志 |
| **删除/不需要** | 决策人已决定"明确不需要"        | 终局判断 | 退出待决策池，记录决策日志 |

**关键区分**：待决策→搁置是从"未决策"到"已决策"的跨越；搁置→不需要是从"时机判断"到"终局判断"的跨越。混同这三种状态会导致两种后果：待决策池堆积已决策事项（真正需要决策的事项被淹没）；终局判断的事项以"搁置"形式长期占用决策注意力（虚假希望和认知负担）。

> **普适性支撑**（2026-07-19 联网补充）：业界 AI 状态管理普遍采用 planned/committed 区分（待决策≈planned，搁置≈committed 但未执行）和 TTL 删除/deferred 区分（不需要≈TTL 过期删除，搁置≈deferred 延后保留）。本项目机制比业界自动化状态机更严格——每条状态变更都经人类决策，而非系统自动转换。详见 P.7 决策归档。

## 看板归档：只展示需关注的工作（原 insights §2.6）

看板中已完成的任务不展示，完成即归档。这属于"信息聚焦"——看板只展示需要关注的工作。

**信息聚焦原则**：看板只展示需要关注的工作。信息展示的终极目标是让用户一眼看到"需要我做什么"，而非"已经做了什么"。已完成的工作归入归档库，需要时可以查阅，但不应占据管理者的日常视野。子任务的完成状态是上级任务进度的依据——灰显+删除线+沉底，既不争夺注意力，又保留进度可追溯性。顶层任务完成即归档（脱离视野），子任务完成即降权（留在视野但降低权重）。

## 用核心原则治理项目：原则—待办—待决策三分层（原 insights §3.2）

用一套长期稳定的核心原则文件治理项目——定义工作方式、核心原则和运行标准。这类设计从反复踩坑中长成方法论，具有长期稳定性。

**三层结构**（本项目判例：CLAUDE.md 甲部 Harness / 乙部执行事项 / 丙部待决策）：

| 层       | 定位               | 生命周期            | 核心约束                    |
| ----------- | ---------------- | --------------- | ----------------------- |
| 核心原则层   | 核心原则——原则+判例+运行标准 | 最稳定，修改须决策人确认     | 修改一处即全仓同步：修改一项原则，所有相关引用同步更新 |
| 执行事项层   | 当前工作上下文          | 完成即删，补充新项          | 不堆积历史，上下文只保留当前待办        |
| 待决策层    | 问题池——拿不定主意的事项    | 决策后删除           | 不得自行决定需要决策人判断的事项      |

**为什么需要三层而非一层？** 因为"原则""待办""待决策"的信息生命周期完全不同——原则稳定不变，待办频繁更替，待决策需要人工介入。混在一起会导致：原则被待办淹没（白白消耗注意成本），待办被原则撑大（上下文浪费），待决策被 AI 自行消化（越权风险）。

**核心原则文件内的上下文分层**：核心原则文件从单一层次重组为热层（每次必读）→温层（修改时读）→冷层（按需参考，外移至扩展文档）三层架构。热层放"怎么做"，冷层放"是什么"和"为什么"，温层是两者之间的缓冲。

**为什么不是"全部放核心原则文件"？** 因为 AI 每次会话加载上下文是有成本的。热层只保留"怎么做"的执行规则，将上下文成本降至最低。

**为什么不是"全部外移只留链接"？** 因为链接依赖 AI 的主动读取行为——而 AI 在执行任务时不会主动去读冷层文件。温层的设计解决了这个矛盾：修改文件时必须读取温层，既不膨胀热层，又不丢失关键规则。

**为什么需要温层而非只有热冷两层？** 因为有些规则不是每次都需要，却在特定场景下必须遵守。温层是"条件触发"的读取层——修改时读，不修改时不读。

**同步修改的执行代价**：修改核心原则层任何一项原则，必须全仓搜索所有引用位置并逐一替换。散落导致漂移与不一致——同一概念在多文件表达时，修改一处遗漏另一处的代价远高于逐一替换的执行成本。

## 上下文工程：让上下文持续有效（原 insights §3.3）

上下文工程解决的核心问题是：在 AI 辅助项目中，如何让上下文在会话间持续有效？

**四种载体及其分工**：

| 载体   | 记录什么    | 谁写入         | 谁读取               | 生命周期 |
| ---- | ------- | ----------- | ----------------- | ---- |
| 操作日志 | 做了什么    | AI          | 下次接手的 AI（恢复上下文）   | 月度归档 |
| 决策档案 | 为什么这样做  | AI（记录决策人的决策） | 决策人与执行人（理解为什么）、经验沉淀 | 持续追加 |
| 状态快照 | 记录当前状态 | AI（触发条件满足时） | AI（了解基线）          | 按需生成 |
| 到期提醒 | 周期性任务到期 | AI          | AI（自动唤醒）          | 持续更新 |

**为什么操作日志和决策档案必须分离？** 因为它们的读者和用途完全不同。操作日志是"操作记录"，读者是下次接手的 AI，用途是恢复上下文；决策档案是"决策记录"，读者是决策人与执行人，用途是理解"为什么"。混在一起会导致：AI 读取时被决策分析干扰（信息过载），决策人查阅时被操作细节淹没。

**快照按需生成**：快照仅按需更新（大版本升级、用户指令、阶段收官），日常变更由日志承载——教训详情见原 insights §6.8。快照是重方案，日志是轻方案，日常用轻量方案。

**关键交接协议从子步骤提升为独立章节**：交接信息（如 next_prompt）原本是执行流程的最后一个子步骤，但"禁止省略"的标注不足以防止遗漏——它被嵌入在流程末尾，视觉权重不够。提升为独立章节后，执行率显著提高。这揭示了一个通用原则：任何"每次必须执行但容易被遗忘"的规则，都应考虑从子步骤提升为独立章节。

**经验沉淀闭环**：日志作为沉淀的原料，从中提炼可复用模式，写入经验沉淀，形成"变更→记账→扫描→提炼→写入→标记"的闭环。日志是原始记录，经验沉淀是提炼后的知识，两者不可互相替代。

## 丙部触发条件：发现待决策项（D-207 判例，原 insights §6.11）

CHECKLIST §8.7 标记了 4 个"孤立组件"，AI 应将其写入丙部但未写入。H50.2 原仅覆盖"AI 拿不定主意"这一触发条件，未覆盖"AI 发现待决策项"的场景。

**根因**：H50.2 的触发条件设计只考虑了 AI 的主观困难（拿不定主意），未考虑 AI 的客观发现（识别出需要人类判断的事项）。后者是独立触发条件——AI 可能对某事项有自己的判断，但该事项涉及功能去留/设计方向，属于人类决策权范畴。

**教训**：丙部的触发条件有两个，逻辑不同：(1) 拿不定主意属主观困难（AI 无法判断方向）；(2) 发现待决策项属客观识别（AI 有判断但无权处置——功能去留和设计方向是人类的决策权，AI 可以有技术判断，但不能代替人类做制度性决策，这是权责边界问题，不是能力问题）。两者都应写入丙部，但触发原因不同。
