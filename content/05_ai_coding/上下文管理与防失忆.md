## 上下文丢失后制度推断陷阱（原 KNOWN_PITFALLS §4）

**原则**：上下文丢失后，不得自行推断制度安排，必须读取 CLAUDE.md 和对应 guides 确认。

**判例**：赋权关系链修正了三轮——第一轮遗漏了组织委员的专班赋权，第二轮混淆了只读视图的继承关系（历史设计：管理者只读继承管理模式/成员只读独立视图，2026-08-05 权限重构后已废弃），第三轮才与 COMMISSIONER_FRAMEWORK.md 对齐。

**纠正**：遇到权限/角色/制度相关问题时，先读取对应 guides 文件确认，再动手修改代码。

**反面论证**：为什么不每次都读取所有 guides？因为 token 有限，按需读取更高效。判断标准：涉及角色/权限/制度 → 必须读取对应 guide。

## 上下文丢失教训（原 KNOWN_PITFALLS §8）

> **本节为 CLAUDE.md 甲部冷层（H90 外部权威源索引）外移归位**。保留原 10 条原则级提醒，供 Agent 在上下文丢失后按需读取，避免重复犯错。
> 原则级提醒的索引见 [CLAUDE.md H90 外部权威源索引](../../CLAUDE.md)。

1. **文件修改必须验证持久化**：Edit工具可能报告成功但未写入磁盘，关键文件修改后必须用Python验证
2. **一改具改必须全仓搜索确认零残留**：不能只改"最明显的几处"
3. **临时文件用完即删**：零容忍.bak/.py遗留，可复用工具归入.tools/
4. **不得自行推断制度安排**：涉及权限/角色/制度时，先读guides确认
5. **经验沉淀写入前检查定位**：确认内容与目标文件定位匹配
6. **选择最合适的工具**：MCP工具 > LLM推理 > Python脚本（仅批量操作）
7. **终端命令禁止写入含中文的文件内容**：PowerShell默认编码可能损坏UTF-8文件。禁止使用`[System.IO.File]::WriteAllText`或`Set-Content`等命令写入含中文的文件。文件写入必须使用Edit/Write工具，终端仅用于读取验证（`Select-String`、`Get-Content`等）
8. **对话回退后必须审计仓库实际状态**：回退可能导致部分文件回退、部分未回退的不一致。恢复后必须用Grep/Read检查关键文件的实际内容，以磁盘为准更新乙部
9. **Read 工具可能返回缓存内容**：Read 工具对 CLAUDE.md 等大文件可能返回与磁盘不一致的缓存内容，与 Edit 工具的"虚假成功"叠加形成误判。验证文件修改必须用 Python `open()` 读回确认，不得仅依赖 Read 工具
10. **决策中阐述的重要原则必须检查是否写入 guides/Harness**（论断 P-018，2026-08-09 自论断汇编迁出）：当决策中阐述的原则超越本次决策、具有长期指导意义时，必须：(a) 写入决策日志；(b) 检查是否需要写入 guides 的对应文件；(c) 若原则具有全局约束力，写入 Harness 对应章节。不得仅记录决策结果而不沉淀原则
11. **同区域连续 Edit 相互覆盖**：对同一文件同一区域连续/并行编辑时，后一次 Edit 可能把前一次改写"还原"为原文。每次编辑后必须用 Read 复核该区域实际状态，不依赖 Edit 的返回输出（详见 §14）

## 对话总结虚假完成陷阱（原 KNOWN_PITFALLS §9）

**原则**：接续会话开始新工作前，必须用 Grep 验证前序会话的"对话总结"描述与实际代码状态一致，不得仅凭总结描述就认为某项修改已完成。

**判例**：T94 权限系统第 4 轮成果补强时，前序会话的对话总结声称"11 个 entry 已添加 storageKey 参数"，但接续会话 Grep 验证发现实际只有 6 个 entry 添加了 storageKey，5 个 entry（party-disc/party-org/party-secretary/ws-prop-commissioner/ws-disc-commissioner）完全未添加；另有 2 个 entry（ws-deep/ws-leader）虽有 storageKey 但 activate 仍为硬编码未改为 activeTab。总共 7 处遗漏。

**根因**：AI 在生成长会话的对话总结时，可能基于"应该完成"的预期而非"实际完成"的证据描述工作成果。特别是在多轮工具调用、多文件修改的长会话中，AI 可能将"计划中的修改"误记为"已执行的修改"。这与 §1 的"Edit 虚假成功"不同——§1 是工具返回值与磁盘状态不符，本节是 AI 总结描述与磁盘状态不符。

**纠正（验证策略）**：

| 场景 | 验证方式 |
|---|---|
| 接续会话开始前 | Grep 验证前序总结声称的"已修改文件清单"与代码实际状态一致 |
| 会话结束前 | verification-before-completion（Grep 零残留 + GetDiagnostics） |
| 对话总结生成时 | "已修改文件清单"必须附 Grep 验证证据，不得仅描述"已添加/已修改" |

**为什么必须 Grep 验证而非信任总结？** 因为总结是 AI 生成的内容，可能包含"应该完成"的预期描述。Grep 是对磁盘状态的直接查询，不受 AI 记忆影响。信任总结等同于信任一个可能基于错误前提的描述。

**为什么不是"每次会话都重新审计所有文件"？** 因为接续会话只需验证"前序总结声称的修改清单"，不需要全仓库审计。判断标准：前序总结提到的每个"已修改文件"都应用 Grep 验证关键标识符是否存在。

**为什么不是"Edit 失败"问题？** 因为如果 Edit 工具报告失败，前序会话会立即重试或换用 Write。本次问题是 Edit 可能成功执行了部分修改（tab-bar.js 组件改造），但 entry 调用方的修改（添加 storageKey 参数）未执行——AI 在总结时将"计划"误记为"已完成"。这是 AI 认知层面的问题，不是工具执行层面的问题。

**与 §1 的区别**：§1 是"Edit 报告成功但磁盘未持久化"（工具层面），纠正措施是改用 Write。§9 是"AI 总结声称完成但磁盘未执行"（认知层面），纠正措施是 Grep 验证。两者可能叠加——Edit 虚假成功 + AI 总结虚假完成，但根因不同，纠正措施也不同。

**生效条件**：仅适用于"接续会话"场景——前序会话留下对话总结，接续会话基于总结继续工作。同一会话内不适用（因为 AI 清楚知道自己刚做了什么）。

**防范措施三层**：
1. 会话内：每次"完成一批修改"后立即运行 Grep 验证，不等到会话结束
2. 会话末：verification-before-completion（Grep 零残留 + GetDiagnostics）作为强制出口
3. 接续会话首：Grep 验证前序总结声称的修改清单与代码实际状态一致后再开始新工作
