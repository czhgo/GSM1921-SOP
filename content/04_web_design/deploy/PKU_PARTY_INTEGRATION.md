## 一、背景与已确认事实

**需求（2026-08-19）**：
1. 明确「嫁接什么 API（尤其北大党校系统 + 智慧党建系统）」「随时爬取什么数据」「系统内部有哪些数据类型和字段」「微信小程序初步设计」——其中小程序为独立问题，设计内容已归位 [WECHAT_INTEGRATION.md](WECHAT_INTEGRATION.md)（2026-08-19 提出：「请一定要让对应的内容进入对应的文档」）。
2. 北大系统对接要提前思考清楚：如何爬取（都在北大服务器上，用什么工具）、信息如何协同——**他们的写入同步我们的写入；我们的写入也能同步到他们的写入**。
3. 全面性优先，避免对接时被动。

**已确认事实（2026-08-19 确认 + 公开信息核查）**：

| 项 | 事实 |
|----|------|
| 党校系统 | `dangxiao.pku.edu.cn`——北京大学党员教育培训平台；主办：北大党校办公室；技术支持：艾唯博瑞（联合北大研发「党校综合信息管理平台」）；登录：**北大统一身份认证（IAAA）** |
| 智慧党建平台 | 高校智慧党建生态（与党校系统同源厂商方案）：三会一课/组织生活网络记载、民主评议、党支部工作手册导出、党费统计、党员发展管理、与上级党建系统链通 |
| 支部权限 | —（本文件不假设支部有任何「管理权限」——对接授权来自党委组织部，见下行） |
| 对接授权 | **学校党委组织部支持技术对接、实现系统协同**（2026-08-19 与党委组织部老师交流确认）——对接是组织部门认可的协同工作，不是支部私下的爬取；具体接口/自动化方式仍按组织部流程确认（§九） |
| 同步方向裁决 | 党校系统：**单向爬取即可**（拉取，不写回）；智慧党建平台：**双向实时同步**（读 + 写） |
| 运行环境 | 爬取/同步任务跑在**校园网内**（如计算中心服务器） |

## 三、我们系统的数据类型与字段（对接映射的「我方」）

### 3.1 后端 26 资源表（server/db.js）

> 统一结构 `id + data JSON`（与前端数据结构完全一致，嵌套字段零损失）。会话与附件独立两表。

| 分类 | 表 | 与北大对接的字段交集 |
|------|-----|---------------------|
| 身份 | `users` | **personId（学号，主键锚）**、name、partyStatus（申请人/积极分子/发展对象/预备/正式）、role、梯队 |
| 党建活动 | `activities` / `act_sub_records` | 三会一课/主题党日：活动名、时间、地点、参与者 → 智慧党建「组织生活记载」 |
| 考察 | `inspections` | 考察记录（民主评议/谈话）：personId、结论、时间 → 智慧党建「民主评议」 |
| 发展流程 | `todos` / `tasks` / `assignments` | 发展任务节点、分工 → 智慧党建「党员发展管理」 |
| 考勤 | `attendances` / `makeup_tasks` | 出席/补课 → 党校「培训出勤」辅助核对 |
| 培训 | `notices` / `experience_deposits` | 通知、经验沉淀 → 党校「学习圈/院系活动」参照 |
| 组织 | `taskforces` / `tf_sub_records` | 专班工作 → 智慧党建「工作专班」 |
| 文档 | `branch_docs` / `file_space_records` / `archive_records` | 支部文件/档案 → 智慧党建「党支部工作手册」导出素材 |
| 协同 | `external_dispatches` / `mailbox_*` / `weekly_reports` / `signups` / `activity_reviews` / `taskforce_reviews` / `prop_tasks` / `compliance_references` / `image_records` | 无直接对接（内部工作流） |

### 3.2 关键映射字段（设计原则）

- **主键锚**：`users.personId = 北大统一身份（学号）`——两系统所有成员数据以此关联（党校按学号、智慧党建按学号/身份证）。
- **状态锚**：`partyStatus`（申请人→积极分子→发展对象→预备→正式）——与党校培训阶段、智慧党建发展流程一一对应，是双向同步的核心比对字段。
- **时间锚**：所有同步记录带 `recordedAt` + `updatedAt`（ISO）——冲突仲裁用（§七）。

## 四、数据映射设计（两系统 ↔ 我们）

| 业务域 | 我们系统 | 党校系统（读） | 智慧党建平台（双向） |
|--------|---------|--------------|-------------------|
| 培训进度 | users.partyStatus + notices | 各阶段培训完成/考试通过/学时 | — |
| 结业评议 | inspections（考察记录） | 结业评议结论 | 民主评议（相互参照） |
| 组织生活 | activities | — | 三会一课/主题党日记载（**双向**） |
| 党员发展 | todos（任务节点） | — | 发展流程（**双向**） |
| 党费 | — | — | 党费记录（读） |
| 支部手册 | branch_docs + archive_records | — | 工作手册导出素材（写） |

**映射规则**：学号匹配 + partyStatus 状态机对齐 + updatedAt 仲裁；无法自动匹配的记录进「待人工核对」队列（§七）。

## 五、党校系统：单向爬取方案

### 5.1 工具链（校园网内定时任务）

| 层 | 工具 | 理由 |
|----|------|------|
| 浏览器自动化 | **Playwright**（Node 生态，与 server/ 同栈） | 无头 Chromium 渲染 JS 页面；支持截图/网络拦截/表单；IAAA 登录态可持久化（storageState 复用，避免反复认证） |
| 调度 | **node-cron**（集成进 server/ 同步模块） | 与后端同进程，定时触发爬取 + 落库 |
| 数据落点 | 新增 `sync_logs` 资源表（或复用 `compliance_references` 旁挂） | 记录每次爬取的原始快照 + 映射结果 + 差异 |
| 凭证 | IAAA 统一认证（党委组织部对接账号）+ Playwright storageState | 校园网内可直接访问；凭据走环境变量，不入库不落盘明文 |

### 5.2 爬取流程

```text
定时触发（如每日 02:00 + 关键节点事件触发）
  → Playwright 启动 → 载入 storageState（IAAA 登录态）
  → 导航到学员列表 → 逐人抓取：培训阶段 / 课程完成度 / 章节自测 / 结业考试成绩 / 学时 / 结业评议
  → 结构化 JSON → 数据映射（学号匹配 users.personId）
  → 差异比对（与上次快照 diff）→ 更新 users / inspections 对应字段
  → 写 sync_logs（成功/失败/差异明细）→ 有差异推送通知（notices）
```

### 5.3 爬取频率策略

| 数据 | 频率 | 理由 |
|------|------|------|
| 培训阶段/完成度 | 每日一次 | 日常进度跟随 |
| 结业考试/评议结论 | 事件触发（阶段临近结业时加强） | 结论性数据，变更即同步 |
| 学时 | 每周汇总 | 变化平缓 |

### 5.4 风险与缓解

| 风险 | 缓解 |
|------|------|
| 页面结构变更 → 爬虫失效 | 选择器集中管理 + 失败告警（通知书记）+ 快照留档便于恢复 |
| IAAA 风控（异地/异常登录） | 校园网内 IP 稳定；登录频率控制；storageState 复用减少认证次数 |
| 自动化访问的实施口径 | 对接授权已获**党委组织部**支持（2026-08-19）；具体抓取方式/接口按组织部流程确认（§九 待确认项），不擅自实施 |

## 六、智慧党建平台：双向同步方案（理想 vs 现实）

### 6.1 技术现实声明（决策者须知情）

厂商系统（艾唯博瑞类）的「双向实时同步」**取决于平台是否开放 API/对接接口**。公开信息显示平台声称「与上级主管部门党建系统链通、一端录入多端使用」——说明**平台有系统间集成能力**，但对外部系统（如我们）是否开放写接口，**必须向厂商/信息中心确认**（§九）。

### 6.2 方案 A（理想）：平台开放 API/Webhook

```text
我们 ──→ 平台：POST /sync/activities（三会一课记载）、POST /sync/inspections（民主评议）、POST /sync/development（发展进度）
平台 ──→ 我们：Webhook 回调（平台记载变更 → 我们实时更新）
冲突仲裁：updatedAt + partyStatus 状态机（§七）
```

前置：平台提供 API 文档 + 认证（OAuth/密钥）+ Webhook 配置。**此方案若成立，双向实时可达。**

### 6.3 方案 B（现实）：组织部对接账号下的定时增量 + 导出导入

无 API 时，「双向实时」退化为**「双向 + 定时增量（分钟级/小时级）」**——在组织部对接账号能力范围内做到最接近实时：

| 方向 | 机制 | 工具 |
|------|------|------|
| 读（平台→我们） | 定时抓取后台记载（组织生活/民主评议/党费/发展进度）→ 映射落库 | Playwright 只读爬取（同 §五） |
| 写（我们→平台） | ① 若后台支持批量导入（Excel/CSV）→ 自动导出 + 文件导入；② 否则 → 表单自动化代填（**稳定性风险高，需与党委组织部确认实施口径后启用**） | 后台导入功能 + 生成标准 Excel（与平台模板对齐） |
| 冲突 | 以「平台权威 + 我们为工作台」为默认；两写冲突由 updatedAt + 人工复核队列仲裁 | sync_logs + notices 提醒 |

**设计取舍**：自动写（表单代填）是最后手段且默认关闭——**宁可导出给书记/党务老师一键导入，不做脆弱自动写**（H10 最小操作成本：自动写失败重填的操作成本远高于人工导入一次）。

### 6.4 双向同步数据流

```text
平台记载变更（组织生活/评议/党费）
  → 定时拉取 → 映射（学号/partyStatus）→ diff → 更新我们系统 → 通知

我们系统变更（活动记载/考察/发展节点推进）
  → 变更日志（sync_pending 队列）→ 定时推送 → 平台导入/API
  → 失败重试（指数退避）→ 人工复核队列
```

## 七、同步机制与数据一致性

### 7.1 一致性模型

- **主键**：学号（personId）为两系统唯一锚；同一条记录在两边各存 `updatedAt`。
- **仲裁规则**：默认**北大平台为权威端**（官方上报口径），我们为工作台；同一字段两边都改时取较新 `updatedAt`，并向另一侧回写；`partyStatus` 变更遵循状态机（不能跳级），跳级视为冲突入人工队列。
- **变更日志**：新增 `sync_pending`（待推送队列）+ `sync_logs`（历史）两张资源表，全量审计可回滚。

### 7.2 去重与幂等

- 所有同步写操作带**幂等键**（来源 + 业务键 + updatedAt），重复推送不产生重复记录。
- 读取侧 diff 比对（哈希快照），无变化不写库。

### 7.3 人工复核队列

无法自动匹配（学号缺失/姓名不唯一/状态机冲突）→ 进 `待人工核对` 队列，工作台可视化呈现，书记/党务老师一键处理。

| M4 | 智慧党建写路径（导出导入优先；API 若开放则 Webhook） | M0 的 2/3 |
| M5 | 微信小程序叠加对接数据（设计归位 [WECHAT_INTEGRATION.md §八](WECHAT_INTEGRATION.md)） | DEPLOYMENT_GUIDE 路径 D（后端上线） |

### 10.2 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 厂商无开放接口 → 双向实时不可达 | 退化为定时增量（分钟级） | 提前确认 §九.2，方案 B 兜底 |
| 爬虫脆弱性（页面变更） | 同步中断 | 选择器集中 + 告警 + 快照恢复 |
| 合规风险（自动化访问校方系统） | 最严重 | 只读低频 + 官方沟通在前（§九.5） |
| 数据冲突（两边都写） | 台账不一致 | 状态机 + updatedAt 仲裁 + 人工队列 |
| IAAA 风控 | 登录失效 | storageState 复用 + 校园网 IP 稳定 |
