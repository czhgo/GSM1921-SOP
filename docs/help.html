1.2权限体系

系统权限不是"给你一个账号就什么都能做"，而是赋权关系链——谁给你赋的权，你就在谁的赋权范围里干活。权限由 canDo() 统一判定：常设角色（书记/副书记/组织委员/宣传委员/纪检委员/党小组组长）+ 项目角色（组织者/深度参与者）的权限取并集，按"能做什么"逐项判定。

知情边界界定"能看什么"（信息密度精确原则——看得见的，精确等于你职责所需的）：

信息层谁能看到什么
L0 个人视角每名成员自己的考勤 / 考察 / 参与记录
L1 条线视角书记/副书记看各角色全局概况"按人视图"：各角色在办任务清单（谁在干什么、有无异常），可点击直达
L2 全局视角书记/副书记全局概况"按维度"：考勤/发展/活动/宣传四维态势

写入范围界定"能改什么"：

写入范围授权人享有角色
职能写入天然权限组织委员 / 宣传委员 / 纪检委员（各自板块）
活动写入天然权限党支书 / 党小组组长
活动写入（需赋权）党小组组长组织者 / 深度参与者
专班发起天然权限党支书 / 党小组组长 / 三委员
专班招募统筹天然权限组织委员（唯一节点）

关键约束：

  • 创建活动仅限党支书和党小组组长；党小组组长可独立创建，须报书记知情同意；组织委员协调的是专班（招募统筹），不是活动
  • 纪检委员考勤数据与组织委员通用同源
  • 宣传委员不可自行招募宣传专班，赋权操作统一归口组织委员
  • 看 ≠ 做：能看他人条线在办（按人视图），不等于能代劳其操作——知情边界是组织内控的第四道防线

二这个系统在干什么

这个系统是北京大学光华管理学院本科生党支部的数字化管理工具——把党支部制度文本转化为可执行的代码工作流，让工作不随人走。

它要解决的核心问题是：党支部工作如何从"人治"走向"制度治理"？支委换届频繁，经验随人走、制度随人变；新支委上任后需要数月摸索才能上手；同一种工作在不同人手里做法完全不同。围绕这个问题，系统展开三个理念：

制度即代码

把制度文本转化为可执行的代码工作流，让工作不依赖某个人。

角色即视图

每个角色打开工作台就是该角色的全部工作视图，无需来回跳转。

经验可传承

复盘与归档沉淀经验，让新支委快速上手、制度随届接续。

系统现有 14 个页面：首页、资料查询、意见反馈、归档库等公共页面，以及六类角色各自的工作台（党支书、党小组组长、组织委员、宣传委员、纪检委员、普通成员）。每个角色打开自己的工作台，就是该角色的全部工作视图——各项功能按 Tab 分组，无需在页面之间来回跳转；所有角色共享同一套数据，看到的是同一数据的不同视角。

三分工中的制度设计

这套系统的 8 种身份分三层理解——上层管全局、中层两条线、下层成员与执行角色。每一层的职责，由制度与赋权定义。

3.1角色总览

组织者与深度参与者是扁平化执行角色，服务活动也服务专班，由党小组组长（活动）或组织委员（专班）赋权产生。

3.2条块双线

纵职能线

支委的职能线：组织委员管发展党员与专班统筹、宣传委员管宣传档案、纪检委员管考勤考察——各管一类专业事务。

横小组线

党小组组长的小组线：按就业/学术方向划分小组，负责组织学习、开展活动。

两条线交汇于党支书——全局统筹与最终决策者。

3.3两个执行角色：组织者与深度参与者

组织者与深度参与者是推动工作扁平化的两种角色，服务活动也服务专班，由赋权产生。

两者之间没有上下级关系，只是分工不同：组织者负责分工记录与协调，深度参与者负责执行具体工作、提交交付物。

3.4活动的组织与专班的统筹

活动的组织

党小组组长沿小组线组织活动——创建活动、向组织者赋权；组织者做好分工记录，深度参与者执行分工。活动的考勤归纪检委员、宣传归档归宣传委员，一件事从创建到归档各归其位。

专班的统筹

发起人（书记/党小组组长/支委）提出需求，组织委员沿职能线统一招募统筹——唯一专班管理节点；专班不限时间、不限地点，推动支部的长期建设。

谁组织、谁统筹，由岗位职责定义而不靠临时协调——组织的分工由此贯穿活动与专班。

3.5普通成员

普通成员以只读方式查看活动动态、专班进展与考勤概况——不参与管理，但有知情权与监督权。

四怎么理解具体的这个组织

这个组织靠分工、协商、记录三件事运转，而不是级别。下面五节，讲清它是怎么运转的。

4.1这个组织靠什么运作

这个组织靠分工、协商、记录三件事运转，而不是级别：谁做什么由制度定好，组织者与深度参与者之间平等协商，做的过程有记录可查。

支委换届频繁、经验容易随人走，制度因此比个人可靠——工作不依赖某个人，才能一届一届接续下去。

你在这里的位置，由"你在做什么事"决定：承担了组织者的活就是组织者，年级与政治面貌不决定你是否胜任。

4.2活动与专班：两种工作

活动

支部的常规工作：固定时间地点、面向全体、重在参与与规范，党小组是基本单元。

专班

不限时间、不限地点，推动支部的长期建设；也是考察积极分子的载体。

两种工作分开管理、流程不同——活动由党小组组长组织，专班由组织委员统筹。

你在其中：活动的组织者做好分工记录；专班参与者是经组织委员统筹、从小组抽调的工作人员。

4.3扁平化：不靠级别，靠协商

组织者不是"领导"——分工记录职责是做好分工记录，不靠命令压人；深度参与者不是"下属"——执行的是协商后的分工。

扁平化让每个人——包括积极分子——都有机会承担建设性工作；身份、年级、政治面貌都不决定是否胜任。

被赋权为组织者，你的价值在"记录好分工"；被赋权为深度参与者，你的价值在"把交付物做好"。

4.4职能线与小组线

纵职能线

组织委员管发展党员与专班统筹，宣传委员管宣传档案，纪检委员管考勤考察——三委员各管一摊专业事务。

横小组线

党小组组长按就业/学术方向划分小组，组织党小组活动。

两条线在书记处交汇，需要协调的事务在书记处汇总。

遇到具体事务找谁

发展党员→组织委员 宣传报道→宣传委员 考勤与考察→纪检委员 本组学习活动→党小组组长
"条"与"块"是理解这套权责关系的方式——从职能视角看是"条"，从单元视角看是"块"。谁做什么，由职责定义决定。

4.5普通成员：参与与监督

不参与管理不等于没有位置：你有知情权（活动动态/专班进展/考勤概况）与监督权。

支部工作对每个成员公开，参与感建立在了解之上。

按通知参与，用知情与监督行使你的位置。

管理事，服务人——服务人的核心，是理解真实的组织与管理：有流程的经验、有科学的协作。理解真实、善用经验、创新沉淀、框架内对话，是理解这个组织的四个入口。

五技术架构

系统采用纯前端静态架构，无需后端部署。以下两层讲清代码与制度的关系。

5.1前中后台分层

层位置职责
前台（UI）docs/*.html（8 根页面 + 6 角色工作台 = 14 页）页面骨架，零硬编码逻辑
中台（路由+渲染）docs/src/entries/（15 个 entry JS）角色面板路由、视图切换、DOM 渲染
后台（服务层）docs/src/services/（20 个 service JS）数据 CRUD、权限计算、持久化
母本层content/02_institution/sop/所有代码逻辑的制度来源

5.2技术栈

  • 纯前端静态架构 — 无需后端部署，GitHub Pages 直接托管
  • ES Modules — 无构建工具、零打包依赖
  • Tailwind CSS CDN — 原子化样式引擎
  • sessionStorage / localStorage — 跨页面状态持久化
  • Custom Events — 组件间解耦通信
  • 多页面应用（MPA）— 14 个独立 HTML 页面
