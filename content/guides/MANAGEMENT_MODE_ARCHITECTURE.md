# 管理模式架构设计

> 本文档定义 Org OS 的三级管理模式架构，涵盖组织者、深度参与者、普通参与者三类角色的权限矩阵、数据流、双场景适配及系统界面实施路径。

---

| 步骤 | 动作 | 责任人 | 时限 |
|------|------|--------|------|
| 1 | 分配任务 | 组织者 | T-3天 |
| 2 | 设置验收标准 | 组织者 | T-3天 |

## 二、角色权限矩阵

| 角色 | 查看所有活动 | 创建活动 | 分配任务 | 修改分工 | 标记完成 | 填写复盘 | 考勤记录 | 参与记录 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 党小组组长 | Y | Y | Y | Y | Y | Y | -- | 导入 |
| 组织者 | Y | Y | Y | Y | Y | Y | -- | 导入 |
| 深度参与者 | 自己的 | -- | -- | -- | Y | -- | -- | 自己的 |
| 普通参与者 | 公开信息 | -- | -- | -- | -- | -- | -- | 自己的 |
| 纪检委员 | Y(审计) | -- | -- | -- | -- | 督办 | Y | 汇总 |
| 组织委员 | Y(建档) | -- | -- | -- | -- | -- | -- | 归档 |
| 宣传委员 | Y(备案) | -- | -- | -- | -- | -- | 备案 | -- |
| 支部书记 | Y(全局) | Y | Y | Y | Y | Y | 审阅 | 审阅 |

**权限说明：**

- **党小组组长**与**组织者**在操作权限上等同，区别在于：党小组组长是常设角色，组织者是按活动指派的角色
- **组织者**在具体活动中享有完整的管理闭环：创建活动 → 分派任务 → 验收 → 复盘
- **深度参与者**可查看自己被分配的任务，标记完成后等待组织者验收
- **纪检委员**以审计视角查看所有活动，但不参与内容编辑；负责考勤记录写入和参与记录汇总
- **组织委员**接收纪检委员提交的参与记录，负责建档管理
- **宣传委员**接收纪检委员提交的考勤记录，负责备案归档

## 三、短期活动管理 vs 长期建设管理

系统需同时支持两种管理模式，以下为关键维度对比：

| 维度 | 短期活动管理 | 长期建设管理 |
|------|------------|------------|
| **时间跨度** | 1天 -- 1月 | 1月 -- 1年 |
| **组织者** | 活动组织者（按活动指派） | 党小组组长 + 组织委员 |
| **深度参与者** | 单次分工完成 | 持续追踪、阶段性验收 |
| **普通参与者** | 单次出勤记录 | 累计统计 + 阶段性评估 |
| **考勤/参与记录** | 单次记录 | 累计统计 + 阶段性评估 |
| **复盘机制** | 活动后1周内 | 每月进度检查 + 季度复盘 |
| **任务粒度** | 一次性任务分配 | 迭代式任务分派 + 中期调整 |
| **验收方式** | 结果验收（是否完成） | 过程验收（进度 + 质量 + 阶段产出） |
| **代表场景** | 主题党日、社会实践、组织生活会 | 宣讲团建设、人生回望录、党员发展培养 |
| **系统数据模型** | `Activity` + 单次 `Task` | `Project` → `Milestone` → `Task` 层级 |
| **复盘模板** | 单次活动复盘模板 | 阶段复盘 + 终期复盘模板 |

### 3.1 数据模型扩展

目前系统以 `Activity` 为核心数据单元，支撑短期活动管理。为支持长期建设管理，需在后续版本引入 `Project` 实体：

```
短期模型：Activity ──has──> Task ──assigned──> DeepParticipant
                              └──attendee──> Participant

长期模型：Project ──has──> Milestone ──has──> Task ──assigned──> DeepParticipant
              │                                                     │
              └──periodic_review (复盘节点)                         └──progress_log (进度日志)
```

## 四、场景应用详解

### 4.1 宣讲团建设场景

**场景特征：** 长期建设项目，涉及研究、撰稿、设计、宣讲等多个子任务，需要多轮反馈与跨组协调。

**角色映射：**

| 实体角色 | 系统角色 | 职责说明 |
|---------|---------|---------|
| 党小组组长 | **组织者** | 跟踪宣讲团整体进展，负责多次反馈循环和跨组协调；设定阶段性目标，验收各轮产出 |
| 小组内部成员 | **深度参与者** | 承担研究/撰稿/设计/宣讲等具体分工；在系统内标记任务完成，提交阶段性成果 |
| 其他参与成员 | **普通参与者** | 出席但不分工，完成学习材料学习；记录为"出勤" |

**工作流程：**

```
[党小组组长/组织者]
      |
      |-- 创建项目 "宣讲团建设"
      |-- 设置里程碑：M1-选题研究 → M2-稿件撰写 → M3-试讲打磨 → M4-正式宣讲
      |
      |-- M1: 分配任务
      |     |-- 成员A: 文献调研（深度参与-研究）
      |     |-- 成员B: 案例收集（深度参与-调研）
      |     └-- 成员C: 框架设计（深度参与-设计）
      |
      |-- M2: 迭代反馈
      |     |-- 成员A 提交初稿 → 组长审阅 → 修改
      |     |-- 成员B 提交案例集 → 组长审阅 → 补充
      |     └-- 跨组协调：与宣传委员对接推文排期
      |
      |-- M3--M4: 试讲 + 正式宣讲
      |
      └-- 终期复盘：整体评估各成员贡献度
```

**参与记录产出示例：**

| 姓名 | 角色层级 | 具体工作 |
|------|---------|---------|
| 党小组组长 | 组织 | 宣讲团整体统筹、跨组协调、阶段验收 |
| 成员A | 深度参与-研究 | 文献调研、初稿撰写、三轮修改 |
| 成员B | 深度参与-调研 | 案例收集整理、数据可视化 |
| 成员C | 深度参与-设计 | PPT设计、宣讲框架搭建 |
| 成员D | 出勤 | 出席试讲、完成学习材料 |

### 4.2 "人生回望录"活动场景

**场景特征：** 需要一对多老师对接的项目制活动，涉及大量协调与材料整理工作。

**角色映射：**

| 实体角色 | 系统角色 | 职责说明 |
|---------|---------|---------|
| 支委 / 指定党员 | **组织者** | 统筹老师对接排期，跟踪全部参与者的进度；一对多老师联络与进度管理 |
| 执行层党员/成员 | **深度参与者** | 一对一与老师对接、整理走访摘要、归档记录材料 |
| 普通参与成员 | **普通参与者** | 参与但未与老师建立一对一联络，仅记录为"出勤" |

**工作流程：**

```
[支委/组织者]
      |
      |-- 创建活动 "人生回望录"
      |-- 统筹排期：确定 8 位老师的访谈时间窗口
      |
      |-- 分配任务：
      |     |-- 深度参与者A: 对接张老师（访谈+摘要+材料归档）
      |     |-- 深度参与者B: 对接李老师
      |     |-- 深度参与者C: 对接王老师
      |     └-- ... 依此类推
      |
      |-- 组织者跟踪：检查进度、协调时间冲突
      |
      |-- 验收阶段：
      |     |-- 检查每位深度参与者的访谈摘要质量
      |     |-- 确认材料归档完整
      |     └-- 汇总形成终期报告
      |
      └-- 复盘：评估整体执行效率与产出质量
```

**判断标准（深度参与 vs 出勤）：**

- **深度参与者**判定条件（满足全部）：
  - 与至少一位老师建立一对一联络关系
  - 实际完成访谈/走访
  - 提交访谈摘要或整理材料
  - 成果可验证（有摘要文档/归档记录）
- **普通参与者**判定条件：参与活动但未与老师建立一对一联络，或联络但未实际完成摘要整理

## 五、考勤 vs 参与记录维度说明

本系统维护两套并行的记录体系，源自 [纪检委员工作流程指南 §1.2](file:///d:/GitHub/GSM1921-SOP/content/SOP/纪检委员工作流程指南.md#L100-L108) 的明确规定。

### 5.1 核心区别

| 维度 | 考勤（0-1变量） | 参与记录（三层记录） |
|------|----------------|---------------------|
| **性质** | 刚性底线 | 弹性贡献 |
| **对象** | 党员、预备党员 | 所有支部成员（党员 + 预备党员 + 发展对象 + 积极分子） |
| **适用范围** | 三会一课（组织生活会） | 所有支部工作（含三会一课、主题党日、社会实践等） |
| **记录方式** | 二元/三元：出勤 / 请假 / 缺勤 | 三层：组织 / 深度参与 / 出勤 |
| **记录时机** | 实时记录（活动中签到） | 实时记录（活动中观察 + 活动后确认） |
| **提交对象** | 宣传委员（备案） | 组织委员（建档，每月提交） |
| **是否考虑质量** | 否，仅记录客观出勤事实 | 是，深度参与须满足 ☑明确分工 ☑实际完成 ☑可验证 ☑有贡献 |
| **补课/补救** | 请假/缺勤须补课，标注"已补" | 不适用（参与记录不可补救） |

### 5.2 判断逻辑

```
                    活动开始
                       |
           +-----------+-----------+
           |                       |
      三会一课？              其他支部工作？
           |                       |
           v                       v
   对象 = 党员+预备党员      对象 = 所有支部成员
           |                       |
           v                       v
   签到/记录出勤状态         是否有明确分工？
   出勤 / 请假 / 缺勤        /              \
                             /                \
                           是                  否
                           |                   |
                           v                   v
                   是否实际完成？         记录为【出勤】
                   /          \
                  /            \
                是              否
                |               |
                v               v
         记录为【深度参与】  记录为【出勤】
         （标注具体角色）   （挂名无实）
                |
                v
         主导策划与实施？
         /            \
        /              \
      是                否
      |                 |
      v                 v
记录为【组织】   记录为【深度参与-角色】
```

### 6.2 界面增强需求

#### 6.2.1 组织者界面：任务分配面板

当用户选择"组织者"角色后，需展示以下功能模块：

```
+--------------------------------------------------+
|  任 务 分 配 面 板                                 |
+--------------------------------------------------+
|  活动名称: [主题党日 - 3月学习会]                   |
|  组织者:   [张三 / 党小组组长]                      |
+--------------------------------------------------+
|  深度参与者指派:                                    |
|  +----------------------------------------------+ |
|  | 成员         | 分工角色     | 验收标准  | 状态  | |
|  +----------------------------------------------+ |
|  | 李四         | 宣传-推文    | 阅读量>50 | 进行中| |
|  | 王五         | 现场统筹     | 设备就绪  | 已完成| |
|  | 赵六         | 技术支持     | PPT可用   | 待验收| |
|  +----------------------------------------------+ |
|  [+ 添加深度参与者]                                |
+--------------------------------------------------+
|  普通参与者: [共 15 人]  [查看名单]                  |
+--------------------------------------------------+
|  [提交参与角色确认]    [发起复盘]                    |
+--------------------------------------------------+
```

**核心交互：**
- **指派深度参与者**：从支部成员列表中选择，指定分工角色与验收标准
- **跟踪完成度**：实时查看各深度参与者状态（未开始 / 进行中 / 已完成待验收 / 已验收）
- **一键提交参与角色**：活动结束后，组织者确认所有参与者的角色层级，提交纪检委员

```
      |
      v
更新 activeRole 状态
      |
      +---> 侧边栏高亮对应卡片
      +---> 主内容区切换为该角色对应的功能面板
      +---> 数据查询范围根据角色权限过滤
      +---> 操作按钮根据角色权限显隐
      +---> URL hash 更新 (#role=organizer)，支持深链接
```

### 7.1 风险与回滚点

| Phase | 主要风险 | 回滚策略 |
|-------|---------|---------|
| Phase 1 | 角色枚举与现有 `data-role` 属性冲突 | 保持现有 HTML `data-role` 不变，新增 `data-tier` 属性做层映射；回滚仅需移除新增属性 |
| Phase 2 | 任务分配面板与现有活动创建流程整合复杂 | 先以独立面板形式实现，再逐步整合；回滚时关闭面板入口即可 |
| Phase 3 | 考勤/参与记录写入权限控制不当可能导致数据污染 | 在数据库层做写入前权限校验；回滚时保留数据，仅关闭写入入口 |
| Phase 4 | 长期模型与短期模型并存可能导致 UI/UX 割裂 | 以统一的活动列表页做聚合入口，用类型筛选区分短期/长期；回滚时移除筛选即可 |
