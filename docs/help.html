1.2权限体系

系统权限不是"给你一个账号就什么都能做"，而是赋权关系链——谁给你赋的权，你就在谁的赋权范围里干活。权限由 canDo() 统一判定：常设角色（书记/副书记/组织委员/宣传委员/纪检委员/党小组组长）+ 项目角色（组织者/深度参与者）的权限取并集，按"能做什么"逐项判定。

知情边界界定"能看什么"（信息密度精确原则——看得见的，精确等于你职责所需的）：

信息层谁能看到什么
L0 个人视角每名成员自己的考勤 / 考察 / 参与记录
L1 条线视角书记/副书记看各角色全局概况"按人视图"：各角色在办任务清单（谁在干什么、有无异常），可点击直达
L2 全局视角书记/副书记全局概况"按维度"：考勤/发展/活动/宣传四维态势

写入范围界定"能改什么"：

写入范围授权人享有角色
职能写入天然权限组织委员 / 宣传委员 / 纪检委员（各自板块）
活动写入天然权限党支书 / 党小组组长
活动写入（需赋权）党小组组长组织者 / 深度参与者
专班发起天然权限党支书 / 党小组组长 / 三委员
专班招募统筹天然权限组织委员（唯一节点）

关键约束：

  • 创建活动仅限党支书和党小组组长；党小组组长可独立创建，须报书记知情同意；组织委员协调的是专班（招募统筹），不是活动
  • 纪检委员考勤数据与组织委员同源共享
  • 宣传委员不可自行招募宣传专班，赋权操作统一归口组织委员
  • 看 ≠ 做：能看他人条线在办（按人视图），不等于能代劳其操作——分工的运行保障中的做与看

二这个系统在干什么

这个系统是北京大学光华管理学院本科生党支部的数字化管理工具——把党支部制度文本转化为可执行的代码工作流，让工作不随人走。

它要解决的核心问题是：党支部工作如何从"人治"走向"制度治理"？支委换届频繁，经验随人走、制度随人变；新支委上任后需要数月摸索才能上手；同一种工作在不同人手里做法完全不同。围绕这个问题，系统展开三个理念：

制度即代码

把制度文本转化为可执行的代码工作流，让工作不依赖某个人。

角色即视图

每个角色打开工作台就是该角色的全部工作视图，无需来回跳转。

经验可传承

复盘与归档沉淀经验，让新支委快速上手、制度随届接续。

系统现有 14 个页面：首页、资料查询、意见反馈、归档库等公共页面，以及六类角色各自的工作台（党支书、党小组组长、组织委员、宣传委员、纪检委员、普通成员）。每个角色打开自己的工作台，就是该角色的全部工作视图——各项功能按 Tab 分组，无需在页面之间来回跳转；所有角色共享同一套数据，看到的是同一数据的不同视角。

三技术架构

系统采用纯前端静态架构，无需后端部署。以下两层讲清代码与制度的关系。

3.1前中后台分层

层位置职责
前台（UI）docs/*.html（8 根页面 + 6 角色工作台 = 14 页）页面骨架，零硬编码逻辑
中台（路由+渲染）docs/src/entries/（16 个 entry JS）角色面板路由、视图切换、DOM 渲染
后台（服务层）docs/src/services/（20 个 service JS）数据 CRUD、权限计算、持久化
母本层content/02_institution/sop/所有代码逻辑的制度来源

3.2技术栈

  • 纯前端静态架构 — 默认本地 mock 数据（localStorage 持久化），GitHub Pages 直接托管；可选 Node 后端（server/）提供 REST API
  • ES Modules — 无构建工具、零打包依赖
  • Tailwind CSS CDN — 原子化样式引擎
  • sessionStorage / localStorage — 跨页面状态持久化
  • Custom Events — 组件间解耦通信
  • 多页面应用（MPA）— 14 个独立 HTML 页面
