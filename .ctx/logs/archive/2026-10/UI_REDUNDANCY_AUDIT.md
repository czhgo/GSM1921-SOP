# 第一轮前端脏乱繁审查：冗余注释与小字

> 范围：`docs/*.html`、`docs/workspace/*.html`、`docs/src/entries/**`、`docs/src/components/**`。
> 方法：全站关键词扫描（口径 / 只读 / 系统 / 自动 / 落档 / 仅 / 无需 / 用于 / 说明等）＋ 逐屏人工抽查。
> 约束：只读审查，未改动任何产品代码；本文件只落 `.ctx/logs/archive/2026-10/`。
> 结论先行：最刺眼的问题不是「字多」，而是**把内部实现口径写给用户看**。这类小字既不能点、也不能改，删掉后用户仍能完成动作，应统一判「删」。

---

## 一、五问结论速览

### 1. 冗余判据

本次统一用一条硬判据：

> **删掉这句话，用户是否仍能完成动作？**
> 能 ⇒ 判「删」；不能，且这句话本身承载动作 ⇒ 判「改」为按钮 / 短标签；两者都不是、但属于结构问题 ⇒ 判「立项」。

据此，系统内部机制类文案（落档、口径、只读、自动同步、不写 mockDB、换壳工作单）一律判「删」；用户必须知道的后果，压成 4–8 字的状态词或按钮，不写解释句。

### 2. 首屏密度

| 屏幕 | 首屏块数 | 标题层级 | 主要问题 | 结论 |
|---|---:|---|---|---|
| 首页 `docs/index.html` | 9 块（1 hero + 4 统计卡 + 4 内容卡） | 5 个同权 `h2` | 「近期活动」卡头同时放日历/列表切换 + 工作台→ + 完整日历→，4 个控件抢一行；4 张内容卡没有主次 | P2，建议首屏只留统计 + 通知 + 近期活动 |
| 工作台概况（六台共用） | 3–4 卡（结论带 + 条线表 + 待我处理 + 支书额外卡） | 页头 H2 + 3 个分区标题 | 4 个指标按钮 + 6 列表格 + 待我处理 + 额外卡，首屏信息量偏大 | P2，指标带与条线表可合并 |
| 工作台页签栏 | 8–12 个页签 | 2 级（工作台 / 我的职责 / 知情查看） | 支书 12 个、成员 11 个、组织/组长 10 个；首屏横向滚动 | P2，主导航建议 ≤7 |
| 「今天」 | 2 卡 + 1 个快捷入口段 | 2 个 `h3` | 结构最干净，问题在提醒卡里塞了一整段系统说明 | P1（文案），结构 P3 |
| 人员档案 | 4 个分区 + 1 个折叠系统说明 | 5 个标题 | 每个分区都带一句解释小字，4 行事实被解释包围 | P1（文案） |
| 纪检考勤 | 1 个录入卡 + 队列 + 表格 | 3 层说明（正文 / 折叠 / 帮助链接） | 同一张卡上「录入即确认」「上传位按会议类型分」「口径与规则」叠了 4 层 | P1（文案） |

「字少且不可改」的区块仍占大块版面的典型：首页 hero 副标题、六台页头副标题、人员档案「进入当前阶段」说明、概况「共 N 条」元信息。

### 3. 字段可理解性

用户能懂的业务词：姓名、学号、届别、党小组、发展阶段、在册状态、活动、专班、考勤、考察、归档。

不可理解或需要二次翻译的标签：

| 标签 | 位置 | 问题 | 建议 |
|---|---|---|---|
| 进入当前阶段 | `person-entry.js:286` | 不是用户语言，用户想的是「什么时候进入现在这个阶段」 | 阶段起始日 |
| 条线 | `work-overview.js:53,500` | 组织内部管理词，成员看不懂 | 工作分工 |
| 最近卡点 | `work-overview.js:57,466` | 「卡点」是项目黑话 | 待处理 / 最近阻塞 |
| 逾期（全口径） | `work-overview.js:130` | 「全口径」是统计术语 | 逾期 |
| 在办 | `work-overview.js:132,464` | 与「待办」边界不清 | 进行中 |
| 赋权 | `org-workspace` 指标 / `assign-tab` | 用户理解为「分配账号权限」，实际是「项目角色」 | 项目角色 |
| 我的处置 | 各台页签 | 「处置」对象不明 | 我的答复 / 待我答复 |
| 知情查看 | 组长台 / 支书台页签 | 内部命名，不像用户动作 | 只读查看（或直接叫「专班 / 其他组」） |
| 落档 | `person-entry.js:289,338` | 档案系统内部动词 | 删除整句 |
| 口径 | `work-overview.js:130`、`attendance-tab.js:862,877`、`archive-tab.js:120` | 内部统计词 | 规则 / 说明 |
| 应到 / 滞留 | 考勤、名册 | 党建业务词，本支部用户可懂；不建议改 | 保留 |
| 换壳工作单 / mockDB / 种子持久 | `org-setup-wizard.js:473,475` | 工程实现词，产品界面不应出现 | 删除 |

### 4. 下拉外观

结论：**深色模式有 1 个 P1 可读性缺口，大字号有 1 个 P1 尺寸断层，主题色只跟随了一半。** 详见第三节。

### 3.3 结论

- **深色**：变量体系基本跟随，唯一硬伤是选中项文字仍是深色（A-10，P1）。

## 五、共识 5 条

1. **页头副标题一律删。** 首页 hero 的「组织生活与工作台账」、六台页头的职责罗列、成员台欢迎语后半句，都是标题的复述；删掉不减少任何能力。
2. **解释系统内部机制的句子默认删。** 「落档」「口径」「只读」「自动同步」「不写 mockDB」「种子持久」「换壳工作单」这些词不是用户语言；用户只需要看到状态和下一步动作。
3. **不可改区块只保留「字段名 + 值」。** 人员档案的阶段起始日、档案编号、留痕来源都是只读事实；不需要在每一行下面再加一句「系统随阶段变更落档，本页只读」。
4. **同一任务只保留一个动词入口。** 首页「工作台→ / 完整日历→」并列、概况「待我处理」与「待办」并存、成员档案三处编辑入口，都是同一任务换文案；应保留主入口、其余降为下钻。
5. **下拉外观必须完整跟随三档设置。** 大字号、深色、主题色是同一个「外观」承诺；不能出现触发器 17px、菜单 12px，或深色下选中项深字叠深底。

## 六、分歧 3 条

1. **「条线」是否改成「工作分工」。** 一方认为「条线」是党建/组织管理既有术语，改了会丢专业感；另一方认为成员台用户看不懂。建议支书拍板：管理台保留「条线」，成员台用「我的分工」。在拍板前，本报告按「改」记录。
2. **「只读」是否一律删。** 一方主张所有「只读」小字都删（详情页本身没有写入口）；另一方认为党委查看支部、党委只读视图这类**权限边界**页面，保留一个「只读」徽章有安全提示价值。建议：普通详情页删，跨角色只读页保留徽章。
3. **下拉展开/聚焦边框是否必须跟随主题色。** 设计系统 §4.3 规定输入族聚焦「边框变金」，而外观设置又承诺主题色跟随；两者在 `.cs-trigger` 上冲突。建议明确：焦点金是设计例外，展开态边框与选中态跟随主题色。
