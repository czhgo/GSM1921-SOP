## 二、「党建」Tab 分组界面设计

### 模块定位与功能边界

#### 模块定位

「党建」Tab 分组承载角色工作台内的功能板块，是**工作台**内的功能分区——2026-08-03 起各类工作统一承载于角色工作台（Tab 分组统一为「党建」），不再作为与工作台并列的独立模块。

#### 功能边界

**工作台其他视图负责（不纳入「党建」Tab 分组）**：
- 活动推演排期（基于 SOP 场景的日期展开与任务实例化）
- 全场景工作日历（calendar 视图 + 聚焦视图）
- 模板与资产（文档模板库、会议记录模板）

**「党建」Tab 分组负责**：

| 子功能 | 说明 | 来源母本 |
|--------|------|---------|
| 发展党员全流程追踪 | 积极分子 -> 发展对象 -> 预备党员 -> 正式党员，各阶段时间节点与材料完成状态 | 组织委员工作流程指南 |
| 补课制度跟踪 | 请假/缺勤人员补课安排、完成情况追踪、补课完成后在考勤记录中标注"已补" | 纪检委员工作流程指南 1.4 |
| 意见反馈 | GitHub Issue 风格开源讨论+支书处置权（双轨数据层：issues.json 权威源 + localStorage 草稿；两类标签：scope 单选 + type 多选；权限：支书独占 8 项处置权，全员共享 7 项基础操作） | D-244 职能动作隐喻 + T105 实施 |

#### 考勤与考察的核心区别（数据模型依据）

本 Tab 分组的"补课制度跟踪"子功能依赖以下数据维度区分：

| 维度 | 考勤（0-1 变量，出勤/请假/缺勤） | 考察（工作量记录，组织/深度参与） |
|------|--------------------------|--------------------------|
| **对象** | 党员、预备党员 | 深度参与者和组织者 |
| **适用** | 三会一课 | 所有支部工作 |
| **记录** | 出勤 / 请假 / 缺勤 | 组织 / 深度参与 |
| **方式** | 实时记录 | 实时记录 |
| **提交** | 支委会（组织委员接收建档） | 组织委员建档（每月提交） |

补课逻辑：考勤记录中出现"请假"或"缺勤"状态时，自动触发补课任务；补课完成后，考勤记录回写为"已补"。此逻辑依赖考勤的 0-1 变量特性，不涉及考察的工作量维度。

## 三、日历功能界面设计

### 日历多视图展示逻辑

#### 视图切换架构设计

需要新增日历视图状态字段：

```javascript
// 在 appState 中新增
calendarView: 'month',  // 'month' | 'week' | 'day' | 'list'
// 替代当前 viewMode 的部分语义：
//   'list' 原意为「点击日期后展示该日 Activity 列表」→ 更名为 inspectorMode
//   'detail' 保持不变，仍用于检查器的详情视图
```

#### 月视图（month）

- CSS Grid 7 列布局
- 每个单元格显示：日期数字 + 最多 3 个任务标签 + "+N 项任务"折叠
- 单元格高度自适应，桌面端与移动端的具体高度值见 DESIGN_SYSTEM.md
- 月视图下角色筛选逻辑沿用现有方案：根据 `viewType`（`participant` / `manager`）渲染不同的单元格内容

#### 周视图（week）

- 7 列布局（周一到周日），每列宽度均分
- 列高度扩展至父容器可用高度，提供更大的任务展示空间
- 每列顶部标注日期和星期，下方按时间顺序（由 `timeOffset` 字段驱动）排列当日任务
- 当前周高亮显示，可通过左右箭头切换至上一周/下一周
- 日期头显示完整日期格式（如"5月12日 周一"），点击日期头可切换至日视图
- 任务展示上限放宽至 8 个，超出折叠

#### 日视图（day）

- 单列全高布局，左侧时间轴（可选：按小时刻度），右侧任务卡片流
- 任务卡片按 `timeOffset` 排序，标注具体时间锚点（如"T-7 天"、"T=0 活动日"、"T+3 天"）
- 每个任务卡片展示完整信息：标题、执行角色、督办人、状态
- 适合支书/支委集中审视单日活动全貌

#### 列表视图（list）

- 放弃日历网格，改为扁平列表
- 排序规则：日期降序（最近的在前），同日期内按 `timeOffset` 升序
- 每行展示：日期、活动名称、关联任务数、状态标签
- 支持关键词搜索过滤（前端内存过滤，不涉及后端）
- 适合快速浏览和移动端场景

#### 各视图下的数据筛选规则

| 筛选维度 | 月视图 | 周视图 | 日视图 | 列表视图 |
|---------|--------|--------|--------|---------|
| 按角色 | 单元格内任务过滤 | 同月视图 | 同月视图 | 全局任务过滤 |
| 按场景 | 活动级过滤（仅显示匹配 `scenarioId` 的活动） | 同月视图 | 同月视图 | 同月视图 |
| 按时间范围 | 当月活动 | 当周活动 | 当日活动 | 全部活动（可选日期范围过滤） |
| 按归档状态 | 排除已归档 | 排除已归档 | 排除已归档 | 排除已归档（归档库独立入口） |

**筛选优先级**：角色 > 场景 > 时间范围。即先确定角色可见性，再缩小到场景，最后限定时间窗口。这是为了确保数据安全性优先于展示便利性。

#### 视图切换时的状态保持策略

视图切换是一个高频操作，状态保持至关重要：

1. **保留 `selectedDate`**：从月视图切换到周视图时，保持当前选中的日期不变，周视图自动定位到包含该日期的周
2. **保留 `selectedActivityId`**：切换到日视图时，若此前在检查器面板选中了某个活动，日视图应高亮该活动的任务卡片
3. **保留 `displayMonth`**：月视图和周视图共享此字段，确保前后一致
4. **重置滚动位置**：视图切换后滚动到当前日期/当前周所在位置

### 文本溢出处理策略

#### 截断规则优化方案

- **月视图**：活动标题单行截断（CSS `text-overflow: ellipsis`）；任务标签单行截断；日期数字不截断。
- **周视图**：任务标题双行截断（`-webkit-line-clamp: 2`）；角色标签单行不截断。
- **日视图**：空间充裕不截断，任务描述超 3 行提供"展开/收起"切换。
- **列表视图**：单行截断。

#### Tooltip 实现方案

推荐混合策略：首页参与者视图保持 `title` 属性（轻量无负担）；工作台月视图单元格 hover 时显示精简 JS tooltip（含任务完整标题、执行人、状态）；日视图/周视图不需 tooltip（信息已完整展示）；移动端长按触发。

#### "+N more" 折叠显示策略

动态阈值计算（基于单元格高度）；点击 "+N" 标签原位展开微型弹出列表（非 Modal），支持点击选中联动检查器面板，点击日历其他区域或按 Escape 关闭。

#### 移动端适配

桌面端（>=1024px）、平板（768-1023px）、手机（<768px）按断点分档调整展示数量与截断长度；移动端月视图单元格点击后原地展开全宽任务列表卡片（不展开右侧面板）。具体单元格高度值见 DESIGN_SYSTEM.md。

日历展示相关的 Activity/Task 字段索引见 [DATA_MODEL.md](../data/DATA_MODEL.md) §2.1/§2.12，本文件不维护并行 Schema。

### 快速聚焦视图设计

#### 聚焦视图交互重构

##### 点击日历日期后的展开/收缩交互

**方案 1：原位展开（推荐）**

点击日历日期单元格后，该单元格在日历网格中**向下展开**，推开下方行，形成一个宽幅聚焦面板。面板内容包含：
- 该日期的活动标题（大字显示）
- 该日期的任务列表（按时间和角色分组）
- 快速操作按钮（查看全部任务、切换管理角色）
- 关闭按钮（点击后收缩回普通单元格）

优势：日历上下文不丢失，用户可以同时看到聚焦日期和周边日期
劣势：布局计算复杂，需要精确控制 Grid 行高变化

**方案 2：弹出面板**

点击日期单元格后，在原位弹出一个浮层面板，类似右键菜单。面板内容同方案 1。

优势：实现简单，不干扰日历布局
劣势：可能遮挡其他日期，移动端弹出位置需要动态调整

**推荐混合策略**：
- 桌面端（>= 1024px）：原位展开（方案 1），因为屏幕够宽
- 移动端（< 768px）：弹出面板（方案 2），因为屏幕窄，原位展开不可行

4. **序号②③④的"尚待确认"折叠夹在流程中**：由"完全同等效力"推导、支书未逐条明答的三条（讨论结果可见范围/缺席处理/是否并行线下任务）以折叠块夹在提示条里（`:426`）——这属**待裁口径**，应与"流程步骤"分离。
5. **与"母本：支委会承担什么"不对应**（根因，也是裁定①的机理）：母本 `COMMISSIONER_DUTY_FRAMEWORK.md:40`（§A.3）「组织关系上，**支委会领导党小组**」；`:181`（§C.1b）「意见反馈处置归支委会，由支书主持支委会」；工作地图模块「支委会」`desc:'研究支部日常工作（支委会不考勤）'`（`work-map.js:93-98`）。⇒ **支委会是一个"承担审议/处置的机构"**；但本页（与支书台入口 tab）**只承载"开一场线上会"这条链，没有承载"这个机构由谁组成"**。这正是支书所说"**支委的配置在党小组与活动中很奇怪**"的根因：**机构页缺"机构成员"**，于是"机构成员"被挤到了"党小组"tab 里。
6. **入口 tab 的统计是存量数字**：`committee-meeting-tab.js:9-14` 数"支委会场次/其中线上召开/未截止"，前两个是**累计存量**，与 `DESIGN_SYSTEM.md §一 原则11`「工作界面不得出现『已完成 N/总数』式无差异存量统计」相抵触（"支委会场次 N"＝一直涨的存量）。⚠ 建议改口径为"**未截止/待你处置**"（面向进行时），或明确标注为累计（需支书定）。
7. **页内层级：五段平铺、无步骤感**：五段各为一张 `card`（`:467-471`），无分步/无折叠，一屏叠 6 类数据格式（见 §四.2 清单 #2）。

> ⚠ **需支书补充口径（证据不足处）**：序号"①–⑤"是**刻意编号的流程步骤**（应规范化），还是仅为**随便的段序**？另：本次改编号会触碰 `copy-*` 族守卫（`docs/src` 界面文案）；**待支书圈定后一并核基线**。

#### ② 按"一 tab 一问"它该回答哪一问

- 现口径：「支委会开了几场、哪场要线上开？」——**只答"开会状态"**，不答"机构是谁"。
- 依裁定①，本 tab / 本页应回答：**「支委会这一机构——由谁组成、议了哪些事、结论是什么？」**
- ⚠ **这仍是两个子问**（机构构成 / 议事记录）⇒ 需支书裁：是**一 tab 容纳"机构"一问（含成员＋议事两个切面）**，还是**拆成"机构构成"与"议事记录"两处**。本方案推荐**前者**（否则会出现"机构无成员"的怪状，见 ①-5）。
