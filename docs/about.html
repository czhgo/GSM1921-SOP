一、系统概述

本系统是北京大学光华管理学院本科生党支部的数字化管理工具。它要解决的核心问题是：党支部工作如何从"人治"走向"制度治理"？支委换届频繁，经验随人走、制度随人变；新支委上任后需要数月摸索才能上手；同一种工作在不同人手里做法完全不同——本系统通过制度即代码、角色即视图、经验可传承三大设计理念，将党支部制度文本转化为可执行的代码工作流。

系统基于双域管理理论构建——将党支部工作划分为党建工作（创新探索·面向未来）与党务工作（合规运行·面向存量）两大域。通过多页面架构为 8 种角色提供差异化的工作视图，由 10 个 AI Agent 组成治理集群持续维护。所有工作流源自制度母本（content/SOP/），改一处制度，全系统同步。

二、核心理论

2.1 双域管理理论

党建与党务不是同一回事。党建工作面向"尚不存在的未来"（策划品牌活动、设计工作方法），强调创新与探索；党务工作面向"已存在的存量"（党员发展流程、补课制度、档案归档），强调合规与运行。两者是产品关系——党建工作产出"怎么做"的方法论，党务工作将其固化为"这样查"的标准规程。

域本质定义判断标准
党建工作创新探索——面向"尚不存在的未来"是否允许创造性发挥、探索边界？
党务工作合规运行——面向"已存在的存量"是否要求符合规定、纪律严明、格式规范？

核心洞察：域的定义锚定的是工作者的心智模式（探索 vs 执行），而非工作的物理载体。同一个人在同一场活动中，可能在两个模式之间频繁切换。

2.2 条块二元结构

条条（职能域）：组织/宣传/纪检三大支委，纵向贯穿所有活动。在党建维度中，宣传委员与纪检委员服务于活动和专班，通过看板视图管理所辖领域的任务，而不直接写入活动。
块块（活动域）：党小组组长按就业/学术方向划分，横向统筹党小组活动。
条块之间不是上下级关系，而是功能决策与信息执行的接力关系。两种协作模式——常规模式（组长中转）与专班模式（支委直达）——适应不同任务性质。

2.3 专班制

专班 = 赋权 × 工作量考察。乘积关系的含义：任一要素为零，专班即失效。组织委员是唯一专班管理节点——所有专班的组建与解散必须经由组织委员统一管理，防止专班泛滥。宣传委员不可自建专班，须通过组织委员审定。专班有明确的解散条件——任务完成或截止时间到达即解散，不得转为常设机构。

2.4 决策树四层模型

活动管理不是"分类"问题，而是"决策"问题。四层决策结构：组织场景（L1）→ 活动形式（L2）→ 时长（L3）→ 发起方向（L4），上层自动排除下层的不合法分支。品牌维度被"吸收"为长期活动的一个可选子流程——品牌认定不再是活动的"属性"，而是长期活动发展到一定阶段后的"认定"。

2.5 赋权关系链

赋权者有权查看被赋权者的工作视图（只读），但不可修改。赋权关系树：党支书 → 条条支委（天然权限）/ 党小组组长（天然权限）；党小组组长 → 组织者 / 深度参与者（需赋权）；组织委员 → 组织者 / 深度参与者（专班域赋权）。宣传委员和纪检委员无赋权能力——职能性质决定，与内控要求相关。

2.6 组织者与深度参与者

组织者和深度参与者是推动支部工作扁平化的两种角色，服务于活动与专班。两者之间没有上下级关系，只是分工不同。核心比喻：组织者是项目的脑子，深度参与者是项目的手。

维度组织者深度参与者
核心职能分工协调、进度同步、打包提交工作成果执行具体工作、提交交付物
产出物分工记录 + 工作考察记录 + 深度参与者成果打包具体工作交付物
考勤要求（活动）最好出席，允许因特定原因缺席但须同步工作必须出席
考勤要求（专班）无严格时空限制无严格时空限制
退出机制须经支委会确定接手人并完成交接向组织者报告后退出

组织者两种情况：Ⅰ 自上而下布置——从支委或组长处承包任务，发挥桥梁作用；Ⅱ 自下而上创建——须联系本组组长或组织委员赋权后方可分派任务。身份不是最重要的，年级和政治面貌不决定是否胜任。

四、页面导航

系统由 19 个独立页面组成，通过侧边栏全局导航和角色选择面板串联。所有子页面共享同一套数据源，不同角色看到的是同一数据的不同切面。

4.1 全局导航结构

主页（通知/招募/日历）
├── 党建工作台 → 角色选择面板 → 8 个角色子页面
├── 党务管理 → 角色选择面板 → 4 个委员子页面
├── 归档库 · 资料查询 · 意见反馈 · 关于

4.2 各页面功能

主页 — 通知公告 + 人员招募 + 活动日历全景；点击条目跳转至对应子页面
党建·党支书 — 活动写入 + 日历视图 + 专班发起 + 数据后台
党建·党小组组长 — 活动写入 + 日历视图 + 专班发起 + 组员管理
党建·组织者 — 日历视图 + 分工记录（经赋权后可编辑）
党建·深度参与者 — 日历视图 + 任务查看（经赋权后可编辑）
党建·组织委员 — 专班管理看板 + 追踪看板 + 专班发布招募 + 搜索筛选
党建·宣传委员 — 活动与专班看板 + 多维表格（全量数据+搜索筛选）
党建·纪检委员 — 考勤总表 + 考察总表 + 活动监督复盘 + 搜索筛选
党建·成员只读 — 活动动态（日历/列表切换）+ 专班进展 + 考勤概况
党务·组织委员 — 党员发展全流程 + 材料催缴
党务·宣传委员 — 宣传档案合规建设 + 周报
党务·纪检委员 — 补课制度 + 公邮管理
归档库 — 已完成工作归档与回溯 + 搜索 + 类别过滤
资料查询 — 合规文件 · 操作指南 · SOP 文档 · 外部链接
意见反馈 — SOP 优化提案反馈表单

5.2 写入权限

写入权限域授权人享有角色
职能域写入天然权限组织委员 / 宣传委员 / 纪检委员（各自板块）
活动域写入天然权限党支书 / 党小组组长
活动域写入（需赋权）党小组组长组织者 / 深度参与者
专班发起天然权限党支书 / 党小组组长 / 三委员
专班招募统筹天然权限组织委员（唯一节点）

5.3 关键约束

  • 创建活动仅限党支书和党小组组长；组长可独立创建，须报书记知情同意；组织委员协调的是专班（招募统筹），不是活动
  • 纪检委员考勤数据与组织委员通用同源
  • 宣传委员不可自行招募宣传专班，赋权操作统一归口组织委员
  • 三委员之间可相互查看（只读），但不可修改彼此的工作
  • 从首页进入管理页面时自动设为只读模式

六、技术架构

6.1 前中后台分层

层位置职责
前台（UI）docs/*.html（19 页面）页面骨架，零硬编码逻辑
中台（路由+渲染）docs/src/entries/（18 个 entry JS）角色面板路由、视图切换、DOM 渲染
后台（服务层）docs/src/services/（7 个 service JS）数据 CRUD、权限计算、持久化
母本层content/SOP/所有代码逻辑的制度来源

6.2 技术栈

  • 纯前端静态架构 — 无需后端部署，GitHub Pages 直接托管
  • ES Modules — 无构建工具、零打包依赖
  • Tailwind CSS CDN — 原子化样式引擎
  • sessionStorage / localStorage — 跨页面状态持久化
  • Custom Events — 组件间解耦通信
  • 多页面应用（MPA）— 19 个独立 HTML 页面
