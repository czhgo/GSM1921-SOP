# 党务管理独立模块架构规划

> 本文档定义党务管理独立模块的功能边界、界面布局、关联关系与实施细则，为 E1（CLAUDE.md 短期规划）的落地架构文档。
> 定位：[人机] -- 人类消费 + AI 自主读取作为工作上下文。

## 1. 模块定位与功能边界

### 1.1 模块定位

党务管理模块是与**党建工作台**（即党建工作域）并列的独立功能板块。两者共同构成 Org OS 的"双域"体系：

| 域 | 对应模块 | 核心职责 |
|----|---------|---------|
| **党建工作** | 党建工作台 | 主题党日、三会一课（支部党员大会/支委会/党小组会/党课）、民主评议、换届选举、发展党员、专班管理 |
| **党务工作** | 党务管理模块（本模块） | 制度修订、职责分工、意见反馈、合规审查、文档规范、定岗定责 |

此双域分类与 [ARCHITECTURE.md](file:///d:/GitHub/GSM1921-SOP/ARCHITECTURE.md#L20-L31) 中定义的领域模型一致。党建工作台承载"党建工作"域，党务管理模块承载"党务工作"域。

### 1.2 功能边界

#### 党建工作台负责（不纳入本模块）

- 活动推演排期（基于 SOP 场景的日期展开与任务实例化）
- 全场景工作日历（calendar 视图 + 聚焦视图）
- 模板与资产（文档模板库、会议记录模板）

#### 党务管理模块负责

| 子功能 | 说明 | 来源母本 |
|--------|------|---------|
| 党员发展全流程追踪 | 入党申请人 -> 积极分子 -> 发展对象 -> 预备党员 -> 正式党员，各阶段时间节点与材料完成状态 | 组织委员工作流程指南 |
| 补课制度跟踪 | 请假/缺勤人员补课安排、完成情况追踪、补课完成后在考勤记录中标注"已补" | 纪检委员工作流程指南 1.1 |
| 意见反馈管理 | 意见建议反馈渠道维护、反馈状态流转、由支部书记全权处理（纪检委员不干预） | 纪检委员工作流程指南 1.1 |
| 公邮查收提醒 | 每周查看支部公邮 1 次，汇总并转发思想汇报与党员发展材料至组织委员归档 | 纪检委员工作流程指南 1.1 |

### 1.3 考勤与参与记录的核心区别（数据模型依据）

本模块的"补课制度跟踪"子功能依赖以下数据维度区分：

| 维度 | 考勤（0-1 变量） | 参与记录（三层记录） |
|------|----------------|---------------------|
| **对象** | 党员、预备党员 | 所有支部成员 |
| **适用** | 三会一课 | 所有支部工作 |
| **记录** | 出勤 / 请假 / 缺勤 | 组织 / 深度参与 / 出勤 |
| **方式** | 实时记录 | 实时记录 |
| **提交** | 宣传委员备案 | 组织委员建档（每月提交） |

补课逻辑：考勤记录中出现"请假"或"缺勤"状态时，自动触发补课任务；补课完成后，考勤记录回写为"已补"。此逻辑依赖考勤的 0-1 变量特性，不涉及参与记录的三层维度。

> 来源：[纪检委员工作流程指南 1.2](file:///d:/GitHub/GSM1921-SOP/content/SOP/纪检委员工作流程指南.md#L100-L108)

### 1.4 引用渲染机制

党务管理模块在展示 `content/references/` 下的合规文件（如党章、发展党员工作细则、纪律处分条例）时，遵循 [ROLE_CLASSIFICATION.md 引用渲染机制](file:///d:/GitHub/GSM1921-SOP/content/guides/governance/ROLE_CLASSIFICATION.md#L135-L145)：

- AI 可读取 `content/references/` 下的 [人] 角色文件内容
- 将内容渲染到 HTML 界面的只读展示区（如"合规文件"面板）
- 源文件保持不可变的 [人] 角色状态，AI 不可修改
- 渲染缓存与源文件保持同步（文件变更时自动更新展示）

此机制填补了"AI 不可访问 [人]"和"界面需要展示官方内容"之间的权限真空。

## 2. 侧边栏并列展示方案

### 2.1 现状分析

当前侧边栏（[index.html L148-L162](file:///d:/GitHub/GSM1921-SOP/index.html#L148-L162)）包含 3 个 module-tab：

```
┌─────────────────┐
│ [党建工作台]     │  ← module-tab active (data-module="calendar")
│ [参考指南]       │  ← module-tab (data-module="reference")
│ [模板与资产]     │  ← module-tab (data-module="templates")
├─────────────────┤
│ ─── 分隔线 ───  │
├─────────────────┤
│ 参与视图        │
│ 管理视图        │
│   ...            │
└─────────────────┘
```

所有 module-tab 均对应 `id="view-*"` 的 view-section，通过 CSS `hidden` 类切换显示。

### 2.2 三种方案

#### 方案 A：module-tab 扩展（新增第 4 个 module-tab）

在现有 3 个 module-tab 下方增加第 4 个"党务管理"module-tab：

```
┌─────────────────┐
│ [党建工作台]     │
│ [参考指南]       │
│ [模板与资产]     │
│ [党务管理]       │  ← 新增
├─────────────────┤
│ ─── 分隔线 ───  │
└─────────────────┘
```

**优点**：与现有导航模式完全一致，复用 module-tab 的 CSS 与 JS 切换逻辑，实现成本最低。
**缺点**：4 个 tab 在收起态侧边栏中可能显得拥挤；"党务管理"与上方 3 个 tab 的语义层级不完全对等（上方 3 个是"功能视角"，党务管理是"领域视角"）。

#### 方案 B：角色卡片区域下方独立入口

在 sidebar 角色卡片区域下方增加独立的"党务工作入口"：

```
┌─────────────────┐
│ [党建工作台]     │
│ [参考指南]       │
│ [模板与资产]     │
├─────────────────┤
│ 参与视图        │
│ 管理视图        │
│   [党小组组长]   │
│   [条条支委]     │
│   [组织者]   │
│   [深度参与者]   │
│   [党支书]       │
├─────────────────┤
│ ═══ 分割区 ═══  │
│ [进入党务管理]   │  ← 新增（独立入口按钮）
└─────────────────┘
```

**优点**：语义清晰，党务管理作为独立入口不混入 module-tab 体系；角色卡片区域保持纯粹。
**缺点**：入口位置偏下，可见性不足；与 module-tab 的视觉层级不一致，用户可能忽略。

#### 方案 C：侧边栏顶部二级切换

在 sidebar 顶部增加"活动管理 | 党务管理"二级切换：

```
┌─────────────────┐
│ [活动管理|党务管理]│  ← 二级切换 Tabs
├─────────────────┤
│ [党建工作台]     │  ← 活动管理下的子 tab
│ [参考指南]       │
│ [模板与资产]     │
├─────────────────┤
│ ─── 分隔线 ───  │
└─────────────────┘

切换到"党务管理"后：
┌─────────────────┐
│ [活动管理|党务管理]│
├─────────────────┤
│ [发展党员]       │  ← 党务管理下的子 tab
│ [补课制度]       │
│ [公邮管理]       │
├─────────────────┤
│ ─── 分隔线 ───  │
└─────────────────┘
```

**优点**：与 ARCHITECTURE.md 中"党建工作 / 党务工作"双域分类完全对齐，语义层级最清晰；为未来党务管理模块的子功能扩展预留了独立导航空间。
**缺点**：实现成本最高，需要新增二级 tab 切换逻辑；现有 module-tab 体系需要增加一级包装层。

### 2.3 推荐方案

**推荐方案 A**，理由如下：

1. **实现成本最低**：扩展一个 module-tab + 一个 view-section 即可完成基本框架，与现有三段式导航完全一致，无需新增切换逻辑层
2. **CLAUDE.md E1 定位匹配**：E1 的描述为"侧边栏与党建工作台并列"，方案 A 的新增 tab 直接体现了"并列"语义
3. **后续可渐进升级**：当党务管理模块子功能增至 3 个以上需要独立导航时，可平滑升级为方案 C；方案 A 是方案 C 的 MVP 阶段
4. **不与现有角色卡片冲突**：党务管理模块不需要角色切换（党务管理面向条条支委，权限由登录态决定），因此 4 个 module-tab 下方仍保留现有的角色视图体系
**渐进路线**：方案 A（当前 E1）--> 方案 C（未来当党务管理子模块 > 3 且需要独立子导航时）

## 4. 与其他模块的关联关系

### 4.1 与党建工作台的数据互通

```
党建工作台                              党务管理模块
┌──────────────┐                    ┌──────────────────┐
│ 考勤记录      │ ── 缺勤/请假 ──→  │ 补课制度跟踪       │
│ (0-1 变量)   │                    │  - 生成补课任务    │
│              │ ←── 补课完成 ────  │  - 跟踪完成状态    │
│              │     回写考勤       │  - 回写"已补"标记  │
└──────────────┘                    └──────────────────┘
```

- 党建工作台的考勤记录（0-1 变量：出勤/请假/缺勤）是补课触发的唯一数据源
- 补课完成后的状态回写直接更新考勤记录，不涉及参与记录（三层维度）
- 数据变更统一经过 Service 层，遵循 [ARCHITECTURE.md 数据变更规则](file:///d:/GitHub/GSM1921-SOP/ARCHITECTURE.md#L224-L239)

### 4.2 与参考指南的场景域展示

参考指南模块中将新增党务管理相关的"场景域"入口，展示的内容包括：

- 党员发展流程对照表（引用组织委员工作流程指南）
- 补课制度流程图（引用纪检委员工作流程指南 1.1）
- 意见建议处理流程图（引用纪检委员工作流程指南 第四章）

党务管理模块负责**执行与跟踪**，参考指南负责**查阅与学习**，两者通过"场景域"标签区分。

### 4.3 与模板资产的模板引用

党务管理模块涉及的模板（从 `content/references/工作模板/` 引用）：

- 入党申请书模板
- 思想汇报模板
- 转正申请书模板
- 发展对象公示模板
- 补课记录表模板

模板资产模块负责**存储与版本管理**，党务管理模块负责**引用与填充**。

### 4.4 与 ROLE_CLASSIFICATION.md 引用渲染机制的映射

```
ROLE_CLASSIFICATION.md                  党务管理模块
┌──────────────────────────┐        ┌──────────────────────┐
│ 引用渲染机制              │        │ 合规文件展示区         │
│                          │        │                      │
│ AI 可读取 [人] 文件       │ ────→  │ AI 读取 content/     │

│ 源文件不可变              │        │ 渲染到 .card 面板     │
```

此为 [ROLE_CLASSIFICATION.md 角色关系矩阵](file:///d:/GitHub/GSM1921-SOP/content/guides/governance/ROLE_CLASSIFICATION.md#L127-L135) 中 `[AI] --> [人]（引用渲染）` 规则的首次工程落地。

### 5.2 JS 逻辑变更

#### 5.2.1 module-tab 切换扩展

在现有 module-tab 点击事件处理中，新增 `party` 模块的 case：

```javascript
// 在 events.js 或 main.js 的 tab 切换逻辑中新增
case 'party':
  showViewSection('view-party');
  hideAllRoleMenus(); // 党务管理模块不需要角色视图
```
