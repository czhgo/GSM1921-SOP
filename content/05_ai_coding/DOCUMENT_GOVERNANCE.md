## 一改具改执行陷阱（原 KNOWN_PITFALLS §2）

**原则**：术语或制度变更后，必须全仓库搜索确认零残留，不能只改"最明显的几处"。

**判例**：ROADMAP→CLAUDE.md 更名时，仅修改了文件名和部分引用，遗漏了 guides/insights/SOP 中的引用。该次更名被指出"一改具改执行不令人满意"。

**纠正**：修改前用 Grep + SearchCodebase 全仓搜索，修改后再搜索确认零残留。搜索时使用多种模式（精确匹配+模糊匹配+上下文搜索）。

**反面论证**：为什么不每次都全仓搜索？因为简单修改（如修 typo）不需要全仓搜索。判断标准：涉及术语/制度/编号变更 → 必须全仓搜索。

## 一改具改遗漏的典型场景（原 KNOWN_PITFALLS §10）

**问题**：路径替换类一改具改任务中，子代理按"路径替换表"机械执行后，仍会遗漏部分文件——这些文件不在替换表中，但包含同类型旧路径。

**根因**：
1. 路径替换表是基于 Grep 主要模式生成的，但相对路径变体（如 `../sop/`、`../strategy/`）可能未全部纳入替换表
2. 子代理按文件清单执行时，未对每个文件做完整性 Grep 验证
3. 同一文件中多处旧路径分散在不同位置（YAML、JSDoc、字符串字面量、UI 显示文本），子代理可能只修复前几处

**典型实例（T127）**：
- `content/04_web_design/module/SOP_WEBSITE_GUIDE.md` L128 `../strategy/COMMISSIONER_FRAMEWORK.md` 未在替换表
- `content/03_doc_system/SERVICE_CATALOG.md` L183/L198/L213 `../sop/` 相对路径未在替换表
- `content/02_institution/COMMISSIONER_FRAMEWORK.md` L378-L381 `../sop/` 4 处遗漏
- `content/insights/党支部管理与实务经验沉淀.md` 任务描述说 2 处旧路径，实际 4 处
- `docs/src/core/domain.js` 9 处路径分散在 JSDoc + 字符串字面量中

**预防机制**：
1. 路径替换表生成时，必须扫描所有相对路径变体（`../xxx/`、`./xxx/`、`content/xxx/`）
2. 子代理完成文件修改后，必须对该文件做完整 Grep 验证（不仅验证替换表中的模式，也验证同类型变体）
3. 大型一改具改任务必须分批派发子代理，每批完成后由主代理做全仓库 Grep 抽样验证
4. 任务描述中的"X 处"是参考值，子代理应按实际 Grep 结果执行，不局限于数字

**修复成本**：主代理发现后直接修复成本低；若进入下一阶段才被发现，需重新打开文件做二次修改，成本翻倍。

## 文档治理：命名、SSOT 与文件归置（insights [3] 并入）

### 命名即认知框架（原 insights §1.1）

命名构成认知框架，而非单纯标签——词汇的精确性影响认知的清晰度，改名揭示"这个名字对应什么样的认知"。

**命名体系要区分官方术语与内部约定**：官方术语（制度文件、上级文件中的原词）直接采用权威定义、不可改写；内部约定词在引用时标注其约定性质，不得提升为官方标准——读者若把约定词当作官方术语，会按官方语义理解而产生认知偏差。本项目术语层级的完整定义见 [USAGE_POLICY.md §1.7](../03_doc_system/USAGE_POLICY.md)。

**判断路由（什么条件下该改名）**：①名字承载技术隐喻而使用者是日常用户——换日常用语；②导航层级冗余——以板块合并消除层级；③命名与真实结构/工作形态不一致——改中立表述。仅当名字造成认知偏差时才改，纯审美偏好不改。

**判例**：本项目三次改名——「支部驾驶舱」→「主页」（从技术隐喻切换到日常用语，回归严肃性）；「参考指南」→并入「资料查询」（消除冗余导航层级）；「活动组织者」→「组织者」（命名不再绑定活动/专班等特定工作形态）。当前一律以新名为准。

### SSOT 溯源链架构与变更流水线（原 insights §1.2）

单一事实源（SSOT）按权威层级分四层：

```
Layer 1: 最高规范层（绝对权威，禁改）
Layer 2: 制度母本层（组织决议，具权威性）
Layer 3: 实施层（实现细节，须溯源母本）
Layer 4: 核心规则层（系统规则，需共识）
```

变更流水线分三步：**识别**（定位根因）→ **溯源**（追踪母本）→ **推进**（级联更新子本）。跳过溯源直接推进，等同「头痛医头」。

**判断路由**：适用于"上级规范 → 制度文件 → 实现 → 内部规则"四层结构的组织文档体系——当同一主题多文件描述、改动需级联同步时，按权威层级归位可防止散落漂移。本项目对应：党章层 → SOP 母本 → 代码 → 系统规则。

### 同一概念只在一个地方表达——散落导致漂移（原 insights §1.3）

同一概念只在一个地方表达，散落必然导致漂移。单一表达位置是根因治理，定期交叉审查只是兜底。

**判例（功能冗余入口）**：旧的"视图代理"功能（党支书可以代理任意子角色视角看日历）与角色切换机制功能重叠，冗余入口导致用户困惑。

**为什么不能"两种方式都能到达"？** 因为两种方式暗示两种规则——用户不知道哪个是"正式"的。一个概念只在一个地方表达，消除了歧义。

**判例（权限矩阵散落）**：权限矩阵散落在三个文件中，各自粒度不同、覆盖面不同，且存在实质性不一致。同一概念在多文件表达时，修改一处容易遗漏另一处——必须定期进行交叉审查，以最高权威源为基准逐项比对。

**为什么不是"定期人工校对就够"？** 因为校对的覆盖率取决于校对人"记得住这个概念散落在哪里"——概念散落三处以上、各自粒度不同，遗漏一处是常态而非意外。定期交叉审查只是缓解漂移的兜底手段，不能消除漂移的根因——根因是"同一概念在多文件表达"本身。

**生效条件**：适用于一切"同一概念多文件表达"的场景（功能入口、权限矩阵、术语定义）。单一表达位置是根因治理，交叉审查是兜底。

### 历史记录不可变原则（原 insights §3.6）

全仓同步修改的搜索范围仅限活跃文件——历史记录文件（.ctx/logs/、.trae/specs/、.ctx/snapshots/、.trae/documents/）是不可变时间胶囊，其中的旧路径引用不应修改。同时，活跃文件中的历史描述（如"从 content/guides/ 移至..."、YAML merged_from 字段、决策记录中的旧路径）也是历史记录，不应被同步修改波及。

**为什么历史记录不能改？** 因为历史记录是事实记录——记录的是"当时做了什么"，不是"现在是什么"。修改历史记录等于篡改历史——后人无法从日志中了解当时实际发生了什么。同步修改的目标是保持当前状态的一致性，不是重写过去。

**为什么不是"全部一起改更彻底"？** 因为彻底性不等于正确性。将历史日志中的旧路径一并替换，看似彻底，实则破坏了日志作为"时间快照"的价值——日志记录的是"当时执行了什么操作"，修改后日志变成了"现在的叙述"，失去了追溯能力。

**为什么不是"活跃文件中的历史描述也要改"？** 因为活跃文件中可能包含合法的历史描述——如 CLAUDE.md 中的决策记录（"D-230: 从 content/guides/ 移至..."）、SSOT_INDEX.md 中的迁移历史表、文件 YAML 中的 merged_from 字段。这些描述的语义是"曾经发生过迁移"，不是"当前路径是 content/guides/"。修改它们会让读者误以为从未发生过迁移。

**生效条件**：适用于全仓同步修改操作的所有场景。判断标准——该引用是"当前状态描述"还是"历史事实记录"。前者需改，后者不改。.ctx/logs/、.trae/specs/、.ctx/snapshots/、.trae/documents/ 整体属于历史记录；活跃文件中带"从...移至..."、"曾经..."、merged_from 等历史性表述的属于历史记录。

### 文件应放在与其层级匹配的目录（原 insights §5.2）

SSOT_INDEX.md 曾长期放在 `.github/` 目录中，但它是 Layer 1 注册表层文档，与 CLAUDE.md、ARCHITECTURE.md 同级。藏在工具配置目录中导致路径引用冗长、不同工具可见性不一致。

**为什么不能"放在哪都行"？** 目录结构是治理层级的物理映射。文件放在与其层级不匹配的目录中，等于在说"这个文件不重要"——而实际上它可能是最高优先级的治理文档。

### 不同 AI 工具的配置应物理隔离（原 insights §5.3）

`.github/` 目录包含 VS Code Agent 专属配置，对 Trae 工作无意义且浪费上下文。最初通过 `.trae/.ignore` 隔离（D-186），但隔离仍占用仓库空间且引用链复杂。2026-07-21 进一步将 `.github/` 整体物理迁出至 `D:\GitHub\System-Residual\.github\`，仓库不再保留 VSCode 专属配置——共享规则通过根目录文件统一管理，工具间配置彻底物理隔离。

**为什么不能让每个工具都读取对方的配置？** 因为不同工具的规则体系可能冲突。物理隔离确保每个工具只看到自己需要的规则，共享规则通过根目录文件统一管理。

### 文件夹治理：命名精确 + 归置合理（原 insights §5.4）

文件夹治理的核心落在命名精确和归置合理，而非层级深浅。

**为什么不是"越扁平越好"？** 因为扁平化消除了层级带来的语义信息——"content/01_strategy/references/合规文件/"比"content/01_strategy/references/官方文件/"更精确，而"content/01_strategy/references/党支部工作记录.docx"提升至根目录比藏在子目录更合理。层级本身不是问题，命名不精确和归置不合理才是问题。

**为什么命名必须精确？** 因为目录名是用户（人和 AI）导航的第一线索。"官方文件"可以是任何官方文件，"合规文件"则明确指向需要合规引用的文件。命名越精确，导航效率越高，误放概率越低。专班按工作性质分（合规性/探索性）而非工作内容分，正是命名精确的体现——按性质分类稳定、不随内容变化漂移，而按工作内容分类则缺乏统一标准。

**为什么归置必须合理？** 因为文件的位置传递了其重要性信号。高层级文件藏在深层子目录中，等于在说"这个文件不重要"——而实际上它可能是最高优先级的治理文档。归置原则：文件应放在与其层级匹配的目录，使用频率高的文件路径应最短。

### 阶段适应性治理——开发期表述按当前阶段更新（原 insights §4.18）

> 来源：T-118 治理文档完善推进（T-212，2026-08-10）。确立于开发阶段方法论随阶段演进需同步更新的治理判断。

**开发不同阶段有不同的方法与观念**——系统从开发期进入上线/稳定期后，早期开发阶段形成的方法与观念（如"什么任务派发给什么 Agent"的任务派发细节、硬编码的角色主题色、mock 数据驱动开发等）已随阶段演进被替代，文档治理须识别并更新这些"开发期表述"，而非让它们滞留在文档中误导读者。识别特征：表述描述的是"当时怎么做"的内部机制细节，而非当前系统的真实状态。

**治理要点**：
- **开发期表述清单**（已识别）：①任务→Agent 派发细节（"派发给 XX Agent"）——已不重要，删或改通用表述；②硬编码机制（如"角色主题色即每角色固定色"）——更新为当前机制（可选择的色盘）；③内部英文技术细节（如读取规则 always-on/relevance-triggered）——改为面向读者可理解的中文表述
- **保留边界**：开发期表述在 AI 治理层（执行日志、05_ai_coding/ 分篇、insights AI 方法论）是历史与经验的合法载体，保留；清理目标是**用户可见文档层**（README、content 用户文档、网页文案）

**为什么不是"机械删除一切旧表述"**：开发期表述可能同时承担历史记录、经验沉淀、方法论价值（如"子代理审查"是 AI 工作方法论核心）。一刀切删除会丢失有效经验。正确做法是区分表述的承载层——用户可见层更新为现状，AI 治理层保留历史与经验。

**生效条件**：适用于系统进入新阶段（开发期→上线/稳定期）后的文档治理。周期性执行（C-5 术语与表达审计 / T-118 治理文档完善）。

## 内容治理与一改具改验证（insights [3][5] 并入）

### 内容治理 spec 全流程（原 insights §4.8 主段）

大规模内容治理（4+ 任务）应采用 spec 全流程：spec 编写 → 决策人审批 → 分阶段并行执行 → 子代理审查 → 全局验证。

**spec 全流程**：

1. **spec 编写**：将治理目标拆解为可独立执行的子任务，每子任务明确范围、输出、验收标准
2. **决策人审批**：spec 提交决策人审批，决策人可能在审批时修订方向（如将"每条论断必须显性写出原因分析"的机械要求内化为问题意识，避免八股文）
3. **分阶段并行执行**：独立子任务并行执行（如文件命名规范/文件分类评估/README 评估/冗余检查可并行）
4. **子代理审查**：反论表述、论断可读性等需要逐条审查的任务，委托子代理执行——子代理能系统性扫描所有条目，发现人工审查容易遗漏的违规
5. **全局验证**：一改具改检查 + Grep 零残留验证 + YAML 同步

**为什么不是"逐任务串行执行"？** 因为独立任务串行执行会浪费大量时间——4 个独立任务串行需要 4 倍时间，并行只需 1 倍。并行的前提是任务之间无依赖关系（如"文件命名规范"和"README 评估"互不影响）。

**为什么不是"AI 自己审查就行"？** 因为 AI 在主任务执行后审查自己的产出，倾向于认为自己做的是对的。子代理审查是独立视角，能发现主任务执行者因思维定势而遗漏的问题（如反论表述不精确、论断可读性不足）。

**生效条件**：spec 全流程适用于 4+ 子任务的大规模内容治理。小规模修订（1-2 个文件）不需要 spec 流程。

### 治理文件功能审计与拆分（原 insights §5.9）

当一个治理文件承担过多职责、导致篇幅膨胀时，应按"功能审计 → 外移/删除 → 一改具改"三步拆分。

**功能审计**：逐节评估每个章节的定位——该章节是"运行规则"（每次执行必须读）、"详细规范"（按需参考）、还是"索引导航"（指向其他文件）。运行规则保留在主文件，详细规范外移到专题文件，索引导航精简为链接。

**外移与删除**：详细规范外移到对应的专题文件（如 OPERATIONS_GUIDE.md、05_ai_coding 分篇），外移后在主文件保留一行链接指向。纯索引章节（如论断汇编、Skills 清单）若信息可在其他文件获取，直接删除——索引的价值在于"快速查找"，若索引本身过长，反而增加查找成本。

**一改具改**：主文件章节编号变更后，必须全仓库搜索旧编号引用并逐一更新。搜索范围包括 content/ 的所有子目录和根目录文件，历史日志按上文「历史记录不可变原则」（原 insights §3.6）保留。

**为什么不是"保留所有章节只做精简"？** 因为当文件承担过多职责时，精简只能压缩文字，不能解决"职责混杂"问题——读者打开文件后仍需在多个不相关主题间跳转。拆分让每个文件职责单一，读者打开就知道"这个文件管什么"。

**为什么不是"全部外移只留链接"？** 因为运行规则必须保留在主文件——主文件是每次执行的强制上下文，如果运行规则也外移，AI 执行时需要逐个读取外移文件，上下文成本急剧上升。外移的是"详细规范"和"索引导航"，不是"运行规则"。

**生效条件**：适用于治理文件篇幅超过 500 行、或单文件承担 3 个以上不相关职责的场景。小规模治理文件不需要拆分。

**约束力三层——"写全 vs 指针"的判断标准**：功能审计三分类（运行规则/详细规范/索引导航）可进一步按**全局约束力**分层——全局约束力强（每次执行必须遵守、违反即违规）的规则写全在主文件，缺失会让执行失去锚点；场景化/按需参考的细节用指针指向专题文件，读者在需要时才读取，避免主文件膨胀。判断标准是"这条规则离开主文件后，执行是否还能成立"，不是"内容是否重要"。配**编号位值对应**：主文件编号按 10 递增预留（热层 10-40 / 温层 50-80 / 冷层 90-100），编号位值表达层级——"第几层"从编号一眼可辨，新增小节不挤占既有编号，跨文档引用编号稳定。确立于甲部约束力三层重组任务（T-215）。

### 函数签名变更的全仓库验证（原 insights §6.4）

setActiveRole 参数从 `setActiveRole(role)` 变为 `setActiveRole(module, role)` 时，新增的子页面使用了旧签名，影响 12 个子页面。

**教训**：函数签名变更后，必须全仓库搜索所有调用点并逐一验证参数——调用点可能散落在任何文件中，不能只改已知调用点就完事：验证须精确到参数个数，而非停留在"差不多的方向"。

### 一改具改遗漏模式：搜索范围不全（原 insights §6.15）

> **与权威源管理的关系**：权威源管理与变更传播讲原则与机制（见原 insights §5.7），本节是「搜索范围不全」这一具体失败模式的判例——两者互为补充。

大规模术语替换（12+ 文件 ~40 处）完成后，仍发现 8 个文件遗漏——根因是搜索范围基于"术语出现在哪些文件"的主观判断，而非"全仓库扫描"的客观范围。术语不仅出现在文档中，也出现在代码注释（如 docs/src/core/domain.js）、UI 文案（如 ws-organizer-entry.js）、配置文件、mock 数据（如 docs/src/mock/seed.js）中——一改具改的搜索范围必须是全仓库，不能按主观判断缩小。

**为什么不是"遗漏了再补就行"？** 遗漏的文件可能在后续使用中误导读者——DATA_CONSISTENCY_CHECKLIST.md 是检查清单，如果其中的术语未更新，下次执行检查时会引用过时术语。补丁修复的成本（单独执行一次修复任务）远高于初次搜索时多花几秒扫描全仓库的成本。

**为什么不是"只搜文件名匹配的"？** 术语引用不一定在文件名中——一个文件可能文件名不含目标术语，但内容中多处引用。文件名搜索只能找到"以术语命名"的文件，找不到"引用术语"的文件。

**教训**：一改具改搜索时，搜索范围默认为全仓库（项目根目录），不按主观判断缩小。若搜索结果过多需要缩小范围，必须明确记录缩小依据，并在缩小后的范围外做抽样验证。

**生效条件**：适用于所有一改具改操作，特别是大规模术语替换（涉及 5+ 文件、10+ 处替换）的场景。小规模修订（单文件内替换）不触发此风险。

### 被否决方案不得以标签残留（T-221 判例，原 insights §6.27）

**事件**：关于页第六章（工作流）动画重构时，被书记否决的「行星/脉冲」动画方案仍以三种形式活在代码里——①配置命名 `PLANETARY_CONFIG`（v5.2「行星动画配置参数」）；②注释（「行星呼吸动效」「行星公转微动」）；③CSS 动画（`ab-planet-drift` 公转 + `ab-ring-pulse` 脉冲）。重构时这些旧标签是「活代码」（当前逻辑仍在引用），AI 视其为有效设计而非被否决方案残留，于是带着枷锁重构——书记批评：「这些被否决的方案还在上下文文件里面吗？这不是一种污染吗？之后 AI 阅读的时候都会'此地无银三百两'？我还怎么做重构呢？永远带着枷锁」。

**教训**：被否决的设计方案不得以命名/注释/动画/文档的形式残留于代码与上下文——重构即整体替换，而非打补丁。残留的旧标签会在未来每次阅读时把 AI 带回被否决的方向，形成认知枷锁。

**Boolean 条件**：重构动画/设计时，须先 grep 旧方案关键词（命名、注释、CSS 类、@keyframes）全仓清零，验证零残留后再实施新方案。

**生效条件**：任何涉及「被否决方案」的动画/设计重构；H40 检查清单应纳入「被否决方案残留」扫描项（与 C-5 已降级定义残留审计并列）。
