# 会议议程与资料查询设计

> **已落地（2026-09-01）**：本设计结论已实现（对照实读：`docs/src/modules/references.js` 支部文件/草案 CRUD + `docs/src/entries/tabs/secretary/calendar-tab.js` 议程与会后衔接 + `docs/src/components/member-change-panel.js` 成员变更面板 + `server/db.js` RESOURCE_TABLES 中 `branch_docs` / `member_change_requests` / `committee_broadcasts` / `agenda_votes` 表 + `server/routes/resources.js` CRUD，配套 server/test/ member-change-flow、agenda-* 系列测试）；本文档继续承担设计论证档案，验收条件见 §五（已达成，2026-09-05 复核）。

> **目标**：让资料查询中的支部文件与重要会议的议程形成一条可追溯的工作路径，并将会议完成后的重复录入收束为少量有责任归属的动作。
>
> **阅读顺序**：先读「一、范围与原则」了解边界；再读「二、资料查询」和「三、议程封装组装」理解使用路径；实施时以「四、数据与权限」和「五、验收条件」为准。
>
> **术语**：官方文件指外部权威来源的只读资料；支部文件指本支部保存、维护和检索的文件；会前草案指在会议召开前已拟定、供议程关联和讨论的支部文件草案；成员变更申请指由会议结果引出的待审批人员阶段调整。

## 一、范围与原则

### 1.1 解决的工作问题

资料查询目前已能区分官方文件与支部文件。后续改造保持这一区分，并把支部文件的准备、讨论、归档同活动议程连起来。

会议中的事项保持活动原有类型。系统把议程组织成可复用的结构：普通事项、讨论文件和成员变更申请可以按一次会议的实际需要共同编排。该结构服务于活动，不创建额外的活动名称或虚构会议类别。

### 1.2 设计原则

- **封装组装**：每种议程事项只承担清晰职责，活动创建时按实际需要组合；新增事项不改写其他事项的数据结构。
- **会前明确对象**：涉及文件讨论时，议程关联会前草案，会议参与者清楚讨论对象。
- **会后少重复录入**：会议结果只填写一次，由关联事项生成后续动作；需要承担责任的动作仍由相应角色确认。
- **单一数据源**：活动、文件、成员变更申请、通知收件记录与成员资料由服务器分别保存；页面只读取和提交这些记录，不以浏览器缓存充当权威状态。
- **资料查询保持直接**：查询页先帮助使用者找到资料，再提供支部文件的写入入口；无关类别筛选不参与文件检索。

### 1.3 视觉边界

资料查询沿用现有页面的整体视觉体系，官方文件和支部文件以内容分区建立层次。颜色、字体、间距、动效和响应式参数统一引用 [DESIGN_SYSTEM.md](../design-system/DESIGN_SYSTEM.md)。已确认的构图是：资料查询不设顶端类别 tab；高级选项默认折叠，展开后才呈现会后衔接；会议结果直接显示在对应议程项下。本文件不新增视觉 token 或参数。

## 二、资料查询

### 2.1 页面信息顺序

页面从上至下依次呈现：

1. 页面标题和搜索框。
2. 官方文件区：外部权威文件和站点。
3. 支部文件区：本支部已归档文件，以及创建会前草案的入口。

顶部类别 tab 移除。它与资料的两类来源交叉，增加筛选理解成本；搜索只过滤当前页面可检索的资料卡片和文件条目。

### 2.2 支部文件状态

支部文件至少区分两个工作状态：

| 状态 | 含义 | 资料查询中的处理 |
| --- | --- | --- |
| 草案 | 会前已拟定，等待某次会议讨论或继续编辑 | 仅具备相应权限的支委可见、编辑和关联 |
| 已归档 | 已完成会议讨论并归入支部文件 | 在支部文件区向有权限的使用者展示和检索 |

会前草案由支部文件写入入口创建。重要会议的高级选项默认折叠，只从可关联草案中选择文件；同一草案不能同时处于两次未完成会议的讨论清单中。

### 2.3 归档动作

活动完成后，系统在对应议程项下记录结果。文件讨论结果为通过时，系统将关联草案归档；归档记录保存活动标识、议程项标识、操作人和时间。资料查询据此把文件展示为已归档。

## 三、议程封装组装

### 3.1 基本结构

重要会议创建页保留现有基本信息和议程输入。高级选项增加「会后衔接」区域，按需要加入下列议程事项：

| 事项 | 会前填写 | 会议完成后填写 | 系统后续动作 |
| --- | --- | --- | --- |
| 普通事项 | 事项名称、主持人 | 会议记录 | 无自动业务动作 |
| 讨论文件 | 事项名称、主持人、会前草案 | 讨论结果、会议记录 | 生成文件归档待办 |
| 成员变更 | 事项名称、主持人、人员、拟变更阶段 | 会议结果、会议记录 | 会议结果通过时生成成员变更申请 |

对于文件事项，默认文案采用「讨论……文件」。系统不以“表决决议”作为固定议程名称。表决情况属于结果记录中的可选信息，可用于不同事项。

### 3.2 可复用议程结构

每个议程项都保存共同字段：标识、事项类型、标题、主持人、排序、记录和结果。不同事项只补充本身所需字段：

- 讨论文件项补充 `branchDocId`。
- 成员变更项补充 `personId`、`fromStage` 和 `toStage`。
- 结果记录补充 `result`、`recordedBy` 和 `recordedAt`，并保留可选表决信息。

活动记录保存议程项的顺序和结果摘要。文件、成员变更申请、通知收件记录都保存对活动与议程项的引用，避免把同一事实复制到多处正文。

### 3.3 会议完成后的角色责任

成员变更申请按已确认的顺序流转：

1. 会议结果通过后，系统创建成员变更申请。
2. 组织委员审批申请。
3. 审批完成后，系统立即向全体支委逐人发送广播记录。
4. 书记确认申请。
5. 系统更新服务器中的成员资料，申请进入正式完成状态。

支委广播用于共同知悉，不增加支委逐人批准环节。每位收件人的已读时间独立保存。

## 四、数据与权限

### 4.1 新增或扩展的记录

| 记录 | 关键字段 | 权威来源 | 生命周期 |
| --- | --- | --- | --- |
| 支部文件 | 状态、关联活动、关联议程项、归档人、归档时间 | 服务器支部文件资源 | 草案、已归档 |
| 议程项 | 类型、排序、会前关联、结果、记录人、记录时间 | 活动记录 | 创建、会议完成后补充结果 |
| 成员变更申请 | 人员、原阶段、拟变更阶段、会议与议程依据、组织委员审批、书记确认 | 服务器专用资源 | 待组织委员审批、待书记确认、正式完成、退回 |
| 广播收件记录 | 申请、收件人、发送时间、阅读时间 | 服务器专用资源 | 已发送、已读 |

`users` 是成员阶段的唯一权威来源。发展党员追踪看板、成员选择器和其他显示入口都由同一服务读取成员资料。活动完成前，原成员阶段保持不变。

### 4.2 权限边界

| 动作 | 责任角色 |
| --- | --- |
| 创建、编辑会前草案；关联和归档支部文件 | 按现有支部文件管理权限 |
| 填写会议结果；发起成员变更申请 | 具备活动写入权限的人员 |
| 审批成员变更申请 | 组织委员 |
| 查看支委广播与记录已读时间 | 全体支委 |
| 确认并更新成员资料 | 书记 |

服务端对每个动作独立鉴权；前端的隐藏或禁用只承担引导作用。

## 五、验收条件

> **验收状态（2026-09-05 复核）：全部通过 ✅**——5.1 资料查询（`references.js` 官方/支部文件分区 + 草案创建/关联活动/归档展示）；5.2 会议与成员变更（`calendar-tab.js` 议程封装 + 成员变更申请审批流 + 服务端 `users` 阶段更新 + 支委广播；`server/test/` member-change-flow、member-change-cross-session、agenda-* 系列测试佐证双会话一致性与重启持久）；5.3 回归与界面质量（`server/test/` 全绿 + 链接/审计守护通过）。

### 5.1 资料查询

- 页面不再显示顶部类别 tab。
- 官方文件区和支部文件区仍清晰分开。
- 支部文件写入入口可创建会前草案。
- 草案关联活动并完成归档后，支部文件区能显示该关联关系。

### 5.2 会议与成员变更

- 一次会议可同时包含普通事项、讨论文件和成员变更事项。
- 讨论文件项只能选择会前草案，且会后可以记录结果并生成归档待办。
- 成员变更事项在会议结果通过后创建申请；组织委员审批后立刻生成全体支委逐人广播记录；书记确认后更新服务器成员资料。
- 两个独立登录会话先后读取同一成员资料时，书记确认后的阶段一致；服务器重启后仍保持一致。

### 5.3 回归与界面质量

- 活动与工作流测试、登录端到端测试、模块加载测试通过。
- 资料查询操作经本地网页测试确认，键盘可访问搜索、创建草案、关联议程和确认操作。
- 资料查询的视觉实现通过现行网页界面设计指南审查；其中任何新增视觉选择均在实现前向书记确认。

## 六、已确认的界面构图

- 高级选项采用折叠区：默认收起，展开后管理会后衔接事项。
- 会议结果采用议程项内呈现：避免另建“会后处理”区而割裂事项与处理结果。
- 讨论文件默认文案保持「讨论……文件」，不把表决措辞固定为议程名称。
