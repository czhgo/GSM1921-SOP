**CLAUDE.md、guides、insights、logs 之间的关系**：

```
                    CLAUDE.md（甲部 Harness）
                    ┌──────────────────────┐
                    │ 核心原则 + 判例       │  ← 最高权威，定义"是什么"和"为什么"
                    │ 乙部执行事项          │  ← 当前工作上下文
                    └──────────┬───────────┘
                               │ 引用
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │  guides/   │   │ insights/  │   │   logs/    │
     │ 设计理念   │   │ 经验沉淀   │   │ 运行记录   │
     └────────────┘   └────────────┘   └────────────┘
     定义"怎么设计"   提炼"什么经验"   记录"做了什么"
```

**四者职责**：

| 维度         | CLAUDE.md 甲部   | guides/          | insights/   | logs/       |
| ---------- | -------------- | ---------------- | ----------- | ----------- |
| **定位**     | 核心原则（原则+判例）    | 详细设计             | 经验模式        | 事实记录        |
| **内容**     | 核心原则、关键判例、运行标准 | 完整设计文档、架构方案      | 可复用经验、管理哲学  | 操作步骤、决策过程   |
| **稳定性**    | 最稳定（修改须支书确认）   | 稳定（设计理念始终存在）     | 渐进增长（定期沉淀）  | 只增不改（归档后冻结） |
| **信息流向** → | ← guides 补充细节  | ← CLAUDE.md 授权原则 | ← logs 沉淀提炼 | ← 执行过程产生    |
| **信息流向** ↓ | ↓ 乙部规定当前工作     | ↓ 代码实现设计         | ↓ 指导未来决策    | ↓ 归档为历史     |

**关键规则**：

- CLAUDE.md 甲部是 guides 的**摘要和索引**，不是 guides 的副本。甲部保留核心原则+判例，详细设计归 guides
- 当甲部与 guides 内容冲突时，以**甲部为准**（本文件 §1.1 上层优先原则）
- guides 的更新如果涉及甲部引用的原则变更，必须**同步更新甲部**（H30.1 一改具改）
- insights 从 logs 中沉淀提炼，不直接从 guides 中产生
- logs 是原始记录，insights 是提炼后的知识，两者不可互相替代

> **标准模板出处与禁止自创字段（原 insights §6.7 并入）**：上述字段顺序与内容以 [ARCHITECTURE.md](ARCHITECTURE.md) 为标准模板，新建文件不得自行添加未经批准的字段。为什么"每个文件按需自定义"不成立：字段自定义膨胀导致维护混乱——owner、audience、purpose 等字段曾被随意添加，后因非批准设定而全部删除；统一模板确保字段含义一致、字段顺序一致、新增字段需经审批。ARCHITECTURE.md 作为仓库架构说明文件，天然是 YAML 规范的权威源。为什么"没有模板也行"站不住：没有模板时每个新建文件会参照不同的既有文件，导致字段名和顺序未同步；模板的作用是减少决策成本而非施加限制——新建文件时无需思考"该加哪些字段"，直接套用即可。

### 5.1 文件职能声明（2026-09-17 支书裁定「一文件一职能」）

**常读文件**（每次会话必读 / 每次开工必扫 / 每次收尾必核者——现行清单与各自职能见 `DOC_MAP.md`「职能」列）除 YAML 头外，**头下必须有一段「职能声明」**，逐条答清三问：

1. **回答什么问题**——本文件**唯一**要回答的那个问题（一句话、用日常语言。**写不出来＝它承担了多个职责**，须按「治理文件功能审计与拆分」拆开，见 [DOCUMENT_GOVERNANCE.md](../05_ai_coding/DOCUMENT_GOVERNANCE.md)）；
2. **不回答什么**——明确列出**容易被误以为该在此处、实际归别处**的内容，并**指名去向文件**；
3. **谁在什么时候读**——读者（`[用户]`/`[工程师]`/`[AI]`）与触发时机。据此定读取策略：**active**＝每次会话必读 / **on-demand**＝按环节触发。

**为什么必须写下来**：本仓的病灶不是「文件太长」，而是「**文件末尾持续追加、且与本文件自述的职责不符**」——「裁决与沿革可查」的前提是**读者在打开之前就知道该打开哪个文件**；职能不写清，追加就没有边界，越追加越没人敢删（判例：`REVIEW_QUEUE.md` 自述「评议完成即清空」而实际积到 281KB；`ENGINEERING_ASSESSMENT.md` 自述「覆盖式维护、不逐轮留历史行」而实际逐批追加，YAML 头停在 09-09）。

**⚠ 第 2 条「不回答什么」是本小节的重点，不是凑数**：只写「回答什么」，追加者仍会以「这也算本文件相关」为由继续加；写明「不回答什么 + 去向」，追加前就必须先回答一遍「它是不是该去别处」。**这一条是追加行为的闸门**。

**生效条件**：新增或修改任何常读文件的头时；发现某文件自述与实际状态不符时（**发现即同批更正**——留着错自述比不写更坏，它会让后来人相信一个不成立的边界）。

**YAML 头同步**：职能声明落地时，同一批须把 YAML 头改准——`last_updated` 必须反映**最后一次实质变更**（不是首次建立），`status` / `related_files` 与新职能一致。**「头没动」本身就是一处未同步**（判例：`ENGINEERING_ASSESSMENT.md` 头停在 `2026-09-09` 而正文已维护到批次 49）。

**内容成段迁走之后，原位只留一行「迁出去向说明」（2026-09-17 立，与本节同规）**：这一行要写清三件事——**迁到哪儿**、**为什么迁**、**现在要查该去哪**；**原标题一并保留、不删**（留一行去向说明比留一个空号更容易被找到：空号只说明「此处曾经有东西」，去向说明才回答「现在该看哪个文件」）。**适用**：任何把成段内容迁入 `.ctx/logs/` 或其它文件的场合；**不适用**：一次性小修小改（改完即就位的，不必留指针）。

**规范里指名的落点，必须与规范同批建立（防死指针）**：写规范时凡**指名一个落点**——某个文件里的**某一列 / 某一节 / 某张表 / 某个字段**——**该落点必须在同一批里建出来**；不得先写「见 XX 文件的 YY 列」，指望以后再补那一列。**为什么**：规范是**被读来照做的**——读者（人与 AI）会照着规范去找那个落点；落点不存在，规范就变成了**教人写死指针的来源**（判例：职能声明写「各文件职能见 `DOC_MAP.md` 的「职能」列」，而那一列当时并不存在 ⇒ 四份 `.ctx` 文件的声明同时指向空处；后由 `DOC_MAP.md §〇.1` 补齐才成立）。**判据**：① **先建落点，再写指针**（顺序可调，但**不能只落指针**）；② 指针要**指到可核的位置**（文件 + 列 / 节名，不只写「见 XX 文档」）；③ 与上一条「内容成段迁走之后原位只留一行迁出去向说明」是**同一条指针纪律的两端**——一端管「**写下时**指得存在」（本段），一端管「**迁走后**原位指得出去」（上段）。**生效条件**：新增或修改任何含指针的规范文本时；发现指针指向不存在的落点时（发现即同批补上落点，或改写指针）。

## 6. 编码规范

全仓库必须遵守以下编码标准，确保中文内容在所有工具链中正确显示：

1. **文件编码**：所有文本文件（`.md`、`.js`、`.html`、`.css`、`.json`、`.yaml`）必须使用 **UTF-8 无 BOM** 编码
2. **换行符**：统一使用 **LF**（`\n`），禁止 CRLF（`\r\n`）。`.gitattributes` 中应设置 `* text=auto eol=lf`
3. **中文标点**：Markdown 正文中使用**中文标点**（，。：；！？""''），代码和表格内使用英文标点
4. **git 操作编码**：执行 `git show`/`git diff` 等命令时，必须设置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，避免中文乱码
5. **PowerShell 输出**：使用 `Out-File -Encoding utf8` 保存文件，禁止使用默认的 Windows 编码

## 7. 文档排版格式规范

> **确立日期**：2026-08-09 | **确立背景**：支书指出"有的有 `---`，有的则没有，有的有 `>`，有的没有。并非说一定要有/没有，但是不能因为写入批次的不同，而出现明显的'有机性'上的问题"。本节为全仓 Markdown 排版格式的唯一权威源。

```markdown
> **与§X的边界**：<与相邻章节的职责边界（可选）>
```

- 无来源故事的条目不写元数据块（避免伪造来源）

## 8. 内容写入与有机性标准

> **确立日期**：2026-08-09 | **确立背景**：支书要求"写入标准要突出有机性——不仅仅是格式上的有机性，而是内容上浑然天成，而不是感觉悬吊着补丁"。

### 8.1 有机性的定义

**补丁**：一段内容可以无损地从文件中摘除，摘除后上下文依然通顺——它是"贴"上去的。
**有机**：一段内容嵌入在主题链条的正确节点，删除它会留下结构性空缺——它是"长"出来的。

### 8.2 五条检查

| # | 检查     | 判断方式                            | 补丁信号                   |
| - | ------ | ------------------------------- | ---------------------- |
| 1 | **归属** | 内容与所在章节主题匹配？换到别处是否更合理？          | 错位——内容与章节主题无关，或有更对口的章节 |
| 2 | **衔接** | 删除它，上下文是否依然通顺？插入后与前后段落是否有承接？    | 可无损摘除；前后无呼应，像独立贴片      |
| 3 | **根系** | 是否沿用既有术语、回应既有反论、关联既有条目（§ 交叉引用）？ | 自说自话，不接入既有概念网络         |
| 4 | **冗余** | 既有内容是否已覆盖此观点？覆盖则并入/更新而非新增       | 同义重复，只是换种说法再写一遍        |
| 5 | **生长** | 写作方式是"附加一段"还是"改写既有段落使其自然延伸"？    | 永远是附加式，从不改写融入          |

### 8.3 写入前自检清单

```
□ 1. 归属：这份内容属于它被写入的章节吗？换到别处是否更合理？
□ 2. 衔接：删掉它上下文依然通顺（补丁）；插入后与前后段落有承接（有机）？
□ 3. 根系：它是否沿用了既有术语、回应了既有反论、关联了既有条目？
□ 4. 冗余：既有内容是否已覆盖？覆盖则并入而非新增。
□ 5. 生长：优先"改写既有段落使其自然延伸"，而非"另起一段附加"。
```

### 8.4 与既有标准的关系

- 与 §9.1（编号插入规则）互补：§9.1 决定"插到哪里"，本节决定"怎么写才不像补丁"
- 与 §11（反论审核标准）互补：反论审核针对"论点是否两面论证"，本节针对"内容是否融入结构"
- 与 §7（排版格式规范）互补：排版管"形式"，本节管"内容"

### 9.2 乙部任务编号体系

格式：`T<轮次>-<序号>`

- **轮次**：按工作日递增（T30, T31, T32...），每轮可包含多个任务
- **序号**：同一轮次内的任务序号（1, 2, 3...）
- **跨轮延续**：若某任务未完成，在新轮次中保留原编号，不重新编号

**防数字爆炸策略**：

- 轮次编号与日期绑定，不与任务数量绑定。一个工作日即一个轮次，无论当天有多少任务
- 轮次编号不要求连续——T30 之后可以是 T35（中间跳过的轮次编号不回收）
- 序号上限：单轮次内序号原则上不超过 20。若超过，说明该轮次应拆分为多个轮次
- **持续任务**使用 `C-<序号>` 前缀，不占用 T 编号空间
- **待讨论议题**使用 `D.<序号>` 前缀，**暂缓议题**使用 `F.<序号>` 前缀

### 9.3 编号对应关系

乙部任务编号与日志条目之间**必须建立双向可追溯关系**：

```

```

**执行日志中的编号规则**：

- 每条日志条目标题格式：`## YYYY-MM-DD | T<轮次> — <一句话摘要>`
- 条目内用 `T<轮次>-<序号>` 标注具体完成的任务

**决策日志中的编号规则**：

- 格式：`D-<序号>`，全局递增，不按月重置
- 若某决策与乙部任务相关，标注对应任务 ID（如 `关联任务: T30-7`）

## 11. 反论表述审核标准

> **确立日期**：2026-07-08 | **确立背景**：insights 文件中存在"为什么不是加法关系""为什么不是乘积关系"等缺乏上下文、易产生歧义的反论表述

### 11.1 什么是反论

反论是指用"为什么不是 X"形式表达的否定性对比论述，目的是通过否定一个错误方向来凸显正确方向。

### 11.2 应该用反论的情况

满足以下**全部条件**时，适合用反论：

- 被否定项 X 是读者**可能合理误选**的方向（读者真的会想到 X）
- 否定 X 后能**凸显正确方向**（对比有教学价值）
- 被否定项 X 是读者**熟悉的具体概念**（而非生造概念）

**正面案例**：`扁平化不能与没有"程序"等同` — 读者确实可能误以为扁平化就是不要程序、随意为之，否定有教学价值（支书 2026-08-09 复核：原标题"扁平化≠无分工，而是无上下级"为错误反论——"无上下级"恰是扁平化的正解而非反论，真正需否定的误区是"扁平化＝没有程序"）

### 11.3 不应该用反论的情况

出现以下**任一情况**时，不适合用反论：

- 被否定项是读者**不熟悉的抽象概念**（如"为什么不是加法关系"——读者不知道"加法关系"指什么）
- 被否定项是**生造概念**或无对照价值（如"为什么不是乘积关系"——"乘积关系"是为反论而生造的术语）
- **缺乏上下文**导致反论无意义（未说明在讨论什么，直接抛出"为什么不是 X"）
- 存在**术语冲突风险**（被否定项与既有术语同名，造成混淆）

### 11.4 反论成立三要素

一个合格的反论必须同时具备：

1. **明确的上下文**：读者知道在讨论什么问题
2. **被否定项的简要说明**：读者知道被否定的是什么（一句话解释 X 是什么）
3. **否定理由与正确方向的关联**：读者理解为什么正确方向更好（不只是"X 不对"，还要说"Y 对在哪里"）

### 11.5 改写策略

对不达标的反论，按以下优先级改写：

1. **首选：改写为正面表述**。直接说"是什么"，而非"不是什么"。如"为什么不是加法关系" → "两者是乘积关系而非简单堆叠"
2. **次选：补充上下文后保留对比**。若对比有教学价值，先说明上下文，再否定。如"有人可能以为是简单堆叠（加法关系），但实际上..."
3. **避免：术语冲突**。若被否定项与既有术语同名，必须改写，不得保留

### 11.6 自检清单

写反论前自检：

```
□ 1. 读者真的会想到被否定项 X 吗？（若不会，改正面表述）
□ 2. 被否定项 X 是读者熟悉的概念吗？（若不是，改正面表述）
□ 3. 上下文是否明确？（若不明确，先补上下文）
□ 4. 否定后是否说明了正确方向？（若没有，补关联）
□ 5. 被否定项是否与既有术语冲突？（若冲突，必须改写）
□ 6. 被否定项在仓库中是否仍被使用？（若已无使用，反论本身应删除）
□ 7. 反论是否涉及AI治理技术？（若是，AI须联网搜索补充普适性+特殊性后，支书再决策）
```

### 11.9 反论评议维度体系

> **确立日期**：2026-07-18 | **确立背景**：反论评议第一轮中，支书对12条反论的反馈揭示了三类系统性的反论问题维度，每类有不同的处理方式
> **定位：** 反论的事后质量评议（区别于 §11.2/§11.3 的事前存在标准），是 H60 支书评议的反论专用补充，速查见 [§18.5.1 反论评议](#1851-反论评议)。

反论评议中发现的三类问题维度：

| 维度    | 含义           | 判定标准                                                                                | 处理方式             |
| ----- | ------------ | ----------------------------------------------------------------------------------- | ---------------- |
| 正确的废话 | 技术正确但无增量信息   | 被否定项已无人主张（历史范畴/生造概念），或反论仅重述正论。**判定标准是"无增量信息"而非"与母本重复"**——与母本重复但提供母本未展开的具体应用场景的反论应保留 | 删除反论，改为正面陈述      |
| 命题错误  | 被否定项不准确或为稻草人 | 被否定项无人会主张，或AI将正确概念错误组合产生新命题                                                         | 删除反论，用支书原话替代     |
| 重点偏差  | 有增量信息但重点偏移   | 反论方向正确但未触及支书判断的核心关切。**反论重点应在正论方向（强化正论），而非仅在排除替代方案**                                 | 修正重点，关联支书判断的核心关切 |

**反论与正论的三种处置关系**（2026-07-19 第二/三轮评议沉淀）：

| 关系类型      | 判定标准                                                      | 处理方式              |
| --------- | --------------------------------------------------------- | ----------------- |
| 保留        | 反论提供独立补充视角，与正论不重复                                         | 维持反论              |
| 融入正论      | 反论与正论重复且应用场景与正论强耦合（正论需要该场景才能完整说明）                         | 删除反论，核心表述融入正论     |
| 删除反论+补充正论 | 反论本质是正论的变形（如"为什么不是 X 总比 Y 好"预设"X 总比 Y 好"是观点，但正论已明确"按需选择"） | 删除反论，强化正论"按需选择"表述 |

> **确立日期**：2026-07-08 | **确立背景**：部分文件命名过长（如"关于支部大会时间调整的改革说明（征求意见稿·修订版）.md" 64 字符），导致管理与阅读困难

### 12.2 命名标准

| 文件名类型 | 命名风格                     | 字符上限    | 示例                                                 |

### 12.3 超长文件名处理原则

1. **保留原名+索引简称**（首选，适用于历史档案）：文件保留原始命名，在目录 README 中建立简称映射。适用于 `content/01_strategy/references/历史会议材料/` 下的文件

3. **拆分**（适用于内容可分离）：当文件内容可合理分为多个独立部分时，拆分为若干短文件

### 12.4 历史档案例外条款

`content/01_strategy/references/历史会议材料/` 下的文件保留原有命名方式，不强制改名。这些文件是历史档案，改名会破坏引用链路且无实际收益。

### 13.7 章节过渡的承接性原则

> **确立日期**：2026-07-20 | **确立背景**：支书指出 SECRETARY\_DIRECTIVES.md 中 11 个"第X章过渡"段落"目前这一句话毫无过渡作用"，并提出章节衔接的核心规则。

**核心规则**（支书原话，2026-07-20）：一个好的逻辑结构是"前面章节提出问题在后面的章节得到回答，后面章节的解答依托于前面章节的讨论"。

**操作要点**：

1. **前一章的自然延伸**：前一章的论述应自然引出未解决的问题或未展开的维度，过渡段点明这个"未解决的问题"
2. **后一章的承接回应**：后一章的展开承接前文的讨论并给出回应，过渡段点明"本章如何回答前文的问题"
3. **承接关系的显化**：过渡段应显化这种"问题→回答"的承接关系，让读者理解章节排序的逻辑
4. **禁止机械复述**：禁止"上一章讲X，下一章讲Y"这种机械复述章节主题的写法——这种写法无过渡作用

**反例**（机械复述，无过渡作用）：

> 上一章讲"支部为谁存在、组织性为什么宝贵"，下一章讲"支部的具体工作怎么组织落实"。

**正例**（体现承接关系）：

> 前一章回答了"组织性为什么宝贵"，但还没说清"支部的具体工作怎么组织落实"——支部里有主题党日、三会一课、专班、发展党员等各类工作，如何有序推进？这正是下一章要回答的问题。

**适用范围**：所有面向用户的阐述性文档中跨章节的过渡段落，特别是 SECRETARY\_DIRECTIVES.md、DEVELOPMENT\_PATH.md 这类按问题脉络组织的长文档。本节是 §13.2"段落化叙述"的进阶——前者要求段落有叙述性内容，本节要求章节过渡段落体现前后章节的问题-回答关系。

### 17.3 自动唤醒机制设计

#### 17.3.1 架构

| 层次               | 职责                                      | 实现位置                           |
| ---------------- | --------------------------------------- | ------------------------------ |
| 时间戳注册表           | 记录每个周期性任务的最后执行时间                        | `.ctx/TIMESTAMPS.md` 的周期性任务追踪区 |

- 若 `(now - last_W1) > 7天` → 触发 W1

### 17.5 常态化工作的制度存续与任务清理解耦（原 insights §3.8 并入）

> **确立日期**：2026-09-04（insights 分流归位）| **项目落地**：CLAUDE.md H60.5 常态化专项评议机制 + `.ctx/REVIEW_QUEUE.md` 附录（即 §17.2.1 W4 专项评议循环的载体）

多轮持续、无"完成"态的经常性工作（周期性评议、常态化审查、持续审计），其**制度本体与任务清单管理应解耦**：

- **制度本体写入治理文件**——「该怎样评」由机制定义（本节 §17 + CLAUDE.md H60.5 表格），不随轮次进度变化
- **轮次进度挂外部承接文件**——「评到哪了」是状态（`.ctx/REVIEW_QUEUE.md` 附录的进行中轮次条目），随执行更新

任务清单清理（一轮完成、条目移除）不影响制度运转——清理的是承接文件中的进度条目，不是机制本身。

**为什么不是"机制与进度放在一起"？** 混在一起时，轮次结束后清理任务清单会误伤制度本体——删除清单时可能连带删掉"该怎样评"的定义；解耦后各归其位，删进度不动机制、改机制不影响进度记录。

**生效条件**：适用于多轮持续、无"完成"态的经常性工作。一次性任务仍按常规生命周期管理；若常态化工作轮次终结（宣布不再需要），对应承接条目同步移除。

### 18.2 预审维度体系（承接 H60.2）

对每条命题按其特性灵活选择预审维度（不锁定数量）：

- **表述**：术语合规性（T1/T2/T3）、设问句、主观预设、书面语风格

- **奥卡姆剃刀**（按需）：是否存在"为概括而概括""fancy 但无内涵"的标签或结构性数字隐喻
- **概念过拟合**（按需）：是否存在 AI 擅自命名的小命题标签、无依据的层级标签、"="式命名、孤立概念——详见 §18.4

**维度选择原则**：AI 默认参考上述常规维度，但根据命题特性灵活选择——纯术语违规的命题可只审"表述"一维度，涉及制度设计的命题可增审"合规溯源"维度。若某命题只审部分维度，预审报告中注明"本次仅审 XX 维度，理由：……"。四维度为常规参考，非强制锁定。

### 18.4 概念复用性扫描流程（承接 CLAUDE.md H40.1 的纠正性扫描）

> "概念复用性扫描"是 T3 工作表达术语，指系统性扫描全仓库中 AI 过拟合命名的孤立概念标签，识别瘦身空间，并触发归并或删除。
> 支书元洞察（2026-07-19）："最大的根因在于：一个大的命题可能有很多个小命题。AI专注于过拟合那些小的命题的命名。但事实上，只需要给总的大命题命名即可。"

**扫描范围**：不仅限于 insights 文件——content/ 五子目录和根目录 .md 文件都存在概念膨胀和表述冗余的空间。

**扫描方法**：概念标签法——从文档中的命名性标签（速查表条目、「」命名概念、标题级概念）出发，按频次和复用性分类，而非全量 n-gram 扫描。

**五条判定维度**：

1. **B 表达原因·特定场景**：该概念因特定表达需要而存在，保留
2. **C AI 错误扩充**：AI 擅自创造的概念，支书从未提过，删除
3. **D AI 错误概括**：AI 擅自概括的标签，应归入大命题或删除
4. **D 应归并到大命题**：小命题标签，应归入大命题下作为描述，不单独命名
5. **需重命名**：命名方式违规（如"="式命名），需修正

**文件瘦身原则**：

1. **大命题优先**：多个小命题归入一个大命题，只保留大命题的命名标签
2. **重复表述归并**：同一命题在不同文件中的重复展开，保留最权威版本，其他文件仅引用
3. **AI 概括清零**：无支书原话或制度依据的 AI 自创概念标签，一律删除
4. **跨文件瘦身**：概念膨胀不仅出现在 insights 速查表中——03_doc_system 治理文档的过细分类标签、01_strategy 文档的冗余阐述、02_institution/sop 文档的重复定义，都应纳入瘦身范围
5. **根目录瘦身**：README.md、SNAPSHOT.md 等根目录文件，以及 ARCHITECTURE.md 等已迁移文件中的过时表述，同样需要随一改具改同步更新
6. **零补丁原则**：支书论断（2026-07-19）——"瘦身的一个重要方面是把文档变成一个有机整体。由于支书论述的批次不同，很容易出现到处打补丁的现象——新增内容单独成段落，即使和前面的段落也是相关的。"AI 无法自行判断如何融入（修改原命题的表述以切中新命题，还是调整新命题以适配原命题结构），须提交支书判定。**最终目标：所有涉及用户阅读的文档，零补丁识别。**

**执行流程**：

1. AI 扫描概念标签，按频次和性质分类
2. 逐条通过 AskUserQuestion 提请支书判定
3. 按判定结果执行：删除/归并/重命名/保留
4. 全仓库一改具改（CLAUDE.md H30.1），确保零残留
5. 记录至执行日志 T 编号

**与 CLAUDE.md H40.1 的关系**：H40.1 是预防性守则（修改时自检），本节是纠正性扫描（系统性排查）。两者互补。

- 三种处置关系：保留 / 融入正论 / 删除反论+补充正论
- 反论用例例子选择约束：避免军事术语/历史典故，优先工程实践或日常管理场景
- 预判差异记录：支书判断与AI预审不同时，差异须在评议记录中分析原因
- AI推导识别与级联修改（§16.4）
- 历史范畴检查：被否定项是否仍在使用（[§11.7](#117-历史范畴检查)）
- AI治理技术特殊性：涉及AI工具使用时需联网补充（[§11.8](#118-ai治理技术特殊性)）
  **详细维度体系**：[§11.9](#119-反论评议维度体系)

#### 18.5.2 理论复用评议

**目的**：评审全仓库跨节/跨文件引用的复用准确性、适用性及效果
**触发**：CLAUDE.md H60.1 触发条件 + T 编号任务
**核心规定**：

- 散落即未同步原则：信息重复散落视为未同步风险（[§1.4](#14-一致性检查规范)）
- 分轮规划：① insights内部复用链 ② 03_doc_system 治理文档间复用 ③ 01_strategy/04_web_design→02_institution/sop 复用链 ④ 跨目录复用断链检查

**四类问题维度**（2026-08-03 第2轮 T193 沉淀，经支书裁决 + CLAUDE.md H60.4 抽样全接受验证）：

| 维度 | 含义 | 判定标准 | 处理方式 |
|------|------|---------|---------|
| A 断裂链接 | 链接指向不存在的相对路径 | 目标文件/锚点不存在或相对路径计算错误 | 修正为实际存在的相对路径 |
| B 已删引用 | 引用已删除的代码/页面/模块 | 被引对象在 docs/src/ 或 docs/ 中不存在（含旧架构残留） | 替换为实际存在的等价引用；整体过时 → 全面重构（`ARCHITECTURE.md §十一` 服务目录 v13→v3.0 先例） |
| C 拓扑错误 | 结构/路径描述与现状不符 | 与 SNAPSHOT.md 权威拓扑或实际文件系统不符 | 按权威源修正描述 |
| D 表述 | 内容概括与文件实际内容不符 | 支书对照原文判定（先例：「26 条路线级论断」→「17 条论断，P-002/P-003 为元命题」） | 按支书统一改法 |

> 🔴 **D 表述为最高权重维度**（支书元洞察 2026-08-03）："【表述】是一个大头，因为这个系统的工作性质，要求表达非常严谨！" 表述严谨性是系统命脉——预审时 D 类须逐条细致审查，即使数量少也不得轻描淡写；处置一律提交支书判定，不机械代改。
>
> 🗣 **黑话审查**（支书指令 2026-08-03 T194 追加，D 表述专项）：重点识别 **AI 自己编造的黑话**——概念过拟合、无依据层级标签、孤立概念、生造术语、同义名词堆砌、**语气轻浮**（带引号俏皮口吻等不庄重表达；支书判例 2026-08-03：对"这不是'催你'"评价"表达就很轻浮"）等。判定标准：① 术语在权威源/上级文件中是否有依据（T1 术语须与原文一致）② 是否可被目标读者直接理解 ③ 是否存在更通俗的同义替代表达。基线方法：以**支书论断汇编**（SECRETARY_DIRECTIVES.md，最接近原话的基线）grep 验证——汇编存在的措辞非 T3；DEVELOPMENT_PATH.md 等 AI 编写文档可能自身已被污染（T-195 判例：哲学锚点/心智模式/切面/漂移（该词第 7 轮已改「失同步」，第 8 轮统一为「未同步」）均曾写入源头文档），不能单独作为基线。处置：识别出的黑话一律提交支书判定，AI 不得自行代改为自造术语。适用于全仓库用户文档，可多轮复用（T-195）。
>
> ⚠️ **源头污染优先警惕**（支书元洞察 2026-08-03 T-195 追加）："目前是检查出来上下游的引用，但是源头可能就是被污染的，这是要非常警惕的！" 引用链路修复（A/B/C 类）只保证链接与路径正确，**若源头文档的表述本身含 AI 编造的黑话，下游引用修复得再正确也是传播污染**。黑话审查须从权威源/母本源头逐层向下审查，而非仅查下游引用。
>
> 🗣 **句式合规**（支书判例 2026-08-03 T-199 P-010 微调）：禁用「不是……而是……」句式——支书否决"不是行政学黑话，而是一种理解手段"（P-010 重写稿）。评议任何表达时以此警觉：凡出现该句式一律提交支书判定改写为叙述式。

**流程要素**（T193 验证的可复用做法）：

#### 18.5.3 补丁审查（零补丁识别评议）

**目的**：识别用户文档中新增内容单独成段落（与前面段落/章节相关但不融入）的"补丁"现象，触发融入或调整
**触发**：CLAUDE.md H60.1 触发条件 + T 编号任务
**核心规定**：

- 零补丁原则：支书论断（2026-07-19）——"瘦身的一个重要方面是把文档变成一个有机整体。由于支书论述的批次不同，很容易出现到处打补丁的现象——新增内容单独成段落，即使和前面的段落也是相关的。"
- 多层过滤方法：问题脉络→主题相关→时间维度
- 三种处置：融入原命题 / 调整新命题 / 保留独立
- AI不得自行判断如何融入——须提交支书判定
- 最终目标：所有涉及用户阅读的文档，零补丁识别

### 19.4 文件角色分类术语

> **确立日期**：2026-07-01 | **最近更新**：2026-07-11（升级为新三分类，合并正交双维度）
> **确立背景**：支书指出"【人】可以划分为'用户'和'工程师'两种角色"——涉及党支部具体建设的解释、思路、支书的具体表述是给用户看的，工程师看的只是跟编程、系统设计、需求落地相关的文档。

#### 19.4.1 三分类定义

| 标记 | 名称 | 定义 | 典型场景 |
|------|------|------|---------|
| `[用户]` | 用户文档 | 涉及党支部具体建设的解释、思路、支书的具体表述 | 支书审阅党章原文、委员查阅 SOP 流程、党员学习建设思路 |
| `[工程师]` | 工程师文档 | 跟编程、系统设计、需求落地相关的文档 | 开发者查看架构说明、AI 读取系统设计、维护代码 |
| `[AI]` | Vibe Coding 协作文档 | AI 协作所需的指令、配置与运行时上下文 | 执行日志记录、Skill 工作流触发、核心规则校验 |

#### 19.4.2 复合标记规则

单个文件可同时属于多个类别，用 `+` 连接：

| 复合标记 | 含义 |
|---------|------|
| `[用户]` | 纯用户文档，AI 不主动读取 |
| `[工程师]` | 纯工程师文档，AI 不主动读取 |
| `[AI]` | 纯 AI 文档 |
| `[用户]+[AI]` | 用户文档 + AI 上下文 |
| `[工程师]+[AI]` | 工程师文档 + AI 上下文 |

**格式规则**：YAML 字符串格式 `role: "[用户]+[AI]"`；排序固定 `[用户]` > `[工程师]` > `[AI]`；单一角色时无 `+`。

> **为什么不用"受众 × AI 权限"双维正交？（原 insights §5.5 并入）** 读者会自然想到"给谁看"和"AI 能否读"是两个不同的问题，值得拆成两个维度。但复合标记已在单维上完整表达了"人类 + AI 共读"的组合——双维正交没有表达任何单维 + 复合标记表达不了的信息，却让读者多理解一个坐标系。分类维度的取舍以"信息能否用一行标记完整表达"为度：能，则不拆。

#### 19.4.3 使用规范

- **文件 YAML** 的 `role:` 字段使用 `[用户]`/`[工程师]`/`[AI]` 及其复合标记，不再使用 `[人]`/`[人机]`
- **DOC_MAP.md** 的"受众"列使用同一套标记，不再区分两个维度
- 三分类的完整定义（读者画像+权限边界+AI 读取规则）见 [§24 三分类定义](#24-三分类定义)

#### 19.4.4 物理分离：目录是第一道导航（原 insights §5.5/§1.7 并入）

> **确立日期**：2026-09-04（insights 分流归位）。§5.5 承接原 insights §1.7 的文件角色标记正文，role 标记体系本身见本节 19.4.1-19.4.3（去重不重复）；本节只承载其独有增量——物理分离原则。

`role:` 标记回答"给谁看"（19.4.1-19.4.3），但**文档归类必须按"受众×层级"矩阵物理分离，不能只靠 YAML 标记区分**——当项目存在多种受众角色（用户/工程师/AI）和多个内容层级（战略 meta/设计理念/具体操作/系统治理）时，**物理目录是第一道导航，元数据标记是第二道筛选**：读者在文件系统中浏览时，无需打开文件、仅凭目录名就能判断该不该读；YAML 标记需要打开文件才能看到。本仓库 `content/01_strategy/`~`05_ai_coding/` + `insights/` 的物理分层即此原则的落地。

**为什么必须物理分离？（三个分类依据）**：

- **受众维度**：受众不同（用户 vs 工程师）→ 关注点不同（做什么 vs 为什么这样设计）→ 表述风格不同（人话 vs 技术变量名）。若混在同一目录，用户翻开战略文档却撞上文件路径和函数名，工程师翻开操作 SOP 却发现全是流程步骤没有设计理由
- **层级维度**：层级不同（meta 战略 vs 具体操作）→ 稳定性不同（战略稳定、操作易变）→ 修改频率不同。若混在同一目录，频繁修改的操作文档会扰动稳定的战略文档所在目录，增加 git diff 噪声和认知负担
- **主题维度**：主题不同（党支部组织治理 vs 项目系统治理）→ 关注对象不同。若混在同一目录，"治理"一词的歧义会让读者无法区分文档管的是支部还是项目

**为什么不按其他方式分？** 两种常见替代方案都有缺陷：

- **按主题分（如"管理"/"技术"/"治理"）**：主题分类会混合不同受众和层级——"治理"目录里既有党支部组织治理（用户读）又有项目系统治理（工程师读），看似整齐，实则混淆了受众和层级两个正交维度
- **同一受众内继续细分（meta/concrete 拆分）**：设计理念与实现方案对工程师是连续的认知过程——读完"为什么"紧接着读"怎么实现"是自然流程；过度拆分会打断连续性、增加跨目录导航成本。物理分离的粒度应停在"受众切换处"和"层级稳定性切换处"，不必深入到同一受众内的认知子阶段

**为什么不用单一目录 + YAML 标记？** 目录是文件系统浏览时的第一道导航，元数据标记只适合做第二道筛选（同一目录内进一步区分），不能替代物理分离。

**生效条件**：文档数量超过 20 个、且存在多种受众角色时适用此原则；小型项目（<10 个文档）单一目录 + YAML 标记即可，物理分离反而增加导航成本。

### 19.5 术语权威层级（T1/T2/T3）

> 术语来源不同，权威性不同，修改规则也不同。混淆来源会导致AI自造术语被误认为支书原话。
> **前缀说明**：T = Terminology（术语层次），与文档权威层级（5 类知识类型）相独立，互不冲突。

| 层级 | 名称 | 定义 | 举例 | 修改规则 |
|------|------|------|------|----------|
| T1 | 官方表达 | 制度性文件、上级文件的原文用语（含权威来源对核心概念的官方定义） | "党支部""三会一课""组织委员""党小组" | 不可改（除非上级改） |
| T2 | 约定表达 | 支书在项目中明确提出或确认的表述 | "管理事、服务人""恢复对话能力""理解真实的组织和管理""善用经验""创新沉淀""框架内对话""一改具改""母本/子本""条/块" | 需支书确认才可改 |
| T3 | 工作表达 | AI为工作便利自行概括的术语 | "热温冷""支委" | AI可优化，但不得伪装为支书原话；"双域管理"已正式弃用；T3表达不进入用户文档和网页 |

**重要区分**：支书在项目中的原话属于T2约定表达，不属于T1官方表达——"官方表达"仅指制度性文件和上级文件的原文用语。上级文件的用语是非常准确的。

**升级规则**：T3→T2 升级须经支书明确确认。AI不得自行将工作表达升级为约定表达。

**标注规则**：在 DEVELOPMENT_PATH.md、CLAUDE.md 等关键文档中，凡使用 T3 工作表达的，应在首次出现处标注 `[工作表达]`。

**AI行为约束**：
- 当支书用自然语言说出N个观察点时，AI不得自动锁定数量——应先确认是否需要结构化
- AI自行概括的术语必须与支书原话明确区分，不得混同
- T3 术语的改写无需支书审批，但改写后必须一改具改
- **概括标签必须有关内容意义**：AI在为概念概括标签时，不得使用"支柱""维度""层面""根"等无内容意义的结构性数字标签（如"三支柱""三维度""三层面"）。若要概括，必须使用**有关内容**的标签——即标签本身应能表达"这是关于工作内容、工作方式还是工作流程等"的具体中心语。例如"纪检委员的三项工作内容"比"纪检委员三支柱"更好——"工作内容"是有内容意义的中心语，而"支柱"是无内容意义的结构性隐喻。违反此约束的标签视为"AI冒充但不自知的内容"。

### 19.6 表达方式分类原则

> **确立日期**：2026-07-15 | **确立背景**：支书指出"涉及结构化的内容（比如程序、制度），用列表式、表格等结构化方式展示的方式是重要的。涉及非结构化的内容（比如支书论断、故事叙述），段落化的表达式最重要的"
> **同步索引**：[§13.5 表达方式分类原则](#135-表达方式分类原则)

#### 19.6.1 核心原则

| 内容性质 | 表达方式 | 典型场景 |
|---------|---------|---------|
| **结构化内容** | 列表式、表格等结构化方式 | 程序、制度、流程步骤、权限矩阵 |
| **非结构化内容** | 段落化表达 | 支书论断、故事叙述、设计理念讲解 |

**判定要点**：内容本身是否具有"可枚举、可步骤化、可矩阵化"的内在结构——若有，用结构化；若无（如论断展开、叙事递进、理念阐释），用段落化。两者不可错配：把段落化的论断硬塞进列表会损失论证递进；把结构化的流程硬写成长句会损失清晰度。

#### 19.6.2 文档与表达方式的对应

| 文档 | 受众 | 内容性质 | 主表达方式 |
|------|------|---------|-----------|
| `content/01_strategy/DEVELOPMENT_PATH.md` | [用户] | 故事叙述 | **段落化**（全仓库唯一需要"故事完整"的文档） |
| `SECRETARY_DIRECTIVES.md` | [用户] | 支书论断 | 段落化为主，元数据单行化（引用块小字） |
| `content/02_institution/sop/*.md` | [用户] | 制度流程 | 结构化为主（表格/列表），why 讲解用段落化 |
| `content/03_doc_system/*.md` | [工程师]+[AI] | 治理规范 | 结构化为主 |
| `content/insights/*.md` | [用户]+[AI] | 经验沉淀 | 混合——理论/共识类段落化，技术/判例类结构化 |
| `content/01_strategy/*.md`（除 DEVELOPMENT_PATH） | [工程师]+[AI] | 设计理念 | 段落化为主，表格辅助 |

#### 19.6.3 "故事完整"的唯一性

**全仓库中需要"故事完整"的文档只有 `DEVELOPMENT_PATH.md` 一个**——承载"从入党申请人到正式党员"的完整叙事（CLAUDE.md H100 项目产出声明标注）。其他【用户】文档只需"用词严谨、尽可能言简意赅"，不要求"故事完整"。

**违反此约束的处理**：
- 把非结构化内容硬塞进列表/表格 → 重写为段落化
- 把结构化内容硬写成长句 → 重写为列表/表格
- 在非 DEVELOPMENT_PATH.md 文档中追求"故事完整" → 调整为"用词严谨、言简意赅"

## 20. AI 展开原则——"吃透精神后写出，而非标注边界"

> **确立日期**：2026-07-16 | **确立背景**：支书指出"AI 作为秘书，写出的话应该就是 grill 支书后的话——不需要在用户文档中区隔'支书写的'和'AI写的'，因为吃透精神后两者本应一致。问题只在于 AI 没吃透就写了"
> **优先级**：P0（强制执行）——本条是 AI 展开支书原话的最高准则（2026-08-05 第4轮评议升为独立章）
> **同步索引**：[§13.6 AI 展开原则](#136-ai-展开原则吃透精神后写出而非标注边界) + [SECRETARY_DIRECTIVES.md P-002](../01_strategy/SECRETARY_DIRECTIVES.md)

### 20.1 核心原则

AI 对支书原话的展开，目标是**吃透支书精神后用自己的语言把原话讲透**，而非复读原话或标注"这段是 AI 写的"。吃透后的展开与支书原话在精神上应无张力——读者无需区隔也能感受到一致性。

### 20.2 四种"没吃透"信号

| 信号 | 判定标准 | 正确做法 |
|------|---------|---------|
| AI 自造术语 | AI 用了自己概括的抽象术语，而非支书会用人话 | 用支书原话的措辞或 T2 级表达 |
| 方向对但措辞走形 | 支书原话方向对，但 AI 展开时措辞走形 | 回到支书原话的措辞重新展开 |
| 精神重心偏移 | 支书强调 X，AI 展开重点变成 Y | 重新对齐支书强调的重心 |
| AI 私加逻辑链 | AI 加了支书没说的因果推导，看起来合理但支书未必认同 | 先确认支书是否认同该逻辑链，再决定是否保留 |

### 20.3 可复用检查规则（支书评议 2026-07-16 确认）

以下 5 条规则由支书在 P.4 冒充排查评议中确认，可在后续检查中反复调用：

1. **"而非"警惕**：所有"A 而非 B"句式都要高度警惕——这是 AI 构造哲学对立的典型句式，支书的表述方式是正面阐述，不是"A vs B"二分
2. **"所以"因果链**：正文以"所以""因此"开头的演绎段落，如果支书原话没有该因果链，属于私加逻辑链
3. **反面假设**："如果不...就..."式反面推导，如果支书原话是正面阐述，AI 私加的反面属于没吃透
4. **私加强调**："这正是""这正是要警惕的""这也就意味着"等强调句，如果支书没有强调该点，属于 AI 自行加权的重心偏移
5. **元叙事标签**："从 X 框架转向 Y 框架""重新确立"等元叙事表述，如果支书没有做过框架性表述，属于 AI 的归纳包装
6. **= / ≠ 符号（2026-08-30 支书裁决新增）**：任何文档、审议草案、AI 展开、REVIEW 相关文字中**不得出现「=」「≠」符号**（含"集中=决策有归属""扁平≠没有程序"等）——符号表达是 AI 懒政，支书"真的很讨厌"，一律用自然语言写关系（且注意不替支书定性，见战略模糊自觉）；"不是…而是…"反论同时全面禁止（同源裁决，详见 CLAUDE.md H10 支书原话表达纪律）

### 20.4 禁止事项

- **禁止在【用户】文档中添加"支书原话/AI展开"区隔标注**——支书明确不希望读者看到这种区隔
- **禁止把 AI 展开全部删除只留引用块**——展开的价值在于"用支书的精神把原话讲透"
- **禁止机械复读支书原话**——展开应该让读者更理解，而不是把原话换种格式再说一遍

## 23. 内部代号简明词典

> **确立日期**：2026-09-05
> **为什么需要**：仓库文档与代码里高频出现一批代号——行业通用词与内部自造词混在一起，新读者（含新接手的 AI）难以分辨哪些可自行查证、哪些离开本仓库读不懂。
> **词典设计原则（支书裁决）**：**行业共识/通用词**只讲行业全称 + 一句解释，一句话带过，不建死板字段表；**真内部黑话/自造词**（离开本仓库读不懂的）才给「一句话人话解释 + 指向权威处」。判断核心 = 分辨行业共识与内部黑话。

### 行业共识词（可自行查证，一句话带过）

- **SSOT**（Single Source of Truth）：单一事实源——同一信息只在一处权威定义、其余只引用，本仓母本/子本关系注册见 [ARCHITECTURE.md §十](ARCHITECTURE.md#十单一事实源注册表与权威源治理)
- **SOP**（Standard Operating Procedure）：标准作业程序——把制度写成可执行的分步流程，制度母本在 `content/02_institution/sop/`
- **UI**（User Interface）：用户界面
- **ROADMAP**（路线图）：分阶段推进计划（如工作流模块化 L1→L5 愿景、各类整改批次 B1→B4）
- **mock**（模拟/桩数据）：开发与演示期的替身数据，相对真实后端数据
- **DataAdapter**（数据适配器）：隔离数据源的接口层，上层不关心数据来自 mock 还是真实后端（`docs/src/core/data-adapter.js`）
- **auth**（authentication / authorization）：认证与授权——登录与权限控制

### 内部黑话（真自造词，离开仓库读不懂）

- **L1-L4 阶段号**：工作流「代码化 → 可拖拽化」演进的推进层级号——L1 能力目录化 → L2 支部组合化 → L3 块封装契约 → L4 拖拽编排（L5 块分享复用）；说「做到 L3」即指推进到该层（[ARCHITECTURE_EVOLUTION.md §八](../04_web_design/evolution/ARCHITECTURE_EVOLUTION.md) 8.2 目标分层表；愿景总述见根 [README.md](../../README.md)「开源项目目标」）

## 25. 复合标记规则

单个文件可同时属于多个类别，用 `+` 连接：

| 复合标记 | 含义 |
|---------|------|
| `[用户]` | 纯用户文档，AI 不主动读取 |
| `[工程师]` | 纯工程师文档，AI 不主动读取 |
| `[AI]` | 纯 AI 文档 |
| `[用户]+[AI]` | 用户文档 + AI 上下文 |
| `[工程师]+[AI]` | 工程师文档 + AI 上下文 |

### 格式规则

- **YAML 字符串格式**：`role: "[用户]+[AI]"`（保持兼容性，不改为数组）
- **排序固定**：`[用户]` > `[工程师]` > `[AI]`（按人类读者优先级递减）
- **单一角色时无 `+`**：`role: "[AI]"` 或 `role: "[用户]"`

## 27. 协作方式

### AI 权限边界

| 标记 | AI 读取 | AI 修改 |
|------|---------|---------|
| `[用户]` | ✅ 只读引用 | ❌ 须 /ask |
| `[工程师]` | ✅ 只读引用 | ❌ 须 /ask |
| `[AI]` | ✅ | ✅（受核心规则约束） |
| `[用户]+[AI]` | ✅ | ✅（受核心规则约束） |
| `[工程师]+[AI]` | ✅ | ✅（受核心规则约束） |

### 跨角色修改规则

| 修改方向 | 规则 | 示例 |
|---------|------|------|
| `[用户]` → `[工程师]+[AI]` | 工程师可自由修改用户文档的工程实现部分，用户内容须 /ask | 工程师修改展示用户内容的代码 |
| `[工程师]+[AI]` → `[用户]+[AI]` | AI 可读取引用工程文档用于用户文档编写，但工程文档修改须 /ask | AI 引用架构说明编写用户指南 |
| `[AI]` → `[用户]` / `[工程师]` | 严格禁止 AI 直接修改用户/工程师文档源文件 | AI 不可修改党章原文、设计文档 |

### 引用渲染机制

当系统功能模块（如工作台「我的职责」Tab 分组）需要在界面上展示 `[用户]` 角色文件的内容时：

- AI 可读取 `content/01_strategy/references/合规文件/` 下的文件内容
- 将内容渲染到 HTML 界面的只读展示区
- 源文件保持不可变的 `[用户]` 角色状态
- 渲染缓存与源文件保持同步（文件变更时自动更新展示）

此机制填补了 `[AI]` 不可访问 `[用户]` 和"界面需要展示官方内容"之间的权限缺口。

### 信息流向

```
[用户] 决策/授权（支书/委员）
  ↓
[工程师]+[AI] 执行/消费 ←→ [AI] 自动化/校验
  ↓
[AI] 记录/归档
```
