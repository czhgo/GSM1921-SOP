0.3登录说明

账号登录：到登录页（顶栏 / 侧栏「登录」）输入学号 + 密码，登录后自动跳转到你身份对应的工作台（0.2 表）。演示 / 测试账号密码统一 123456（如书记 储子禾 2300010001、党委组织员 9000000001）。
开发演示卡：登录页勾选「开发模式」开关 → 出现身份卡片网格 → 点任意角色卡一键进入该工作台（仅本地开发 / 演示形态可用）。
未登录：11 个根页面大多可匿名浏览（见 0.1 表）；顶栏铃铛左侧与侧栏底部都有「登录」按钮；点工作台、提交反馈等需登录的操作会自动跳登录页。

1快速上手

这一章讲登录后的通用规则：登录落在哪、工作台长什么样、哪些事你能看能改。逐台 tab 详表在第 2 章，按你的身份翻对应小节即可。

1.1登录与角色落点

登录后系统按角色直达工作台（映射见 0.2），且工作台打开即「今天」页——它是登录落点：当天到期的待办、临近的会议与分工一眼可见。 党委工作台的登录落点是「治理总览」（全院支部概览）。公共根页面未登录即可浏览，需要动手的操作一律先登录（0.3）。

1.2工作台通用骨架

七个工作台都是「一个页面、顶栏 tab 切功能」。tab 条按组分段（各组名因台而异），各台都有以下通用件：

  • 「今天」置首（登录落点）：当天到期 / 逾期与近期会议、分工的速览。行内「到期 / 逾期」点击直接去待办处理；「会议 / 分工」点击进对应活动详情；「全部」跳到本台承载活动的 tab。
  • 「待办」＝ 页顶「未读通知 N 条」轻量条 + 9 业务域折组：页顶点开逐条阅读、读后即消；下方待办按工作类型分 9 域折组——会务 / 活动与项目 / 考勤纪律 / 考察 / 成员发展 / 专班 / 决议上报 / 归档宣传 / 汇报反馈。每条待办卡片写明「做什么」并带「去处理」跳转——点按钮直达负责该事的 tab 或详情页（这就是“处理在哪做”的提示），做完自动消。书记 / 纪检等不落库的实时提醒也会并入对应域。
  • 「工作概况」三区总览：汇报 / 卡点 / 在办三区，条线数据按职责注入；书记台为「全局概况」，另含「按人视图」（各角色在办清单，谁在干什么、有无异常）与维度态势。
  • 「党建」组各域 tab：该角色的职责操作都在这组里（写活动、考勤、考察、归档……具体见第 2 章逐台表）。
  • 「我的处置」：你经手的反馈 / 上报及处理记录（书记台为「反馈管理」，成员台与党委台无此 tab）。

处理在哪做：写操作都落在对应业务的 tab 或详情页里（例如写活动在「活动管理 / 活动写入」，交思想汇报在成员台「思想汇报」）；待办只做“提醒 + 跳转”，不做操作。

1.3权限知情边界

系统权限不是“给你一个账号就什么都能做”，而是赋权关系链：谁给你赋的权，你就在谁的赋权范围里干活。能否操作由 canDo() 统一判定——常设角色（书记 / 副书记 / 组织委员 / 宣传委员 / 纪检委员 / 党小组组长）与 项目角色（组织者 / 深度参与者）的权限取并集，按“能做什么”逐项判定。党委组织员是组织级角色，走党委工作台的全院治理权限，不属于支部内部权限链。

知情边界界定“能看什么”（看 ≠ 做：看得见不等于能代劳；信息精确等于职责所需的最小充分范围）：

视角谁能看到什么
个人视角每名成员自己的考勤 / 考察 / 参与记录、在办与汇报
块块视角党小组组长本党小组组员的「组员进展」：进度 / 考勤 / 考察（点开看，不能替做）
条线视角有赋权链的角色（组织委员看专班组织者 / 深度参与者；纪检委员看全员考勤考察）被赋权者的条线在办——谁给你赋的权，你在谁的范围内被看见
全局视角书记 / 副书记全局概况“按人视图”（各角色在办、可点击直达）与维度态势；支部分工视图
组织级视角党委组织员全院支部监控台账 / 上报审批 / 支部配置——跨支部、组织级，不参与任一支部内部闭环

写入范围界定“能改什么”：

写入范围授权方式享有角色
职能写入天然权限组织委员 / 宣传委员 / 纪检委员（各自板块）
活动写入天然权限书记工作台（书记 / 副书记共台）与党小组组长工作台（活动管理）
活动写入（需赋权）书记 / 组长赋权组织者 / 深度参与者（在成员台被赋权后操作）
专班发起 / 招募统筹天然权限 / 唯一节点发起：书记 / 组长 / 三委员；招募统筹：组织委员
思想汇报归档把关式初阅组织委员（通过才正式归档；退回附意见可修改重交）
支部配置 / 模块启停部署期职责党委组织员（党委台「支部配置」）；书记台「支部配置」为同源内嵌入口
通知发布天然权限书记（通知自动派生成员待办）；党委组织员（下发通知，标「党委下发」）

关键约束：

  • 创建活动仅限书记（副书记共台）与党小组组长；组长独立创建须报书记知情同意；组织委员协调的是专班（招募统筹），不是活动
  • 复盘提交入口归组织者 / 深度参与者（成员台「我的复盘」）；组长台「复盘状态」只读查看本组复盘情况
  • 宣传委员不可自行招募宣传专班，赋权操作统一归口组织委员
  • 看 ≠ 做：能看他人条线在办（按人视图 / 组员进展），不等于能代劳其操作

6这个系统在干什么

这个系统是北京大学光华管理学院本科生党支部的数字化管理工具——把党支部制度文本转化为可执行的代码工作流，让工作不随人走。

它要解决的核心问题是：党支部工作如何从"人治"走向"制度治理"？支委换届频繁，经验随人走、制度随人变；新支委上任后需要数月摸索才能上手；同一种工作在不同人手里做法完全不同。围绕这个问题，系统展开三个理念：

制度即代码

把制度文本转化为可执行的代码工作流，让工作不依赖某个人。

角色即视图

每个角色打开工作台就是该角色的全部工作视图，无需来回跳转。

经验可传承

复盘与归档沉淀经验，让新支委快速上手、制度随届接续。

系统现有 18 个页面：11 个根页面（首页、登录、资料查询、归档库、活动 / 通知 / 专班详情、意见反馈、帮助、关于、换组织向导）+ 7 个角色工作台（书记、组织委员、宣传委员、纪检委员、党小组组长、成员、党委工作台；副书记与书记共台，组织者 / 深度参与者归入成员工作台）。每个角色登录后直达自己的工作台，该工作台就是该角色的全部工作视图——各项功能按 tab 分组，无需在页面之间来回跳转；所有角色共享同一套数据，看到的是同一数据的不同视角。

系统采用「静态前端 + 一体化后端」：界面在浏览器渲染，数据经登录认证后落库持久化——换届不丢档、操作有留痕。谁负责哪块、谁能看到哪层，由赋权链计算：书记向下委托执行边界，其余角色的操作权限与知情范围随之派生（详见第 1 章 1.3「权限知情边界」）。

7技术架构

系统采用「静态前端 + Node 一体化后端」：界面在浏览器渲染，后端同源提供登录认证与数据持久化。以下分层讲清代码与制度的关系。

7.1分层结构

层位置职责
前台（页面）docs/（18 个页面：11 个根页面 + 7 个工作台）页面骨架，零硬编码逻辑
中台（逻辑）docs/src/entries/ + components/ + core/ + modules/角色面板路由、视图切换、DOM 渲染、能力注册
后台（服务层）docs/src/services/ + mock/数据 CRUD、权限计算、持久化
后端（server/）server/（Express + better-sqlite3 单进程）同源托管静态页面 + /api/v1 REST（登录认证 / 资源表读写 / 附件上传 / 快照持久化）
母本层content/02_institution/sop/所有代码逻辑的制度来源

7.2技术栈与运行方式

  • 静态前端 + Node 一体化后端 — 本地完整运行：进入 server/ 目录执行 npm start，浏览器访问即全链路使用（登录 → API → 数据持久化）；docs/ 亦可独立静态托管作演示形态
  • ES Modules — 无构建工具、零打包依赖
  • Tailwind CSS CDN — 原子化样式引擎
  • REST API（/api/v1）— 登录认证、资源表读写、附件上传、快照持久化
  • Custom Events — 组件间解耦通信
  • 多页面应用（MPA）— 18 个独立 HTML 页面
