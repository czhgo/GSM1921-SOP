> 定位：[用户]+[AI] — 用户决策参考 + AI 自主读取作为实施上下文。

## A. 设计背景与核心定义

### A.1 问题缘起

E1（ORGANIZATION_BUILDING_MODULE）定义了党务管理模块功能；E2（MANAGEMENT_MODE_ARCHITECTURE）定义了三级管理权限。**缺口**：三位支委在党务管理模块中的权限、入口、协作模式以及与党小组的交互关系尚未系统化。

### A.2 设计目标

| 目标 | 说明 |
|------|------|
| 权限明确 | 每位支委在党建工作台 + 党务管理 + 条块交互中各能做什么 |
| 入口自然 | 侧边栏进入"党务管理"后，系统自动识别角色展示对应面板 |
| 协作闭环 | 三委数据交接 + 条块任务对接均在系统内自动流转 |
| 最小侵入 | 不修改现有 SPA 路由和角色卡片体系 |

### A.3 条块二元结构与专班定位

当前组织格局为**条块二元结构**——条（vertical）：纪检/组织/宣传委员按职能分工；块（horizontal）：党小组按成员分布。专班打破了这一格局：既不完全是「条」（跨职能），也不完全是「块」（跨小组），而是**临时性、目标导向的横向切口**。

### A.4 专班核心定义

> **概念定位**：专班建设与活动组织实施是党建工作下的**并列概念**，归不同人管理。专班建设配套的定人定责定岗工作要点，主要涉及招募、考察等对专班人员的支持保障工作。

**专班是活动之外考察积极分子的载体**——通过赋权机制触发工作量记录线程，专班解散时自动生成工作量汇总报告（生命周期与赋权流程详见 §A.7）。

### A.5 专班类型矩阵

| 专班名称 | 挂靠角色 | 赋权内容 | 典型场景 | 存续周期 |
|---------|---------|---------|---------|---------|
| **宣传专班** | 宣传委员 | 素材归档+新闻稿起草+推送排版 | 大型活动/年度总结前期 | 按活动周期 |
| **SOP 维护专班** | 党支书 | SOP文档编辑+流程测试+bug反馈 | 系统升级/制度修订期 | 按版本周期 |
| **活动筹备专班** | 组织委员 | 场地协调+物资采购+外部联络 | 参访/共建活动 | 按活动周期 |
| **档案整理专班** | 宣传委员 | 历史活动档案补录+照片标注 | 年底/评优季 | 2-4周 |
| **技术保障专班** | 党支书 | 部署/域名/服务器+功能开发 | 系统新建/大版本 | 按项目周期 |

### A.6 条块衔接规则

1. ★ **组织委员是唯一专班管理节点**（党建工作最高优先级职能）
2. 宣传委员提出宣传专班需求 → 组织委员审核后在赋权面板中执行招募
3. 纪检委员的条因内控要求不生长专班（审查权力不可转授）
4. 党支书的条可跨所有职能提出专班需求，仍由组织委员执行管理
5. 专班成员来自任意党小组，不改变其原有党小组归属
6. 同一同志可同时加入多个专班（工作量分别记账，考勤数据与纪检共享）

### A.7 专班生命周期

```
发起 → 挂靠角色的委员向组织委员提出需求（名称+人数+周期+考核标准）
招募 → =赋权+记账：组织委员在赋权面板勾选同志→授予子角色权限→触发工作量记录
运行 → 专班成员看到专属工作台（任务清单+材料入口）→完成提交→记账线程记录产出
解散 → 组织委员点击「解散」→自动生成工作量汇总报告→赋权回收→报告写入个人档案
```

> 赋权是组织者/深度参与者角色的唯一来源。登录系统必须能查询赋权记录来确定用户角色。

> **积极分子担任专班组织者（D-240）**：积极分子可担任专班组织者，前提是经组织委员赋权（authorize_taskforce）。此设计体现"管理事、服务人"中"服务人"的一面——积极分子在专班中获得组织经验是培养路径的重要环节。赋权链不因发展阶段而阻断，组织委员赋权是组织者身份的唯一来源，与被赋权者的发展阶段无关。

#### 专班赋权流程（组织委员发起）

```
1. 需求提出 → 宣传委员/党支书向组织委员提出专班需求
2. 专班创建 → 组织委员在赋权面板创建专班（名称+人数+周期+考核标准）
3. 成员招募 → 组织委员在赋权面板勾选同志 → 选择授予角色（组织者/深度参与者）
4. 标记写入 → 系统自动标记 scope='taskforce'，sourceId=专班ID
5. 赋权生效 → 写入赋权记录表 → 被赋权者下次加载页面时可见专班视图
6. 通知被赋权者 → 系统推送通知（站内信/邮件）
7. 运行记账 → 被赋权者在专班中的产出自动记入工作量
```

#### 活动赋权流程（党小组组长发起）

```
1. 活动创建 → 党小组组长创建活动后，系统自动生成活动赋权入口
2. 成员指派 → 党小组组长在活动管理面板勾选同志 → 选择授予角色（组织者/深度参与者）
3. 标记写入 → 系统自动标记 scope='activity'，sourceId=活动ID
4. 赋权生效 → 写入赋权记录表 → 被赋权者下次加载页面时可见组织者视图
5. 通知被赋权者 → 系统推送通知
6. 活动结束 → 赋权自动过期（endDate=活动结束日期）
```

#### 赋权撤销流程

```
1. 发起撤销 → 赋权者（组织委员/党小组组长）在赋权面板点击「撤销」
2. 记录更新 → 赋权记录 endDate 设为当前时间
3. 通知被赋权者 → 系统推送通知
4. 权限回收 → 被赋权者下次操作时，若当前视图已不可用，自动回退到站位视图
5. 工作量结算 → 撤销前的工作量记录保留，不回溯删除
```

#### 赋权记录数据结构

```javascript
{
  id: string,              // 赋权记录ID
  fromPerson: string,      // 赋权者personId
  toPerson: string,        // 被赋权者personId
  role: string,            // 'organizer' | 'deep-participant'
  scope: string,           // 'activity' | 'taskforce'
  sourceId: string,        // 活动ID或专班ID
  sourceName: string,      // 活动名称或专班名称
  assignedAt: string,      // 赋权时间 ISO 8601
  endDate: string | null,  // 过期时间，null=永久有效
}
```

## E. 三委数据协作流

### E.1 月度闭环流程

```
活动结束
  → 纪检 [考勤管理] 确认考勤数据 → 录入考勤总表
  → 纪检 [考察管理] 确认考察数据 → 录入考察总表
  → 纪检 [活动监督复盘] 批注/确认/打回复盘总结
  → 纪检点击「提交考勤至宣传委员」（考勤记录）
  → 纪检点击「提交考察至支委会」（考察记录）
  → 宣传 [档案归档] 接收考勤记录→备案
  → 组织 [思想汇报] 接收考察记录→建档
```

### E.2 数据交接协议

| 方向 | 数据内容 | 触发方式 | 通知机制 |
|------|---------|---------|---------|
| 纪检→宣传 | 考勤记录 (JSON) | 纪检点击「提交考勤至宣传委员」 | 宣传面板 badge +1 |
| 纪检→组织 | 考察记录 (JSON) | 纪检点击「提交考察至支委会」 | 组织面板 badge +1 |
| 组织→纪检 | 专班名单同步 | 专班建立后自动同步 | 纪检考勤面板高亮 |
| 组织→纪检 | 补课需求回执 | 组织标记材料缺失 | 纪检补课制度高亮 |
| 宣传→纪检 | 考勤备案确认 | 宣传确认备案 | 纪检状态→"已备案" |

## F. 条块交互机制

### F.1 任务对接闭环

```
条条支委 → ①下发职能任务 → 党小组组长
                                    → ②执行任务
条条支委 ← ③上报执行结果 ← 党小组组长
条条支委 → ④确认/驳回 → 党小组组长（驳回则回②）
条条支委 → ⑤归档完成 → 党小组组长
```

### F.2 活动组织协同模式（核心）

**短期活动**（一次性：参访、线下学习等）：组织者建群招人 → 对接纪检（考勤确认→考察确认→复盘监督，纪检事后汇总考勤→宣传委员、考察→支委会）→ 对接宣传（审核宣传标准→统筹产出），按 T-7/T-5/T-0/T+3/T+7 节奏推进。

**长期活动**（持续打磨/多小组并行）：大活动群汇总全员信息，各活动小组独立运作（组织者+深度参与者）；核心群 = 各组织者+承办党小组组长+书记+调研参与者+[联络者]+[审稿者]+[考勤负责人]；纪检和宣传不在核心群内，通过党小组组长同步至支委扩大群获取信息。组织者长期深耕，深度参与者可轮换。

**组织者协调清单**：承办党小组组长（方向对齐）、纪检（考勤确认+考察确认+复盘监督）、宣传（内容同步+产出）、组内深度参与者（分工记录）。

### F.3 信息共享渠道

**信息传递两原则**（D-215）：
1. **信息传递无遗漏**（原则1）——任何信息在传递链中不得丢失
2. **最小化信息传递成本**（原则2）——用最少的传递步骤完成信息闭环
3. **原则1 > 原则2**——当两者冲突时，优先保证信息无遗漏

| 渠道 | 用途 |
|------|------|
| 支委会例会（每周/双周） | 条条+块块汇报进展、交叉议题讨论 |
| 公邮通知 | 制度性发布、党小组组长传达 |
| 系统 | 党务管理三委面板 + 活动党建工作台 |

### F.4 协同决策

- 活动策划：块块提案 → 条条审核合规 → 书记审批
- 制度制定：条条起草 → 块块反馈 → 支委会通过
- 紧急事项：条条/块块发起 → 书记直接决策 → 事后补流程

### F.5 冲突解决

| 场景 | 解决方式 | 决策者 |
|------|---------|--------|
| 条条要求与块块能力不匹配 | 协商调整或增配资源 | 书记仲裁 |
| 多条条对同一块块下达矛盾任务 | 优先级：组织>纪检>宣传 | 书记仲裁 |
| 块块对条条规范有异议 | 块块书面反馈，条条7日回应 | 支委会裁决 |
| 支委兼任党小组组长时冲突 | 主身份优先，涉及本人审核主动回避 | — |

## §审批流程规范（原 APPROVAL_FLOW.md）

> **权威源声明**：本节是审批流程的唯一权威源（原 APPROVAL_FLOW.md 全量合并），定义 Org OS 中所有审批场景的统一流程、状态机与权限矩阵。冲突时以本节为准。

### 一、活动创建审批

活动创建存在两条路径，取决于发起人的角色：

#### 1.1 自上而下（党支书 / 党小组组长发起）

党支书和党小组组长拥有活动创建权，无需审批，直接创建。

> 依据：[P-006/P-007 党建与党务工作理论](../../SECRETARY_PRONOUNCEMENTS.md)——党建工作是管理组织活动之事（三会一课、主题党日、专班），组织者有权发起活动。

#### 1.2 自下而上（组织者 / 深度参与者提议）

非党支书/党小组组长的成员提议活动，须走块块提案 → 条条审核合规 → 书记审批的流程。

**流程**：

```
提议人填写活动方案
       ↓
对应支委审核合规性
       ↓
书记最终审批
       ↓
  ┌────┴────┐
通过        驳回
  ↓          ↓
活动创建    退回提议人
通知参与人   修改后重新提交
```

**详细步骤**：提议人填写方案 → 支委按职能分工审核合规性 → 书记综合意见做出通过/驳回决定 → 通过则活动创建并通知参与人，驳回则退回修改重新提交。状态机与权限矩阵见 §六、§七。

### 二、专班创建审批

> 依据：[SECRETARY_PRONOUNCEMENTS.md](../../SECRETARY_PRONOUNCEMENTS.md) P-012+P-013（专班与赋权考察）→ 本文档 §A.6~A.7

**流程**：

```
宣传委员/党支书提出专班需求
       ↓
组织委员审核可行性
       ↓
组织委员制定招募方案
（人数/周期/考核标准）
       ↓
书记审批专班方案
       ↓
  ┌────┴────┐
通过        驳回
  ↓          ↓
组织委员     调整方案
开始招募     重新提交
赋权成员
```

**详细步骤**：宣传委员/党支书提出专班需求 → 组织委员评估可行性并制定招募方案 → 书记审批方案 → 通过则组织委员开始招募赋权成员，驳回则调整方案重新提交。状态机与权限矩阵见 §六、§七。

### 三、赋权审批

> 依据：[P-009~P-013 赋权关系链](../../SECRETARY_PRONOUNCEMENTS.md) → 本文档 §A.7

赋权分为两个类别，均无需额外审批，但赋权范围受限于赋权者自身的权限边界。

#### 3.1 专班赋权（组织委员发起）

- **审批要求**：无需额外审批，组织委员有权直接赋权
- **边界约束**：赋权范围限于已通过审批的专班（见第二节），组织委员不得在未获批专班中赋权

#### 3.2 活动赋权（党小组组长发起）

- **审批要求**：无需额外审批，党小组组长有权在自有活动内赋权
- **边界约束**：赋权范围限于党小组组长自己创建的活动，不得跨活动赋权

> **核心原则**：赋权本身不需要审批，但赋权范围受限于赋权者的权限边界。赋权者只能在自身权限范围内赋权，不能越权。

### 四、考勤确认审批

党小组组长上传考勤记录 → 纪检委员审核确认 → 确认通过则考勤生效记入统计 / 确认驳回则退回党小组组长修正重新提交。

> 状态机与权限矩阵见 §六、§七。

### 五、复盘审批

组织者提交复盘报告 → 纪检委员审核（可批注/打回/确认）→ 确认通过则复盘归档并产出记入工作量 / 打回则组织者修改重新提交。

> 状态机与权限矩阵见 §六、§七。

### 六、审批状态机

所有审批场景共享统一的状态机，确保流程一致、可追踪。

#### 6.1 状态定义

```
DRAFT → PENDING_REVIEW → APPROVED / REJECTED
                              ↓              ↓
                           生效执行        退回修改 → DRAFT
```

| 状态 | 含义 | 可执行操作 |
|------|------|-----------|
| `DRAFT` | 草稿，可编辑 | 编辑、提交审批、删除 |
| `PENDING_REVIEW` | 待审批，不可编辑 | 审批人可：通过、驳回 |
| `APPROVED` | 已通过，生效执行 | 系统自动执行后续流程 |
| `REJECTED` | 已驳回，退回修改 | 提交人可：修改后重新提交（→ DRAFT） |

#### 6.2 状态转换规则

| 当前状态 | 触发动作 | 目标状态 | 执行人 |
|---------|---------|---------|--------|
| `DRAFT` | 提交审批 | `PENDING_REVIEW` | 提交人 |
| `PENDING_REVIEW` | 审批通过 | `APPROVED` | 审批人 |
| `PENDING_REVIEW` | 审批驳回 | `REJECTED` | 审批人 |
| `REJECTED` | 修改后重新提交 | `DRAFT` → `PENDING_REVIEW` | 提交人 |

#### 6.3 多级审批扩展

部分场景（如活动创建自下而上路径、专班创建）涉及多级审批。多级审批在状态机上的体现为 `PENDING_REVIEW` 状态内部的多步流转：

```
PENDING_REVIEW
  ├─ Level 1: 支委审核
  ├─ Level 2: 书记审批
  └─ 任一级驳回 → REJECTED
```

任一级审批人驳回即进入 `REJECTED` 状态，全部通过才进入 `APPROVED` 状态。

### 七、审批权限矩阵

| 审批场景 | 提交人 | 审批人 | 驳回权限 |
|---------|--------|--------|---------|
| 活动创建（自上而下） | 党支书 / 党小组组长 | 无需审批 | — |
| 活动创建（自下而上） | 组织者 / 深度参与者 | 支委 → 书记 | 审批人可驳回 |
| 专班创建 | 宣传委员 / 党支书 | 组织委员 → 书记 | 审批人可驳回 |
| 专班赋权 | 组织委员 | 无需额外审批 | — |
| 活动赋权 | 党小组组长 | 无需额外审批 | — |
| 考勤确认 | 党小组组长 | 纪检委员 | 纪检委员可驳回 |
| 复盘确认 | 组织者 | 纪检委员 | 纪检委员可驳回 |

### 八、通知机制

审批流程中的关键节点均触发通知，确保相关人员及时获知状态变更。

| 触发时机 | 通知对象 | 通知内容 |
|---------|---------|---------|
| 提交审批时 | 审批人 | 有新的审批待处理，包含提交人、事项摘要 |
| 审批通过时 | 提交人 | 审批已通过，可执行后续操作 |
| 审批驳回时 | 提交人 | 审批已驳回，含驳回理由，可修改后重新提交 |
| 生效执行时 | 相关参与人 | 事项已生效，包含具体执行信息 |

**通知渠道**：站内信优先，辅以邮件通知。通知记录写入系统日志，可追溯。
