## 一、设计哲学

### 核心原则

> 原则按场景灵活选用，不锁定数量。下表为基础参考集，可按页面特性增补（如探索页可加"叙事性"、表单页可加"反馈清晰"）。

1. **清洁优先（Clean First）**：能用纯色解决的，不用渐变；能用扁平解决的，不用阴影；能用留白解决的，不用分割线
2. **最小三成本（Min Cost First）**：任务流默认直接展示在工作台，不要求用户额外操作才能看到"我需要做什么"。包含三个维度：①**信息成本**——用户获取"我需要做什么"所需的信息搜寻成本，任务流默认直接展示；②**操作成本**——从"进入工作台"到"看到可执行事项"的点击/操作次数，进入即见，系统主动推送；③**适应学习成本**——新用户理解工作分工、工作任务、信息流运作方式的学习成本，通过系统设计本身自解释。适用于全系统所有角色工作台。
   - **知情权优先（裁定 2026-08-08）**：无职责不代表没有知情权。支委/角色即便业务上不负责活动/专班的操作（如纪检无专班职责、组织无活动 tab），仍有权查看其详情。凡首页跳转携带 `activityId`/`taskforceId`/`view=activities` 参数，各角色工作台均须有对应「查看」承载（激活相关 tab 或复用活动/专班查看组件），不得因"无职责"而丢弃参数、让用户信息成本升高。
3. **哑光质感（Matte Aesthetic）**：背景采用低饱和中性色，拒绝高光/镜面反射/玻璃拟态
4. **色彩克制（Color Restraint）**：每个页面主色 ≤ 2 种，功能色仅用于状态指示
5. **动效适度（Motion Modesty）**：过渡动画 150-250ms，仅使用 opacity/transform（GPU 加速）
6. **渐进增强（Progressive Enhancement）**：基础体验不依赖 backdrop-filter（低端设备友好）
7. **同一套数据（One Source, Multi Entry）**：能够顺路产生的数据，尽可能不要单独填写，但可以保留多个入口——只要做到读取、写入、写出的数据是同一套数据。例如活动数据必然携带诸多副产物字段，赋权这类副产物应整合进活动数据流，而非另起一套与活动数据割裂的记录。可验证条件：`has_parent(entity, byproduct)` 且 `parent_record[byproduct] == 所有入口读取值` 视为通过；存在独立表/独立数组承载同类副产物数据 → 违反。（2026-08-02 确立）
8. **降低填写负担（Low Friction Filling）**：降低每一个功能的填写负担，让填写者愿意填写、有正向反馈（确实完成了某项工作，且启动不那么困难）。三个可验证条件：① `field_derivable(field)` → 必须自动填充/预填，不得要求手填；② `action_completed` → 必须有正向反馈（toast / 状态流转 / 记录可见）；③ 从待办/列表到可操作状态 ≤ 2 跳，启动直达。（2026-08-02 确立，呼应原则 2 最小三成本）
9. **信息密度精确原则（Precision of Information Density）（2026-08-10 确立，战略级）**："执行委托与知情监督是对应的，统一的。统筹是最大的管理！"——赋权链（执行委托的操作边界）与按人视图（知情监督的信息边界）对应统一，是同一枚硬币的两面；"一个尽可能降低管理摩擦的方向是任何角色的信息可见范围，应精确等于其职责空间所需的最小充分信息"——**信息可见性是职责空间的投影**。信息密度分层：**L0 个人视角**（自己）/ **L1 条线视角**（上级看下级的条线在办：谁在干什么、有无异常）/ **L2 全局视角**（书记看全部条线+块块）。向上越层需职责依据（赋权链），向下缩层是对他人职责空间的保护。**看与做相区分**：做与看是分工运行保障的一环（[P-012 分工的运行保障](../../01_strategy/SECRETARY_PRONOUNCEMENTS.md#p-012-分工的运行保障执行委托与知情监督的统一)）——监督停留在"方向把握"（P-027②），不沉入"细节干预"；内控失效的常见入口是"知情过载"（看到他人操作细节→越过职责边界干预/代劳）。可验证条件：某角色可见信息超出其职责空间所需（可见他人操作细节但无监督关系）→ 违反；按人视图按赋权链投影、不含操作细节 → 通过。设计落点：书记工作台全局概况"按维度/按人"双视图（按人视图=各角色在办任务清单，异常高亮可直达）。
10. **高频零跳转（High-Frequency Zero-Jump）（2026-08-10 确立）**：最小三成本的最终验收标准落在「**完成一个高频工作，需要操作多少次？信息的展示是否和操作在同一个地方，便于参考？**」。①**答复类置顶待办**：汇报答复是书记最高频动作，待办 tab 顶部内建「待答复」收件箱（问题优先排序、行内填写即发、零跳转），而非藏在全局概况→按人→汇报区多层之下；②**答复回路全角色化**：信息流畅是双向的——其他角色同样有答复机制（组长可答复本组组员，书记仍全局可见，P-012 做与看不破坏）；③**工作概况三区总览**：全部角色新增「工作概况」tab，汇报（待我行动，信息展示与操作同屏）/卡点（我的超期+条线缺口）/在办（我的聚合+条线态势）三区上下排布、问题优先，让"看到"与"操作"在同一可视区域。可验证条件：① 完成任一高频工作的点击/跳转次数 > 2 → 违反（呼应原则 2 操作成本）；② 某数据与其操作入口不在同一可视区域（需滚动/跳转才能从看到变为操作）→ 违反；③ 某角色存在单向汇报却无答复回路 → 违反；④ 待办列表顶部存在比"答复类"更高频的动作类型 → 违反。孤零零数据行（不属于任何卡片的裸 `div` 字段，数值与结论与卡片冗余）属信息成本冗余，须整合进卡片或直接删除。
11. **工作进度指标设计（Progress Indicator Design）（2026-08-10 确立，战略级）**：工作进度的指标设计与显示必须谨慎——**"已完成 N"是无信息量的存量统计**，只可作为归档统计信息存在于归档库；面向"要完成的工作"，进度指标必须指向"进行时与未完成"（待办/待完成/超期/缺口/进行中），并提供信息增量与操作入口。①**只显未完成类**：工作界面（工作台 tab、概况、详情）不得出现"已完成 N/总数"式无差异存量统计；"已完成"仅在归档库/归档统计中出现；②**可下钻**：进度数字/聚合须可点击进入具体任务清单或详情（信息展示与操作同地，呼应原则 10）；③**从"看"到"做"**：概况"在办"区列出具体可点击条目（待办→定位工作台待办 tab 对应任务；活动/专班→下钻只读详情视图），杜绝"只有数字没有入口"。可验证条件：① 工作界面出现"已完成 N/总数"类存量统计（归档库除外）→ 违反；② 进度数字聚合不可点击、无下钻入口 → 违反；③ 概况在办区仅显示聚合数字、无具体条目 → 违反。
12. **工作台集成制（Workspace Integration）（2026-08-10 确立）**：角色单页制后，**视图切换（header 工作台切换 / sidebar 切换）已失去作用——每个人就是每个人**；组织者与深度参与者的所有信息均集成在工作台中，任务来了就都在工作台内完成，不再依赖任何"切换到某角色视角"的入口。可验证条件：出现需"切换到某角色/视角"才能完成的操作路径 → 违反；信息展示或操作入口越出工作台边界（依赖别的页面）→ 违反。
13. **文件流外发确认闭环（External Dispatch Confirmation）（2026-08-10 确立，战略级）**：任务流/信息流均可通过系统实现，**唯一缺口是"文件流"——文件本体暂靠微信传输**。当任务/材料需微信外发给对方确认时，系统不得静默——发送方须在系统中标记「已通过微信发送给 XX」（外发确认），接收方在系统内「确认收到」，形成可审计闭环（谁 / 何时 / 发给谁 / 何时确认）。**"总是有内控设计的方法的！！"**——内控设计的必然要求就是：外部依赖（微信）发生时，系统内必须有状态记录兜底。面向书记目标（低成本小程序/服务号与微信原生协同），记录模型保持简单可迁移——"标记已发送"演进为"发送到对方微信"，"确认收到"保持同构。可验证条件：① 存在需微信外发文件的工作环节但系统无外发标记/确认入口 → 违反；② 外发记录缺发送方/接收方/时间任一要素 → 违反；③ 接收方确认后记录未闭环（审计时间线不完整）→ 违反。设计落点：宣传材料上传后「文件外发确认」模态（标记已微信外发+选择接收方）；接收方工作台卡点区/异常队列「文件待确认 → 确认收到」。
14. **KPI 行为异化防御（KPI Behavioral Integrity）（2026-08-10 确立，战略级）**：**指标设定必须考虑行为激励——"完成率 100%"类指标会诱导凑数提交，目标即异化**（例：复盘率设 100% → 大家随意提交凑数，违背"从最初设定上我们就只是希望大家提交真问题"的初衷）。面向"要完成的工作"，指标应指向工作的真实意图而非形式完成：复盘要的是"真问题"（问题导向）而非"完成率"；承诺要的是"兑现质量"而非"次数"。可验证条件：① 某指标为百分比/计数类"完成率"且目标设为 100%（或接近）→ 须审查是否诱导凑数；② 指标计量对象与工作真实意图（产出真问题/真成果）不一致 → 违反；③ 指标被形式达成但对工作无信息增量 → 违反。设计落点：复盘 KPI 由「复盘完成率 目标100%」改为「复盘问题 真问题导向」（计量活跃活动复盘中提出的真问题数量，复盘表单内建"提出的真问题"填写）。

### 减负空间排查（分批规划，2026-08-10 发起）

**目标**：系统性排查并精简工作流冗余环节与信息冗余，持续降低最小三成本（原则 2）。

- **第一批（T-208 已完成）**：① 复盘 KPI 异化修复（完成率 100% → 真问题导向，原则 14）；② 文件流外发确认闭环落地（宣传材料上传 → 接收方工作台确认，原则 13）；③ 金色主题"再黄一点"统一（#B45309 → 金黄 #A16207，覆盖 tab 字 / role-label / 按钮）；④ header「切换工作台」冗余清理（原则 12，跨台经待办/通知直达）。
- **第二批（待执行）**：① 各 SOP 工作流环节精简排查（流程是否存在多余审批/确认环节）；② 工作台 tab 精简排查（是否存在低使用频率 tab / 可合并视图）。

## 三、排版系统

### 3.1 字体家族

| 用途 | CSS Font Family | 中文字体 | 英文/数字 | Class |
|------|----------------|---------|----------|-------|
| 正文/UI | `'Noto Sans SC', -apple-system, 'PingFang SC', 'Microsoft YaHei', sans-serif` | 思源黑体 | 系统无衬线 | `.font-sans-primary` |
| 标题/强调/标签/按钮 | `'STZhongsong', '华文中宋', 'Noto Serif SC', 'STSong', 'SimSun', serif` | 华文中宋 → 思源宋体 → 宋体 | Times New Roman | `.font-title-cn` |
| 英文标题 | `'Times New Roman', 'Georgia', serif` | — | Times New Roman | `.font-title-en` |

**字体使用规则**：

| 元素类型 | 字体 | 说明 |
|---------|------|------|
| 页面主标题（h1） | `.font-title-cn` | 华文中宋，weight 800 |
| 区块标题（h2/h3） | `.font-title-cn` | 华文中宋，weight 700-800 |
| 表单标签（label） | 衬线字体（CSS规则） | 工作台内所有 label 自动应用 |
| 按钮（.btn-primary） | 衬线字体 | 写入活动等关键操作按钮 |
| 侧边栏标签 | 衬线字体 | module-tab span 自动应用 |
| 正文/辅助文字 | `.font-sans-primary` | 思源黑体，保持可读性 |
| 输入框内文字 | 系统默认 | 跟随 body 字体 |

**禁止使用黑体（Microsoft YaHei/Heiti SC）作为标题字体**。标题必须使用衬线字体（华文中宋/宋体系列）。

### 3.3 排版规则

#### 3.3.1 标题语义层级规则（2026-08-07 裁决「语义+样式全统一」）

**规则核心：标题语义必须用语义化标签（h2/h3/h4/h5/h6），禁止用 `<span>` 冒充标题。** 选择层级看「容器语义」而非字号——卡片面板标题就是 h3，卡片内分组就是 h4，与字号无关。

| 容器语义 | 标签 | 标准样式 | 示例 |
|---------|------|---------|------|
| 页面主标题（header） | `h2` | `font-title-cn text-xl font-bold text-gray-800` | 各工作台头部「XXX工作台」 |
| 区块标题（首页区块） | `h2` | `font-title-cn text-2xl font-bold text-gray-800` | index.html「光华…管理引擎」 |
| 卡片面板标题 | `h3` | `font-title-cn text-base font-semibold text-gray-800` | 工作台「我的待办」「考勤总表」「活动查询」 |
| 弹窗/浮层面板标题 | `h3` | `font-title-cn text-sm font-semibold text-gray-800` | modal/归档弹窗/通知详情标题 |
| 卡片内分组标题 | `h4` | `font-title-cn text-sm font-bold text-gray-700` | 「当前党小组组长」「材料标准」「报送历史」、月份分组 |
| 卡片内更小分组（活动角色/子记录） | `h5`/`h6` | `text-xs font-bold text-gray-600` | 活动角色分组、子记录分组 |

**判例（2026-08-07 全系统检查后落地）**：
- `<span>` 承担标题语义（如「活动查询」「我的本月考勤」）→ 一律改 `h3`
- 卡片面板标题用 `h4`（历史遗留，如「我的待办」「专班名单」）→ 升为 `h3`
- 月份分组标签（含月标签+场数）→ `h4`（卡片内分组级）
- 子记录分组标签（如「积极分子 (n)」带添加按钮）→ `h5`
- 例外：位于 `<button>` 折叠组头内的文字（如待办折叠组头）保持 `span`——按钮内不允许嵌入标题标签
- 例外：行内强调文本（badge、计数、状态点）用 `span`，不承担标题语义

```css
/* 中文正文 */
.text-body, .text-body-sm, .text-body-lg {
  letter-spacing: normal;
}

/* 英文短文本/标题 */
.font-title-en, .text-overline {
  letter-spacing: 0.02em;
}

/* 段落间距 */
p + p { margin-top: 0.75em; }

/* 列表间距 */
li + li { margin-top: 0.25em; }
```

## 五、交互反馈规范

### 5.1 过渡动效标准

| 场景 | CSS 属性 | 时长 | 缓动函数 |
|------|---------|------|---------|
| 颜色变化 | `background-color`, `color`, `border-color` | `150ms` | `ease-out` |
| 透明度变化 | `opacity` | `200ms` | `ease-out` |
| 位移 | `transform` | `200ms` | `ease-out` |
| 视图切换 | `opacity` + `transform` | `250ms` | `ease-out` |

### 5.2 反馈模式速查

| 交互类型 | 视觉反馈 | 代码实现 |
|---------|---------|---------|
| 按钮悬停 | 背景色偏移至下一色阶 | `:hover { background-color: next-shade }` |
| 卡片悬停 | 边框色变为主色浅调 | `:hover { border-color: --primary-300 }` |
| 输入框聚焦 | 边框变为主色，无外发光 | `:focus { border-color: --primary-500 }` |
| 列表项悬停 | 背景变为浅灰 | `:hover { background-color: --surface-hover }` |
| 选中态 | 浅红背景 + 红边框 | `.active { bg: --surface-active; border: --primary-300 }` |
| 加载态 | 骨架屏（灰色占位块） | 脉冲透明度动画 |
| 空状态 | SVG 图标 + 中性色提示文字 | SVG + `--neutral-400` 文字 |

### 5.3 禁止的动效效果

| 禁止项 | 原因 |
|--------|------|
| `backdrop-filter: blur()` | 玻璃态效果，低端设备性能差 |
| `cubic-bezier()` overshoot | 弹性过渡，与哑光风格冲突 |
| `box-shadow` 发光扩散 | 扁平化不需要 |
| `transform: scale()` | 缩放反馈过于花哨 |
| `transform: translateY(-Npx)` | 上浮效果违反扁平原则 |
| `linear-gradient()`（按钮/卡片） | 纯色优于渐变 |

### 5.5 workflow 关系图动画原则（2026-08-13 设计 · 2026-08-30 沉淀）

> 来源：`.trae/specs/2026-08-13-workflow-animation-redesign-design.md`（未落地设计，2026-08-30 过程文件清理时将其可复用原则沉淀于此）。
> 适用于任何「角色/实体关系流」可视化（如工作流关系图）：

1. **扁平化**——无分层无中心包围，连线（交流）是主角而非节点
2. **动/静分离**——视窗静、本镜节点进出、连线出现、多线程并行同时亮
3. **分镜式进出**——节点移入/移出视野，每镜有停留稳态（不连续运镜）
4. **flow 级分镜**——每个 flow（谁→谁做什么）一镜，对齐 SOP 操作级

### 5.6 动效分层与动画语义（承接原 insights §4.5 动效/动画段 + §4.7 动效分层段，2026-09-04 分流）

> **承接说明**：2026-09-04 自 content/insights/工程演进与设计方法论.md 分流——§4.5 的动效/动画段 + §4.7 末尾「动效分层」段归入本规范（方法论文体与规范文体分离，论证与判例档案见 [DESIGN_METHODOLOGY.md](../evolution/DESIGN_METHODOLOGY.md)）。出处注记：（原 insights §4.5 动效/动画段 / §4.7 动效分层段）。
> **去重核对（2026-09-04）**：与 §5.4（Exploration 区块滚动驱动场景切换）、§5.5（workflow 关系图动画原则）同题相邻但**互补不重复**——§5.4/§5.5 规定"场景切换 / 关系图"的动画形态大原则；本节规定"文字 vs SVG 边"的时序语义、SVG 多类型边的动画区分、以及声明式动画优先的工程选型，三者并存。

**动效分层：文字先于 SVG 边**（原 insights §4.7 末尾段）：文字用 CSS transition（快速切换，~200ms），SVG 边用滚动驱动（渐进绘制）——内容优先于装饰。文字是"讲什么"，应先出现；SVG 边是"怎么画"，应慢慢绘制。共用同一进度变量会导致文字显示太慢，违背"内容优先"。为什么文字要先于 SVG 边？因为文字承载内容语义，SVG 边承载装饰语义——读者打开页面的第一需求是"读什么"，不是"看什么画"；若两者同时出现，SVG 边的绘制过程会分散读者对文字的注意力；文字先出现，读者可以立即开始阅读，SVG 边在阅读过程中渐进绘制完成。生效条件：包含文字+SVG 动效配合的页面，且文字和 SVG 边有主次关系的场景。

**探索工作动画区分对待原则**（原 insights §4.5）：探索工作 SVG 网络图包含三类边——task（派活交付，有方向）/ info（报备告知，有方向）/ collab（横向配合，无方向）。动画形式应服务于边的语义区分：task 边用 `stroke-dashoffset` 绘制动画（从起点画到终点，强化"派活交付"的方向感），info/collab 边用 `opacity` 渐显（保留 CSS 的虚线/点线样式，不设置 JS `strokeDasharray`）。统一绘制会覆盖 CSS 中 info 虚线和 collab 点线的样式，导致三类边视觉同质化——全部变成实线，无法区分类型。动画形式服务于语义区分，而非语义服从于动画统一。生效条件：在包含多类型边（有方向/无方向混合）且需视觉区分的 SVG 网络图中成立。

**规避 JS 动画库——静态叙事页的最优解**（原 insights §4.5）：静态滚动叙事页的动画应优先 CSS `animation-timeline: view()`（滚动驱动、引擎级优化、初始可见无闪变）+ 原生 scroll 监听；JS 动画库（GSAP）带来的 ScrollTrigger.refresh 全量重算（640ms 级长任务）与"先隐藏后显示"闪变是复杂度与卡顿根源（T-249 判例：规避后性能提升约 20 倍，458ms→22.4ms）。"能事先算好的动画不如事先准备好"——CSS 声明式动画由浏览器引擎处理，静态页面应零 JS 动画依赖。动画节奏应统一（约 1s 沉稳），局部特例（出场类 0.9s）不破坏整体。生效条件：静态/半静态叙事页、动画可声明式表达的场景成立；复杂交互动效（拖拽/物理模拟）仍需 JS。

## 七、深色模式设计规范

> **确立背景（2026-08-09 指令）**："每一个色块的设计，请都要考虑【深色模式】。只要是主题色，每一个颜色都必须平行——如果一个在深色模式下是淡色的底深色的字，别的也应该是淡色的底深色的字（总之是一致的，且易用的）。对于功能色，因为不随主题色变化而变化，也要记得去做好深色模式下可见度、可分辨率的评估。"
> **实现机制**：[theme.js](../../../docs/src/core/theme.js) — `<html class="theme-dark">` 前缀驱动三态（浅色/深色/跟随系统，默认跟随系统）；CSS 侧深色规则统一 `html.theme-dark` 前缀（T231 决策，2026-08-07 替代 @media prefers-color-scheme）。
> **分层覆盖**（T-207 D3 沉淀）：CSS 变量反向 + 高频 Tailwind 类 `!important` 提权 + 硬编码组件逐一覆盖；`--party-red` 系不变 / `--surface-header` 深红保持 / 角色识别色不变。

### 7.1 色块平行性总则（主题色）

> **色值权威源见 [COLOR_SYSTEM.md](COLOR_SYSTEM.md) §2.3**；本节只记深色模式下的使用约定，不重复定义色值。

**总则**：深色模式下，所有主题色色块必须使用**同一套明暗关系**——统一「深底浅字」或统一「淡底深字」，禁止出现"这个色块淡底深字、那个色块深底浅字"的单独反转。

| # | 主题色族 | 深色模式约定 |
|---|---------|-------------|
| 1 | 党建红系（`--party-red-*`） | 不变，保持 `#CE1126` 语义；深色下文字/背景对比度达标，红色不刺眼、不糊 |
| 2 | 角色识别色（书记/副书记/组长/三支委/组织者/参与者） | 不变，深色下可区分、不撞色 |
| 3 | 党徽金（`--party-gold`） | 不反白、不荧光，保持庄重；金底文字一律金黄 `#A16207`（延续 COLOR_SYSTEM.md 金点描边约定） |
| 4 | 主题色 X（各角色 `getAccentColors(role)`） | 三件套（浅底/边框/文字）整体随主题反转，明暗关系与全站一致 |

### 7.2 功能色可见度与可分辨率（不随主题色变化的色）

功能色不随主题变化，深色模式下单独评估可见度与可分辨率：

| # | 功能色 | 深色模式约定 |
|---|--------|-------------|
| 1 | 状态色（成功 `#16A34A` / 警告 `#D97706` / 错误 `#EF4444` / 信息 `#3B82F6`） | 可见度达标，不以亮度过低或过高丢失信息 |
| 2 | 状态点 / 徽章底色 | 与卡片底色可分辨，不融为一体 |
| 3 | 中性文字（正文/辅助文字/占位符） | 在深色卡片上均可读 |
| 4 | 边框 / 分隔线 | 深色下依然可见，不因底色变深而消失 |
| 5 | hover / 选中态 | 反馈明显，不因全局变暗而失效 |

### 7.3 人工自查清单（深色模式验收）

> 深色模式属于"机器因截图原因难以客观判定、需人工实测"的检查项。以下按「人在哪里 → 做什么 → 应该看到什么」逐条核验（2026-08-09 指定人工检查）。

| # | 人在哪里 | 做什么 | 应该看到什么 |
|---|---------|--------|-------------|
| 1 | 任意页面·侧边栏「主题选择」 | 依次切换「浅色」「深色」「跟随系统」 | 三态即时生效、无闪烁；默认跟随系统；刷新后偏好保持 |
| 2 | 登录页·开发模式卡片 | 深色下查看 7 个角色卡片色点 | 各角色识别色在深色底上可区分、不撞色 |
| 3 | 首页 | 深色下查看顶部导航、主题党日胶囊、强调卡边框、待办行动按钮 | 党建红系与党徽金保持语义；金不反白、不荧光 |
| 4 | 书记工作台 | 深色下逐 tab 查看 tab 激活态、主按钮、党务标签、日历条目 | 主题色三件套与全站同一明暗关系；党建红不糊 |
| 5 | 组织/宣传/纪检/组长工作台 | 深色下逐 tab 查看各自主题色渲染 | 各角色主题色色块明暗关系一致，无一处单独反转 |
| 6 | 任一工作台·状态徽章 | 深色下查看完成绿/待处理琥珀/告警红/进行中蓝徽章 | 徽章底色与卡片底可分辨，文字可读 |
| 7 | 任一工作台·列表/卡片 | 深色下查看正文、辅助文字、占位符、边框、分隔线 | 文字对比度达标，边框分隔线可见 |
| 8 | 任一工作台·交互 | 深色下 hover 卡片/按钮、点击选中项 | 反馈明显，不因全局变暗失效 |
| 9 | 帮助页（about.html / help.html） | 深色下浏览 | 独立变量体系正常，无亮斑、无死黑 |
