## 一、六条判例（逐条事实与结论）

### 判例① 活动日历：点日期是否直接跳活动页？右栏是否永远看不到/无作用？

**事实：不跳活动页；右栏不是看不到，而是只做「当日清单」这一件事，且与左栏、下方查询重复。**

点击链路（支书台 `#inspector-container`）：

1. 月视图渲染每个日期格：`calendar.js:285` 输出 `data-date` + `role="gridcell"`；只有「当日有活动或有任务」的格子在 `calendar.js:282` 追加 `has-tasks`。
2. 鼠标点击绑定只挑 `.cal-cell-large.has-tasks`：`calendar.js:613-621`。
3. 点中后执行 `setState({ selectedDate, viewMode: 'list', selectedActivityId: null })`（`calendar.js:619`）。
4. 支书台收到 state 后重渲染：`calendar-tab.js:246-247` → `renderInspectorFromState(filteredState)`。
5. 右栏进入 `renderInspectorList`（`inspector.js:191-279`），标题写成「X月X日 · 活动列表」（`inspector.js:227`），卡片文案是「点击查看任务详情 →」（`inspector.js:255`）。
6. 只有点格内的活动条目（不是日期空白）才进详情：`calendar.js:637-653` → `renderInspectorDetail`（`inspector.js:609+`）；支书另有一条「活动详情页 ›」外链（`inspector.js:668-670`）。
7. 支书台渲染后又补了「查看活动详情 →」深链：`calendar-tab.js:1739-1761`。

**判断：**

- 「点击日期 → 直接跳活动页」**不成立**。日期点击只在右栏出当日活动卡列表；活动条目点击才在右栏出详情；完整页还要再点一次外链。
- 「右侧检视区永远看不到/无作用」**也不成立**，但它的信息增量确实很低：左格已经显示最多 3 条活动标签（`calendar.js:557-563`），下方「活动查询」还能按类型/品牌筛选（`calendar-tab.js:301-323`），右栏只是把同一批活动按日再列一遍，**没有一个就地动作**（不能在此考勤、上传材料、关闭活动）。
- 另一个真实缺陷：**没有活动/任务的日期格鼠标点不动**（只绑 `has-tasks`），但这些格子仍有 `tabindex="0" role="gridcell"`，键盘 Enter 却能触发并显示「当日暂无活动」（`calendar.js:596-608`）。鼠标与键盘行为不一致，且空态提示「点击日期查看活动详情」（`calendar-tab.js:188`）与实际「出列表」不符。
- 2026-10-04 支书明确要求「所有的日历台 都得是 日历在左侧，详情在右侧！！不能有全屏的日历！」（`shared/activity-calendar-tab.js:17-20`）。因此**「删除右栏」与现行裁定相抵**，本轮不建议删。

**建议（判据：改）：** 右栏改为「当日清单 + 就地操作」，让每次点击都有产出：

```
右栏 = 日期头（10月20日 · 2 场）
     + 每场一行：标题 / 生命周期徽章 / 组织者
     + 行内动作（按角色显隐）：考勤 · 材料 · 关闭 · 打开详情页
     + 空日：「当日无活动」+「在此日写入活动」（预填日期）
```

**结论：点击日期不跳活动页，右栏并非永远不可见，但只是「只读回声」，与左格标签和活动查询三重重复；应改为当日清单+就地操作，不建议删除（与 2026-10-04 裁定冲突）。**

### 判例② 浮窗表单：全站盘点与共性问题

全量清单见第三节。此处只给结论与最重的五类问题。

**1. 标题里的 HTML 被二次转义（确定性缺陷）**

`person-edit-modal.js:284` 把「查看完整档案 →」的 `<a>` 拼进 `title`，而 `modal.js:112` 统一执行 `escHtml(title)`，`modal.js:135` 直接插入。结果是标题栏逐字显示：

```
成员档案 · 罗文杰 <a href="person.html?id=p1" class="...">查看完整档案 →</a>
```

链接不可点、样式失效。全站只有这一处（`grep title: \`...<` 唯一命中）。**判据：改；P1。**

**2. 取消写入会留下「待提交赋权名单」**

`calendar-tab.js:1228-1232` 的 `wp-cancel` 只 `closeModal`，不调用 `wp.reset()`；`DecisionTreeState.reset()` 本身也只清 `selections/step/showPanel/submitting`，不清 `pendingAuth`（`decision-tree.js:160-165`）。`pendingAuth` 只在写入成功（`calendar-tab.js:1511-1523`）或被逐个删除 chip 时清空。后果：支书填了「项目赋权」名单后取消，下次打开写入同一批人仍挂在 chips 上，提交新活动时会被**静默授权到新活动**。**判据：改；P1。**

**3. 长表单的提交按钮在滚动区里**

`modal.js:123,138`：面板 `max-height:85vh`，`.modal-body` 是唯一滚动容器；而「写入活动」的取消/创建按钮写在表单文末（`calendar-tab.js:852-857`），「发布招募」的取消/发布也写在文末（`taskforce-tab.js:1534-1537`）。写到第 10 个字段时按钮已滚出视口，用户必须先把整页滚到底；页脚的 `settingsLink` 反而是固定的（`modal.js:141`），形成「说明常驻、动作消失」的反比。**判据：改；P1。**

**4. 移动端高度与两列**

- `modal.js:123` 用 `85vh`（非 `dvh`），软键盘弹起后浮窗底部会被遮住；无 `env(safe-area-inset-bottom)`。
- `inspector.js:1381`（编辑活动）、`taskforce-tab.js:1478,1494`（招募）、`calendar-tab.js:694`（写入活动日期/时间）都在无断点时用 `grid-cols-2`。390px 屏上每列约 150px，`<input type="date">` 会挤压/溢出。

**5. 关闭后状态**

- 招募浮窗的 PersonPicker 只在「取消」按钮路径销毁（`taskforce-tab.js:1581-1587`）；Esc / 遮罩 / × 关闭不销毁，靠下次 `openRecruitForm()` 开头兜底（`taskforce-tab.js:1447`）。组件不泄漏到用户可见层，但属于「关闭路径不完整」。
- 成员档案浮窗关闭后有双重焦点归还（`modal.js:212` + `person-edit-modal.js:296-307`），功能上无害，但属于重复实现。

**结论：浮窗的问题不在「字段多少」，而在「状态、按钮位置、移动端」三处；其中标题转义与取消后残留赋权名单是确定性缺陷，必须先修。**

### 判例③ 思想汇报：个人档案是否已集成？组织台这一页是否重复？

**事实对照：**

| 维度 | 个人档案 `person-entry.js` | 组织台 `thought-review-tab.js` |
|---|---|---|
| 数据对象 | 组织事实 / 在册留痕 / 本人自述（15 个问卷字段） | 思想汇报记录（人 × 期次） |
| 思想汇报内容 | **没有**。全文只在 24-25 行引入 `person-profile-sections`（本人自述），无 `thought-report` 引用 | 台账矩阵：行=在册成员、列=期次，格子=状态色块（`thought-review-tab.js:159-184`） |
| 可做的动作 | 编辑组织事实 / 变更阶段 / 变更在册 / 编辑自述 | 只能点色块跳到 `thought-report.html`；页内无阅读、无打回（`thought-review-tab.js:9-10`） |
| 角色 | 本人 / 组织委员 / 党委只读 | 仅 `org-commissioner`（`thought-review-tab.js:102-108`） |

**制度依据（明确要求归集到个人档案）：**

- `content/03_doc_system/ARCHITECTURE.md:525`：「提交即入库即归档：**按 personId 算法自动归集至个人档案**，无人工归档环节」。
- `content/04_web_design/data/DATA_MODEL.md:429`：「思想汇报｜党员本人｜组织委员归档｜**个人档案**（不经纪检/宣传）」。
- `content/insights/党支部管理与实务经验沉淀.md:260`：「思想汇报由党员在系统内提交、算法自动归档**归集至个人档案**，组织委员考察时调用」。
- `content/02_institution/sop/常见工作场景快速指南.md:339`：组织委员第 3 步「**查看**系统自动归集的思想汇报」。

**判断：**

1. **个人档案没有集成**——制度三处都写「归集至个人档案」，但 `person-entry.js:224-320` 只有结论带 / 组织事实 / 在册与留痕 / 本人自述 / 系统说明，没有思想汇报段，也没有一条指向 `thought-report.html?personId=` 的入口。

3. 但**这一页的呈现方式过空**：整页只有标题、2 个视图钮、图例、3 个筛选钮和一片 10px 色块；「留痕台账 · 不提供删除（打回 / 重交走状态）」是一句解释「为什么没有删除」的此地无银（`thought-review-tab.js:152`）；图例里的「状态＝该期次汇总（就高不就低）」（`:66`）与表头 `headTitle`（`:170`）逐字重复。
4. 无权限提示直接输出原始角色键：「当前角色：secretary」（`:105`），支书误入时会看到英文代码。

**建议（判据：改 + 立项）：**

- 个人档案补一段「思想汇报」：最近 3 篇（期次 + 状态 + 链接）+「全部 N 篇 →」；这是制度承诺的落地，不是新功能。
- 组织台收窄为「例外清单」：默认只显示**未交 / 待补充**，全量矩阵降为「查看全部」；导出保留。
- 删 `:152` 整行、`:105` 改中文角色名、`:66` 与 `:170` 只留一处。

**结论：个人档案未集成（制度承诺未落地），组织台这一页不重复、不能删；但应补个人档案段、把组织台从「全量色块矩阵」收窄为「未交/待补充例外清单」。**

### 判例④ 专班管理：页签「专班管理」里却有「活动工作组」，名实不符还是合理？

**事实：名实不符，且「活动工作组」与组织台「活动日历」重复。**

- 页签注册名＝「专班管理」（`org-workspace.js:76`），`id` 为 `taskforce`。
- 页内第一行是 3 个并列视图钮：`专班工作组` / `活动工作组` / `报名总表`（`taskforce-tab.js:91-93`），三者是平级的 `aria-pressed` 组。
- 「活动工作组」渲染的是**全部活动**的查询列表（`taskforce-tab.js:1695-1761`）：类型/状态筛选、组织者、深度参与人数、「材料闭环」链接、「确认完成」按钮。它与组织台自己的「活动日历」页签（`org-workspace.js:65`，共享只读日历）回答的是同一个问题「支部有哪些活动、进展如何」。
- 「报名总表」只统计 `sourceType === 'taskforce'` 的报名（`taskforce-tab.js:219`），是专班域，名实相符。
- 另有一处**数据语义缺陷**：活动工作组的「确认完成」只执行 `updateActivity(status:'completed')`，然后 toast「活动已完成并归档」（`taskforce-tab.js:1770-1774`）；没有调用 `archiveActivity`，也没有跑 `checkActivityCloseConditions`。它既没有真正归档，又绕过了支书台归档前的材料/考勤闸门。

**制度约束：** `.ctx/ACTIVE_RULINGS.md:21`（`D-442`）明确「**tab 名＝「专班管理」**」。因此**不能擅自改名**，否则与现行裁定相抵。

**建议（判据：拆）：**

- 首选：保留页签名「专班管理」，把「活动工作组」整块移出——组织台已有「活动日历」，活动进展/材料入口应回该页或回活动详情；本页只留 `专班工作组` + `报名总表`（报名总表作为专班视图内的一个转置开关，不再与两个「工作组」平级）。

- 无论哪条，**「确认完成」必须与支书台归档同源**：要么改文案为「标记完成」，要么调用同一归档服务并显示缺失项。

**受影响链接 / 断言（若改名或搬移，需同批改准）：**

| 类型 | 位置 |
|---|---|
| 页签注册 | `docs/src/capabilities/org-workspace.js:76` |

### 判例⑤ 我的处置：视觉混乱的具体来源与重排方案

先澄清事实：**概况页已经没有独立的「汇报」卡**。`work-overview.js:4-9` 与 `org/overview-tab.js:5-6` 写明 2026-10-18 起统一三层（结论带 / 条线表 / 待我处理），汇报并入「待我处理」。所以本轮的问题不是「汇报卡重复」，而是**三层之间的语义与视觉冲突**。

**混乱来源（按可见顺序）：**

1. **4 个指标按钮长得一样，行为却分两派**：`逾期`/`待我处理` 点击是「筛选下方列表」，`在办`/`待赋权` 点击是「滚到条线表」（`work-overview.js:855-871`）。样式只有 hover 底色和选中下划线（`styles.css:4572-4591`），没有任何「筛选 / 跳转」的区分。
2. **「待我处理」一词在同一屏出现两次**：结论带的 label（`work-overview.js:131`）和下方分区标题（`:517`）。
3. **每行动作按钮同款重复**：3 条汇报 → 3 个一模一样的「去我的处置 ›」；3 条待办 → 3 个「去待办 ›」；最后再来一行「共 N 项 · 去待办」（`:475-491`）。一屏可出现 4 个同义按钮。
4. **6 列条线表里「动作」列大量是「—」**（`work-overview.js:470-471,674`），而「待处理」列已经写了缺口（如「待赋权 3 个」），动作列只是把同一件事再说一次。
5. **同一个数字出现两次**：组织台的「待赋权」既是结论带第 4 数（`:205`），又是「赋权」条线的 `active`（`:221-225`）。
6. **条线行名与动作目的地不一致**：「成员流动」行的按钮写「去成员名册」，落 `roster`（`:227`），用户以为是去名册而不是去流动台账。
7. 另有一个独立面：组织台「我的处置」页自身有 **4 个区块、4 个计数标题、3 个独立搜索框**（`issue-dispatch-view.js:49,57,65,74-76`），视觉噪声不亚于概况。

**重排方案（判据：改）：**

```
① 结论带：只保留「逾期」为可点筛选；「待我处理 / 在办 / 待赋权」改静态读数，
   或全部加同一枚「›」并把行为统一成「筛选下方列表」。
② 条线表：6 列 → 5 列，删「动作」列；「待处理」格 = 缺口文字 + 行内链接（有缺口才出现）。
③ 待我处理：按来源分 3 组（待办 / 文件 / 汇报），每组最多 2 行；

④ 我的处置页：4 段压成 2 段（待我汇报 / 我提交的），全页只留 1 个搜索框。
```

**结论：「汇报区」已不在概况；混乱源是结论带 4 按钮语义混排、「待我处理」标题重复、每行同款动作按钮、6 列表的动作列空值，以及「我的处置」页 4 段 3 搜索；按「删动作列 / 分组动作 / 单搜索」三步重排即可。**

### 判例⑥ 成员名册筛选：chip 改三个下拉 + 搜索的点击成本与控件清单

**现状：** `roster-tab.js:186-196` 调用 `renderFilteredList`，`facets: personFacets(...)`、`facetStyle: 'chip'`。`personFacets` 返回 4 个维度：党小组 / 发展阶段 / 角色 / 在册（`list-filter.js:336-344`）。chip 形态把「全部 + 每个取值」全部平铺为按钮（`list-filter.js:198-204`）。

按当前种子（3 个党小组、4 个发展阶段、7 种角色、2 种在册状态）估算：**20 个胶囊 + 4 个维度名 + 搜索框 + 清除按钮**。桌面 1280px 约 2–3 行，390px 约 6–7 行。

**点击成本对比：**

| 操作 | 现 chip | 三下拉 + 搜索 | 差值 |
|---|---:|---:|---:|
| 选 1 个维度 | 1 次（值已在屏上） | 2 次（展开 + 选） | +1 |
| 同时选 3 个维度 | 3 次 | 6 次 | +3 |
| 清除全部 | 1 次（「清除」） | 1 次（条件显示的「清除」） | 0 |
| 首屏占用（桌面） | 约 90–120px | 约 38–46px | −60px |
| 首屏占用（390px） | 约 190–230px | 约 80–90px | −120px |
| 误点风险 | 高（相邻胶囊、选中态弱） | 低（一次只看一个维度） | — |

**判断：** 名册是「按人找、按组核对」的表格页，不是标签浏览页。chip 的优势（值全可见、少一次展开）在这里被「20 个按钮压掉首屏」抵消；手机上甚至要滚动才能看到第一名成员。**判据：改。**

**控件清单（建议）：**

| 控件 | 类型 | 说明 |
|---|---|---|
| 搜索 | 文本框 | 姓名 / 学号，沿用 `personKeyword()` |
| 党小组 | 下拉 | 选项来自 `groupOptions()`；含「未分组」 |
| 发展阶段 | 下拉 | 选项来自 `DEVELOP_STAGE_OPTIONS` |
| 在册状态 | 下拉 | `在校 / 滞留` |
| 角色 | **不进主行** | 低频；如需保留，放「更多筛选」或人才库 |
| 清除 | 文本按钮 | 仅在有筛选值时显示 |
| 结果计数 | 文本 | 「N 人」，与列表同源 |

**结论：4 组 chip ≈20 个按钮把名册推下首屏；改「搜索 + 党小组 / 发展阶段 / 在册状态 三个下拉」，每次筛选多 1 次点击，换来桌面约 60px、手机约 120px 的首屏空间与更低的误点率，值得。**

## 八、共识 5 条

1. **浮窗的动作必须固定。** 长表单的取消/提交不能随内容滚走；页脚要么给动作，要么什么都不放，不能「说明常驻、按钮消失」。
2. **关闭必须等价于放弃。** 任何「暂存名单 / 待提交赋权 / 已选人员」在 Esc、遮罩、× 关闭时都要清；只在「取消」按钮清是不完整的。
3. **页签名、视图名、数据对象三者必须对齐。** 「专班管理」里出现「活动工作组」不是分类问题，是命名与对象不一致；改名受 `D-442` 约束，优先拆内容而不是改名字。
4. **日历右栏必须能办事。** 支书已裁定「左日历右详情」，不能删；那就让右栏承担「当日清单 + 就地操作」，否则它永远只是左格的复述。
5. **筛选器的形态由表的任务决定。** 名册是核对表，不是标签墙；chip 适合「少量值 + 快速切换」，20 个值时应回到下拉。

## 九、分歧 3 条

1. **活动日历右栏是「改」还是「删」。** 一方主张支书已有 2026-10-04 明确裁定（左日历右详情），不能删；另一方认为右栏无信息增量、留着就是重复。本报告按「改」记录，删除需支书另行改口。
2. **「专班管理」改名还是拆内容。** 一方认为改名为「工作组」最省事；另一方指出 `D-442` 锁定页签名，改名会牵动帮助页、README、测试与用户习惯。本报告按「拆内容、保留页签名」记录。
3. **思想汇报组织台是否收窄为「未交/待补充」。** 一方担心收窄后看不到全量分布；另一方认为全量矩阵只是一片色块、没有阅读价值。本报告建议「默认例外清单 + 一键查看全量」，不等同于删数据。
