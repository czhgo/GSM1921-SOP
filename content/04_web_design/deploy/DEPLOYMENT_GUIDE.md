## 一、系统形态速览（对外第一屏）

**一句话定位**：GSM1921-SOP（光华管理学院本科生党支部管理引擎）是一套承载支部「管理事、服务人」完整叙事的支部工作系统——把从入党申请人到正式党员的培养、考察、发展全流程，以及三会一课、主题党日、考勤考察、通知协同、宣传档案等日常工作，沉淀为**可记录、可检索、可上报、可交接**的数字化台账，并在此之上支撑支部与学校（计算中心 / 党委组织部 / 党校）之间的数据协同。

**部署在哪 / 给谁用**：

| 形态 | 是什么 | 数据 | 面向谁 |
|------|--------|------|--------|
| 静态演示（GitHub Pages 托管 `docs/`） | 公开门面 + 演示版（about.html 为公开叙事页） | mock（localStorage + 内存，刷新丢失） | 学校/评审先看「系统长什么样」；支部公开门面 |
| 自托管（`server/` Node + SQLite，路径 B） | 支部日常正式使用的工作台 | SQLite 单文件持久化 | 支部成员（按角色工作台登录使用） |
| 计算中心托管（目标形态，路径 C） | 正式上线目标：前端 + 后端迁至学校托管 | 学校数据库 | 支部成员 + 学校统一管理 |
| 微信小程序（规划，路径 D） | 移动端微信内协同（过程性批复零成本） | 与网页共用后端 | 支部成员在微信内完成批复/浏览 |

**一句话给三方**：给支部成员——一套真实组织的数字化工作台；给支书/支委——管理事、服务人、对外迎检汇报的台账底座；给学校（计算中心/组织部/党校）——一个**数据边界清晰、可对接可交付**的支部侧系统（详细诉求见 §三）。

## 二、四条部署落地路径总览与部署决策

### 2.1 路径总览

| 路径 | 形态 | 数据 | 前置条件 | 当前就绪度 | 适用场景 |
|------|------|------|---------|-----------|---------|
| A 静态托管 | GitHub Pages 直接部署 `docs/` | mock（localStorage + 内存缓存，刷新丢失） | 无 | ✅ 完全就绪 | 开发调试 / 演示 / 公开门面（about.html 是公开页） |

| C 计算中心对接 | 学校提供后端（数据库 + API 服务器） | 计算中心数据库 | 前置条件见 §3.4 | 🔶 准备阶段（代码已就绪，待对接） | 正式上线目标形态 |

**路径关系**：A → B 是「数据从 mock 到持久化」的升级；B → C 是「自托管到学校托管」的迁移（前端数据层切换 api 即可，UI 零改动）；D 依赖 B/C 先落地（小程序必须共用已上线的后端）。

### 2.2 部署决策矩阵

| 场景 | 路径 |
|------|------|
| 开发调试 / 单机演示 | A（`docs/` 静态）或 B（`server/` 本地） |
| 公开门面 / 开源展示 | A（GitHub Pages，about.html 为公开叙事页） |

| 移动端微信内协同 | D（小程序，中期，依赖 B/C 上线） |

**判定口诀**：要演示走 A，要持久化走 B，要学校托管走 C，要微信协同走 D——D 必须站在 B/C 之上。

### 3.1 对接总叙事与决策矩阵

**总叙事（一段话）**：支部建设方兴未艾，「管理事、服务人」需要把成员培养、考察、发展的全过程做成可信台账（战略母本见文件头）。这套台账由我方系统承载后，**对学校只有三类协同诉求**——①**托管**：请计算中心提供数据库/API/HTTPS 等运行环境，让系统正式上线（路径 C）；②**读取外部依据**：党校培训进度、智慧党建记载是支部考察/发展判断的外部依据，需单向读入；③**回写与上报**：支部活动记载、考察结论、发展进度经审核后回写北京大学智慧党建平台（党旗飘飘）、按日上报供平台收录。对接授权已获**党委组织部**支持（2026-08-19 确认）——这是组织部门认可的协同工作，不是支部私下的爬取。

### 3.2 我方系统能力与后端对接需求

> 本节回答对接方最关心的两个问题：**这套系统是什么、能做什么**（3.2.1），**后端需要为我方提供什么能力**（3.2.2-3.2.5）。对计算中心而言，本节即「系统概述 + 对接需求」清单。

#### 3.2.1 系统概述与核心功能（对接对象自述）

光华管理学院本科生党支部管理引擎（GSM1921-SOP）是一套面向学生党支部的综合性管理工具，核心功能包括：

- **党建活动管理**：创建、赋权、分工、考勤、考察建档、人才库维护
- **党员发展路径**：从入党申请人到正式党员的全流程追踪（对应 [DEVELOPMENT_PATH.md](../../01_strategy/DEVELOPMENT_PATH.md) 第四章 发展党员流程）
- **通知系统**：程序被动通知 + 支书/支委主动通知，`actionRequired` 驱动交互
- **意见反馈**：GitHub Issue 风格的反馈追踪（提交→审核→合并）
- **数据可视化**：关系网络图、时间轴、日历、归档库

**技术基座（对接方须知）**：前端功能完整（`docs/` ESM 分层 + 工作台体系）；`server/` 后端全栈已实现（Express + better-sqlite3，35 资源表 + 认证 + 附件上传 + 邮件 + 上报，测试全绿）。**数据层为 mock/api 双模式**——本地默认 mock，对接计算中心时切 api 即可，**UI 零改动**（见 3.2.4）。整体处于**对接准备阶段**。

#### 3.2.2 后端服务需求

| 功能模块 | 需要的后端能力 | 数据结构 | 优先级 |
|---------|--------------|---------|-------|
| 用户认证 | 登录/注销/会话管理 | `users` 表（studentId, name, role, partyStatus） | P0 |

| 归档库 | 查询+按月分页 | `activities` 表的 completed/archived 子集 | P2 |

#### 3.2.3 数据持久化需求

- **存储方式**：关系型数据库（PostgreSQL 推荐）或学校计算中心提供的数据库服务
- **数据量预估**：初期 <1000 条记录，年增长 <500 条
- **备份策略**：每日自动备份 + 支书手动导出能力

#### 3.2.4 API 设计要求

`services/runtime.js` 已预留 mock/api 切换点，DataAdapter 抽象层已实现，对接后只需：

```javascript
// runtime.js 中调用：
setDataSource('api', {
  apiBaseUrl: '',            // ⚠ 留空 = 同源相对（api-adapter 的请求 path 已含 `/api/v1/...`）
  authToken: '<JWT Token>',
});
```

> ⚠ **不要把 `/api/v1` 写进 `apiBaseUrl`**：`api-adapter.js` 的每个请求 `path` **本身就含** `/api/v1/...`（如 `_get('/api/v1/activities')`），再拼一个 `/api/v1` 会得到 `/api/v1/api/v1/activities` ⇒ **全部接口 404**。代码里所有切换点都传 **`apiBaseUrl: ''`（同源相对）**——前后端同源部署（Node 同时托管 `docs/` 与 `/api/v1`，或反向代理把 `/api/v1/` 转给 Node）时这是唯一正确取值；只有前端与后端**不同源**时才需要填域名前缀（且**不含** `/api/v1`），同时还要解决 CORS（服务端未挂 CORS 中间件，见下）。

UI 层零改动，通过 `getAdapter()` 访问数据自动走 API 适配器。DataAdapter 架构详见 [DATA_MODEL.md §4.4](../data/DATA_MODEL.md)。API 需满足以下规范：

- RESTful 风格
- JSON 响应格式
- JWT 会话认证
- 分页查询支持（`?page=1&per_page=20`）
- 月份分组查询支持（`?month=2026-07`）
- 完整路由设计见 DATA_MODEL.md §4.4.5

#### 3.2.5 信息安全与多级可见性

系统采用多级可见性设计，后端需实现基于 `partyStatus` 和 `role` 的访问控制：

| 可见性层级 | 适用场景 | 过滤逻辑 |
|-----------|---------|---------|
| 全员公开 | 一般通知、活动公告 | 无过滤 |
| 仅党员 | 党内事务讨论 | `partyStatus IN ('正式党员','预备党员')` |
| 仅支委 | 支委会议、考察建档 | `role IN ('secretary','vice-secretary','org-commissioner','disc-commissioner','prop-commissioner')` |
| 指定人（私发） | 工作私信 | `targetPersonIds` 字段 |

> 登录门控（谁能进页面/谁能写/谁能下载）的四层模型见 **§4.4**（对内专项章，对外读者可跳过）。

### 3.3 数据流边界：我方数据从哪来到哪去

**内部数据全景**：支部工作实录（活动 / 考勤 / 考察 / 通知 / 反馈 / 专班 / 档案…）由成员在 `docs/` 工作台录入 → 经 DataAdapter（mock/api 双模式）→ 落到 `server/` 35 资源表（`id + data JSON` 通用结构）→ 备份即复制 SQLite 单文件。数据只外发**已确认/已归档**的记录（源头审校 + 异常驱动原则：草稿/待确认数据不外发）。

**对外数据流边界总表（单向/双向）**：

| 通道 | 方向 | 边界内容 | 权威细节 |
|------|------|---------|---------|
| 计算中心托管 | 双向承载 | 我方系统整体运行于学校基础设施；数据存学校数据库；我方保留数据模型/接口控制权（api-adapter 路由表） | §3.4-3.7 |
| 党校系统爬取 | **单向（读）** | 党校 → 我方：培训阶段/课程完成度/成绩/学时/结业评议（只读，不写回） | §6.5 |
| 智慧党建读 | **单向（读）** | 平台 → 我方：组织生活/民主评议/党费/发展进度记载 | §6.6 |
| 智慧党建写 | **单向（写，审核后）** | 我方 → 平台：活动记载/考察结论/表决公示（API 或导出导入，默认不做脆弱自动写） | §6.6 |
| 数据上报出口 | **单向（出）** | 我方 → 智慧党建/党校平台：党员/活动/考勤/学习四域，每日批量 + 手动触发 | §3.9 |
| 邮件通道 | **单向（出）** | 我方 → 成员邮箱：通知/待办/汇报/会议提醒（SMTP） | §3.8 |
| 迎检外链 / 归档包 | 人工（出） | 支书生成临时查看链接 / 导出归档包面向上级审查 | §5.3.2 |

### 3.5 对接步骤与登录落点

1. **第一步**：学校计算中心提供后端 API 环境（数据库 + API 服务器 + HTTPS 域名）

4. **第四步**：通知 + 反馈模块对接
5. **第五步**：AI 本地部署环境搭建（见 §3.6）
6. **第六步**：全功能联调测试（`server/test/` 用例作为回归基线，含链接/审计守护）

> **注意**：每一步对接前，需要与学校计算中心确认技术规范和数据安全协议。

**登录落点：北大 IAAA 单点登录（后续目标）**——登录门控四层已预留 IAAA 为登录落点的最终目标（**§4.4**）：工作台（L1）与写入操作（L2）的跳转目标由本地 `login.html` 替换为 IAAA 网页。**接入前不改变门控触发条件**——IAAA 只是换登录落点，门控模型不变。

### 3.8 邮件发送通道：对接学校邮件系统（通用 SMTP）

> **定位**：本系统与学校邮件系统之间的发送通道。本系统只做「发送」，邮箱由学校/支部提供 SMTP 服务。**读者对象：计算中心对接人**——本节自包含，不需要本项目任何上下文。
> **前置依赖**：路径 B（Node 自托管）已上线，或与路径 C 同步规划。

#### 3.8.1 目的与覆盖场景

系统在站内通知/待办/反馈/会议之外，**同时通过邮件触达成员**（站内 + 邮件双通道，不漏人）。共四个场景：

| 场景 | 触发点 | 收件人 |
|------|--------|--------|
| ① 通知发布 | 支书/副支书在「通知发布」发布通知 | 通知受众（全体/党小组/指定角色） |
| ② 待办提醒 | 任何新待办生成（审批/报名/考察/交接） | 待办责任人 |
| ③ 反馈/汇报 | 意见反馈提交、一键汇报发出 | 汇报对象（支书/纪检等） |
| ④ 会议提醒 | 三会一课/主题党日活动（开始前 N 小时） | 活动参与人 |

#### 3.8.2 依赖与前置条件（计算中心需提供）

| 项 | 说明 | 示例 |
|----|------|------|
| SMTP 服务器地址 | 学校统一邮件系统的发送服务器 | `smtp.pku.edu.cn` |
| SMTP 端口 | 465（SSL）或 587（STARTTLS） | `465` |
| 发件账号 + 密码/授权码 | 支部专用发件邮箱（如 `gsm1921@xxx.edu.cn`） | — |
| 发件人显示名 | 邮件中显示的发送者名称 | 「光华管理学院本科生党支部」 |
| 出站白名单（若学校有） | 本系统服务器 IP 加入邮件系统允许发送白名单 | — |

> 若学校暂无 SMTP 开放，可先用任意标准 SMTP 服务（腾讯企邮/阿里企业邮等）联调，参数不变、切换只改配置。

#### 3.8.3 技术方案

- 后端新增邮件发送模块（Node `nodemailer`），配置经**环境变量**注入（不写进代码/仓库）：
  ```
  SMTP_HOST=smtp.xxx.edu.cn
  SMTP_PORT=465
  SMTP_USER=gsm1921@xxx.edu.cn
  SMTP_PASS=******
  SMTP_FROM=光华管理学院本科生党支部 <gsm1921@xxx.edu.cn>
  SMTP_TLS=true            # 465 用 SSL / 587 用 STARTTLS
  MAIL_ENABLED=true        # false 时仅站内通知，邮件通道静默关闭
  ```
- 发送策略：
  - **站内优先、邮件并行**：站内通知照常入库，邮件发送异步进行，**邮件失败不影响站内功能**（降级不阻断）。
  - **失败重试**：每条邮件最多重试 3 次（间隔 1min/5min/30min），最终失败记入发送日志（可查）。
  - **去重**：同一收件人同一内容的批量邮件合并为一封；通知类按人合并。
- 邮件正文 = 站内内容快照 + 系统入口链接（登录后直达对应页面）；纯文本 + 简洁 HTML 双版本。
- 隐私：收件人邮箱从系统内成员档案读取（字段预留）；凭据与邮件日志**只存服务端**，不外发。

#### 3.8.4 计算中心 Checklist（验收标准）

- [ ] 提供 SMTP 服务器地址/端口/账号/授权码/发件人显示名（§3.8.2 表）
- [ ] 配置 §3.8.3 环境变量后重启服务，`MAIL_ENABLED=true`
- [ ] 验证：支书发布一条通知 → 目标收件人邮箱收到邮件（正文含通知内容 + 直达链接）
- [ ] 验证：触发一条待办（如报名审批）→ 责任人收到提醒邮件
- [ ] 验证：SMTP 账号错误时系统**不崩溃**（站内通知仍正常，日志记录发送失败）
- [ ] 确认出站白名单（若有）已加入本系统服务器 IP

#### 3.9.3 上报接口协议（与计算中心/平台侧约定）

- **上报出口**（本系统提供，供平台拉取或人工导出）：
  - `GET /api/v1/report/:domain?from=YYYY-MM-DD&to=YYYY-MM-DD` → 返回该时段 JSON 数据

- **推送模式**（若平台提供接收端）：本系统定时任务 POST 至平台指定 URL，格式 JSON，鉴权用平台下发的 Token（`REPORT_WEBHOOK_URL` / `REPORT_TOKEN` 环境变量）。

#### 3.9.4 同步频率与可靠性

- 默认**每日凌晨 03:00 批量上报**（可配），另支持**手动触发**（界面按钮 / 接口调用）。
- 失败重试 3 次；连续失败发管理员通知（站内 + 邮件，若邮件通道已启用）。
- 上报仅发送**已确认/已归档**数据（源头审校 + 异常驱动原则：草稿/待确认数据不外发）。

## 四、认证与登录门控（部署形态 / 登录态 / 门控统一模型）

> 本章定义系统的部署形态、登录态与登录门控的统一模型，作为侧边栏统一与全站登录跳转逻辑的权威依据。

### 4.1 问题缘起

系统存在多种部署形态与登录态，侧边栏与登录跳转逻辑在不同页面间存在不一致：哪些页面强制跳登录、哪些匿名可访、未登录时侧边栏显示什么、内部附件与公开外链的下载权限如何区分——此前缺乏统一模型，靠各入口分散实现。

本章将这些「场景」拆成两个正交维度，统一约定侧边栏 footer 与登录门控的行为。

### 4.2 5 场景模型（两轴正交）

系统行为由两个正交维度决定，二者不可混为一谈：

- **轴一 · 部署形态**：决定「能否真正登录 / 数据存哪」
  - **静态托管**：GitHub Pages，`docs/` 直接部署，无后端。只能 mock，登录是「演示/开发绕过」；**有 about**（`about.html` 是公开门面「支部的故事」）。
  - **有后端**：Node 一体化（`server/` 同源）或计算中心对接。可真实账号登录 + API + 持久化；**无 about**（内部工具不需要公开门面）。
- **轴二 · 登录态**：决定「侧边栏显示什么」
  - **未登录**（访客）
  - **已登录 · 演示绕过**（mock：dev 卡片 / `?dev=ROLE` / 无后端时账号密码回退，无真实 token）
  - **已登录 · 正常**（api：账号密码 → 后端签发 token）

两轴笛卡尔积，去掉「静态托管下正常登录」这一不可能项，得到 5 个实际场景：

| # | 场景 | 部署 | 登录态 | 数据源 |
|---|------|------|--------|--------|
| S1 | 静态托管 · 访客 | 静态 | 未登录 | mock |
| S2 | 静态托管 · 演示登录 | 静态 | 已登录 · 演示 | mock |

### 4.4 登录门控四层模型

登录门控采用分层触发：

| 层 | 门控对象 | 未登录时行为 |
|----|---------|------------|
| L1 页面 | 工作台 `workspace/*` | 强制跳 `login.html` |
| L2 功能 | 一切「写入」操作（建活动 / 写支部文件 / 提交反馈等） | 触发跳登录（或弹登录引导） |

### 4.5 下载情形（L4）

2. **内部附件**：支部文件、宣传档案、考勤考察附件（`/api/v1/uploads`）→ 需登录（后端 `requireAuth`）。

### 5.2 文件流分类原则

把文件流按「用途与生命周期」分为两类，各归其所：

| 维度 | 过程性文件 | 审查文件 + 辅助照片 |
|------|-----------|-------------------|
| 典型形态 | 草稿、待批复的流转材料、过程汇报 | word/pdf 正式文件、活动照片 |
| 用途 | 流转、批复、修改往返 | 展示覆盖面、体现成效、迎接审查 |
| 时效 | 短（批复完成即过期） | 长（长期可查可调） |
| 最佳场所 | 微信（随手、即时、对方在线） | 系统（沉淀、检索、展示） |
| 系统职责 | 留痕闭环（已发/已收/已批复，见 §5.4） | 承载浏览（宣传墙 + 档案，见 §5.3） |

**判断标准**：文件是「流转物」还是「成果物」——流转物归微信（系统留痕），成果物归系统（承载浏览）。

### 5.3 浏览功能设计：宣传墙 + 档案分层

#### 5.3.1 形态

- **宣传墙（展示层）**：支部工作覆盖与成效的「门面」——活动照片墙 + 成果入口（新闻稿、审查文件列表），供内部浏览与迎检展示。
- **档案库（沉淀层）**：正式文件按归档管理（宣传委员「档案归档」板块承接），可检索、可筛选、可调取。
- **入口互通**：宣传墙展示的成果可一键进入档案库对应条目；档案归档时可选「上宣传墙」。

#### 5.3.2 权限

- **内部全员**：支部成员默认可见宣传墙与档案。
- **迎检外链**：支书可生成临时查看链接 / 导出归档包，面向上级审查，链接可设置有效期。

#### 5.3.3 与宣传墙初衷的呼应

2026-08-11 决策：审查文件与辅助照片「和设计【宣传墙】的初衷是一致的」——用照片证明覆盖面、用正式文件支撑成效。宣传墙不是装饰，是支部工作成果的可信呈现。

### 5.4 过程性汇报的集成方案

#### 5.4.1 迁移复杂度：从微信群聊到网页，是行为做法的转变

2026-08-11 决策：「从微信群聊到网页的转变，是一个很复杂的事情！！」——这比「登记成本」更根本：**微信群聊是即时通讯做法（随手说、对方在线、零门槛），网页是结构化工作台做法（留痕、可追溯、需打开）**。使用者已习惯前者，迁移意味着行为习惯改变——这正是 H10 最小三成本中**适应学习成本**的最高门槛。本方案的一切设计（§5.4.2-5.4.6）都是在压低这道迁移门槛，而不是假装它不存在。

#### 5.4.2 致命问题：任何「登记」都有操作成本

网页系统读不到微信消息（技术硬约束）。「一键登记」只是把成本压到最低，不是消除——批复人在微信批完后还要切到系统登记，成本高、动机无，必然无人使用（死功能）。迁移复杂度（§5.4.1）决定了：**凡是要求使用者「离开微信做额外动作」的设计，都要以「使用者是否有动机做」为第一验收标准**。

#### 5.4.3 成本翻转：受益者登记

登记成本由**受益方**承担而非**负担方**：

| 谁登记 | 成本 | 动机 |
|--------|------|------|
| 批复人（接收方） | 最高（刚批完还要切系统） | 无（帮他人留痕） |
| 发送方 | 最低（本就因留底而在系统发起） | 有（登记即自己的台账完整） |

#### 5.4.4 终极形态：小程序原生承接

```
发送方（网页/小程序）发起过程性汇报
  → 小程序推送微信订阅消息给批复人（用户授权，非打扰式群发）
  → 批复人在微信点开消息卡片 → 直达小程序批复页
  → 点「同意/需修改/退回」→ 数据直接写入共享数据层
  → 网页台账实时更新：谁 / 何时 / 批复了什么
```

批复人全程不离开微信、不打开网页、不做任何「登记」——点一下就是批复，批复就是数据。**零操作成本**。

#### 5.4.5 过渡形态（小程序落地前）：发送方登记制

- 发送方在系统发起汇报（为了留底：可追溯、与活动/任务关联、责任清晰）
- 材料微信转给对方 → 对方微信批复
- 发送方回系统把自己的汇报更新为「对方已批复：同意/需修改/退回」（+可选理由）
- **价值前提**：系统内「留底」对发送方有真实价值（台账完整性），登记才成立

#### 5.4.6 两端分工（「小程序有，网页也有」）

| 能力 | 小程序 | 网页 |
|------|--------|------|
| 批复入口 | 微信内原生批复（零成本） | 过渡期发送方登记制 |
| 台账沉淀 | 只读查看 | 发起 + 追踪 + 审计 + 浏览 |
| 文件流 | 过程性文件微信内流转 | 审查文件/照片 → 宣传墙 + 档案 |

### 5.5 小程序路径评估与原生承接机制

### 6.3 我们系统的数据类型与字段（对接映射的「我方」）

#### 6.3.1 后端 35 资源表（server/db.js）

> 统一结构 `id + data JSON`（与前端数据结构完全一致，嵌套字段零损失）。会话与附件独立两表。

| 分类 | 表 | 与北大对接的字段交集 |
|------|-----|---------------------|
| 身份 | `users` | **personId（学号，主键锚）**、name、partyStatus（申请人/积极分子/发展对象/预备/正式）、role、梯队 |
| 党建活动 | `activities` / `act_sub_records` | 三会一课/主题党日：活动名、时间、地点、参与者 → 智慧党建「组织生活记载」 |
| 考察 | `inspections` | 考察记录（民主评议/谈话）：personId、结论、时间 → 智慧党建「民主评议」 |
| 发展流程 | `todos` / `tasks` / `assignments` | 发展任务节点、分工 → 智慧党建「党员发展管理」 |
| 考勤 | `attendances` / `makeup_tasks` | 出席/补课 → 党校「培训出勤」辅助核对 |
| 培训 | `notices` / `experience_deposits` | 通知、经验沉淀 → 党校「学习圈/院系活动」参照 |
| 组织 | `taskforces` / `tf_sub_records` | 专班工作 → 智慧党建「工作专班」 |
| 文档 | `branch_docs` / `file_space_records` / `archive_records` | 支部文件/档案 → 智慧党建「党支部工作手册」导出素材 |
| 协同 | `external_dispatches` / `weekly_reports` / `signups` / `activity_reviews` / `taskforce_reviews` / `prop_tasks` / `compliance_references` / `image_records` | 无直接对接（内部工作流） |

#### 6.3.2 关键映射字段（设计原则）

- **主键锚**：`users.personId = 北大统一身份（学号）`——两系统所有成员数据以此关联（党校按学号、智慧党建按学号/身份证）。
- **状态锚**：`partyStatus`（申请人→积极分子→发展对象→预备→正式）——与党校培训阶段、智慧党建发展流程一一对应，是双向同步的核心比对字段。
- **时间锚**：所有同步记录带 `recordedAt` + `updatedAt`（ISO）——冲突仲裁用（§6.7）。

### 6.5 党校系统：单向爬取方案

#### 6.5.1 工具链（校园网内定时任务）

| 层 | 工具 | 理由 |
|----|------|------|
| 浏览器自动化 | **Playwright**（Node 生态，与 server/ 同栈） | 无头 Chromium 渲染 JS 页面；支持截图/网络拦截/表单；IAAA 登录态可持久化（storageState 复用，避免反复认证） |
| 调度 | **node-cron**（集成进 server/ 同步模块） | 与后端同进程，定时触发爬取 + 落库 |
| 数据落点 | 新增 `sync_logs` 资源表（或复用 `compliance_references` 旁挂） | 记录每次爬取的原始快照 + 映射结果 + 差异 |
| 凭证 | IAAA 统一认证（党委组织部对接账号）+ Playwright storageState | 校园网内可直接访问；凭据走环境变量，不入库不落盘明文 |

#### 6.5.2 爬取流程

```text
定时触发（如每日 02:00 + 关键节点事件触发）
  → Playwright 启动 → 载入 storageState（IAAA 登录态）
  → 导航到学员列表 → 逐人抓取：培训阶段 / 课程完成度 / 章节自测 / 结业考试成绩 / 学时 / 结业评议
  → 结构化 JSON → 数据映射（学号匹配 users.personId）
  → 差异比对（与上次快照 diff）→ 更新 users / inspections 对应字段
  → 写 sync_logs（成功/失败/差异明细）→ 有差异推送通知（notices）
```

#### 6.5.3 爬取频率策略

| 数据 | 频率 | 理由 |
|------|------|------|
| 培训阶段/完成度 | 每日一次 | 日常进度跟随 |
| 结业考试/评议结论 | 事件触发（阶段临近结业时加强） | 结论性数据，变更即同步 |
| 学时 | 每周汇总 | 变化平缓 |

#### 6.5.4 风险与缓解

| 风险 | 缓解 |
|------|------|
| 页面结构变更 → 爬虫失效 | 选择器集中管理 + 失败告警（通知支书）+ 快照留档便于恢复 |
| IAAA 风控（异地/异常登录） | 校园网内 IP 稳定；登录频率控制；storageState 复用减少认证次数 |
| 自动化访问的实施口径 | 对接授权已获**党委组织部**支持（2026-08-19）；具体抓取方式/接口按组织部流程确认（§6.9 待确认项），不擅自实施 |

### 6.6 智慧党建平台：双向同步方案（理想 vs 现实）

#### 6.6.1 技术现实声明（决策者须知情）

厂商系统（艾唯博瑞类）的「双向实时同步」**取决于平台是否开放 API/对接接口**。公开信息显示平台声称「与上级主管部门党建系统链通、一端录入多端使用」——说明**平台有系统间集成能力**，但对外部系统（如我们）是否开放写接口，**必须向厂商/信息中心确认**（§6.9）。

#### 6.6.2 方案 A（理想）：平台开放 API/Webhook

```text
我们 ──→ 平台：POST /sync/activities（三会一课记载）、POST /sync/inspections（民主评议）、POST /sync/development（发展进度）
平台 ──→ 我们：Webhook 回调（平台记载变更 → 我们实时更新）
冲突仲裁：updatedAt + partyStatus 状态机（§6.7）
```

前置：平台提供 API 文档 + 认证（OAuth/密钥）+ Webhook 配置。**此方案若成立，双向实时可达。**

#### 6.6.3 方案 B（现实）：组织部对接账号下的定时增量 + 导出导入

无 API 时，「双向实时」退化为**「双向 + 定时增量（分钟级/小时级）」**——在组织部对接账号能力范围内做到最接近实时：

| 方向 | 机制 | 工具 |
|------|------|------|
| 读（平台→我们） | 定时抓取后台记载（组织生活/民主评议/党费/发展进度）→ 映射落库 | Playwright 只读爬取（同 §6.5） |
| 写（我们→平台） | ① 若后台支持批量导入（Excel/CSV）→ 自动导出 + 文件导入；② 否则 → 表单自动化代填（**稳定性风险高，需与党委组织部确认实施口径后启用**） | 后台导入功能 + 生成标准 Excel（与平台模板对齐） |
| 冲突 | 以「平台权威 + 我们为工作台」为默认；两写冲突由 updatedAt + 人工复核队列仲裁 | sync_logs + notices 提醒 |

**设计取舍**：自动写（表单代填）是最后手段且默认关闭——**宁可导出给支书/党务老师一键导入，不做脆弱自动写**（H10 最小操作成本：自动写失败重填的操作成本远高于人工导入一次）。

#### 6.6.4 双向同步数据流

```text
平台记载变更（组织生活/评议/党费）
  → 定时拉取 → 映射（学号/partyStatus）→ diff → 更新我们系统 → 通知

我们系统变更（活动记载/考察/发展节点推进）
  → 变更日志（sync_pending 队列）→ 定时推送 → 平台导入/API
  → 失败重试（指数退避）→ 人工复核队列
```

---

### 6.7 同步机制与数据一致性

#### 6.7.1 一致性模型

- **主键**：学号（personId）为两系统唯一锚；同一条记录在两边各存 `updatedAt`。
- **仲裁规则**：默认**北大平台为权威端**（官方上报口径），我们为工作台；同一字段两边都改时取较新 `updatedAt`，并向另一侧回写；`partyStatus` 变更遵循状态机（不能跳级），跳级视为冲突入人工队列。
- **变更日志**：新增 `sync_pending`（待推送队列）+ `sync_logs`（历史）两张资源表，全量审计可回滚。

#### 6.7.2 去重与幂等

- 所有同步写操作带**幂等键**（来源 + 业务键 + updatedAt），重复推送不产生重复记录。
- 读取侧 diff 比对（哈希快照），无变化不写库。

#### 6.7.3 人工复核队列

无法自动匹配（学号缺失/姓名不唯一/状态机冲突）→ 进 `待人工核对` 队列，工作台可视化呈现，支书/党务老师一键处理。

### A.2 真实部署 checklist（2026-09-02 部署件登记；2026-09-23 按「六项 P0」重核）

> 供 B 路径（Node 自托管正式使用）与 C 路径（计算中心对接）落地时逐项执行。代码基座已就绪（`server/env.js` 的运行形态判定 / `server.js` 的 DISABLE_SEED 与生产默认不播种 / `scripts/backup.mjs`）。

**新建库启动（首次，防演示种子混入真实账本）**

1. **设 `APP_ENV=production`**：生产形态下 ① **未设 `LOGIN_PASSWORD` 启动即拒**（进程退出并打印原因）；② `DISABLE_PASSWORD_CHECK` **一律不认**；③ 空库**默认不播种**（不再依赖「记得加 `DISABLE_SEED=1`」）。等价显式做法：`DISABLE_SEED=1`（空库不导入 50 人演示支部种子，全新建库直接录入真实人员）。
2. **设 `LOGIN_PASSWORD`**（所有账号共用的统一口令）；可改的其余项见 `server/.env.example`。
3. **关断前端空域回退（防污染真实账本）**：路径 B/C 是 Node 托管，`/src/config/deploy.js` 由 `server/app.js` 动态注入（`DEPLOY_MODE` 恒为 `'server'`，**无需手改磁盘常量**）⇒ **设环境变量 `SEED_FALLBACK=0`**（注入串据此注入 `false`，见 `server/.env.example`）：置 `false` 后 `core/data-adapter.js::init()` **不再**为考勤 / 考察 / 待办三域回退注入演示种子（缺省 `true`＝演示形态）。若改用静态托管形态，则改 `docs/src/config/deploy.js` 的 `DEPLOY_MODE` 与 `SEED_FALLBACK` 常量即可。它**只管那三处**，不替代第 1 步/第 4 步。
4. 逐一关闭 **services 层 9 处空表回退**（`_loadX` 空则注入演示 seed：attendance/inspection/review/thought-report/activity/makeup/notice/todo/signup）。**原因**：空表回退只填前端缓存本无害，但用户任一后续写会触发快照上传，把回退的演示种子整体写到服务端，污染真实账本。
5. **确认库内只有真人**：看启动日志的 `[server] 自检 · users 计数=…；演示种子账号=…`（判据＝`docs/src/mock/people.js::PEOPLE` 的 id 集）；若演示种子账号 > 0 而这是正式库 ⇒ 换空库重建（生产形态已默认不播种）。

**日常运维**

6. **备份 = 跑脚本，不要手拷库文件**：`cd server; .\scripts\backup.ps1`（或 `node scripts/backup.mjs --out <目录>`）——数据库走 SQLite **在线备份**（`db.backup()`，**含 WAL 内容的一致性快照，不需停服**）+ `uploads/` 整目录 + 备份当场校验。⚠ **只拷 `data.db` 会丢最近写入**（WAL 未并回）**且会丢附件物理文件**（库里只有元数据）。用法与定时备份建议见 `server/README.md`「备份与恢复」。
7. 恢复 = **停服务** → 用备份的 `data.db` 覆盖库文件（并删除同目录 `data.db-wal` / `data.db-shm`）→ 用备份的 `uploads/` 覆盖附件目录 → 启动（users 表非空不会重新 seed）。
8. 更新 = 覆盖 `docs/` 与 `server/` 代码（保留 `data.db` 不动）→ `npm start`。
9. 上传目录 = 附件物理文件所在处（缺省 `server/uploads/`，可由 `UPLOAD_DIR` 改；服务首次启动会自动建目录）：**该目录须可写**（不可写则所有上传失败），且**须与 `data.db` 一并纳入备份**——附件文件只在磁盘上，丢库可重建、丢文件不可恢复。
10. 反向代理的**请求体上限须 ≥ 上传上限**（上传上限＝**10MB**，见 `server/routes/uploads.js` 的 `MAX_SIZE`）：如 nginx 的 `client_max_body_size` 至少设 `10m`（低于此值时，大图在**代理层**就被拦下，表现为 413 或连接中断，与后端 413 是两层不同的失败）。另 `/snapshot` 原始体上限 4MB（前端 gzip 压缩后传输，通常远小于该值）。
11. ⚠ **若由 nginx 直接托管 `docs/` 静态资源**：必须把 **`/src/config/deploy.js` 单独放行到 Node**（`location = /src/config/deploy.js { proxy_pass ...; }`）——该文件是 Node **动态注入**路由（`server/app.js`），不是磁盘上的静态文件；被静态托管走会返回磁盘版 `DEPLOY_MODE='static'` ⇒ **「关于」门面与部署形态判定会错**。
