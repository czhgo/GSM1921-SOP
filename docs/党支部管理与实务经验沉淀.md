### §1.1 党建主旨的"双域"认知

**[双域认知]** — 场景路由的第一判断键

党建工作的本质，不是流水线式的任务堆砌，而是在**两个正交维度**上的结构化运营：

| 域 | 英文标识 | 核心命题 |
|---|---|---|
| **活动建设域** | `activity` | 以活动为载体，驱动党员参与感与组织凝聚力 |
| **组织建设域** | `organization` | 以制度为骨架，驱动党支部的合规性与可持续性 |

**操作规程**：每一项工作任务，必须首先完成域归属判断（`domain routing`），再进行权责分配与产出物设计。混淆两域是任务失焦和职责模糊的根本原因。

> 工程验证：`常见工作场景快速指南.md` v3.0 以 `# 一、活动建设` 与 `# 二、组织建设` 作为一级标题，将域归属编码进文档结构本身——这是双域认知从哲学落地为架构的标志性节点。

---

### §1.2 条块体系与分工逻辑

**[条块逻辑]** — 高决策权场景的不可委托原则

党支部组织架构遵循"条条（功能线）× 块块（党小组）"矩阵模型：

- **条条**（commissioner roles）：组织委员、宣传委员、纪检委员，各自持有专属职能域的执行权。
- **块块**（host group）：党小组组长，持有所辖党员的信息触达权与组织权。
- **书记**（secretary）：党支部法定第一责任人，持有若干**不可委托**的高决策权场景。

**核心铁律**：在以下场景中，党支书的角色不可被替代或委托，**委托即失效**：

1. **党课**（party-lecture）：书记是党课的法定主讲或审定人，任何委托均导致制度合规性失效。
2. **意见反馈处理**（feedback-handling）：书记是唯一的意见接收与处置决策者，委托会造成制度真空。

> 工程验证：`sopData.js` 中 `party-lecture` 与 `feedback-handling` 两个场景的任务节点，角色字段已硬编码为 `secretary`，`timeOffset` 精确锚定，杜绝了模糊委托的技术可能性。

### §1.3 减负与奥卡姆剃刀原则

**[减负原则]** — 产出物的三重验证门控

组织运营中存在大量"伪需求"——看似有价值、实则增加负担而不产生实质效益的产出物。奥卡姆剃刀要求：**如无必要，勿增实体**。

每一项产出物，必须通过以下三重门控检验，**任一不通过即视为伪需求，直接删除**：

| 验证维度 | 判断问题 | 失败后果 |
|---|---|---|
| **硬性要求** | 上级党组织是否有明文规定要求此产出？ | 无制度依据，伪需求 |
| **无重叠** | 是否已有其他产出物覆盖此功能？ | 冗余产出，直接合并或删除 |
| **防真空** | 若删除此产出，是否会造成工作断点或归档缺失？ | 结构性需求，保留 |

**典型案例**：
- 微信备忘录 → 未通过"硬性要求"（无制度依据）→ **删除**，改为直接与组织者对接
- 多份宣传截图 → 未通过"无重叠"（宣传推文+配图已覆盖）→ **合并**

> 工程验证：Burden Reduction 战役（Phase 3.1 ~ 4）系统性删除了跨越多个 SOP 文档的伪需求产出物，`sopData.js` 同步清除了 `branch-discussion` 场景。

### §1.4 双轨制隔离架构

**[双轨制架构]** — 人类阅读面板与 AI 数据面板的物理隔离

本系统采用严格的双轨制架构，两轨之间**物理隔离，禁止互相污染**：

| 轨道 | 路径 | 受众 | 内容边界 |
|---|---|---|---|
| **人类阅读面板** | `docs/` | 支委成员、换届接班人 | 管理哲学、实践经验、制度解读 |
| **AI 数据面板** | `.vibe_context/` | AI 代理（Copilot） | 上下文规则、场景脚本、执行日志、系统快照 |

**污染的两种模式及后果**：

1. **人类内容混入 AI 面板**：导致 AI 代理在错误的叙事框架下产生"AI 幻觉"，输出偏离制度真相的指令。
2. **AI 内容混入人类面板**：导致可读性崩溃，制度文档被技术噪声污染，"制度失真"。

> 操作规程：新增文档时，首先判断受众——面向人类则落入 `docs/`，面向 AI 则落入 `.vibe_context/`，严禁混放。本文件即双轨制的典型执行样本：内容纯粹是人类可读的管理哲学，无任何 AI 指令。

### §2.1 UI 设计的业务隐喻

**[UI隐喻]** + **[UI隐喻-视觉投影]** — 前端是后端业务规则的像素级投影

**核心认知**：前端 UI 的每一个控件，都不是独立的视觉元素，而是后端业务规则的**视觉投影**。因此：

> **UI 重构即业务重构**。任何 UI 层的修改，必须被视为一次业务规则变更，而非样式调整。

**双重推论**：

**推论一：字段增删三层同步律**（[UI隐喻]）  
UI 字段的增加或删除，必须同步处理以下三层，缺一不可，否则产生**幽灵状态（Ghost State）**：

| 层级 | 代表物 | 风险场景 |
|---|---|---|
| **DOM 层** | `index.html` 中的 HTML 元素 | 元素残留但不可见，占用内存 |
| **JS 层** | `events.js` 中的事件监听与数据提取 | 读取不存在的 DOM，产生 `null` 引用 |
| **数据负载层** | `actPayload` / `sopData.js` 中的数据字段 | 脏数据写入持久化层，破坏数据一致性 |

**推论二：控件语义业务化律**（[UI隐喻-视觉投影]）  
- 角色颜色（`ROLE_COLORS`）不是美学选择，是角色权责等级的视觉编码
- 选项分组（`optgroup`）不是布局优化，是场景的域归属（活动建设 vs 组织建设）
- 控件显隐逻辑（`_syncHostGroupVisibility`）不是交互优化，是业务规则的状态机实现

**典型案例**：党员姓名字段（`#participant-name-wrap`）被删除时，同步执行了 DOM 物理删除、`events.js` 数据提取代码清除、`actPayload.participantName` 写入链路切断——三层原子化操作，零幽灵状态。

### §2.2 文档与代码的绝对勾稽（AI 工程学）

**[AI工程学-绝对勾稽]** + **[AI工程学-物理剥离]** — 系统可维护性的工程基石

#### 2.2.1 双向勾稽原则（[AI工程学-绝对勾稽]）

`docs/` 与 `src/workflow/sopData.js` 之间存在**严格的双向勾稽关系**，二者共同构成本系统的 SSOT（Single Source of Truth）：

```
制度变更（SOP文档）  ──正向注入──►  sopData.js（代码实现）
代码节点变更          ──反向沉淀──►  SOP文档（制度更新）
```

**违反后果**：两者出现偏差，即意味着"代码行为"与"制度规定"脱节，产生合规风险与 AI 幻觉。

**操作规程**：
- 任何对 SOP 制度的更改，必须触发对 `sopData.js` 中对应场景的同步更新（正向注入）
- 任何对 `sopData.js` 节点的新增或修改，必须触发对对应 SOP 文档的说明追加（反向沉淀）

#### 2.2.2 物理剥离原则（[AI工程学-物理剥离]）

**阈值规则**：业务模块代码行数超过 **150 行**，必须实施**目录级物理剥离**（directory-level physical separation）。

**原理**：AI 代理（如 GitHub Copilot）的上下文窗口（context window）是有限资源。单文件过长会导致：
- 关键逻辑被稀释，AI 理解精度下降
- 编辑操作的副作用范围扩大，增加引入缺陷的概率
- 增量式变更难以精确定位

**实施路径**：
1. 识别超过 150 行的业务模块
2. 按业务域或场景 ID 拆分为独立文件，归入专属子目录
3. 更新主入口文件的 `import/require` 链路
4. 在对应 SOP 文档中记录物理剥离操作（反向沉淀）

> 工程验证：`knowledge/SOP/` 下的各委员工作流程指南均按角色域独立归档，有效降低了 AI 代理的上下文负载，同时确保每次修改的影响域可控。
