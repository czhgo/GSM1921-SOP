## 15. 甲部修改流程

> **本节为 CLAUDE.md 原 H4 内容的外移归位（2026-08-11 甲部重编后为 H50）**。定义甲部修改的标准工作流、钩稽联动、Snapshot 更新规则。
>
> **（书记论断 原 P-017，2026-08-09 自书记论断汇编迁出·甲部自省原则）：当书记指出 Harness 存在欠缺时，必须首先反思甲部的表达与规定本身是否有缺陷——是规则没写清楚、覆盖有遗漏、还是执行标准不够具体？有则改之，无则加勉。不得仅归因于"执行不力"而回避制度层面的反思。**

### 15.1 甲部修改工作流

> 🔴 **当用户对甲部提出修改意见时，必须按以下 5 步执行，不得跳过任何步骤。**

**Step 1 — 修改甲部**：将用户的新看法准确写入甲部对应章节

**Step 2 — 影响评估**：识别修改波及的范围（甲部内部/guides/insights/SOP/代码）

**Step 3 — 写入乙部**：将同步更新任务写入乙部，作为甲部修改的衍生任务链

**Step 4 — 逐项执行**：按乙部中的任务链顺序执行

**Step 5 — 全局验证**：Grep 确认全仓库无旧版表述残留

**禁止**：仅修改甲部而不写入乙部衍生任务。

### 15.2 钩稽联动

> 🟡 **修改任何文件前触发。**

修改任何文件前，必须检查 CLAUDE.md 及 guides 中是否存在对该文件的钩稽声明并按要求联动更新。

### 15.3 Snapshot 更新规则

> 🟢 **仅在特定触发条件下执行。**

`.ctx/SNAPSHOT.md` **不再每次执行更新**。仅在以下触发条件满足时更新：

- (a) 大版本升级（v3→v4），如架构重大变更、角色体系迭代
- (b) 用户显式指令触发（如"/snapshot"或"生成快照"）
- (c) 项目阶段性收官（Phase 1/2/3 完成）

日常变更仅由 `EXECUTION_LOG` + `DECISION_LOG` + `TIMESTAMPS` 承载。

> **出处与根因（原 insights §6.8）**：快照按需生成源于一次教训——最初设计为每次执行都更新 Snapshot，结果维护负担过重，快照沦为"日志的冗余副本"。根因是混淆了「记录当前状态」（快照）与「记录变更过程」（日志）的职责边界——快照是重方案、日志是轻方案，日常变更用轻量方案承载。上述 (a)-(c) 即该教训的触发条件化，正文不重复。

## 16. 吸收外部输入操作流程

> **本节为原** **`content/governance/SYNC_EXTERNAL.md`** **的合并归位**（2026-07-11 合并）。定义"外部输入→内部知识"的完整操作流程，作为 CLAUDE.md H30.1 吸收外部输入原则的配套指南——与 H30.1 互补：H30.1 覆盖"内部变更"流程（修改前→修改中→修改后），本节覆盖"外部输入→内部知识"（识别→归位→一改具改→验证）。

### 16.1 适用场景

当以下外部输入到达时，触发本流程：

1. **书记评议**：书记对现有制度/代码的修正意见
2. **外部文档**：书记上传的官方文件、评议文档、制度更新
3. **人类自行更新**：书记直接修改了仓库中的文件（非AI操作）

### 16.2 操作流程

#### 第一步：识别变更范围

收到外部输入后，首先识别变更涉及的范围：

- **术语变更**：概念的增删改、定义的修正
- **制度变更**：流程/规则/权限的调整
- **设计变更**：架构/数据模型/交互逻辑的修改
- **纯增量**：新增内容，不涉及既有条目的修改

#### 第二步：归位到权威源

根据 H30.2 母本子本表，将变更归位到对应的权威源：

| 变更类型 | 权威源                                                                          | 操作               |
| ---- | ---------------------------------------------------------------------------- | ---------------- |
| 术语变更 | USAGE\_POLICY.md                                                             | 更新术语定义，触发全仓一改具改  |
| 制度变更 | content/02\_institution/sop/\*.md                                            | 先改SOP母本，再改代码     |
| 设计变更 | content/{01\_strategy,02\_institution,03\_doc\_system,04\_web\_design}/\*.md | 先改设计理念/治理母本，再改代码 |
| 原则变更 | CLAUDE.md 甲部                                                                 | 按 §15 甲部修改工作流执行   |

#### 第三步：触发一改具改

变更写入权威源后，按 H30.1 执行标准执行一改具改：

> **（书记论断 原 P-016，2026-08-09 自书记论断汇编迁出）：修改任何一项制度/设计/术语，必须在全仓库范围内同步更新所有相关引用，不得遗漏。修改前全仓库搜索所有引用位置；修改中逐一替换，每处替换记录到执行日志；修改后再次全仓库搜索确认零残留。**

1. **修改前**：全仓库搜索所有引用位置
2. **修改中**：逐一替换，每处替换记录到执行日志
3. **修改后**：再次全仓搜索确认零残留

#### 第四步：验证与记录

1. 运行 GetDiagnostics 确认代码无错误
2. 写入执行日志
3. 更新乙部（如有衍生任务）

### 16.3 AI生成过程中的HARNESS清单

> 书记明确：不需要references模板，而是AI在生成过程中自检的HARNESS清单。

AI在执行任何写入操作时，必须自检以下清单（对应 H40 文件修改检查清单的生成时版本）：

```
□ 1. 本次写入是否涉及外部输入？→ 是则触发本流程
□ 2. 变更范围是否已识别？→ 术语/制度/设计/原则
□ 3. 权威源是否已确定？→ 按 H30.2 母本子本表归位
□ 4. 一改具改是否已执行？→ 全仓搜索+逐一替换+零残留确认
□ 5. YAML是否已更新？→ last_updated字段
□ 6. 执行日志是否已写入？
□ 7. 乙部是否已更新？
```

### 16.4 AI推导识别与级联修改

> **确立日期**：2026-07-18 | **确立背景**：反论评议第一轮中发现§3.3"两种协作模式"为AI推导内容（非书记原话），删除后需级联更新4个子本文件

当AI生成的内容无法追溯到书记原话或制度原文时，按以下规则处理：

**识别**：内容声称描述书记判断，但Grep全仓库无法找到书记原始表述来源的，视为AI推导内容。

**标注**：删除AI推导内容时，在修改处添加来源说明：

> **来源说明**（YYYY-MM-DD）：此节原为AI推导内容，经反论评议确认非书记原话，已删除。书记原始判断见 [权威源文件](路径) §X。

**级联修改**：AI推导内容若被其他文件引用，删除后必须：

1. 定位所有引用该内容的子本文件（Grep搜索关键词）
2. 逐一更新子本，在修改处附来源说明
3. Grep确认全仓库零残留

**与 H30.1 一改具改的关系**：本节是一改具改原则在"内容删除"场景的细化——一改具改管"改"，本节管"删"，两者都要求全仓库级联+零残留验证。

### 17.3 自动唤醒机制设计

#### 17.3.1 架构

唤醒机制由三个层次组成：时间戳注册表 → 调度逻辑 → 分发逻辑，最终汇入三步工作流闭环执行。

| 层次               | 职责                                      | 实现位置                           |
| ---------------- | --------------------------------------- | ------------------------------ |
| 时间戳注册表           | 记录每个周期性任务的最后执行时间                        | `.ctx/TIMESTAMPS.md` 的周期性任务追踪区 |
| 调度逻辑（SCHEDULER）  | 对比当前时间与 `last_*` 时间戳，判断是否到期             | CLAUDE.md H20.1 前置指令            |
| 分发逻辑（DISPATCHER） | 根据任务编号查找对应执行流程，生成 next\_prompt，写入待办列表 | `.ctx/PENDING_TASKS.md`        |
| 执行闭环             | 规划 → 执行 → 验证 → 更新时间戳 → 记账               | 三步工作流                          |

**调度规则**：

- 若 `(now - last_W1) > 7天` → 触发 W1
- 若 `(now - last_M1) > 30天` → 触发 M1
- 若 `(now - last_Q1) > 90天` → 触发 Q1

#### 17.3.2 TIMESTAMPS.md 扩展字段

在 `.ctx/TIMESTAMPS.md` 中维护周期性任务追踪区（见该文件"周期性任务最后执行时间"表）。

#### 17.3.3 唤醒触发方式

| 方式                     | 适用         | 实现                                                             |
| ---------------------- | ---------- | -------------------------------------------------------------- |
| **会话入口检查**             | 每次新对话开始时   | `CLAUDE.md` H20.1 前置指令：读取 TIMESTAMPS.md → 检查到期任务 → 若存在到期任务则优先汇报 |
| **手动检查指令**             | 用户主动触发     | `/check-recurring` → 执行 SCHEDULER 逻辑并输出到期列表                    |
| **GitHub Actions（远期）** | 全自动月级/季级任务 | cron 触发 workflow → Agent 自主执行 → 更新日志                           |

#### 17.3.4 通知策略

| 到期天数     | 级别 | 行为                        |
| -------- | -- | ------------------------- |
| 到期前 3 天  | 提醒 | 下次 AI 会话开头显示"即将到期"        |
| 到期当天     | 警告 | 标记为 ⚠️ overdue pending    |
| 到期后 7 天  | 升级 | 在 CLAUDE.md 乙部 中追加为短期规划任务 |
| 到期后 30 天 | 紧急 | 标记为 🔴 管理遗漏——写入存档以便追责追溯   |

### 17.4 维护与演进

- 每次新增周期性任务时，同步更新本节 §17.2 + TIMESTAMPS.md 追踪表
- 每次执行周期性任务后，通过三步工作流闭环更新 `last_*` 时间戳
- 季度审查时评估周期性任务的执行质量和覆盖完整性

### 17.5 常态化工作的制度存续与任务清理解耦（原 insights §3.8 并入）

> **确立日期**：2026-09-04（insights 分流归位）| **项目落地**：CLAUDE.md H60.5 常态化专项评议机制 + `.ctx/REVIEW_QUEUE.md` 附录（即 §17.2.1 W4 专项评议循环的载体）

多轮持续、无"完成"态的经常性工作（周期性评议、常态化审查、持续审计），其**制度本体与任务清单管理应解耦**：

- **制度本体写入治理文件**——「该怎样评」由机制定义（本节 §17 + CLAUDE.md H60.5 表格），不随轮次进度变化
- **轮次进度挂外部承接文件**——「评到哪了」是状态（`.ctx/REVIEW_QUEUE.md` 附录的进行中轮次条目），随执行更新

任务清单清理（一轮完成、条目移除）不影响制度运转——清理的是承接文件中的进度条目，不是机制本身。

**为什么不是"机制与进度放在一起"？** 混在一起时，轮次结束后清理任务清单会误伤制度本体——删除清单时可能连带删掉"该怎样评"的定义；解耦后各归其位，删进度不动机制、改机制不影响进度记录。

**生效条件**：适用于多轮持续、无"完成"态的经常性工作。一次性任务仍按常规生命周期管理；若常态化工作轮次终结（宣布不再需要），对应承接条目同步移除。

## 18. 书记评议工作流细节（承接 CLAUDE.md H60 指针）

> **确立日期**：2026-08-11 | **确立背景**：CLAUDE.md 甲部重组（按约束力三层 + 编号重编），评议细节从甲部下沉本节，甲部只保留触发/流程/分流/校验/常态化专项骨架（CLAUDE.md H60）。
> **定位：** 本节承接 [CLAUDE.md H60](../../CLAUDE.md) 的细节指针，定义抽样规则、预审维度体系、评议记录格式、概念复用性扫描流程、三类评议类型速查。执行书记评议时按需读取本节。

### 18.1 抽样规则（承接 H60.2）

- **抽样范围**：content/ 五子目录（01_strategy / 02_institution / 03_doc_system / 04_web_design / 05_ai_coding）
- **抽样单位**：具体命题（非完整文档）
- **选取规则**：AI 按文档现有结构标记抽取（如论断编号 P-001\~P-025、反论标记、设计原则、why 讲解、战略命题等）
- **抽样数量**：每次 10-15 条，每子目录 2-3 条
- **不重复机制**：AI 启动时扫描最近 4-8 周执行日志中带"书记评议"标记的 T 编号条目，从未评议过的命题中抽取

### 18.2 预审维度体系（承接 H60.2）

对每条命题按其特性灵活选择预审维度（不锁定数量）：

- **表述**：术语合规性（T1/T2/T3）、设问句、主观预设、书面语风格
- **内容**：与母本一致性、跨文件引用断裂、事实准确
- **精神实质**：是否传达书记思想精髓（AI 给初步判断+存疑点）
- **实现方法**：是否有代码/设计支撑、是否可落地
- **合规溯源**（按需）：是否可追溯到书记原话或制度原文，AI 推导须标注
- **奥卡姆剃刀**（按需）：是否存在"为概括而概括""fancy 但无内涵"的标签或结构性数字隐喻
- **概念过拟合**（按需）：是否存在 AI 擅自命名的小命题标签、无依据的层级标签、"="式命名、孤立概念——详见 §18.4

**维度选择原则**：AI 默认参考上述常规维度，但根据命题特性灵活选择——纯术语违规的命题可只审"表述"一维度，涉及制度设计的命题可增审"合规溯源"维度。若某命题只审部分维度，预审报告中注明"本次仅审 XX 维度，理由：……"。四维度为常规参考，非强制锁定。

### 18.3 评议记录格式（承接 H60.3）

作为月度执行日志的一条 T 编号条目（如 T73 书记评议·首评），包含：

- 抽样清单（10-15 条命题+位置）
- 预审结果摘要（按命题特性灵活选择的维度+各维度结果）
- 书记反馈摘要
- 反馈落实摘要：
  - 机械性问题：全仓库扫描范围 + 修订数量 + 抽样校验清单 + 书记判断结果 + 零残留 Grep 验证结果
  - 设计性问题：入丙部 P 编号清单
  - 即时小修订：修订位置清单
- 衍生任务编号清单（链接到乙部/丙部）

### 18.4 概念复用性扫描流程（承接 CLAUDE.md H40.1 的纠正性扫描）

> "概念复用性扫描"是 T3 工作表达术语，指系统性扫描全仓库中 AI 过拟合命名的孤立概念标签，识别瘦身空间，并触发归并或删除。
> 书记元洞察（2026-07-19）："最大的根因在于：一个大的命题可能有很多个小命题。AI专注于过拟合那些小的命题的命名。但事实上，只需要给总的大命题命名即可。"

**扫描范围**：不仅限于 insights 文件——content/ 五子目录和根目录 .md 文件都存在概念膨胀和表述冗余的空间。

**扫描方法**：概念标签法——从文档中的命名性标签（速查表条目、「」命名概念、标题级概念）出发，按频次和复用性分类，而非全量 n-gram 扫描。

**五条判定维度**：

1. **B 表达原因·特定场景**：该概念因特定表达需要而存在，保留
2. **C AI 错误扩充**：AI 擅自创造的概念，书记从未提过，删除
3. **D AI 错误概括**：AI 擅自概括的标签，应归入大命题或删除
4. **D 应归并到大命题**：小命题标签，应归入大命题下作为描述，不单独命名
5. **需重命名**：命名方式违规（如"="式命名），需修正

**文件瘦身原则**：

1. **大命题优先**：多个小命题归入一个大命题，只保留大命题的命名标签
2. **重复表述归并**：同一命题在不同文件中的重复展开，保留最权威版本，其他文件仅引用
3. **AI 概括清零**：无书记原话或制度依据的 AI 自创概念标签，一律删除
4. **跨文件瘦身**：概念膨胀不仅出现在 insights 速查表中——03_doc_system 治理文档的过细分类标签、01_strategy 文档的冗余阐述、02_institution/sop 文档的重复定义，都应纳入瘦身范围
5. **根目录瘦身**：README.md、SNAPSHOT.md 等根目录文件，以及 ARCHITECTURE.md 等已迁移文件中的过时表述，同样需要随一改具改同步更新
6. **零补丁原则**：书记论断（2026-07-19）——"瘦身的一个重要方面是把文档变成一个有机整体。由于书记论述的批次不同，很容易出现到处打补丁的现象——新增内容单独成段落，即使和前面的段落也是相关的。"AI 无法自行判断如何融入（修改原命题的表述以切中新命题，还是调整新命题以适配原命题结构），须提交书记判定。**最终目标：所有涉及用户阅读的文档，零补丁识别。**

**执行流程**：

1. AI 扫描概念标签，按频次和性质分类
2. 逐条通过 AskUserQuestion 提请书记判定
3. 按判定结果执行：删除/归并/重命名/保留
4. 全仓库一改具改（CLAUDE.md H30.1），确保零残留
5. 记录至执行日志 T 编号

**与 CLAUDE.md H40.1 的关系**：H40.1 是预防性守则（修改时自检），本节是纠正性扫描（系统性排查）。两者互补。

### 18.5 三类评议类型速查

#### 18.5.1 反论评议

**目的**：评审全仓库反论的表述质量和命题准确性
**触发**：CLAUDE.md H60.1 触发条件 + T 编号任务
**核心规定**：

- 三类问题维度：正确的废话（删除反论改为正面陈述）/ 命题错误（删除反论用书记原话替代）/ 重点偏差（修正重点关联书记判断的核心关切）

- 预判差异记录：书记判断与AI预审不同时，差异须在评议记录中分析原因

- 历史范畴检查：被否定项是否仍在使用（[OPERATIONS_GUIDE.md §11.7](OPERATIONS_GUIDE.md#117-历史范畴检查)）

#### 18.5.2 理论复用评议

**目的**：评审全仓库跨节/跨文件引用的复用准确性、适用性及效果
**触发**：CLAUDE.md H60.1 触发条件 + T 编号任务
**核心规定**：

- 复用评议指标：复用是否准确、是否过时、是否遗漏、是否过度引用
- 母本子本关系：下游命题对上游命题的复用，母本优先（CLAUDE.md H30.2）
- 散落即漂移原则：信息重复散落视为漂移风险（[OPERATIONS_GUIDE.md §1.4](OPERATIONS_GUIDE.md#14-一致性检查规范)）
- 分轮规划：① insights内部复用链 ② 03_doc_system 治理文档间复用 ③ 01_strategy/04_web_design→02_institution/sop 复用链 ④ 跨目录复用断链检查

**四类问题维度**（2026-08-03 第2轮 T193 沉淀，经书记裁决 + CLAUDE.md H60.4 抽样全接受验证）：

| 维度 | 含义 | 判定标准 | 处理方式 |
|------|------|---------|---------|
| A 断裂链接 | 链接指向不存在的相对路径 | 目标文件/锚点不存在或相对路径计算错误 | 修正为实际存在的相对路径 |
| B 已删引用 | 引用已删除的代码/页面/模块 | 被引对象在 docs/src/ 或 docs/ 中不存在（含旧架构残留） | 替换为实际存在的等价引用；整体过时 → 全面重构（SERVICE_CATALOG v13→v3.0 先例） |
| C 拓扑错误 | 结构/路径描述与现状不符 | 与 SNAPSHOT.md 权威拓扑或实际文件系统不符 | 按权威源修正描述 |
| D 表述 | 内容概括与文件实际内容不符 | 书记对照原文判定（先例：「26 条路线级论断」→「17 条论断，P-002/P-003 为元命题」） | 按书记统一改法 |

> 🔴 **D 表述为最高权重维度**（书记元洞察 2026-08-03）："【表述】是一个大头，因为这个系统的工作性质，要求表达非常严谨！" 表述严谨性是系统命脉——预审时 D 类须逐条细致审查，即使数量少也不得轻描淡写；处置一律提交书记判定，不机械代改。
>
> 🗣 **黑话审查**（书记指令 2026-08-03 T194 追加，D 表述专项）：重点识别 **AI 自己编造的黑话**——概念过拟合、无依据层级标签、孤立概念、生造术语、同义名词堆砌、**语气轻浮**（带引号俏皮口吻等不庄重表达；书记判例 2026-08-03：对"这不是'催你'"评价"表达就很轻浮"）等。判定标准：① 术语在权威源/上级文件中是否有依据（T1 术语须与原文一致）② 是否可被目标读者直接理解 ③ 是否存在更通俗的同义替代表达。基线方法：以**书记论断汇编**（SECRETARY_DIRECTIVES.md，最接近原话的基线）grep 验证——汇编存在的措辞非 T3；DEVELOPMENT_PATH.md 等 AI 编写文档可能自身已被污染（T-195 判例：哲学锚点/心智模式/切面/漂移均曾写入源头文档），不能单独作为基线。处置：识别出的黑话一律提交书记判定，AI 不得自行代改为自造术语。适用于全仓库用户文档，可多轮复用（T-195）。
>
> ⚠️ **源头污染优先警惕**（书记元洞察 2026-08-03 T-195 追加）："目前是检查出来上下游的引用，但是源头可能就是被污染的，这是要非常警惕的！" 引用链路修复（A/B/C 类）只保证链接与路径正确，**若源头文档的表述本身含 AI 编造的黑话，下游引用修复得再正确也是传播污染**。黑话审查须从权威源/母本源头逐层向下审查，而非仅查下游引用。
>
> 🗣 **句式合规**（书记判例 2026-08-03 T-199 P-010 微调）：禁用「不是……而是……」句式——书记否决"不是行政学黑话，而是一种理解手段"（P-010 重写稿）。评议任何表达时以此警觉：凡出现该句式一律提交书记判定改写为叙述式。

**流程要素**（T193 验证的可复用做法）：

- 基线对照：SNAPSHOT.md 权威拓扑 + 实际文件系统 glob 双向验证
- 处置分层：A/B/C 客观事实错误 → 机械性批量修；D 表述 → 书记判定
- 零残留验证：修订后全仓 Grep 旧模式零残留（含概念改名后旧概念名引用残留排查）
- 抽样校验：CLAUDE.md H60.4 分层抽样覆盖各类，书记逐条判定
- 四指标 ↔ 四类映射：复用准确（A/C/D）、复用过时（B）、遗漏/过度引用（预审观察视角）

#### 18.5.3 补丁审查（零补丁识别评议）

**目的**：识别用户文档中新增内容单独成段落（与前面段落/章节相关但不融入）的"补丁"现象，触发融入或调整

### 18.8 专项⑨ 文件目的达成度（五类判据，2026-09-05 书记发起）
