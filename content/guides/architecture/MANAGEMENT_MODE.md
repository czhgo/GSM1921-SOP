# 管理模式架构设计

> 本文档定义 Org OS 的三级管理模式架构，涵盖组织者、深度参与者、普通参与者三类角色的权限矩阵、数据流、双场景适配及系统界面实施路径。

### 1.2 数据流

```
[组织者]                    [深度参与者]                 [纪检委员]                  [归档]
   |                             |                          |                          |
   |-- ① 平等协商分工 --------->|                          |                          |
   |-- ② 确认分工内容 ---------->|                          |                          |
   |                             |                          |                          |
   |                             |-- ③ 执行并反馈 -------->|                          |
   |                             |                          |                          |
   |<-- ④ 分工记录汇总 ----------|                          |                          |
   |                             |                          |                          |
   |-- ⑤ 提交分工记录与考察记录 -------------------------->|                          |
   |                             |                          |                          |
   |                             |                          |-- ⑥ 汇总考勤/参与记录 -->|
   |                             |                          |                          |
   |-- ⑦ 完成复盘报告 ----------------------------------------------------------------->|
   |                             |                          |                          |
   |                             |                             |<-- ⑧ 复盘监督（批注/打回/确认） --|
   |                             |                          |                          |
   |-- ⑨ 补交/修改复盘 ----------------------------------------------------------------->|
```

**流程说明：**

| 步骤 | 动作 | 责任人 | 时限 |
|------|------|--------|------|
| 1 | 平等协商分工 | 组织者 | T-3天 |
| 2 | 确认分工内容 | 组织者 | T-3天 |
| 3 | 执行并反馈 | 深度参与者 | 活动中 |
| 4 | 分工记录汇总 | 组织者 | T+3天 |
| 5 | 提交分工记录与考察记录 | 组织者 | T+3天 |
| 6 | 确认考勤+录入总表 | 纪检委员 | 活动后 |
| 7 | 完成复盘报告 | 组织者 | T+7天 |
| 8 | 复盘监督（批注/打回/确认） | 纪检委员 | T+1天提醒 / T+7天检查 |
| 9 | 补交/修改复盘 | 组织者 | 督办后 |

## 二、角色权限矩阵

| 角色 | 查看所有活动 | 创建活动 | 分配任务 | 修改分工 | 标记完成 | 填写复盘 | 考勤记录 | 参与记录 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 党小组组长 | Y | Y | Y | Y | Y | Y | -- | 导入 |
| 组织者 | Y | -- | Y | Y | Y | Y | -- | 导入 |
| 深度参与者 | 自己的 | -- | -- | -- | Y | -- | -- | 自己的 |
| 普通参与者 | 公开信息 | -- | -- | -- | -- | -- | -- | 自己的 |
| 纪检委员 | Y(审计) | -- | -- | -- | -- | 督办 | Y | 考察汇总 |
| 组织委员 | Y(建档) | -- | -- | -- | -- | -- | -- | 归档 |
| 宣传委员 | Y(备案) | -- | -- | -- | -- | -- | 备案 | -- |
| 支部书记 | Y(全局) | Y | Y | Y | Y | Y | 审阅 | 审阅 |

**权限说明：**

- **党小组组长**与**组织者**在分工记录权限上等同，区别在于：党小组组长是常设角色且可独立创建活动，组织者是按活动指派的角色且不能独立创建活动
- **组织者**在具体活动中享有完整的分工记录闭环：承包/发起 → 平等协商分工 → 分工记录 → 打包产出物
- **深度参与者**承担具体分工，标记完成后由组织者记录分工完成情况
- **纪检委员**以审计视角查看所有活动，但不参与内容编辑；负责考勤记录写入和参与记录汇总
- **组织委员**接收纪检委员提交的参与记录，负责建档管理
- **宣传委员**接收纪检委员提交的考勤记录，负责备案归档

## 三、短期活动管理 vs 长期建设管理

系统需同时支持两种管理模式，以下为关键维度对比：

| 维度 | 短期活动管理 | 长期建设管理 |
|------|------------|------------|
| **时间跨度** | 1天 -- 1月 | 1月 -- 1年 |
| **组织者** | 组织者（按活动指派） | 党小组组长 + 组织委员 |
| **深度参与者** | 单次分工完成 | 持续追踪、阶段性分工记录 |
| **普通参与者** | 单次出勤记录 | 累计统计 + 阶段性评估 |
| **考勤/参与记录** | 单次记录 | 累计统计 + 阶段性评估 |
| **复盘机制** | 活动后1周内 | 每月进度检查 + 季度复盘 |
| **任务粒度** | 一次性任务分配 | 迭代式任务分派 + 中期调整 |
| **记录方式** | 结果记录（分工完成情况） | 过程记录（进度 + 质量 + 阶段产出） |
| **代表场景** | 主题党日、社会实践、组织生活会（依托三会形式） | 宣讲团建设、人生回望录、党员发展培养 |
| **系统数据模型** | `Activity` + 单次 `Task` | `Project` → `Milestone` → `Task` 层级 |
| **复盘模板** | 单次活动复盘模板 | 阶段复盘 + 终期复盘模板 |

### 3.1 数据模型扩展

目前系统以 `Activity` 为核心数据单元，支撑短期活动管理。为支持长期建设管理，需在后续版本引入 `Project` 实体：

```
短期模型：Activity ──has──> Task ──assigned──> DeepParticipant
                              └──attendee──> Participant

长期模型：Project ──has──> Milestone ──has──> Task ──assigned──> DeepParticipant
              │                                                     │
              └──periodic_review (复盘节点)                         └──progress_log (进度日志)
```

## 四、场景应用详解

### 4.1 宣讲团建设场景

**场景特征：** 长期建设项目，涉及研究、撰稿、设计、宣讲等多个子任务，需要多轮反馈与跨组协调。

**角色映射：**

| 实体角色 | 系统角色 | 职责说明 |
|---------|---------|---------|
| 党小组组长 | **组织者** | 跟踪宣讲团整体进展，负责多次反馈循环和跨组协调；设定阶段性目标，记录各轮分工完成情况 |
| 小组内部成员 | **深度参与者** | 承担研究/撰稿/设计/宣讲等具体分工；在系统内标记任务完成，提交阶段性成果 |
| 其他参与成员 | **普通参与者** | 出席但不分工，完成学习材料学习；记录为"出勤" |

**工作流程：**

```
[党小组组长/组织者]
      |
      |-- 创建项目 "宣讲团建设"
      |-- 设置里程碑：M1-选题研究 → M2-稿件撰写 → M3-试讲打磨 → M4-正式宣讲
      |
      |-- M1: 分配任务
      |     |-- 成员A: 文献调研（深度参与-研究）
      |     |-- 成员B: 案例收集（深度参与-调研）
      |     └-- 成员C: 框架设计（深度参与-设计）
      |
      |-- M2: 迭代反馈
      |     |-- 成员A 提交初稿 → 组长审阅 → 修改
      |     |-- 成员B 提交案例集 → 组长审阅 → 补充
      |     └-- 跨组协调：与宣传委员对接推文排期
      |
      |-- M3--M4: 试讲 + 正式宣讲
      |
      └-- 终期复盘：整体评估各成员贡献度
```

**参与记录产出示例：**

| 姓名 | 角色层级 | 具体工作 |
|------|---------|---------|
| 党小组组长 | 组织 | 宣讲团整体统筹、跨组协调、分工记录 |
| 成员A | 深度参与-研究 | 文献调研、初稿撰写、三轮修改 |
| 成员B | 深度参与-调研 | 案例收集整理、数据可视化 |
| 成员C | 深度参与-设计 | PPT设计、宣讲框架搭建 |
| 成员D | 出勤 | 出席试讲、完成学习材料 |

### 4.2 "人生回望录"活动场景

**场景特征：** 需要一对多老师对接的项目制活动，涉及大量协调与材料整理工作。

**角色映射：**

| 实体角色 | 系统角色 | 职责说明 |
|---------|---------|---------|
| 支委 / 指定党员 | **组织者** | 统筹老师对接排期，跟踪全部参与者的进度；一对多老师联络与进度管理 |
| 执行层党员/成员 | **深度参与者** | 一对一与老师对接、整理走访摘要、归档记录材料 |
| 普通参与成员 | **普通参与者** | 参与但未与老师建立一对一联络，仅记录为"出勤" |

**工作流程：**

```
[支委/组织者]
      |
      |-- 创建活动 "人生回望录"
      |-- 统筹排期：确定 8 位老师的访谈时间窗口
      |
      |-- 分配任务：
      |     |-- 深度参与者A: 对接张老师（访谈+摘要+材料归档）
      |     |-- 深度参与者B: 对接李老师
      |     |-- 深度参与者C: 对接王老师
      |     └-- ... 依此类推
      |
      |-- 组织者跟踪：检查进度、协调时间冲突
      |
      |-- 分工记录阶段：
      |     |-- 记录每位深度参与者的分工完成情况
      |     |-- 确认材料归档完整
      |     └-- 汇总形成考察记录
      |
      └-- 复盘：评估整体执行效率与产出质量
```

**判断标准（深度参与 vs 出勤）：**

- **深度参与者**判定条件（满足全部）：
  - 与至少一位老师建立一对一联络关系
  - 实际完成访谈/走访
  - 提交访谈摘要或整理材料
  - 成果可验证（有摘要文档/归档记录）
- **普通参与者**判定条件：参与活动但未与老师建立一对一联络，或联络但未实际完成摘要整理

## 五、考勤 vs 参与记录维度说明

本系统维护两套并行的记录体系，源自 [纪检委员工作流程指南 §1.2](file:///d:/GitHub/GSM1921-SOP/content/SOP/纪检委员工作流程指南.md#L100-L108) 的明确规定。

### 5.1 核心区别

| 维度 | 考勤（0-1变量） | 参与记录（三层记录） |
|------|----------------|---------------------|
| **性质** | 刚性底线 | 弹性贡献 |
| **对象** | 党员、预备党员 | 所有支部成员（党员 + 预备党员 + 发展对象 + 积极分子） |
| **适用范围** | 三会一课；组织生活会（依托三会形式，同等刚性） | 所有支部工作（含三会一课、主题党日、社会实践等） |
| **记录方式** | 二元/三元：出勤 / 请假 / 缺勤 | 三层：组织 / 深度参与 / 出勤 |
| **记录时机** | 实时记录（活动中签到） | 实时记录（活动中观察 + 活动后确认） |
| **提交对象** | 宣传委员（备案） | 组织委员（建档，每月提交） |
| **是否考虑质量** | 否，仅记录客观出勤事实 | 是，深度参与须满足 ☑明确分工 ☑实际完成 ☑可验证 ☑有贡献 |
| **补课/补救** | 请假/缺勤须补课，标注"已补" | 不适用（参与记录不可补救） |

### 5.2 判断逻辑

```
                    活动开始
                       |
           +-----------+-----------+
           |                       |
      三会一课？              其他支部工作？
           |                       |
           v                       v
   对象 = 党员+预备党员      对象 = 所有支部成员
           |                       |
           v                       v
   签到/记录出勤状态         是否有明确分工？
   出勤 / 请假 / 缺勤        /              \
                             /                \
                           是                  否
                           |                   |
                           v                   v
                   是否实际完成？         记录为【出勤】
                   /          \
                  /            \
                是              否
                |               |
                v               v
         记录为【深度参与】  记录为【出勤】
         （标注具体角色）   （挂名无实）
                |
                v
         主导策划与实施？
         /            \
        /              \
      是                否
      |                 |
      v                 v
记录为【组织】   记录为【深度参与-角色】
```

```

      |
      v
设置 primaryRole + activeRole (sessionStorage)
      |

      +---> Sidebar 高亮对应卡片
      +---> 根据视图模式三分类渲染主内容区：
      |       |-- manage: 该角色的管理工作台（可编辑）

      +---> 赋权关系链 (AUTHZ_CHAIN) 约束可查看角色范围
```

赋权关系链规则：
- 党支书可查看所有角色的视图

- 党小组组长可查看组织者、深度参与者
- 赋权者查看被赋权者视图时为只读模式（manager-observe），不可修改

## 八、差异化视图设计规范

> 本节源自 CLAUDE.md H8.2，定义同一数据源（`ActivityRecordStore`）在不同角色和活动类型下的差异化展示规则。角色决定**可见范围和操作权限**，活动类型决定**字段侧重和交互模式**。

### 8.1 核心原则

**同一数据源，不同切面展示**：所有视图共享同一数据源 `ActivityRecordStore`，通过角色过滤和类型映射实现差异化呈现。

**双域分化**：同一角色在「党建工作台」和「党务管理」中看到的是**完全不同的视图和功能集**。党建工作台聚焦创新探索，党务管理聚焦合规运行。

**视图分配规则**：
- 日历视图：仅只读模式全员 + 管理模式中的 secretary/leader/organizer/deep
- 任务看板：条条支委（组织/宣传/纪检）在管理模式中的视图
- 默认信息面板：未选定角色时展示全量信息只读面板

### 8.2 双域视图矩阵（角色维度）

| 角色 | 党建工作台视图 | 党务管理视图 |
|------|--------------|------------|
| **党支书** | 全局视图（所有面板可切换） | 全局视图 + 数据后台 |
| **组织委员** | 专班协调视图 + 看板 | 党员发展管理（考察/催缴/归档） |
| **宣传委员** | 多维表格视图 + 专班面板 | 宣传档案合规建设 |
| **纪检委员** | 考勤管理·考察管理·活动监督复盘（各支柱均覆盖活动+专班两个维度） | 补课制度跟踪/公邮查收提醒 |
| **组织者** | 分工记录视图 | — |
| **深度参与者** | 活动详情视图 | — |
| **默认参与者** | 只读信息面板 | — |
| **党小组组长** | 块块活动管理视图 | 小组成员管理 |

> **双域同源说明**：党建板块与党务板块在后台指向同一份数据（`ActivityRecordStore`），差异仅在于展示切面——党建板块展示"你的出勤记录"（服务同学们的个人视角），党务板块展示"全支部的考察分析"（供支委会决策的管理视角）。

> 完整三委员双域职责对照见 [COMMISSIONER_SYSTEM.md](../design/COMMISSIONER_SYSTEM.md)。

### 8.4 视图组件规范

| 维度 | 展示字段 | 交互方式 | 权限控制 |
|------|---------|---------|---------|
| **多维表格（宣传委员）** | 12字段全显 | 行点击展开子记录；行悬停编辑/删除；全选批量操作 | 宣传委员: write/delete; 其他: readonly |
| **日历（参与者）** | 月网格+彩色标签+图例 | 点击日期展开当日活动；图例筛选 | 参与者: readonly; 管理者: 可创建 |
| **甘特图（组织者）** | 时间轴+任务条+里程碑 | 拖拽调整时间；缩放切换周/月 | 组织者: write; 其他: readonly |
| **看板（组织委员）** | 泳道列（待办→进行中→完成） | 点击确认完成→后台数据变化→渲染实时改变 | 组织委员: write; 其他: readonly |

> **看板归档原则**：已完成的任务不需要在看板中展示，完成即归档。看板只展示"进行中"和"待办"的任务，已完成的任务自动归入归档区域（可折叠查看）。这确保看板始终聚焦于待处理工作，避免信息过载。

| **考勤总表（纪检委员）** | 姓名/活动/类型/状态/确认人 | 按活动/按人员筛选；超期提醒 | 纪检委员: write; 支委: readonly; 成员: 自查 |
| **考察总表（纪检委员）** | 姓名/活动专班/类别标签/考察内容/状态 | 按活动/按人员筛选；类别标签自动填入 | 纪检委员: write; 支委: readonly; 成员: 自查; 组织者: 分工记录只读 |
| **活动监督复盘（纪检委员）** | 活动/组织者/进度/复盘状态 | 时间流阅览；超时邮件提醒；复盘批注/打回/确认 | 纪检委员: full access |

### 8.5 子记录关联结构

每条活动主记录可挂载三类子记录，构成完整的数据关联模型：

```
ActivityRecord (主记录)
├── id, name, theme, desc, link, date, type
├── leaders[], leaderPhotos[]
├── filledBy, createdAt
└── subRecords[]
    ├── { type: "attendance", items: [...] }
    ├── { type: "materials", items: [...] }
    └── { type: "publicity", items: [...] }
```

**子记录类型说明**：

| 子记录类型 | 含义 | 典型写入者 | 关联角色 |
|-----------|------|-----------|---------|
| `attendance` | 考勤记录 | 纪检委员 | 纪检委员（写入）→ 组织委员（归档） |
| `materials` | 活动材料 | 深度参与者（组织者打包提交） | 宣传委员（备案） |
| `publicity` | 宣传素材 | 宣传专班成员 | 宣传委员（审核） |

### 8.6 活动四维度决策树

活动创建时须依次确定四个维度，每个维度决定不同的系统行为：

```
Q1: 组织场景（必选）→ determines role + flow
    ├── 主题党日（非强制·学习型）→ 承办: 按需指定党小组
    └── 三会一课（明确定义·制度型）→ 党小组会/支部大会/支委会/党课

Q2: 活动形式（必选）→ determines color + data
    ├── 学习(蓝) ─ 参访(绿) ─ 座谈(橙) ─ 共建(品红) ─ 会议(紫)
    └── 组织生活会=以三会形式召开的组织生活内容（非独立活动类型）; 发展党员=跨多个活动的流程; 党员培训=学习的子类

Q3: 时长（必选）→ 短期 / 长期

Q4: 发起方向（必选）→ 自上而下 / 自下而上 → 决定写入权限门禁
```

**特殊定位说明**：
- **组织生活会**：以三会形式召开的组织生活内容（非独立活动类型），在 Q2 中归入"会议(紫)"
- **发展党员**：不是单一活动，而是跨多个活动的流程，在 Q2 中不归入任何色系
- **党员培训**：学习类型的子类，在 Q2 中归入"学习(蓝)"

**品牌维度**（叠加层）：品牌/非品牌为叠加属性，待双轨工作流稳定后再上线。

**赋权范围链**：党支书最高赋权 → 组织委员可招募/赋权专班 → 党小组组长可赋权组织者和深度参与者 → 宣传委员和纪检委员不可转授权。

### 8.7 默认信息面板原则

进入党建工作台或党务管理时，若未选定具体角色，展示**全量信息只读面板**。

**信息透明基线**："所有信息都能看到但不能编辑"。这一原则确保：
- 新成员或临时访客可浏览全部活动信息
- 需要编辑操作时，必须先选定对应角色
- 只读面板不显示任何编辑/删除/创建按钮

### 8.8 宣传专班与多维表格备注

宣传档案专班是专班制的**特例**——专班制本身是通用制度框架，组织委员作为唯一管理节点，任何委员均可提出专班需求。

**关键区分**：多维表格视图不应被理解为"宣传委员专属"，而应理解为"宣传委员的职能域展示形态"。具体而言：
- 多维表格是视图组件的一种，可被任何有权限的角色使用
- 宣传委员在党建工作台中的多维表格视图，是其职能域（素材归档+新闻稿起草+推送排版）的自然展示
- 专班的创建和管理权归口组织委员（详见 [COMMISSIONER_SYSTEM.md](../design/COMMISSIONER_SYSTEM.md)）
