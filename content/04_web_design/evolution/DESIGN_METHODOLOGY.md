## 一、系统与工作台设计方法论

> 本节承接系统级与工作台级的设计方法论与判例（原 insights §4.4 / §4.10 / §4.12 / §4.13 / §4.14）。规范权威源：DESIGN_SYSTEM §一（设计哲学）、COLOR_SYSTEM §2.7（主体色配色规则）、DATA_MODEL §2.18~§2.20（待办/通知派生）。

### 1.1 架构演进：大型单体文件拆分——路由+子模块模式（原 insights §4.4）

**大型单体文件拆分：路由+子模块模式**：workspace-entry.js 从 2070 行拆分为 65 行路由页 + 8 个独立子模块。拆分四步流程：(1) 确认子模块完全独立——无交叉引用、无共享状态、无循环依赖；(2) 逐个创建子模块——每个子模块自包含完整的初始化、渲染、事件绑定逻辑；(3) 瘦身为路由页——原文件仅保留角色检测 + `window.location.replace()` 跳转逻辑；(4) 全局引用验证——6 项检查（无 JS 导入旧文件、无跳转旧 URL、HTML 引用正确、entry JS 全部存在）。用 `replace` 而非 `href`——replace 不产生历史记录，用户按返回不会回到空白路由页。

### 1.2 最小三成本原则——论证档案（原 insights §4.10）

> **规范权威源**：规则正文已落位 [DESIGN_SYSTEM.md](../design-system/DESIGN_SYSTEM.md) §一 第2条（最小三成本 Min Cost First，任务流默认直接展示）；数据模型位置 [DATA_MODEL.md](../data/DATA_MODEL.md) §2.18~§2.20（待办任务数据/通知→待办派生）。本文档仅承接论证补强（来源、落地机制、适用边界），与 §1.3.1（4.12.1 最高优先级原则）互为表里。

工作台设计的三条成本底线——信息成本（用户获取"我需要做什么"所需的搜寻成本，任务流默认直接展示）、操作成本（从"进入工作台"到"看到可执行事项"的点击次数，进入即见、系统主动推送；**操作次数上限为至多跳转 2 次、一般 1 次，能就地解决就就地解决**）、适应学习成本（新用户理解工作分工与信息流运作方式的学习成本，通过系统设计本身自解释）。三成本适用于全系统所有角色工作台，是工作台设计的元原则——任何"用户需要先点击 X 才能看到 Y"的设计都违反最小操作成本，任何"用户需要培训才能理解"的设计都违反最小适应学习成本。

**关键落地机制**：

- 待办列表+详情面板取代"日历+inspector"作为工作台默认视图（日历迁移至首页）
- 行动性通知自动派生为对应角色待办（用户无需手动从通知列表中筛选"我需要做什么"）
- 待办按 category 分组+折叠展示，避免信息爆炸
- 赋权入口直接体现在对应角色工作台的待办列表中（不要求用户进入独立赋权页面）

**功能清单与待办推送的适用边界**：待办列表模式让系统主动推送——系统知道"为活动X赋权"是党小组组长的当前任务，直接推送到其工作台，用户进入即见，省去"先知道我需要做什么再去找功能"的搜寻成本。功能清单仍适用于"用户主动查询"场景（如人全景只读视图）——用户带着明确目的进入，查找是预期动作；工作台默认视图则用待办推送，用户进入即见当前要做什么。

### 1.3 设计决策原则（原 insights §4.12.1 / §4.12.4 / §4.12.5）

> **承接说明**：原 insights §4.12（系统功能与视觉设计决策原则，T-142 后续迭代收尾，2026-08-01）集中收录反复强调或要求写入乙部长期排查的功能与视觉决策原则。本次按映射清单承接其中三条 [4] 决策原则（4.12.1 / 4.12.4 / 4.12.5），收录标准机制（原 4.12.6 反复强调内容提级机制）仍在原文件。

#### 1.3.1 最小三成本——最高优先级原则（原 insights §4.12.1）

最小三成本原则（详见本章 1.2 与 DESIGN_SYSTEM §一 第2条）在短期内两次明确强调（2026-07-31 提出、2026-08-01 确认提级），证明其是系统功能设计的最高优先级原则，而非一般设计偏好。凡系统功能设计涉及信息成本、操作成本、适应学习成本取舍时，以三成本最小化为准绳；与三成本冲突的功能设计默认让位。

#### 1.3.2 全站视觉一致性排查（原 insights §4.12.4）

同一视觉元素（label、按钮、卡片、字体字号、间距）在全站必须保持统一规格。视觉不一致是"最小适应学习成本"的直接破坏者——用户在同一页面看到两种 label 样式，会认为系统未完成或质量低劣。本原则写入乙部 C-5 作为长期排查项（与术语一致性审计并列），新页面或新组件上线时对照设计系统基线自查。

#### 1.3.3 布局视觉平衡（原 insights §4.12.5）

页面多栏/多区块布局必须追求视觉平衡——左右栏高度接近、区块面积不悬殊、空态不占据大块空间。不平衡的布局（如左列表远高于右详情卡且右卡大面积空白）会形成"未完成感"。设计要点：空态文案精简、默认选中态填充详情区、sticky 仅当内容充足时使用。本原则写入乙部 C-4 作为长期排查项。

### 1.4 主体色配色规则——论证档案（原 insights §4.13）

> **规范权威源**：配色规则五条与全部色值（tab 激活态用主体色 X、品牌金统一层、状态色全局统一、暖白底、灰只做中性；角色冷色系/活动暖色系双权威源分离；语义红保留清单）已权威落位于 [COLOR_SYSTEM.md](../design-system/COLOR_SYSTEM.md) §2.7 主体色配色规则（打样样板）。本文档仅承接原 §4.13 中规范文件未展开的**论证部分**——规则与色值一律以 COLOR_SYSTEM §2.7 为准。

**为什么"红色太多、意义不明确"是危险的？** 红色同时承担品牌语义（党建红标签）、告警语义（超期/删除/必填）与角色语义（参与者身份色）时，用户无法区分"这是身份色还是警示色"——多种颜色语义相互冲突。T-185 修复轮确立**双权威源分离**：角色维度冷色系（`ROLE_COLORS`：组织者天蓝/深度参与紫/参与者灰/发起人靛蓝），活动类型维度暖色系（`getActivityTypeColors()`：三会一课红/主题党日金），红色收敛到品牌+告警语义。后续任何页面的"装饰红"（本应为主题色却用了品牌红）一律按此修正。

**为什么用"内联三件套"而非 Tailwind 类变体？** `bootstrapPage` 已解构 `accentRgba/accentBorder`，主操作按钮需要角色主题色时拼 `style="background:${accentRgba};color:${accent};border:1px solid ${accentBorder};"`——零新增 CSS 类、颜色自动跟随角色、与打样版内联写法一致。Tailwind 类名写进 style 属性会失效（computed color 退化灰），故不得混用。

**为什么保留"语义红清单"？** 超期/过期/打回/删除/必填星号/「必修」标签/解散专班（破坏性操作）是告警与危险语义，红色是用户识别的安全信号，不可为了"去红"而消除。去红只针对"装饰红/身份红"。

### 1.5 审美审计轮方法论——字号档位、细体克制与四阶段闭环（原 insights §4.14）

> **来源：**T-188 最小三成本与审美审计轮（2026-08-01 发起 → 2026-08-02 闭环）。发起于一次对显示审美的全量审计与整改。

**审计轮四阶段闭环**（大型 UI 审计固定节奏）：审计（产出清单，必须带 getComputedStyle/DOM 数值证据）→ 评议（逐条 AskUserQuestion，一次一条）→ 分步修复（按判定分批落地，每步浏览器验证）→ 验证与沉淀（全量回归 + 决策归档 + 经验蒸馏 + 清单清空）。"修复项必须先有数值证据再动手"——把"看起来不对劲"转化为可复现的确凿证据，避免凭直觉改样式。

**字号档位碎片是"视觉细碎感"的隐蔽根因**：全仓 9/9.6/10/11/12px 五档并存时，同屏元素字号参差直接产生"没打磨"的观感。统一方法是全仓 grep 清零式替换（`text-[11px]`→`text-xs`、`text-[10px]`→`text-[11px]`、日历标签 9.6px→10px），替换后再 grep 确认旧档零残留、新档数量吻合。T-188 实操：9px 有 7 处、10px 有 7 处、11px 有 218 处，上调一档后 9px 清零、10px 清零。

**视觉方案先打样再推广（2026-08-02）**：一次为徽标/日历标签引入的细体衬线字体方案，在铺开后经复审判定效果不佳而全仓撤回。教训：小字号衬线字体在不同设备/分辨率下渲染差异大，易产生"廉价感"而非预期"精致感"；任何视觉方案（字体、字号、配色）应先小范围打样并经确认后再推广，避免全仓铺开后返工。

**色彩克制落地检查点**（与 1.3.2/1.4 呼应）：① 同页左边条不得多色（纪检 9 个橙条→每 tab 仅首个主卡留条；书记 4 色卡→单色进度总览）；② 同一文件色值来源统一（硬编码 hex 与 CSS 变量混用必清零，统一 `var(--accent-xxx)`）；③ 小图标底色用 `${hex}15` 8 位 hex 拼接（`var(--primary-700)15` 浏览器无法解析）。

**正文版式 6 档字号梯队（T-201 判例）**：说明书/长文类页面按 6 档字号收敛，消除"字号跳变"观感——`1rem` 导语/引语/致谢、`0.95rem` 正文段、`0.9rem` 要点卡/列表/表格、`0.85rem` 卡标题、`0.82rem` 卡正文、`0.78rem` 小标签。收敛动作与字号碎片清理（本节约 T-188 段）一致：全页 getComputedStyle 数值取证 → 逐元素归一 → 浏览器实测无跳变才闭环（T-201 实测 12 项通过）。若既有基线字号小于该梯队（如 0.66/0.7rem 矩阵格），先上抬归位再统一，不保留例外档。

## 二、前端实现方法论与判例

> 本节承接前端实现层的方法论与判例（原 insights §6.3 / §6.24 / §6.28 / §6.30）。规范权威源：DESIGN_SYSTEM §五 交互反馈规范。

### 2.1 DOM 优先的状态检测（原 insights §6.3）

党务管理的 commission tab 点击后始终展示默认概览，因为 `getActiveCommissioner()` 依赖全局 state，而 tab 点击只操作 DOM 不写入 state。

**为什么 DOM 优于 state？** 全局 state 是"意图"，DOM 是"事实"。当两者可能不一致时，事实优于意图。交互驱动的状态判定应以 DOM 的实际状态为第一优先级，全局 state 作为兜底。

### 2.2 TOC 滚动高亮失效——相交比阈值法对高章节的局限（T197 判例）（原 insights §6.24）

> **事件**：帮助页圆点导航滚动高亮，IntersectionObserver 阈值方案（`threshold:[0.15,0.4,0.6]` + `rootMargin:'-15% 0px -55% 0px'`）对高章节失效——快速上手章节 3532px 高，观察带仅视口中间 30%（约 198px），最大相交比约 5.6%，永远低于 15% 阈值，圆点永不切换到该章节。

**Generalized rule（Boolean 条件）**：基于相交比（threshold）的 TOC 滚动高亮只在"章节高度与观察带同量级"时成立；当章节高度远大于观察带高度时相交比存在上限，永远无法达标。改用「章节顶部越过标记线」scroll 定位法——逐节读取 section 顶部到视口顶部的距离，越过固定标记线（如 120px）即激活；该判定只读顶部位置、与章节高度无关，长章节与短章节一视同仁。另需页面底部兜底：页面总高不足时末章顶部可能永远无法越过标记线，当 `scrollY + innerHeight >= scrollHeight - 1` 时直接激活末章。

**为什么不是"调小阈值 / 放大观察带"**：观察带放大到全视口后两个相邻章节会同时满足条件，需额外判定"谁更靠下"；调小阈值（如 0.02）能让高章节勉强触发，但短章节一进入视口即相交 100%，"刚开始出现"与"完全占据视口"被判为同一状态，语义失真。标记线法用"顶部越过线"单一条件统一两种场景，判定最简。

**生效条件**：页面含固定小目录 + 滚动高亮需求，且各章节高度差异大（说明书、长文档）。若所有章节高度相近且均低于视口高度，IntersectionObserver 阈值法仍可用。

### 2.3 环形排布的弦长校验——相邻元素互不重叠的几何前提（T-223 判例）（原 insights §6.28）

**事件**：关于页「行百里者半九十」四阶段卡片做环形排布时，首版用「top/right/bottom/left: 17%」贴边定位，浏览器实测四张相邻卡**全部重叠**（重叠 86-159px）——因为相邻卡夹角 90° 时弦长 = 偏移 × √2 ≈ 240px < 卡片宽度 280px，几何上必然侵入。CSS 注释声称「互不重叠」与实测不符，属注释说谎而非布局正确。

**教训**：环形/圆周排布相邻元素是否重叠是纯几何问题——**相邻元素 90° 夹角弦长 = 圆心偏移 × √2，必须大于元素对角线长度才不重叠**。用「top/right/bottom/left 百分比贴边」无法精确控制圆心偏移，应改为「元素中心统一锚定圆心 + translate 平移固定偏移量（CSS 变量 --dl-off）」，偏移量按弦长公式反算。布局类 CSS 注释描述的空间关系必须用浏览器实测验证，不能只靠几何直觉。

**Boolean 条件**：环形排布元素 → 相邻弦长（偏移×√2）> 对角线；注释声明布局关系 → 浏览器实测确认。

**生效条件**：任何环形/圆周/网格对称布局；任何在注释中描述空间关系的 CSS。

### 2.4 ScrollTrigger refresh 的滚动根偏移——懒加载后布局重算失效的根因（T-223 判例）（原 insights §6.30）

**事件**：关于页探索区懒加载插入约 4000px 高度后，对话区四卡的 ScrollTrigger 触发点全部失效——正放时对话卡在探索区起点即提前点亮（start 实测≈4700，正确应≈8856）。首轮修复在懒渲染后调用 `ScrollTrigger.refresh()` 无效：refresh 于非零滚动位置（y≈4100-5300）执行时，把 start/end 整体算低了「当前 scrollY」。根因是页面滚动根为 BODY（实测 `document.scrollingElement === BODY`、`documentElement.scrollTop` 恒 0、`body.scrollTop` 在滚），ScrollTrigger 读滚动位置时取到 0，于是 `trigger 文档位置 = getBoundingClientRect().top + 0` 比真实位置低了一个 scrollY。最终修复：对话卡弃 ScrollTrigger 布局测量，改 `lenis.on('scroll')` + 每次实时 `getBoundingClientRect()` 计算 progress——视口坐标与滚动根归属无关，触发窗口错位也只影响「何时开始更新」，progress 被 clamp 到 0 不会提前点亮。

**教训**：依赖布局测量的 ScrollTrigger（start/end 在创建时按当前布局 + 滚动位置计算）在「滚动根非 documentElement」或「懒加载插入高度后」两种场景下都不可靠——前者 refresh 在非零滚动位置整体偏移，后者旧布局的 start/end 直接失效。凡「滚动到某个元素才触发」且该元素后方有懒加载内容的动画，优先用「滚动事件 + 实时 getBoundingClientRect」计算触发进度（语义用 `(vh×a − rect.top) / (h + vh×b)` 表达 start/end 线），天然对滚动根与布局变化鲁棒。

**Boolean 条件**：页面含懒加载 + 其后有 ScrollTrigger 动画 → 该 trigger 用实时 rect 计算而非静态 start/end；`document.scrollingElement === BODY` 时 → 禁止在非零滚动位置依赖 `ScrollTrigger.refresh()` 重算。

**生效条件**：任何「懒加载插入内容改变后续元素位置」的页面；任何在 Lenis 平滑滚动 + GSAP ScrollTrigger 组合下的布局重算场景。

## 三、工作台行为设计底线

### 3.1 "打卡化"判定——完成必须对应真实产物（2026-08-02 判例）（原 insights §6.23）

> **事件**（2026-08-02 判例）：系统曾把"待办完成"当作纯状态翻转——点击完成即视为解决，使网页沦为"线上的打卡软件"，对真实工作（线下会议/谈话/活动执行、微信群通知/接龙/资料流转）零承载。若任其发展，系统将无人使用；正确方向是把线下与微信中的真实工作集成进系统，而非以虚拟操作替代真实工作。

**Diff 提取（AI 假设 vs 人类意图）**：

| AI 假设 | 人类意图 |
|---|---|
| 待办"完成"即状态字段翻转，视为任务闭环 | 真实工作发生在线下（会议/谈话/活动执行）与微信（群通知/接龙/资料流转）；网页应承载真实工作的**记录、产物、流转、台账** |
| 系统内的虚拟操作即工作本身 | 系统是真实工作的**集成层与记录层**，不是替代层 |

**Generalized rule（Boolean 条件）**：判断某"完成"交互是否打卡化——`complete(task)` 的副作用集合是否**仅包含状态字段翻转**。布尔条件：`task.completeSideEffects ⊆ {statusFlip}` 为真 → 打卡化 → 设计缺陷，必须为任务绑定真实产物（产出类强制产物表单+附件，操作类可不强制）。任何纯 nudge 性质的"完成"只允许用于"阅读通知"这类本就只有已读语义的操作。

**为什么不是"打卡化只是体验问题"**：它决定系统生死。如果用户只需点完成就能声称工作结束，系统对真实工作零承载，用户失去使用动机，系统沦为无人使用的打卡软件。工作流程的每一环都应在系统中留有真实痕迹。

产物要求按任务类型区分：产出类任务（有真实工作结果）强制绑定产物表单+附件，操作类任务（阅读通知、签到）本就无产物可言、豁免——一律要求交产物只会增加负担、制造新的形式主义。

**生效条件**：任何"完成/确认/提交"类交互的设计评审。触发信号：任务完成不产生、不关联任何真实数据（产物、台账条目、记录行）。

## 四、叙述性人读方法论

> 本节两节保留完整原文（人读价值高，未做删改），供工程师与 AI 设计决策时把握"需求输入"与"制度反思"两条人读方法论。

### 4.1 用户截图即需求（原 insights §1.5）

最高效的需求输入来自**用户提供的真实数据截图**，优于 PRD 文档。

**为什么截图比 PRD 准确？** 因为截图反映的是**已经在用的工作模式**，而非想象中的功能。PRD 描述的是"应该怎样"，截图展示的是"实际怎样"。

### 4.2 制度自省原则：执行失败时先反思制度（原 insights §3.5）

当治理规则的执行失败时，不能仅归因于"执行不力"，必须首先反思制度本身——是规则没写清楚、覆盖有遗漏、还是执行标准不够具体？

**为什么不能只归因于"执行不力"？** 因为制度的设计目标就是让执行者无需额外判断即可正确执行。如果规则写清楚了但执行者仍然犯错，那是执行问题；如果规则本身模糊、遗漏或标准不够具体，那再强的执行力也无法弥补。

**为什么不是"每次都提醒执行者注意"？** 因为提醒依赖人的记忆和注意力，而制度依赖流程和检查清单。前者是"希望不犯错"，后者是"机制防犯错"。制度自省的本质是：当问题反复出现时，升级制度而非加强提醒。
