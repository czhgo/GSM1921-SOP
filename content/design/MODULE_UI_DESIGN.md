# 模块界面设计

> **定位**：本文档是系统功能模块界面设计的单一权威源，涵盖党务管理模块和日历功能模块的界面布局、交互逻辑、视图切换设计。
> **受众**：[工程师]+[AI] —— 供前端开发决策参考。
> **视觉规范**：色彩、字体、间距等视觉规范见 [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md)，本文档不重复。

---

## 一、模块界面设计总览

### 设计原则

1. **模块化并列展示**：功能模块通过侧边栏 module-tab 并列切换，每个模块对应独立的 view-section，复用统一的切换逻辑层，避免新增二级导航包装层。
2. **数据安全优先于展示便利**：日历视图筛选优先级为 角色 > 场景 > 时间范围，先确定角色可见性，再缩小到场景，最后限定时间窗口。
3. **引用渲染而非复制**：展示官方制度文件时，AI 读取 `content/references/` 下的 [用户] 角色文件内容并渲染到只读展示区，源文件保持不可变，避免权限真空。
4. **渐进式演进**：MVP 阶段采用最小实现成本方案，当子模块数量增长或需求复杂化时再升级，避免过早过度设计。
5. **视图状态保持**：日历视图切换属高频操作，需保留选中日期、选中活动、显示月份等上下文状态，切换后自动定位至当前焦点。

### 与 DESIGN_SYSTEM.md 的关系

本文档仅定义模块层面的界面布局、交互逻辑、视图切换。色彩方案、字体规范、间距体系、卡片样式等视觉规范统一引用 [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md)，不在本文档重复。

### 模块定位

本文档涵盖两个功能模块的界面设计：

- **党务管理模块**：与党建工作台并列的独立功能板块，涵盖发展党员全流程追踪、补课制度跟踪、提案讨论、公邮查收提醒等子功能。
- **日历功能模块**：党建工作台的核心视图组件，涵盖月/周/日/列表多视图展示、文本溢出处理、活动数据存储、快速聚焦视图等设计。

角色权限与逻辑层面请参阅 [DATA_ARCHITECTURE.md](./DATA_ARCHITECTURE.md)（三级管理模式数据流）和 [COMMISSIONER_FRAMEWORK.md](../strategy/COMMISSIONER_FRAMEWORK.md)（支委系统设计）。日历视图范围限定（仅对参与者/组织者/书记/党小组组长展示，支委不展示日历）的已落地规则见 [SOP_WEB.md §B.4](../governance/SOP_WEB.md)。

## 二、党务管理模块界面设计

### 模块定位与功能边界

#### 模块定位

党务管理模块是与**党建工作台**（即党建工作）并列的独立功能板块。

#### 功能边界

**党建工作台负责（不纳入本模块）**：
- 活动推演排期（基于 SOP 场景的日期展开与任务实例化）
- 全场景工作日历（calendar 视图 + 聚焦视图）
- 模板与资产（文档模板库、会议记录模板）

**党务管理模块负责**：

| 子功能 | 说明 | 来源母本 |
|--------|------|---------|
| 发展党员全流程追踪 | 入党申请人 -> 积极分子 -> 发展对象 -> 预备党员 -> 正式党员，各阶段时间节点与材料完成状态 | 组织委员工作流程指南 |
| 补课制度跟踪 | 请假/缺勤人员补课安排、完成情况追踪、补课完成后在考勤记录中标注"已补" | 纪检委员工作流程指南 1.1 |
| 提案讨论 | GitHub Issue 风格开源讨论+书记处置权（双轨数据层：issues.json 权威源 + localStorage 草稿；双轴标签：scope 单选 + type 多选；权限：书记独占 8 项处置权，全员共享 7 项基础操作） | D-244 职能动作隐喻 + T105 实施 |
| 公邮查收提醒 | 每周查看支部公邮 1 次，汇总并转发思想汇报与发展党员材料至组织委员归档 | 纪检委员工作流程指南 1.1 |

#### 考勤与考察的核心区别（数据模型依据）

本模块的"补课制度跟踪"子功能依赖以下数据维度区分：

| 维度 | 考勤（0-1 变量，基础层） | 考察（工作量记录，进阶层） |
|------|--------------------------|--------------------------|
| **对象** | 党员、预备党员 | 深度参与者和组织者 |
| **适用** | 三会一课 | 所有支部工作 |
| **记录** | 出勤 / 请假 / 缺勤 | 组织 / 深度参与 |
| **方式** | 实时记录 | 实时记录 |
| **提交** | 宣传委员备案 | 组织委员建档（每月提交） |

补课逻辑：考勤记录中出现"请假"或"缺勤"状态时，自动触发补课任务；补课完成后，考勤记录回写为"已补"。此逻辑依赖考勤的 0-1 变量特性，不涉及考察的工作量维度。

#### 引用渲染机制

党务管理模块在展示 `content/references/` 下的制度文件（如党章、发展党员工作细则、纪律处分条例）时，遵循 [ROLE_CLASSIFICATION.md 引用渲染机制](../governance/ROLE_CLASSIFICATION.md)：

- AI 可读取 `content/references/` 下的 [用户] 角色文件内容
- 将内容渲染到 HTML 界面的只读展示区（如"制度文件"面板）
- 源文件保持不可变的 [用户] 角色状态，AI 不可修改
- 渲染缓存与源文件保持同步（文件变更时自动更新展示）

此机制填补了"AI 不可访问 [用户]"和"界面需要展示官方内容"之间的权限真空。

### 侧边栏并列展示方案

#### 现状分析

当前侧边栏包含 3 个 module-tab：

```
┌─────────────────┐
│ [党建工作台]     │  ← module-tab active (data-module="calendar")
│ [参考指南]       │  ← module-tab (data-module="reference")
│ [模板与资产]     │  ← module-tab (data-module="templates")
├─────────────────┤
│ ─── 分隔线 ───  │
├─────────────────┤
│ 参与视图        │
│ 管理视图        │
│   ...            │
└─────────────────┘
```

所有 module-tab 均对应独立的 view-section，通过 CSS `hidden` 类切换显示。

#### 三种方案

**方案 A：module-tab 扩展（新增第 4 个 module-tab）**

在现有 3 个 module-tab 下方增加第 4 个"党务管理"module-tab：

```
┌─────────────────┐
│ [党建工作台]     │
│ [参考指南]       │
│ [模板与资产]     │
│ [党务管理]       │  ← 新增
├─────────────────┤
│ ─── 分隔线 ───  │
└─────────────────┘
```

**优点**：与现有导航模式完全一致，复用 module-tab 的切换逻辑，实现成本最低。
**缺点**：4 个 tab 在收起态侧边栏中可能显得拥挤；"党务管理"与上方 3 个 tab 的语义层级不完全对等（上方 3 个是"功能视角"，党务管理是"领域视角"）。

**方案 B：角色卡片区域下方独立入口**——不选：入口位置偏下可见性不足，与 module-tab 视觉层级不一致，用户可能忽略。

**方案 C：侧边栏顶部二级切换**——不选：实现成本最高，需新增二级 tab 切换逻辑与一级包装层，当前阶段过度设计；留待未来党务管理子模块 > 3 且需要独立子导航时再升级。

#### 推荐方案

**推荐方案 A**，理由如下：

1. **实现成本最低**：扩展一个 module-tab + 一个 view-section 即可完成基本框架，与现有三段式导航完全一致，无需新增切换逻辑层
2. **CLAUDE.md E1 定位匹配**：E1 的描述为"侧边栏与党建工作台并列"，方案 A 的新增 tab 直接体现了"并列"语义
3. **后续可渐进升级**：当党务管理模块子功能增至 3 个以上需要独立导航时，可平滑升级为方案 C；方案 A 是方案 C 的 MVP 阶段
4. **不与现有角色卡片冲突**：党务管理模块不需要角色切换（党务管理面向支委，权限由登录态决定），因此 4 个 module-tab 下方仍保留现有的角色视图体系

**渐进路线**：方案 A（当前 E1）--> 方案 C（未来当党务管理子模块 > 3 且需要独立子导航时）

## 三、日历功能界面设计

### 日历多视图展示逻辑

#### 视图切换架构设计

需要新增日历视图状态字段：

```javascript
// 在 appState 中新增
calendarView: 'month',  // 'month' | 'week' | 'day' | 'list'
// 替代当前 viewMode 的部分语义：
//   'list' 原意为「点击日期后展示该日 Activity 列表」→ 更名为 inspectorMode
//   'detail' 保持不变，仍用于检查器的详情视图
```

#### 月视图（month）

- CSS Grid 7 列布局
- 每个单元格显示：日期数字 + 最多 3 个任务标签 + "+N 项任务"折叠
- 单元格高度自适应，桌面端与移动端的具体高度值见 DESIGN_SYSTEM.md
- 月视图下角色筛选逻辑沿用现有方案：根据 `viewType`（`participant` / `manager`）渲染不同的单元格内容

#### 周视图（week）

- 7 列布局（周一到周日），每列宽度均分
- 列高度扩展至父容器可用高度，提供更大的任务展示空间
- 每列顶部标注日期和星期，下方按时间顺序（由 `timeOffset` 字段驱动）排列当日任务
- 当前周高亮显示，可通过左右箭头切换至上一周/下一周
- 日期头显示完整日期格式（如"5月12日 周一"），点击日期头可切换至日视图
- 任务展示上限放宽至 8 个，超出折叠

#### 日视图（day）

- 单列全高布局，左侧时间轴（可选：按小时刻度），右侧任务卡片流
- 任务卡片按 `timeOffset` 排序，标注具体时间锚点（如"T-7 天"、"T=0 活动日"、"T+3 天"）
- 每个任务卡片展示完整信息：标题、执行角色、督办人、状态
- 适合重度管理场景：党支书/支委需要审视单日活动全貌

#### 列表视图（list）

- 放弃日历网格，改为扁平列表
- 排序规则：日期降序（最近的在前），同日期内按 `timeOffset` 升序
- 每行展示：日期、活动名称、关联任务数、状态标签
- 支持关键词搜索过滤（前端内存过滤，不涉及后端）
- 适合快速浏览和移动端场景

#### 各视图下的数据筛选规则

| 筛选维度 | 月视图 | 周视图 | 日视图 | 列表视图 |
|---------|--------|--------|--------|---------|
| 按角色 | 单元格内任务过滤 | 同月视图 | 同月视图 | 全局任务过滤 |
| 按场景 | 活动级过滤（仅显示匹配 `scenarioId` 的活动） | 同月视图 | 同月视图 | 同月视图 |
| 按时间范围 | 当月活动 | 当周活动 | 当日活动 | 全部活动（可选日期范围过滤） |
| 按归档状态 | 排除已归档 | 排除已归档 | 排除已归档 | 排除已归档（归档库独立入口） |

**筛选优先级**：角色 > 场景 > 时间范围。即先确定角色可见性，再缩小到场景，最后限定时间窗口。这是为了确保数据安全性优先于展示便利性。

#### 视图切换时的状态保持策略

视图切换是一个高频操作，状态保持至关重要：

1. **保留 `selectedDate`**：从月视图切换到周视图时，保持当前选中的日期不变，周视图自动定位到包含该日期的周
2. **保留 `selectedActivityId`**：切换到日视图时，若此前在检查器面板选中了某个活动，日视图应高亮该活动的任务卡片
3. **保留 `displayMonth`**：月视图和周视图共享此字段，确保前后一致
4. **重置滚动位置**：视图切换后滚动到当前日期/当前周所在位置
5. **URL Hash 同步（可选增强）**：将 `calendarView` + `displayMonth` + `selectedDate` 写入 URL hash，实现浏览器前进/后退支持。格式示例：`#calendar/month/2026-05/2026-05-02`

### 文本溢出处理策略

#### 截断规则优化方案

- **月视图**：活动标题单行截断（中文约 10-12 字，CSS `text-overflow: ellipsis`）；任务标签单行截断（中文约 8-10 字）；日期数字不截断。
- **周视图**：任务标题双行截断（中文约 16-20 字，`-webkit-line-clamp: 2`）；角色标签单行不截断。
- **日视图**：空间充裕不截断，任务描述超 3 行提供"展开/收起"切换。
- **列表视图**：单行截断，字符数约 20 字。

#### Tooltip 实现方案

推荐混合策略：参与者视图保持 `title` 属性（轻量无负担）；管理视图月视图单元格 hover 时显示精简 JS tooltip（含任务完整标题、执行人、状态）；日视图/周视图不需 tooltip（信息已完整展示）；移动端长按触发（500ms 延迟）。

#### "+N more" 折叠显示策略

动态阈值计算（基于单元格高度，每项任务标签约 24px，日期头约 20px）；点击 "+N" 标签原位展开微型弹出列表（非 Modal），支持点击选中联动检查器面板，点击日历其他区域或按 Escape 关闭。

#### 移动端适配

桌面端（>=1024px）月视图单元格展示 4-5 条任务，任务标题截断中文 12 字；平板（768-1023px）展示 3-4 条，中文 10 字；手机（<768px）展示 2-3 条，中文 8 字。移动端月视图单元格点击后原地展开全宽任务列表卡片（不展开右侧面板）。具体单元格高度值见 DESIGN_SYSTEM.md。

### 活动数据存储结构

#### 数据存储方案

**推荐方案 A：纯前端 localStorage（当前方案）**——实现难度低，数据容量约 5-10MB 足够存储数百条活动和数千条任务，适用于 MVP/Demo/单人使用阶段。当前待启用：将 `SANDBOX_MODE` 改为 `false` 并取消注释持久化恢复代码即可获得跨刷新持久化能力。

**方案 B（IndexedDB）**：不选——当前数据量未达阈值，待活动总数超 500 条或需存储二进制附件时再迁移。

**方案 C（后端 API）**：不选——需后端+认证+同步协议，实现成本高，留待 Phase 2（Supabase Backend）上线。迁移路径：`localStorage → Supabase + localStorage(本地缓存) → Supabase + IndexedDB(离线缓存)`。

#### 数据持久化与备份策略

**当前过渡方案（1-2 周内）**：
1. 将 `SANDBOX_MODE` 改为 `false`，启用 localStorage 持久化
2. 保持 Schema 版本校验，版本不匹配时提示用户而非静默丢弃
3. 在设置面板（待新建）中添加"导出数据"按钮，将全部数据序列化为 JSON 文件下载

**中期方案（Phase 2 上线前）**：
1. **双写机制**：数据同时写入 localStorage（本地缓存）和 Supabase（远程）
2. **冲突解决**：以 `createdAt` 时间戳为准，后写入的覆盖先写入的
3. **离线恢复**：Supabase 不可用时回退到 localStorage，上线后自动同步差异数据

**长期方案（Phase 3 及以后）**：
1. **增量同步**：基于 `updatedAt` 字段做增量拉取，减少全量传输
2. **定期快照**：每 100 次写操作生成一次 localStorage 快照（JSON 备份），避免单点损坏
3. **审计日志**：`.ctx/logs/` 目录记录所有写操作的时间、操作人、操作类型

### 快速聚焦视图设计

#### 聚焦视图交互重构

##### 点击日历日期后的展开/收缩交互

**方案 1：原位展开（推荐）**

点击日历日期单元格后，该单元格在日历网格中**向下展开**，推开下方行，形成一个宽幅聚焦面板。面板内容包含：
- 该日期的活动标题（大字显示）
- 该日期的任务列表（按时间和角色分组）
- 快速操作按钮（查看全部任务、切换管理角色）
- 关闭按钮（点击后收缩回普通单元格）

优势：日历上下文不丢失，用户可以同时看到聚焦日期和周边日期
劣势：布局计算复杂，需要精确控制 Grid 行高变化

**方案 2：弹出面板**

点击日期单元格后，在原位弹出一个浮层面板，类似右键菜单。面板内容同方案 1。

优势：实现简单，不干扰日历布局
劣势：可能遮挡其他日期，移动端弹出位置需要动态调整

**推荐混合策略**：
- 桌面端（>= 768px）：原位展开（方案 1），因为屏幕够宽
- 移动端（< 768px）：弹出面板（方案 2），因为屏幕窄，原位展开不可行

##### 聚焦状态下活动列表的排序规则

1. **默认排序**：按 `timeOffset` 升序（T-14 → T-7 → T=0 → T+3），逻辑最直观
2. **按状态排序**（可选切换）：未完成在前，已完成在后
3. **按角色排序**（可选切换）：按 ROLE_ORDER 排列（leader → commissioner → organizer → deep → secretary）
4. **按优先级排序**（可选切换）：urgent → normal → low

排序规则通过聚焦面板顶部的 Tab 切换，默认为时间排序。

##### 从聚焦视图返回日历的过渡动画

1. **关闭按钮 / 点击日历其他区域**：聚焦面板向上收缩，height 从展开值过渡到 0，opacity 淡出（300ms）
2. **点击日历其他日期**：当前聚焦面板收缩，新日期展开（交替动画，250ms）
3. **按 Escape**：同关闭按钮行为
4. **CSS 实现**：使用 `max-height` 过渡动画，参考现有展开/收起组件的实现模式
