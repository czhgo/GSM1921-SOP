## 二、文件流分类原则

把文件流按「用途与生命周期」分为两类，各归其所：

| 维度 | 过程性文件 | 审查文件 + 辅助照片 |
|------|-----------|-------------------|
| 典型形态 | 草稿、待批复的流转材料、过程汇报 | word/pdf 正式文件、活动照片 |
| 用途 | 流转、批复、修改往返 | 展示覆盖面、体现成效、迎接审查 |
| 时效 | 短（批复完成即过期） | 长（长期可查可调） |
| 最佳场所 | 微信（随手、即时、对方在线） | 系统（沉淀、检索、展示） |
| 系统职责 | 留痕闭环（已发/已收/已批复，见 §四） | 承载浏览（宣传墙 + 档案，见 §三） |

**判断标准**：文件是「流转物」还是「成果物」——流转物归微信（系统留痕），成果物归系统（承载浏览）。

## 三、浏览功能设计：宣传墙 + 档案分层

### 3.1 形态

- **宣传墙（展示层）**：支部工作覆盖与成效的「门面」——活动照片墙 + 成果入口（新闻稿、审查文件列表），供内部浏览与迎检展示。
- **档案库（沉淀层）**：正式文件按归档管理（宣传委员「档案归档」板块承接），可检索、可筛选、可调取。
- **入口互通**：宣传墙展示的成果可一键进入档案库对应条目；档案归档时可选「上宣传墙」。

### 3.2 权限

- **内部全员**：支部成员默认可见宣传墙与档案。
- **迎检外链**：书记可生成临时查看链接 / 导出归档包，面向上级审查，链接可设置有效期。

### 3.3 与宣传墙初衷的呼应

2026-08-11 决策：审查文件与辅助照片「和设计【宣传墙】的初衷是一致的」——用照片证明覆盖面、用正式文件支撑成效。宣传墙不是装饰，是支部工作成果的可信呈现。

## 四、过程性汇报的集成方案

### 4.1 迁移复杂度：从微信群聊到网页，是行为范式的转变

2026-08-11 决策：「从微信群聊到网页的转变，是一个很复杂的事情！！」——这比「登记成本」更根本：**微信群聊是即时通讯范式（随手说、对方在线、零门槛），网页是结构化工作台范式（留痕、可追溯、需打开）**。使用者已习惯前者，迁移意味着行为习惯改变——这正是 H10 最小三成本中**适应学习成本**的最高门槛。本方案的一切设计（§4.2-4.6）都是在压低这道迁移门槛，而不是假装它不存在。

### 4.2 致命问题：任何「登记」都有操作成本

网页系统读不到微信消息（技术硬约束）。「一键登记」只是把成本压到最低，不是消除——批复人在微信批完后还要切到系统登记，成本高、动机无，必然无人使用（死功能）。迁移复杂度（§4.1）决定了：**凡是要求使用者「离开微信做额外动作」的设计，都要以「使用者是否有动机做」为第一验收标准**。

### 4.3 成本翻转：受益者登记

登记成本由**受益方**承担而非**负担方**：

| 谁登记 | 成本 | 动机 |
|--------|------|------|
| 批复人（接收方） | 最高（刚批完还要切系统） | 无（帮他人留痕） |
| 发送方 | 最低（本就因留底而在系统发起） | 有（登记即自己的台账完整） |

### 4.4 终极形态：小程序原生承接

```
发送方（网页/小程序）发起过程性汇报
  → 小程序推送微信订阅消息给批复人（用户授权，非打扰式群发）
  → 批复人在微信点开消息卡片 → 直达小程序批复页
  → 点「同意/需修改/退回」→ 数据直接写入共享数据层
  → 网页台账实时更新：谁 / 何时 / 批复了什么
```

批复人全程不离开微信、不打开网页、不做任何「登记」——点一下就是批复，批复就是数据。**零操作成本**。

### 4.5 过渡形态（小程序落地前）：发送方登记制

- 发送方在系统发起汇报（为了留底：可追溯、与活动/任务关联、责任清晰）
- 材料微信转给对方 → 对方微信批复
- 发送方回系统把自己的汇报更新为「对方已批复：同意/需修改/退回」（+可选理由）
- **价值前提**：系统内「留底」对发送方有真实价值（台账完整性），登记才成立

### 4.6 两端分工（「小程序有，网页也有」）

| 能力 | 小程序 | 网页 |
|------|--------|------|
| 批复入口 | 微信内原生批复（零成本） | 过渡期发送方登记制 |
| 台账沉淀 | 只读查看 | 发起 + 追踪 + 审计 + 浏览 |
| 文件流 | 过程性文件微信内流转 | 审查文件/照片 → 宣传墙 + 档案 |

## 五、小程序路径评估与原生承接机制（承接 T-230）

### 5.1 三条路径（T-230 评估结论）

| 路径 | 改动 | 体验 | 前置条件 | 结论 |
|------|------|------|---------|------|
| A WebView 套壳 | 极小（现有网页套壳） | 一般 | 企业主体 + 域名备案 | 短期可行 |
| B Taro 跨端重写 | 20+ 页面全重写 | 最佳 | 后端上线 + 数据层切 api | 中期主选 |
| C 原生小程序 | 双份维护 | 最佳 | — | 不推荐 |

### 5.2 原生承接机制（过程性批复零成本的关键）

- **微信订阅消息**：批复人首次在小程序内授权订阅 → 后续发起汇报可推「有新的过程性汇报待批复」→ 点开直达批复页。一次性订阅需每次授权，长期订阅受类目限制（落地时核实类目权限）。
- **共享数据层**：网页与小程序共用同一后端（规划中的 Node Express + better-sqlite3 / 微信云开发），「标记已发送」演进为「发送到对方微信」，「确认收到」保持同构（原则 13 记录模型可低成本迁移）。

### 5.3 前置条件（T-230 已列）

1. 企业主体注册 + 服务类目
2. 后端上线 + HTTPS + ICP 备案
3. 数据层切 api 模式（DataAdapter 双模式已就绪）

### 5.4 路线图

- **短期（现状）**：网页端发送方登记制 + 宣传墙/档案浏览功能 + 外发确认闭环（原则 13）
- **中期**：后端部署 + 数据层切 api → WebView 套壳快速上线验证
- **长期**：Taro 跨端重写 → 订阅消息原生批复 → 微信内全流程协同

## 六、与现有系统的衔接

- **原则 10 答复回路**：待办 tab「待答复」收件箱是网页内批复形态；过程性汇报的微信批复与其互补——高频短批复走微信（零成本），重要答复在网页留档（可审计）。
- **原则 13 外发确认闭环**：external-dispatch.js 已实现「已发/已收」；过程性汇报扩展「已批复」状态，模型同构、可迁移。
- **宣传委员「档案归档」**：档案库浏览功能以现有归档板块为沉淀底座。
