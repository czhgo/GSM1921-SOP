# 真实工作集成设计：从"线上打卡"到"线下+微信真实工作集成平台"

## 1. 背景与问题

### 1.1 书记反思（2026-08-02）

> 现在一定有大量工作，只要点击"完成"就完成了，声称解决了，就解决了。除非是阅读通知，纯 nudge 性质多加了一道防线。现在给我的感觉，似乎这个网页完全是一个线上的打卡软件。如果是这样，这个系统将没有人用！！我们要做的是线下的工作、微信的工作集成到里面！！

### 1.2 系统现状诊断

* **打卡化**：待办"完成"即 `TodoStore.complete(id)` 改一个状态字段，无需任何真实产物支撑。工作"被声明完成"而非"被完成"。

* **虚拟闭环**：系统内通知发布→待办派生→点击完成，形成网页内自洽的虚拟闭环，与线下/微信真实工作域脱节。

* **证据已在 issue 库**：`docs/data/issues.json` 两条真实需求——

  * "党小组会签到流程建议改为扫码"（希望数据直接回传系统）

  * "主题党日参访报名统计靠微信群接龙容易漏人"（期望系统支持活动报名登记）

### 1.3 本质问题（AI 与人类意图的偏差）

| AI 假设           | 人类意图                                                                    |
| --------------- | ----------------------------------------------------------------------- |
| 待办点击完成 = 任务闭环   | 真实工作发生在**线下**（会议/谈话/活动执行）与**微信**（群通知/接龙/资料流转），网页应承载真实工作的**记录、产物、流转、台账** |
| 系统内的虚拟操作 = 工作本身 | 系统是真实工作的集成层与记录层，不是工作本身的替代层                                              |

**核心原则**：网页不再"虚拟完成"工作，而是让线下/微信的真实工作"有据可查、有材料可出、有流程可跟、有台账可归"。

## 2. 设计原则

1. **真实产物原则**：产出类工作必须附真实产物（结构化表单/附件）才能闭环；操作类工作只需完成系统内操作。
2. **填空题优先原则**：表单字段以单选/多选/日期/数字/人员选择为主，开放文本框仅限"备注/说明"。做填空题，不做简答题。
3. **最小填写负担原则**：批量录入、模板导入、上次记录复用，降低高频操作（如考勤）的人工负荷。
4. **同一套数据集原则**：所有角色写入同一数据库，按角色权限区分读写范围，杜绝多份 Excel/微信来回传。
5. **阅读确认保留原则**：阅读通知类待办保留"确认环节"（防"点了没看"导致阅读率下降），但**不要求产物**——它属于操作类。
6. **服务器优先原则**：以有服务器（目标对接北京大学计算中心）为设计前提，Node 一体化架构。

## 3. 总体架构

### 3.1 架构选型（书记已确认）

```
┌─────────────────────────────────────────────┐
│  前端：现有 14 静态页面 + ESM 模块（保留）      │
│  新增 fetch 数据层（替代 localStorage 直读）     │
└──────────────┬──────────────────────────────┘
               │ HTTP API（JSON）
┌──────────────▼──────────────────────────────┐
│  后端：Node.js 一体化                         │
│  Express（静态托管 + API 路由）                │
│  SQLite（better-sqlite3 单文件数据库）         │
│  uploads/（附件文件目录）                      │
└─────────────────────────────────────────────┘
```

* **技术栈**：Node.js + Express + better-sqlite3 + multer（附件上传）

* **部署**：单 Node 进程，`node server.js`；静态页与 API 同端口

* **目标环境**：北京大学计算中心（校内 Linux 虚拟机）；数据不出校

* **前端改动**：新增 API 客户端模块，各 service（todo/notice/activity 等）的读写底层从 localStorage 切换为 API；localStorage 仅保留登录会话与离线缓存

* **本轮不做**：微信回流（扫码签到/接龙回传）留待下一轮

### 3.2 数据模型（SQLite）

```
表名                    说明
users / members         人员与角色（迁移自 mock/people.js）
activities              活动（迁移自 mock/activities.js）
taskforces              专班
notices                 通知
todos                   待办（含 sourceType/sourceId/actionType）
auth_records            赋权审计
table_defs              共享表格模板定义（字段结构）
table_rows              共享表格数据行
table_row_roles         行级权限/分工（谁能看、谁能填）
artifacts               待办产物记录（表单结果 + 附件引用）
attachments             附件元数据（文件名/路径/上传者/上传时间）
```

* 迁移策略：首次启动时从内置 seed（现有 mock 数据）初始化 SQLite；localStorage 中已有运行数据优先导入。

* 附件存储：上传文件落盘 `uploads/`，数据库仅存元数据；静态托管 `/uploads/*` 受登录校验保护。

## 4. 共享表格引擎（核心新能力）

### 4.1 概念

"共享表格" = 一张由**模板定义结构**、由**多人按权限协作填写**、**写入同一数据集**的结构化表格。首批落地：考勤记录表、宣传归档表。

### 4.2 模板定义（table\_defs）

```
table_def {
  id, name, description,
  columns: [ column { key, label, type, required, editableRoles[], visibleRoles[], options? } ],
  rowPermission: { viewRoles[], editRoles[], adminRoles[] },
  createdBy, createdAt
}
```

**字段类型（填空题优先）**：

| type          | 输入形态              | 示例            |
| ------------- | ----------------- | ------------- |
| select        | 单选下拉              | 考勤状态：出席/请假/缺席 |
| multi\_select | 多选                | 请假原因：病假/事假/其他 |
| date          | 日期选择              | 会议日期          |
| number        | 数字                | 学时数           |
| person        | 人员选择（从 members 选） | 应到人员          |
| short\_text   | 短文本（≤50字）         | 姓名/活动简称       |
| text          | 长文本（仅"备注/说明"列）    | 请假说明          |
| attachment    | 附件上传              | 会议照片/签到表      |

### 4.3 权限模型

* **行级权限**：谁能查看该行（如考勤表行按"应到人员所属党小组"限定可见）

* **字段级权限**：谁能编辑该列（如考勤表"考勤状态"仅纪检委员可改，成员只读")

* **审核角色**：adminRoles 可审核/锁定整表

* **登录态校验**：所有 API 校验会话角色，与现有 `AuthStore` 权限矩阵（`ROLE_PERMISSIONS`）对齐

### 4.4 批量写入（回应纪检负荷）

考勤场景：一个活动应到 30+ 人，逐条点选不现实。批量能力：

1. **整列批量勾选**：按活动生成"应到人员行"，纪检整列一键勾选默认值（如全部"出席"），再改个别差异行。
2. **上次记录复用**：同组人员、上次考勤结果一键载入，仅调整变更。
3. **粘贴导入**：从微信接龙/Excel 复制的文本（如"张三 出席，李四 请假"）粘贴到输入框，智能解析为多行。
4. **CSV 导出**：整表/过滤结果导出 CSV 下载（宣传归档、考勤统计共用）。

### 4.5 审核与归档

* 表格数据可"提交审核"→ 审核角色查看 → "通过/打回"

* 通过后整表锁定（只读），数据进入台账视图，供书记概况实时引用

## 5. 首批两张共享表格

### 5.1 考勤记录表

**用途**：三会一课/活动出勤登记，纪检委员维护，书记/组长可查看，统计自动汇总。

| 列    | 类型                    | 填写人 | 说明            |
| ---- | --------------------- | --- | ------------- |
| 活动名称 | select（关联 activities） | 纪检  | 或"活动+日期"联动生成行 |
| 日期   | date                  | 纪检  | <br />        |
| 应到人员 | person（批量生成）          | 系统  | 按活动参与名单生成     |
| 考勤状态 | select：出席/请假/缺席       | 纪检  | 整列批量勾选        |
| 请假原因 | select：病假/事假/其他       | 纪检  | 状态=请假时必填      |
| 缺席说明 | short\_text           | 纪检  | 状态=缺席时必填      |
| 备注   | text                  | 纪检  | 可选            |

**批量路径**：`选择活动 → 系统生成全部应到行 → 整列默认"出席" → 勾改差异 → 提交`。5 分钟完成 30 人考勤。

**汇总联动**：书记全局概况"考勤"维度、纪检考勤管理 Tab 直接读本表聚合结果，替换现有 localStorage 手工考勤。

### 5.2 宣传归档表

**用途**：活动照片/推文/新闻稿逐项登记，宣传委员录入，书记审阅。

| 列      | 类型                    | 填写人 | 说明      |
| ------ | --------------------- | --- | ------- |
| 活动名称   | select（关联 activities） | 宣传  | <br />  |
| 材料类型   | select：照片/推文/新闻稿/视频   | 宣传  | <br />  |
| 材料标题   | short\_text           | 宣传  | <br />  |
| 上传时间   | date                  | 系统  | 默认今天    |
| 上传人    | person                | 系统  | 默认当前用户  |
| 附件     | attachment            | 宣传  | 照片/文档上传 |
| 外部链接   | short\_text           | 宣传  | 如已发推文链接 |
| 书记审阅状态 | select：待审阅/已通过/需补充    | 书记  | 书记可改    |
| 备注     | text                  | 任意  | 可选      |

## 6. 产物闭环机制

### 6.1 原则（书记已确认）

* **产出类待办强制产物**：会议记录、考察谈话、复盘提交、材料收交等"要产出东西"的待办，完成前必须提交产物（结构化表单 + 可选附件）。

* **操作类待办不强制产物**：赋权、归档、审核、阅读确认等"系统内操作"类，完成系统内操作即闭环。

### 6.2 机制

1. **待办绑定产物模板**：派生/创建待办时声明 `artifactTemplateId`（引用 table\_def 或内置表单模板）。
2. **完成按钮状态**：

   * 产出类：产物未提交 → "完成"按钮禁用，显示"需先填写产物"；

   * 操作类：按钮可用，点击完成（或操作成功即自动完成）。
3. **产物形态**：结构化表单（填空题优先）+ 附件上传；产物写入 `artifacts` 表，附件写入 `uploads/`。
4. **审核流（按模板配置）**：产物模板声明 `requiresReview` 时，产物提交后进入"待审核"→ 审核角色查看 → 通过后待办才置 `completed`；未声明则提交产物即完成。
5. **产物可追溯**：待办详情展示已提交产物（表单结果 + 附件列表 + 提交人/时间），不可被"点完成"绕过。

### 6.3 阅读通知待办（书记已确认保留）

* **保留"阅读确认"环节**：防"点了没看"导致阅读率下降。

* 归类为**操作类**：不要求产物；点开通知 → 确认已读 → 自动完成（或确认浮窗内点完成）。

* 维持现有 `deriveFromNotices` 派生机制不变，但确认动作一次完成，不额外增加"再点一次完成"以外的步骤。

### 6.4 待办分类映射（落地示例）

| 待办示例      | 类别  | 产物要求         |
| --------- | --- | ------------ |
| 撰写/录入会议记录 | 产出类 | 强制：会议记录表单    |
| 考察谈话登记    | 产出类 | 强制：谈话记录表单    |
| 提交复盘      | 产出类 | 强制：复盘表单      |
| 材料收交      | 产出类 | 强制：附件        |
| 去赋权       | 操作类 | 无（完成赋权操作即闭环） |
| 去归档       | 操作类 | 无            |
| 去审核       | 操作类 | 无            |
| 阅读通知      | 操作类 | 无（确认已读即闭环）   |

## 7. 材料表单生成器

### 7.1 定位

让线下/微信工作"拿来即用"的产出：系统按数据生成可直接复制/下载的材料。

### 7.2 首批能力

1. **考勤统计 CSV 导出**：按活动/月份导出考勤汇总 CSV（纪检、宣传归档共用）。
2. **会议记录模板导出**：填空式会议记录模板（结构化字段预览 + 下载），线下开会时可携带。
3. **活动通知文案生成**：基于活动信息（名称/时间/地点/要求）一键生成可转发微信的通知文案，复制即用。
4. **模板下载**：共享表格的 CSV 模板（含列头与选项说明），供粘贴导入前参照。

### 7.3 与共享表格的关系

材料生成器 = 共享表格引擎的"导出/模板"能力 + 通知文案生成器，不单独建模块。

## 8. 真实工作台账

* **定位**：所有共享表格数据 + 产物 + 活动/专班记录的归档视图，是"线下+微信真实工作"的唯一台账。

* **组织方式**：按活动/专班 → 关联表格数据（考勤/宣传归档/会议记录）→ 产物 → 材料，形成完整档案。

* **现状衔接**：替换现有"归档库"的静态展示，读 SQLite 实时数据；书记概况各维度（考勤/考察/活动/宣传）改读台账聚合。

## 9. 分阶段实施

| 阶段               | 内容                                                               | 里程碑                            |
| ---------------- | ---------------------------------------------------------------- | ------------------------------ |
| **P1 后端基建**      | Node/Express/SQLite 骨架；静态托管；登录会话 API；数据迁移（mock → SQLite）；附件上传基础  | `node server.js` 起服务，14 页可登录访问 |
| **P2 共享表格引擎**    | table\_defs/table\_rows/权限/批量录入/审核/导出；考勤记录表 + 宣传归档表落地；书记概况联动考勤汇总 | 两张表可协作填写、批量录入、书记审阅             |
| **P3 产物闭环**      | artifacts + 待办绑定产物模板 + 完成按钮状态机 + 审核流；产出类强制、操作类不强制；阅读确认保留         | 产出类待办无法空点完成                    |
| **P4 材料生成 + 台账** | CSV 导出/模板下载/通知文案生成；台账归档视图整合                                      | 材料可导出、台账完整                     |

## 10. 非目标（本轮不做）

* 微信数据回流（扫码签到、接龙报名回传）——留待下一轮（P5+）

* 自由格式文档协作（简答题式长文档）——坚持"填空题优先"

* 实时多人同步编辑（协同光标等）——本轮为"按权限分工填写 + 提交审核"，非实时协同

* 移动端 App / 小程序

## 11. 风险与对策

| 风险         | 对策                                                      |
| ---------- | ------------------------------------------------------- |
| 数据迁移丢失     | 迁移前 localStorage 导出备份；迁移日志可追溯；保留 seed 兜底                |
| 无全栈经验维护难   | 单语言栈 + SQLite 零配置 + 单一进程；API 契约文档化（OpenAPI 轻量版）         |
| 附件存储膨胀     | 上传大小/类型限制；台账归档后可清理；容量告警                                 |
| 浏览器会话安全    | 服务端会话（httpOnly cookie）+ 现有角色权限矩阵双重校验；/uploads 静态访问受登录保护 |
| 真实组织规模考勤负荷 | 整列批量勾选 + 上次复用 + 粘贴导入 + CSV 模板，见 §4.4                    |

## 12. 已确认决策（2026-08-02 书记确认）

1. **考勤"应到人员名单"来源**：系统自动生成——纪检选择活动后，按活动参与/报名名单自动生成全部应到人员行，再整列批量勾选；允许纪检微调增删个别人员（"自动+可微调"）。
2. **附件类型与大小上限**：图片 5MB/个、文档 10MB/个；支持 jpg/png/pdf/docx/xlsx。
3. **通知文案生成**：纳入 P4 首批——选活动一键生成可转发微信的通知文案，与导出能力并行。
