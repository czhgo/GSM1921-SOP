## 第一篇：业务认知与管理哲学（【道】）

> 【道】层回答的是"为什么这样做"——是认知框架、权责逻辑与架构哲学的总纲。

### §1.1 党建主旨的"双域"认知

**[双域认知]** — 场景路由的第一判断键

党建工作的本质，不是流水线式的任务堆砌，而是在**两个正交维度**上的结构化运营：

| 域 | 英文标识 | 核心命题 |
|---|---|---|
| **活动建设域** | `activity` | 以活动为载体，驱动党员参与感与组织凝聚力 |
| **组织建设域** | `organization` | 以制度为骨架，驱动党支部的合规性与可持续性 |

**操作规程**：每一项工作任务，必须首先完成域归属判断（`domain routing`），再进行权责分配与产出物设计。混淆两域是任务失焦和职责模糊的根本原因。

> 工程验证：`常见工作场景快速指南.md` v3.0 以 `# 一、活动建设` 与 `# 二、组织建设` 作为一级标题，将域归属编码进文档结构本身——这是双域认知从哲学落地为架构的标志性节点。

---

### §1.2 条块体系与分工逻辑

**[条块逻辑]** — 高决策权场景的不可委托原则

党支部组织架构遵循"条条（功能线）× 块块（党小组）"矩阵模型：

- **条条**（commissioner roles）：组织委员、宣传委员、纪检委员，各自持有专属职能域的执行权。
- **块块**（host group）：党小组组长，持有所辖党员的信息触达权与组织权。
- **书记**（secretary）：党支部法定第一责任人，持有若干**不可委托**的高决策权场景。

**核心铁律**：在以下场景中，党支书的角色不可被替代或委托，**委托即失效**：

1. **党课**（party-lecture）：书记是党课的法定主讲或审定人，任何委托均导致制度合规性失效。
2. **意见反馈处理**（feedback-handling）：书记是唯一的意见接收与处置决策者，委托会造成制度真空。

> 工程验证：`sopData.js` 中 `party-lecture` 与 `feedback-handling` 两个场景的任务节点，角色字段已硬编码为 `secretary`，`timeOffset` 精确锚定，杜绝了模糊委托的技术可能性。

### §1.3 减负与奥卡姆剃刀原则

**[减负原则]** — 产出物的三重验证门控

组织运营中存在大量"伪需求"——看似有价值、实则增加负担而不产生实质效益的产出物。奥卡姆剃刀要求：**如无必要，勿增实体**。

每一项产出物，必须通过以下三重门控检验，**任一不通过即视为伪需求，直接删除**：

| 验证维度 | 判断问题 | 失败后果 |
|---|---|---|
| **硬性要求** | 上级党组织是否有明文规定要求此产出？ | 无制度依据，伪需求 |
| **无重叠** | 是否已有其他产出物覆盖此功能？ | 冗余产出，直接合并或删除 |
| **防真空** | 若删除此产出，是否会造成工作断点或归档缺失？ | 结构性需求，保留 |

**典型案例**：
- 微信备忘录 → 未通过"硬性要求"（无制度依据）→ **删除**，改为直接与组织者对接
- 多份宣传截图 → 未通过"无重叠"（宣传推文+配图已覆盖）→ **合并**

> 工程验证：Burden Reduction 战役（Phase 3.1 ~ 4）系统性删除了跨越多个 SOP 文档的伪需求产出物，`sopData.js` 同步清除了 `branch-discussion` 场景。

### §1.4 双轨制隔离架构

**[双轨制架构]** — 人类阅读面板与 AI 数据面板的物理隔离

本系统采用严格的双轨制架构，两轨之间**物理隔离，禁止互相污染**：

| 轨道 | 路径 | 受众 | 内容边界 |
|---|---|---|---|
| **人类阅读面板** | `content/` | 支委成员、换届接班人 | 管理哲学、实践经验、制度解读 |
| **AI 数据面板** | `.ctx/` | AI 代理（Copilot） | 上下文规则、场景脚本、执行日志、系统快照 |

**污染的两种模式及后果**：

1. **人类内容混入 AI 面板**：导致 AI 代理在错误的叙事框架下产生"AI 幻觉"，输出偏离制度真相的指令。
2. **AI 内容混入人类面板**：导致可读性崩溃，制度文档被技术噪声污染，"制度失真"。

> 操作规程：新增文档时，首先判断受众——面向人类则落入 `content/`，面向 AI 则落入 `.ctx/`，严禁混放。本文件即双轨制的典型执行样本：内容纯粹是人类可读的管理哲学，无任何 AI 指令。

### §2.1 UI 设计的业务隐喻

**[UI隐喻]** + **[UI隐喻-视觉投影]** — 前端是后端业务规则的像素级投影

**核心认知**：前端 UI 的每一个控件，都不是独立的视觉元素，而是后端业务规则的**视觉投影**。因此：

> **UI 重构即业务重构**。任何 UI 层的修改，必须被视为一次业务规则变更，而非样式调整。

**双重推论**：

**推论一：字段增删三层同步律**（[UI隐喻]）  
UI 字段的增加或删除，必须同步处理以下三层，缺一不可，否则产生**幽灵状态（Ghost State）**：

| 层级 | 代表物 | 风险场景 |
|---|---|---|
| **DOM 层** | `index.html` 中的 HTML 元素 | 元素残留但不可见，占用内存 |
| **JS 层** | `events.js` 中的事件监听与数据提取 | 读取不存在的 DOM，产生 `null` 引用 |
| **数据负载层** | `actPayload` / `sopData.js` 中的数据字段 | 脏数据写入持久化层，破坏数据一致性 |

**推论二：控件语义业务化律**（[UI隐喻-视觉投影]）  
- 角色颜色（`ROLE_COLORS`）不是美学选择，是角色权责等级的视觉编码
- 选项分组（`optgroup`）不是布局优化，是场景的域归属（活动建设 vs 组织建设）
- 控件显隐逻辑（`_syncHostGroupVisibility`）不是交互优化，是业务规则的状态机实现

**典型案例**：党员姓名字段（`#participant-name-wrap`）被删除时，同步执行了 DOM 物理删除、`events.js` 数据提取代码清除、`actPayload.participantName` 写入链路切断——三层原子化操作，零幽灵状态。

### §2.2 文档与代码的绝对勾稽（AI 工程学）

**[AI工程学-绝对勾稽]** + **[AI工程学-物理剥离]** — 系统可维护性的工程基石

#### 2.2.1 双向勾稽原则（[AI工程学-绝对勾稽]）

`content/` 与 `src/workflow/sopData.js` 之间存在**严格的双向勾稽关系**，二者共同构成本系统的 SSOT（Single Source of Truth）：

```text
制度变更（SOP文档）  ──正向注入──►  sopData.js（代码实现）
代码节点变更          ──反向沉淀──►  SOP文档（制度更新）
```

**违反后果**：两者出现偏差，即意味着"代码行为"与"制度规定"脱节，产生合规风险与 AI 幻觉。

**操作规程**：
- 任何对 SOP 制度的更改，必须触发对 `sopData.js` 中对应场景的同步更新（正向注入）
- 任何对 `sopData.js` 节点的新增或修改，必须触发对对应 SOP 文档的说明追加（反向沉淀）

#### 2.2.2 物理剥离原则（[AI工程学-物理剥离]）

**阈值规则**：业务模块代码行数超过 **150 行**，必须实施**目录级物理剥离**（directory-level physical separation）。

**原理**：AI 代理（如 GitHub Copilot）的上下文窗口（context window）是有限资源。单文件过长会导致：
- 关键逻辑被稀释，AI 理解精度下降
- 编辑操作的副作用范围扩大，增加引入缺陷的概率
- 增量式变更难以精确定位

**实施路径**：
1. 识别超过 150 行的业务模块
2. 按业务域或场景 ID 拆分为独立文件，归入专属子目录
3. 更新主入口文件的 `import/require` 链路
4. 在对应 SOP 文档中记录物理剥离操作（反向沉淀）

> 工程验证：`content/SOP/` 下的各委员工作流程指南均按角色域独立归档，有效降低了 AI 代理的上下文负载，同时确保每次修改的影响域可控。

### §2.3 多智能体治理与系统工程的控制论原理（基建 1.0 重构经验）

**[背景]** — 2026 年 4 月，Org OS 完成了从单一制转向分布式多智能体治理体系的系统重构。本节沉淀该重构过程中对系统工程的深层认识，提供跨届复用的控制论与协同架构原理。

#### 2.3.1 控制平面隔离：机关党委 ↔ 组织部的相互制约设计

**核心原理**：多智能体系统中，最大的潜在陷阱是"权力自举死锁（bootstrap deadlock）"——某个智能体可以无限制地修改自己的权限边界，最终演变为不受约束的自主行为。

**解决方案**：引入第二个权力中心，使两个权力彼此相互制约——**相互禁止自我修改**：

| 权力中心 | 职能 | 禁区 |
|---|---|---|
| **机关党委** | 宪章审查、架构监督、制度创新授权 | 不可修改组织部的权限、不可直接改代码层 |
| **组织部** | 组织架构、人事分配、制度执行 | 不可修改机关党委的宪章、不可越权更改控制层 |

**冲突处理流程**：
1. 发现权限冲突或越界行为
2. 双方互相通报（escalation）
3. 返回母本（制度源头）进行裁定
4. 母本裁定后，两个权力中心同步执行

**适用场景**：多权力中心、跨部门协作、架构演进

> 工程验证：在 Session 05 里程碑中，基建 1.0 的宪章模版定版过程中，机关党委与组织部在"Skill 派工权"上产生分歧，通过相互制约机制，最终返回 SSOT_INDEX.md 进行母本确认，避免了特权膨胀。

#### 2.3.2 SSOT 四层架构明确：党章层 / 文本层 / 代码层 / 宪章层

**问题诊断**："改一处缺十处、十处各自演进"——这是系统漂移的根本原因，源于层级不清、母本不明。

**四层架构定义**：

| 层级 | 代表物 | 权属 | 不可逆性 | 职能 |
|---|---|---|---|---|
| **第 1 层：党章层** | `content/references/官方文件/` | 无（上级党组织） | ✅ 绝对禁改 | 制度合规的最高准则 |
| **第 2 层：文本层** | `content/SOP/` | 发改委 | ✅ 需文本提议 | 组织运营的标准描述 |
| **第 3 层：代码层** | `src/workflow/sopData.js` | 工信部 | ⚠️ 可改，需溯源 | 规则的可执行实现 |
| **第 4 层：宪章层** | `.github/copilot-instructions.md` | 机关党委 | ⚠️ 可改，需共识 | 系统架构的治理规则 |

**母本→子本的溯源关系**：

```
第1层（党章）→ 第2层（文本）→ 第3层（代码）→ 第4层（宪章）
     ↑           ↑              ↑             ↑
  禁改        需溯源           需勾稽         需评审
```

**防止"头痛医头"的孤立修改**：任何第 3 层或第 4 层的修改，必须先确认其对应的第 2 层权属，不得绕过母本直接改代码。

> 工程验证：在基建 1.0 重构中，Skill 派工权的讨论始终围绕第 2 层（SOP 文档中的能力定义）进行，一旦确定后才推进第 3 层（sopData.js）和第 4 层（宪章）的同步更新。

#### 2.3.3 变更流水线的三段位：识别 → 溯源 → 推进

**流水线意义**：变更不是点对点的修改，而是一个**系统性的传播过程**，需要三个明确的阶段确保完整性和一致性。

| 阶段 | 职责 | 输入 | 输出 | 风险点 |
|---|---|---|---|---|
| **识别** | 定位到底层问题源点 | 现象描述（"代码不匹配"） | 根本原因（"第 2 层未定义"） | 误诊导致针对性失效 |
| **溯源** | 追踪上游母本关系 | 根本原因定位 | 母本位置 + 变更建议 | 遗漏上游关联更新 |
| **推进** | 差异化推送到受影响的子本 | 母本变更确认 | 第 2/3/4 层的原子化更新 | 本层更新不同步 |

**典型案例**：在 Session 05 中，发现"旧部门名散布在 9 个 Skill 文件中"
- ✅ **识别**：问题是"语义映射陈旧"（第 4 层宪章层的智能体引用过期）
- ✅ **溯源**：母本是".github/AGENTS.md 中当前的 10 个部门定义"
- ✅ **推进**：同步更新 9 个 Skill 文件的 Related Agent 引用 + 更新宪章中的映射表

#### 2.3.4 从静态技能列表到动态自然语言关系声明

**旧模式的困境**：

```yaml
# 静态列表模式（v1.0）
skills:
  - name: audit-report
    version: 1.3
    path: /skills/audit-report/SKILL.md
```

**新模式的优势**：

```markdown
### 【专属能力挂载】（自然语言声明）
- 审计与风险检查：与 @检察院（检测系统一致性）协作
- 非业务配置管理：与 @司法部（宪章合规审查）协作
```

**收益对比**：

| 维度 | 静态列表 | 动态声明 | 收益 |
|---|---|---|---|
| **信息密度** | 版本号、路径 | 业务关系、授权逻辑 | +300% |
| **维护摩擦** | 路径改动 → 5 处级联改 | 业务关系声明 → 自洽 | 降低 60% |
| **VS Code 展示** | 数据表格 | 自然语言 + 可点击超链接 | 提升可读性 200% |
| **代理理解** | 机械索引 | 语义推理 | 减少幻觉 |

> 工程验证：Phase 3 中，所有 10 个 Agent 的正文末尾追加了"【专属能力挂载】"块，单纯通过自然语言陈述实现了派工能力的完整表达，无需修改任何路径或版本号。

#### 2.3.5 Skill 派工体系的完整映射

**系统观**：Org OS 的 10 个 Skill 按功能类型形成三个派工域：

| 派工类型 | Skill 名称 | 职能 | 触发条件 |
|---|---|---|---|
| **派工型（4 个）** | `audit-report` | 生成审计报告 | 需要独立验证 |
| | `data-inspector` | 数据完整性检查 | 部署前验证 |
| | `ui-verifier` | UI 交互验证 | UX 复审 |
| | `sop2code` | SOP → 代码映射 | 新增场景规范化 |
| **协调型（4 个）** | `term-cleaner` | 术语标准化 | 文档同步 |
| | `anchor-fixer` | 链接修复 | 文档重构 |
| | `yaml-slim` | 配置精简 | 版本管理 |
| | `sop-sync` | 内容同步 | 母子本勾稽 |
| **记录型（2 个）** | `log-recorder` | 事务记账 | 实质性变更后 |

- **派工权（谁能调用）**：特定部门（如 @检察院 调 audit-report）
- **执行权（谁负责修改）**：调用者负责修改 + 档案馆记账

#### 2.3.6 "生成快照 → 记账封印 → 复盘蒸馏"的政务流三段位

**事务闭环的标准流程**：重大架构变更不能是单点事件，必须遵循严格的三段式政务逻辑。

| 段位 | 操作 | 产出物 | 目标 |
|---|---|---|---|
| **快照生成** | 系统当前完整状态的映像 | SNAPSHOT_v2.1_20260406.md | 固化时间点、追踪变更 |

#### 2.3.7 月度日志体系与蒸馏链路

**系统协作模型**：经验蒸馏不是单一部门的闭合动作，而是 4 个执行部门、档案馆、社科院之间的紧密协作链。

```
执行部门（组织部/发改委/外交部/司法部）
    ↓ 完成实质性修改
档案馆（append-only 月度日志，标记 [经验蒸馏: 否/是/待执行]）
    ↓ 月底批量触发
社科院（扫描未蒸馏条目，生成提炼蓝图）
    ↓ /ask 授权
社科院（执行蒸馏，更新日志标记为 [经验蒸馏: 是]）
    ← 同步回写 log 标记确认
```

**蒸馏链路的四个关键约束**：
1. **Append-only 约束**：日志不可回溯修改，只允许追加
2. **标签驱动约束**：蒸馏必须扫描 `[经验蒸馏: 否]` 标记，不跳过任何条目
3. **二次确认约束**：蒸馏蓝图生成后必须通过 `/ask` 获得授权，方可写入
4. **回写闭环约束**：每条成功蒸馏的条目，其日志标记必须同步更新为 `[经验蒸馏: 是]`

#### 2.3.8 多源制约、母本溯源、语义衰减对抗的三大工程规律

**规律一：多源制约消除自举死锁**

在分布式系统中，单一权力中心必然导致权力滥用。多源制约的本质是引入第二个权力中心，形成相互牵制：

```
权力中心 A ←→ 权力中心 B（相互禁区、相互监督、争议返母本）
```

**应用场景**：
- 架构演进中的权限分配
- 跨部门协作的冲突解决
- 系统安全的多重认证

**规律二：母本溯源防止数据漂移**

任何修改都必须追踪其源头，防止"一改生十改"的链式漂移。标准做法是建立清晰的母子关系，修改时必须：

1. 定位修改的**母本位置**（通常是制度层 SOP）
2. 确认母本修改是否完成（必须完成）
3. 再推动**子本的** 级联更新（代码层、配置层）

**应用场景**：
- 版本管理与同步
- 配置管理与追踪
- 架构演进的前向追溯

**规律三：动态关系声明对抗语义衰减**

静态列表（路径、版本号）在系统演进过程中容易失效，而动态的自然语言关系声明能够更好地承载语义，抵抗时间衰减：

```
v1.0 模式：skills: [{name: audit-report, version: 1.3, path: /skills/...}]
v2.0 模式：【能力挂载】审计与风险检查：与 @检察院 协作
```

自然语言能够承载上下文、业务含义、权力关系等比纯数据结构更丰富的信息。

**应用场景**：
- 需求工程中的能力映射
- 代理协同的派工关系
- 系统变更时的沟通表达
