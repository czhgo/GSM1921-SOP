# 活动、专班与个人档案界面改造设计规格

状态：待支书复核
日期：2026-10-17
性质：临时任务设计稿；实施完成并把长期规则归并到权威文档后删除本文件。

## 1. 目标

在现有活动、工作组、专班和成员档案模型上，重整活动详情、专班详情和个人档案的展示与操作路径。使用者应能快速识别页面的主对象、当前状态、责任人、下一步动作和可查看范围；相同业务语义的组件共享实现，不同业务流程保持清楚边界。

本轮同时落实已确认的工作组成员编辑方案 A：一个名单内管理组织者、深度参与者和一般参与成员；每人的系统授权作为独立内容展开，并与成员变更通过一次服务端事务保存。

## 2. 已确认的产品边界

1. **组织目标**：支撑一个党委、多个支部。所有关联写入由服务端验证支部归属；界面隐藏不能替代授权检查。
2. **活动承办范围**：活动数据记录“组内承办”或“跨组承办”。该字段描述组织责任，不限制其他成员报名或参加。组内活动由本党小组组长从组长台创建；跨组活动由书记或副书记从书记台创建并指定组织者及深度参与者。
3. **工作组角色**：活动工作组和专班工作组都具有组织者、深度参与者及一般参与成员。工作组成员身份不自动生成系统授权，也不自动进入活动报名、应到或考勤名单。
4. **两类工作组的语义**：活动创建时随活动建立活动工作组；专班工作组围绕自身任务存在，可不关联活动。任务和产出可分别关联工作组、活动或业务能力包。专班的任务/产出闭合条件按已登记事项判断；只有制度、议程或事项明确要求时才办理考察或表决。
5. **个人档案访问制度参数**：全组织统一，当前规则为“本人 + 本支部现任支委角色”。只允许依制度裁定改变，不提供支部级自定义。支委角色集合沿用 `BRANCH_COMMISSION_ROLES`：书记、副书记、组织委员、宣传委员、纪检委员。党委组织员、党小组组长、普通成员和其他支部人员不能查看他人档案。
6. **档案字段职责**：本人维护自我描述；组织字段仍按既有字段所有权和写入角色处理。组织人员可在授权的字段编辑流程中执行限定写入；此能力不构成查看整份他人档案的权限，也不能读取自我描述。
7. **报名、参与与考勤分离**：工作组名单展示工作关系；活动报名和考勤仍走各自流程，不从工作组名单自动复制人员。
8. **会议议程**：会议类型继续使用正式“三会”定义。议题可以分为讨论项与表决项；同一事项需要讨论后表决时，表决项固定关联前置讨论项。继续按会议场景执行既有表决门槛。

## 3. 共用界面基础

共用部分限定在含义、数据和操作一致的内容：

- 实体标题区：名称、类型、状态、责任范围和主要后续动作。
- 紧凑事实区：日期、地点、关联组织或任务等适合快速扫读的信息。
- 状态徽标、人员身份行、空状态、分段标题与必要的页内定位。
- 活动与专班共用的工作组成员编辑器和权限展开行。
- 现有活动报名面板继续共用；活动日历使用已有共享实现。

共用组件按语义变体呈现真实差异，避免为统一外观把不同职责塞进同一块泛化卡片。重复的装饰性容器不构成抽取组件的理由。组件遵循《设计系统》的“最小三成本”、数据形状决定展示方式、键盘可达、语义状态和响应式规则。

## 4. 活动详情

### 主信息顺序

1. 活动名、正式类型、状态、日期/地点、组内或跨组承办范围、负责人。
2. 当前最重要的行动（如编辑、报名处理、会议议程、考勤或归档），与其所需事实相邻。
3. 活动议程：普通事项、讨论项、关联表决项按业务顺序呈现；投票资格与现有场景门槛保持不变。
4. 报名与工作组分别呈现；报名状态不并入工作组成员角色。
5. 考勤、分工任务、产出和历史信息放在对应数据层中，避免以一个笼统“参与者”集合代表不同事实。

组内活动的创建入口属于组长台；跨组活动的创建入口属于书记台。两类活动最终仍使用同一活动详情能力，但创建和权限路径清楚反映责任来源。继续保留 `activity.html?id=tf-*` 的历史入口，并委托给同一专班详情渲染逻辑。

## 5. 专班详情

- 页面主对象是专班工作组及其承担的任务，不是某一场活动。
- 展示专班目的、状态、组织者/深度参与者/一般成员、登记任务及产出。
- 可以在具体任务或产出上关联活动或业务能力包；没有真实关系时不人为建立专班与活动的直接关联。
- 专班允许独立存在，用于材料申报/审查、档案整理、宣传或周刊等明确工作；与某场活动相关的筹办事项可通过任务和产出连接活动。
- 专班与活动工作组复用成员和授权的呈现与保存机制，不复用活动报名、应到和考勤语义。
- 已结束专班的事项按历史只读规则展示；结束条件是所有已登记任务和产出闭合。

## 6. 工作组成员编辑器 A

### 列表与编辑

- 活动工作组、专班工作组使用一个同义成员列表：人员、工作组角色、授权概况和当前状态。
- 每人可展开查看和调整其显式授权；建议权限模板仅用于填写初值，保存结果仍逐项记录。
- 新增、调整、移除成员以及对应授权增撤由一个批量接口作为单一事务提交。任一校验或写入失败时整体回滚。
- 移出成员时撤回其在该工作组下全部有效授权并记下撤销人、时间和原因；重新加入不恢复旧授权。
- 工作组内已有 `participant` 显示为一般参与成员，与组织者和深度参与者处于同一名单；不自动报名、不自动记为应到或出席。
- 工作组成员关系和系统权限独立存储；跨支部关联、越权授权和通过通用快照绕过专用接口的请求均拒绝。

### 操作成本

日常小幅调整应在单一工作组上下文内完成，操作者能在保存前看清成员角色和授权影响。批量保存应明确成功/失败状态，并在失败时保留未提交的编辑内容，避免重复输入。

## 7. 个人档案的三种投影

| 投影 | 可访问者 | 内容与操作 |
| --- | --- | --- |
| 本人档案 | 本人 | 查看组织维护字段；查看、编辑本人自我描述；维护本人允许编辑的资料 |
| 支委阅档 | 同支部 `BRANCH_COMMISSION_ROLES` 五类角色 | 依制度查看本支部成员档案；字段编辑仍按既有字段所有权分开授权 |
| 组织字段编辑 | 具有现行字段写权限的组织角色 | 仅通过限定字段的写入流程维护其获授权字段；不获得完整档案读取、跨支部读取或自我描述读取能力 |

具体规则：

- 档案访问制度参数采用全组织固定配置，在制度参数页只读展示；修改必须先有制度裁定，不能由某支部在运行时扩大范围。
- 服务端负责在单人档案读取、通用成员列表及其他返回成员对象的接口中执行同一策略。不得只在页面隐藏信息。
- `selfProfile` 不进入无权用户收到的响应；缓存、导出和兼容路由遵循相同投影。
- 党委组织员、党小组组长、普通成员及其他支部的支委打开他人档案时应被拒绝；本人仍可查看自己的档案。
- 当前不增加揭名或审计解密入口。
- 移除主要档案页中无法完整核实的活动/专班计数。若保留关联经历，改为有来源、有链接的具体记录列表，并置于档案主体内容之后。
- 空白自我描述要提供本人编辑入口；不显示虚构统计或把“无数据”误写为“无经历”。

## 8. 访问与错误状态

- 无权限访问他人档案时返回清楚的无权限结果，页面不先渲染再遮罩敏感内容；页面不显示可继续探测成员资料的链接。
- 无权限读取自我描述时 API 不返回字段本身，避免客户端缓存或导出间接泄露。
- 成员批量保存失败时事务回滚，保留表单草稿并给出可理解的原因。
- 工作组引用了不存在、已停用或不同支部的活动/能力包时，写入拒绝并指出关联对象问题。
- 历史 URL 继续工作，但不得借兼容路由绕开角色和支部校验。

## 9. 实施分片与依赖

### A. 先落安全边界

- 将档案访问规则纳入组织级固定制度参数，并在设置页只读说明。
- 为单人档案与所有成员对象出口增加服务端统一投影；检查跨支部读取、列表、缓存和导出。
- 增加按角色、支部和字段范围覆盖的针对性 API 回归。

### B. 工作组事务成员编辑

- 设计成员与授权批量保存接口的请求校验、变更审计和事务回滚。
- 实现一个共享编辑器，并分别接入活动工作组与专班工作组。
- 验证撤员撤权、成员不自动得权、报名/考勤不被隐式改变。

### C. 活动与专班详情统一基础、保留语义

- 提取标题区、紧凑事实区、空状态等确实同义的基础呈现。
- 把 `activity.html?id=tf-*` 与 `taskforce.html?id=*` 收到一个专班详情渲染实现。
- 按本规格重新组织活动与专班内容层级，保留创建责任和流程差异。
- 根据实际页面长度决定是否增加局部目录；不将高频操作藏入额外切换层。

### D. 个人档案重整

- 拆分本人、支委查看、组织字段限定编辑的读写投影。
- 明确本人自我描述和组织维护资料的区块、字段来源及操作权限。
- 以可验证记录替换或移除现有不完整计数。

### E. 收尾

- 把已实施的长期规则同步到《设计系统》《数据模型》和相关权限/架构权威源；此规格随后删除。
- 各分片只运行涉及的 API、数据库、文档和浏览器检查，不跑全量套件。
- 浏览器检查桌面三页面及重点移动视图；拒绝越权访问、主操作可见、键盘操作和兼容链接需覆盖。

## 10. 验收标准

1. 本人可看/改本人自我描述；同支部五类支委可查看；普通成员、组长、党委组织员及其他支部账号无法读他人档案或从通用列表拿到 `selfProfile`。
2. 档案读范围由全组织只读制度参数驱动，支部配置无法覆盖；经制度裁定后能统一改政策值。
3. 组织字段写入继续按字段职责与角色授权工作，不能借写权限读取完整档案。
4. 活动和专班成员列表语义相同且实现共享；组织者、深度参与者和一般成员都可明确管理；撤员撤权准确且可审计。
5. 批量成员与授权保存具备事务回滚；越支部关联和快照绕过被服务端拒绝。
6. 工作组名单不自动改变活动报名、应到和考勤；组内/跨组活动责任入口符合约定。
7. 活动议程仍保留讨论项→关联表决项和现有门槛；专班任务可独立存在，活动关联落在具体任务或产出。
8. 活动与专班页面共享同义基础组件；详情能分别回答各自主对象、责任和下一步动作；历史专班 URL 与旧活动专班 URL 保持兼容。
9. 三个档案投影、主要操作、无权限状态在桌面和重点移动宽度可读、可键盘操作；不以全量测试替代本规格的定向验收。

## 11. 明确不在本规格内

- 不改变正式会议类型、投票资格或制度表决门槛。
- 不让党委组织员查看支部匿名反馈或他人自我描述。
- 不自动把工作组成员导入活动报名、应到或考勤。
- 不强制每个专班关联活动，也不把专班本身当作活动。
- 不新造工作组成员自动继承的角色权限体系。
- 不建立泛化的“所有业务详情都一样”的卡片框架；仅共享语义相同的基础呈现与操作组件。
- 不重建活动、专班或用户的全部数据模型；只有满足本规格已确认的数据边界、且现有表无法表达时才在实施计划中列出最小字段/API 变更。
