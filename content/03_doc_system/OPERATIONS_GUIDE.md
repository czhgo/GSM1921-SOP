## 4. 编码规范

全仓库必须遵守以下编码标准，确保中文内容在所有工具链中正确显示：

1. **文件编码**：所有文本文件（`.md`、`.js`、`.html`、`.css`、`.json`、`.yaml`）必须使用 **UTF-8 无 BOM** 编码
2. **换行符**：统一使用 **LF**（`\n`），禁止 CRLF（`\r\n`）。`.gitattributes` 中应设置 `* text=auto eol=lf`
3. **中文标点**：Markdown 正文中使用**中文标点**（，。：；！？""''），代码和表格内使用英文标点
4. **git 操作编码**：执行 `git show`/`git diff` 等命令时，必须设置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，避免中文乱码
5. **PowerShell 输出**：使用 `Out-File -Encoding utf8` 保存文件，禁止使用默认的 Windows 编码

## 5. 文档关系定义

**CLAUDE.md、guides、insights、logs 之间的关系**：

```
                    CLAUDE.md（甲部 Harness）
                    ┌──────────────────────┐
                    │ 核心原则 + 判例       │  ← 最高权威，定义"是什么"和"为什么"
                    │ 乙部执行事项          │  ← 当前工作上下文
                    └──────────┬───────────┘
                               │ 引用
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │  guides/   │   │ insights/  │   │   logs/    │
     │ 设计理念   │   │ 经验沉淀   │   │ 运行记录   │
     └────────────┘   └────────────┘   └────────────┘
     定义"怎么设计"   提炼"什么经验"   记录"做了什么"
```

**四者职责**：

| 维度         | CLAUDE.md 甲部   | guides/          | insights/   | logs/       |
| ---------- | -------------- | ---------------- | ----------- | ----------- |
| **定位**     | 核心原则（原则+判例）      | 详细设计         | 经验模式   | 事实记录    |
| **内容**     | 核心原则、关键判例、运行标准 | 完整设计文档、架构方案      | 可复用经验、管理哲学  | 操作步骤、决策过程   |
| **稳定性**    | 最稳定（修改须书记确认）   | 稳定（设计理念始终存在）     | 渐进增长（定期沉淀）  | 只增不改（归档后冻结） |
| **信息流向** → | ← guides 补充细节  | ← CLAUDE.md 授权原则 | ← logs 沉淀提炼 | ← 执行过程产生    |
| **信息流向** ↓ | ↓ 乙部规定当前工作     | ↓ 代码实现设计         | ↓ 指导未来决策    | ↓ 归档为历史     |

**关键规则**：

- CLAUDE.md 甲部是 guides 的**摘要和索引**，不是 guides 的副本。甲部保留核心原则+判例，详细设计归 guides
- 当甲部与 guides 内容冲突时，以**甲部为准**（本文件 §7.1 上层优先原则）
- guides 的更新如果涉及甲部引用的原则变更，必须**同步更新甲部**（H2.1 一改具改）
- insights 从 logs 中沉淀提炼，不直接从 guides 中产生
- logs 是原始记录，insights 是提炼后的知识，两者不可互相替代

## 6. 编号命名规则

### 6.1 甲部 Harness 编号体系

采用**字母+数字**的层级编号，格式为 `H<层>.<节>`：

```
H1   ← 一级章节（大领域）
H1.1 ← 二级章节（具体事项）
H1.1.1 ← 三级章节（细则，仅在必要时使用）
```

**层级约束**：

- 最多**三级**（H1.1.1），不得出现四级（H1.1.1.1）
- 若三级不够用，说明该节应拆分为独立的二级章节
- 新增章节时，在当前同层级末尾追加编号，**不得插队**

**编号预留策略（防数字爆炸）**：

- 一级章节编号按 10 递增预留：H10, H20, H30...（当前 CLAUDE.md 甲部实际使用 H1\~H7）
- 但为可读性，当前阶段使用连续编号，当 H10 用满后切换为 H20 递增制
- 二级编号按 1 递增，不预留
- 三级编号按 1 递增，不预留

**编号语义对照**（与 CLAUDE.md 甲部实际结构对齐）：

| 编号 | 语义   | 当前内容                                             |
| -- | ---- | ------------------------------------------------ |
| H1 | 工作流  | 审查/执行/next\_prompt                                |
| H2 | 一改具改 | 一改具改/母本子本/Guides定位/经验沉淀                           |
| H3 | 检查清单 | 文件修改检查清单+概念命名守则                                   |
| H4 | 乙部与丙部 | 乙部生命周期/丙部待决策                                      |
| H5 | 书记评议 | 触发/抽样/流程/分流/记录/校验/概念复用性扫描                         |
| H6 | 外部权威源索引 | 外部权威源导航表（按需参考层）                              |
| H7 | 项目产出声明 | 系统最最重要的产出/逻辑缺漏与书记亲补/引用流程                       |

> **理论基石**已外移到 [SECRETARY_PRONOUNCEMENTS.md](../01_strategy/SECRETARY_PRONOUNCEMENTS.md)（项目顶级战略文档，26 条论断，P-045/P-047 为元命题引子）；**运行标准**即本文件（OPERATIONS_GUIDE.md）；**日志规范**见本文件 §13；**已知陷阱**见 [KNOWN_PITFALLS.md](../05_ai_coding/KNOWN_PITFALLS.md)。

### 6.2 乙部任务编号体系

格式：`T<轮次>-<序号>`

- **轮次**：按工作日递增（T30, T31, T32...），每轮可包含多个任务
- **序号**：同一轮次内的任务序号（1, 2, 3...）
- **跨轮延续**：若某任务未完成，在新轮次中保留原编号，不重新编号

**防数字爆炸策略**：

- 轮次编号与日期绑定，不与任务数量绑定。一个工作日 = 一个轮次，无论当天有多少任务
- 轮次编号不要求连续——T30 之后可以是 T35（中间跳过的轮次编号不回收）
- 序号上限：单轮次内序号原则上不超过 20。若超过，说明该轮次应拆分为多个轮次
- **持续任务**使用 `C-<序号>` 前缀，不占用 T 编号空间
- **待讨论议题**使用 `D.<序号>` 前缀，**暂缓议题**使用 `F.<序号>` 前缀

### 6.3 编号对应关系

乙部任务编号与日志条目之间**必须建立双向可追溯关系**：

```
CLAUDE.md 乙部任务 T30-7  ←→  EXECUTION_LOG 中包含 "T30-7" 的条目
```

**执行日志中的编号规则**：

- 每条日志条目标题格式：`## YYYY-MM-DD | T<轮次> — <一句话摘要>`
- 条目内用 `T<轮次>-<序号>` 标注具体完成的任务
- 若一次工作完成多个任务，在条目内逐项标注

**决策日志中的编号规则**：

- 格式：`D-<序号>`，全局递增，不按月重置
- 若某决策与乙部任务相关，标注对应任务 ID（如 `关联任务: T30-7`）

### 6.4 用户补充工作的流程

用户在对话中直接提出的任务（非乙部已有条目），按以下流程处理：

1. **判断是否涉及决策**：
   - 若涉及方案选择（A vs B）、制度变更、架构调整 → **必须写入决策日志**
   - 若仅为执行性操作（修 bug、补字段）→ 仅写入执行日志
2. **写入乙部**：将用户补充的任务追加到乙部对应优先级分组，分配新编号
3. **执行**：按 H1.2 标准流程执行
4. **完成后**：从乙部删除，写入执行日志

**特殊场景**：用户直接要求"立即做 X"且 X 可在当次工作中完成——先追加到乙部（标注 `🔄 当次`），完成后立即标记 ✅ 并在下次乙部更新时删除。

### 6.5 Guides 文件编号

Guides 文件不使用数字编号，使用**语义化文件名**（大写+下划线），按 MECE 分类归入子目录（见 guides/README.md）。

### 7.2 索引规范（README 的职责）

每个目录的 README.md 是该目录的**唯一入口索引**，职责为：

1. **列出所有文件**及其一句话说明
2. **按 MECE 分类**组织（不得有文件不属于任何分类，不得有文件属于多个分类）
3. **标注权威源**：当本目录文件与其他目录存在内容重叠时，标注哪个是权威源
4. **减少 AI token 消耗**：AI 读取 README 即可决定需要深入读取哪些文件，无需逐个扫描

**禁止**：README 中不得重复文件内容，仅做索引和导航。

## 9. 文件命名规范

> **确立日期**：2026-07-08 | **确立背景**：部分文件命名过长（如"关于支部大会时间调整的改革说明（征求意见稿·修订版）.md" 64 字符），导致管理与阅读困难

### 9.2 命名标准

| 文件名类型 | 命名风格 | 字符上限 | 示例 |
|----------|---------|---------|------|
| 英文文件名 | 大写蛇形（UPPER_SNAKE_CASE） | ≤ 30 字符 | `PARTICIPANT_DATAFLOW.md`、`LOGIN_SYSTEM_DESIGN.md` |

- 禁止使用空格、连字符（`-`）以外的特殊符号
- 禁止使用中文标点（顿号、书名号、全角括号等），但历史档案除外
- 禁止缩写过度导致语义丢失（如 `PD.md` 代替 `PARTICIPANT_DATAFLOW.md`）

### 9.3 超长文件名处理原则

对超长文件名（英文 > 30 字符 / 中文 > 20 字符），按以下优先级选择处理策略：

1. **保留原名+索引简称**（首选，适用于历史档案）：文件保留原始命名，在目录 README 中建立简称映射。适用于 `content/01_strategy/references/历史会议材料/` 下的文件
2. **缩写**（适用于内部文档）：在保留核心语义前提下简化命名。如"支委与党小组定人定责定岗说明"在边界 20 字符，语义清晰，可不改
3. **拆分**（适用于内容可分离）：当文件内容可合理分为多个独立部分时，拆分为若干短文件

### 9.4 历史档案例外条款

`content/01_strategy/references/历史会议材料/` 下的文件保留原有命名方式，不强制改名。这些文件是历史档案，改名会破坏引用链路且无实际收益。

## 10. 反论表述审核标准

> **确立日期**：2026-07-08 | **确立背景**：insights 文件中存在"为什么不是加法关系""为什么不是乘积关系"等缺乏上下文、易产生歧义的反论表述

### 10.1 什么是反论

反论是指用"为什么不是 X"形式表达的否定性对比论述，目的是通过否定一个错误方向来凸显正确方向。

### 10.2 应该用反论的情况

满足以下**全部条件**时，适合用反论：

- 被否定项 X 是读者**可能合理误选**的方向（读者真的会想到 X）
- 否定 X 后能**凸显正确方向**（对比有教学价值）
- 被否定项 X 是读者**熟悉的具体概念**（而非生造概念）

**正面案例**：`扁平化≠无分工，而是无上下级` — 读者确实可能误以为扁平化就是无分工，否定有教学价值

### 10.3 不应该用反论的情况

出现以下**任一情况**时，不适合用反论：

- 被否定项是读者**不熟悉的抽象概念**（如"为什么不是加法关系"——读者不知道"加法关系"指什么）
- 被否定项是**生造概念**或无对照价值（如"为什么不是乘积关系"——"乘积关系"是为反论而生造的术语）
- **缺乏上下文**导致反论无意义（未说明在讨论什么，直接抛出"为什么不是 X"）
- 存在**术语冲突风险**（被否定项与既有术语同名，造成混淆）

### 10.4 反论成立三要素

一个合格的反论必须同时具备：

1. **明确的上下文**：读者知道在讨论什么问题
2. **被否定项的简要说明**：读者知道被否定的是什么（一句话解释 X 是什么）
3. **否定理由与正确方向的关联**：读者理解为什么正确方向更好（不只是"X 不对"，还要说"Y 对在哪里"）

### 10.5 改写策略

对不达标的反论，按以下优先级改写：

1. **首选：改写为正面表述**。直接说"是什么"，而非"不是什么"。如"为什么不是加法关系" → "两者是乘积关系而非简单堆叠"
2. **次选：补充上下文后保留对比**。若对比有教学价值，先说明上下文，再否定。如"有人可能以为是简单堆叠（加法关系），但实际上..."
3. **避免：术语冲突**。若被否定项与既有术语同名，必须改写，不得保留

### 10.6 自检清单

写反论前自检：

```
□ 1. 读者真的会想到被否定项 X 吗？（若不会，改正面表述）
□ 2. 被否定项 X 是读者熟悉的概念吗？（若不是，改正面表述）
□ 3. 上下文是否明确？（若不明确，先补上下文）
□ 4. 否定后是否说明了正确方向？（若没有，补关联）
□ 5. 被否定项是否与既有术语冲突？（若冲突，必须改写）
□ 6. 被否定项在仓库中是否仍被使用？（若已无使用，反论本身应删除）
□ 7. 反论是否涉及AI治理技术？（若是，AI须联网搜索补充普适性+特殊性后，书记再决策）
```

### 10.7 历史范畴检查

### 10.9 反论评议维度体系

> **确立日期**：2026-07-18 | **确立背景**：反论评议第一轮中，书记对12条反论的反馈揭示了三类系统性的反论问题维度，每类有不同的处理方式
> **定位**：反论的事后质量评议（区别于 §10.2/§10.3 的事前存在标准），是 H5 书记评议的反论专用补充，速查见 [CLAUDE.md H5.8.1](../../CLAUDE.md)（反论评议类型速查）。

反论评议中发现的三类问题维度：

| 维度 | 含义 | 判定标准 | 处理方式 |
|------|------|---------|---------|
| 正确的废话 | 技术正确但无增量信息 | 被否定项已无人主张（历史范畴/生造概念），或反论仅重述正论。**判定标准是"无增量信息"而非"与母本重复"**——与母本重复但提供母本未展开的具体应用场景的反论应保留 | 删除反论，改为正面陈述 |
| 命题错误 | 被否定项不准确或为稻草人 | 被否定项无人会主张，或AI将正确概念错误组合产生新命题 | 删除反论，用书记原话替代 |
| 重点偏差 | 有增量信息但重点偏移 | 反论方向正确但未触及书记判断的核心关切。**反论重点应在正论方向（强化正论），而非仅在排除替代方案** | 修正重点，关联书记判断的核心关切 |

**反论与正论的三种处置关系**（2026-07-19 第二/三轮评议沉淀）：

| 关系类型 | 判定标准 | 处理方式 |
|---------|---------|---------|
| 保留 | 反论提供独立补充视角，与正论不重复 | 维持反论 |
| 融入正论 | 反论与正论重复且应用场景与正论强耦合（正论需要该场景才能完整说明） | 删除反论，核心表述融入正论 |
| 删除反论+补充正论 | 反论本质是正论的变形（如"为什么不是 X 总比 Y 好"预设"X 总比 Y 好"是观点，但正论已明确"按需选择"） | 删除反论，强化正论"按需选择"表述 |

**反论用例的例子选择约束**：例子需符合书记表达风格，避免使用书记明确不喜欢的表达或带特定意识形态色彩的例子（如"三大纪律"等军事术语/历史典故），优先使用工程实践或日常管理场景的例子。

### 11.7 章节过渡的承接性原则

> **确立日期**：2026-07-20 | **确立背景**：书记指出 SECRETARY_PRONOUNCEMENTS.md 中 11 个"第X章过渡"段落"目前这一句话毫无过渡作用"，并提出章节衔接的核心规则。

**核心规则**（书记原话，2026-07-20）：一个好的逻辑结构是"前面章节提出问题在后面的章节得到回答，后面章节的解答依托于前面章节的讨论"。

**操作要点**：

1. **前一章的自然延伸**：前一章的论述应自然引出未解决的问题或未展开的维度，过渡段点明这个"未解决的问题"
2. **后一章的承接回应**：后一章的展开承接前文的讨论并给出回应，过渡段点明"本章如何回答前文的问题"
3. **承接关系的显化**：过渡段应显化这种"问题→回答"的承接关系，让读者理解章节排序的逻辑
4. **禁止机械复述**：禁止"上一章讲X，下一章讲Y"这种机械复述章节主题的写法——这种写法无过渡作用

**反例**（机械复述，无过渡作用）：
> 上一章讲"支部为谁存在、组织性为什么宝贵"，下一章讲"支部工作怎么分域——党建与党务"。

**正例**（体现承接关系）：
> 前一章回答了"组织性为什么宝贵"，但还没说清"支部的工作怎么分域"——支部里那么多事，哪些归"党建"、哪些归"党务"？这正是下一章要回答的问题。

**适用范围**：所有面向用户的阐述性文档中跨章节的过渡段落，特别是 SECRETARY_PRONOUNCEMENTS.md、DEVELOPMENT_PATH.md 这类按问题脉络组织的长文档。本节是 §11.2"段落化叙述"的进阶——前者要求段落有叙述性内容，本节要求章节过渡段落体现前后章节的问题-回答关系。

### 13.3 执行日志模板

```markdown
- **来源**: <用户指示 / Agent 执行 / 周期性唤醒>
- **变更文件**: <文件1>, <文件2>, ...
- **关键动作**: YYYY-MM-T<序号>-<子序号> ✅ / YYYY-MM-T<序号>-<子序号> ✅

  - <紧凑表述：每个变更点一行，用动词开头，不展开实现细节>
  - ⚠️ 排除Harness固定动作（更新YAML、记录日志、乙部更新等），只记录实质性内容变更
- **设计决策**: <仅非显而易见的选择，关联 D-<序号>>
- **结果**: <完成情况>
- **沉淀标签**: 省略（按规执行时）/ `[待沉淀: <简述新发现>]`（发现新模式时）/ `[已沉淀: <沉淀位置>]`（沉淀完成后）
  - 🔴 条件触发制：只有产生新模式时才需标注，按规执行时省略标签（详见 CLAUDE.md H2.4 规则6）
```

### 13.5 编号与分片规则

**编号规则**（D-188）：执行日志按月重置编号，格式为 `YYYY-MM-T<序号>`（如2026-05-T1、2026-06-T1）。跨月引用需加月份前缀。小任务（可一次性完成、不涉及3+文件或制度变更）不分配T编号，直接写日志。

**分片规则**：大任务（5+文件或200+行修改）必须提前分片：预估→拆分→写入乙部→顺序执行→上下文传递

### 13.6 日志归档机制

> 🔴 **硬阈值强制归档**——当活跃日志超过阈值时，AI 必须执行归档，不得跳过。

**触发条件**（任一满足即触发）：
- 活跃日志文件体积 > 50KB
- 活跃日志详细条目（非摘要表）> 30 条

**归档操作**：
1. 将超出阈值的早期详细条目移入 `archive/YYYY-MM-early-entries.md` 或 `archive/YYYY-MM-mid-entries.md`
2. 在活跃日志中用摘要表替代已归档条目，保留关键信息（T编号/日期/标题/关键决策/沉淀状态）
3. 归档文件与活跃日志通过相对链接互指

**摘要表格式**（与 H2.4 条件触发制统一）：

```markdown
## TXX-TYY 早期/中段条目摘要

> 详细内容见 [archive/YYYY-MM-early-entries.md](archive/YYYY-MM-early-entries.md)

| T编号 | 日期 | 标题 | 关键变更文件 | 沉淀 |
|-------|------|------|-------------|------|
| T37 | 07-01 | 确立战略路线 | MANAGE_SERVE.md | ✅ |
| T42 | 07-02 | SECRETARY_PRONOUNCEMENTS 重构 | — | — |
```

**沉淀列格式**（条件触发三档）：
- `✅` = 已沉淀至 insights
- `[待沉淀: 简述]` = 发现新模式，待沉淀
- `—` = 按规执行，省略沉淀标签（对应旧体系的"否"）

**归档文件标题格式**（🔴 强制统一）：

```markdown
## T<编号> <标题>（YYYY-MM-DD）
```

示例：`## T91 权限系统大改·第 2 轮（2026-07-12）`

> 不使用 `## 2026-07-12 | T91 —` 或 `## 2026-07-18 | T-116 —` 等变体格式。统一为 `T编号 + 标题 + 日期`，便于 Grep `^## T\d+` 模式搜索。

**归档边界划分**：
- early：当月1日至中旬之前的条目
- mid：中旬至月末前的条目
- 具体边界由 AI 根据条目数量和逻辑分组灵活划分，不做硬性日期切割

**与 H1.1 的关系**：H1.1 要求"读取 .ctx/ 确定当前基线"——AI 应优先读取活跃日志的摘要表和近期详细条目，按需读取归档文件。不得一次性读取全部归档内容。

## 14. 吸收外部输入操作流程

> **本节为原 `content/governance/SYNC_EXTERNAL.md` 的合并归位**（2026-07-11 合并）。定义"外部输入→内部知识"的完整操作流程，作为 CLAUDE.md H2.1 吸收外部输入原则的配套指南——与 H2.1 互补：H2.1 覆盖"内部变更"流程（修改前→修改中→修改后），本节覆盖"外部输入→内部知识"（识别→归位→一改具改→验证）。

### 14.1 适用场景

当以下外部输入到达时，触发本流程：

1. **书记评议**：书记对现有制度/代码的修正意见
2. **外部文档**：书记上传的官方文件、评议文档、制度更新
3. **人类自行更新**：书记直接修改了仓库中的文件（非AI操作）

### 14.2 操作流程

#### 第一步：识别变更范围

收到外部输入后，首先识别变更涉及的范围：

- **术语变更**：概念的增删改、定义的修正
- **制度变更**：流程/规则/权限的调整
- **设计变更**：架构/数据模型/交互逻辑的修改
- **纯增量**：新增内容，不涉及既有条目的修改

#### 第二步：归位到权威源

根据 H2.2 母本子本表，将变更归位到对应的权威源：

| 变更类型 | 权威源 | 操作 |
|---------|--------|------|
| 术语变更 | USAGE_POLICY.md | 更新术语定义，触发全仓一改具改 |
| 制度变更 | content/02_institution/sop/*.md | 先改SOP母本，再改代码 |
| 设计变更 | content/{01_strategy,02_institution,03_doc_system,04_web_design}/*.md | 先改设计理念/治理母本，再改代码 |
| 原则变更 | CLAUDE.md 甲部 | 按H4.1甲部修改工作流执行 |

#### 第三步：触发一改具改

变更写入权威源后，按 H2.1 执行标准执行一改具改：

1. **修改前**：全仓库搜索所有引用位置
2. **修改中**：逐一替换，每处替换记录到执行日志
3. **修改后**：再次全仓搜索确认零残留

#### 第四步：验证与记录

1. 运行 GetDiagnostics 确认代码无错误
2. 写入执行日志
3. 更新乙部（如有衍生任务）

### 14.3 AI生成过程中的HARNESS清单

> 书记明确：不需要references模板，而是AI在生成过程中自检的HARNESS清单。

AI在执行任何写入操作时，必须自检以下清单（对应H3检查清单的生成时版本）：

```
□ 1. 本次写入是否涉及外部输入？→ 是则触发本流程
□ 2. 变更范围是否已识别？→ 术语/制度/设计/原则
□ 3. 权威源是否已确定？→ 按H2.2母本子本表归位
□ 4. 一改具改是否已执行？→ 全仓搜索+逐一替换+零残留确认
□ 5. YAML是否已更新？→ last_updated字段
□ 6. 执行日志是否已写入？
□ 7. 乙部是否已更新？
```

### 14.4 AI推导识别与级联修改

> **确立日期**：2026-07-18 | **确立背景**：反论评议第一轮中发现§3.3"两种协作模式"为AI推导内容（非书记原话），删除后需级联更新4个子本文件

当AI生成的内容无法追溯到书记原话或制度原文时，按以下规则处理：

**识别**：内容声称描述书记判断，但Grep全仓库无法找到书记原始表述来源的，视为AI推导内容。

**标注**：删除AI推导内容时，在修改处添加来源说明：

> **来源说明**（YYYY-MM-DD）：此节原为AI推导内容，经反论评议确认非书记原话，已删除。书记原始判断见 [权威源文件](路径) §X。

**级联修改**：AI推导内容若被其他文件引用，删除后必须：

1. 定位所有引用该内容的子本文件（Grep搜索关键词）
2. 逐一更新子本，在修改处附来源说明
3. Grep确认全仓库零残留

**与H2.1一改具改的关系**：本节是一改具改原则在"内容删除"场景的细化——一改具改管"改"，本节管"删"，两者都要求全仓库级联+零残留验证。

### 15.3 自动唤醒机制设计

#### 15.3.1 架构

唤醒机制由三个层次组成：时间戳注册表 → 调度逻辑 → 分发逻辑，最终汇入三步工作流闭环执行。

| 层次 | 职责 | 实现位置 |
|------|------|---------|
| 时间戳注册表 | 记录每个周期性任务的最后执行时间 | `.ctx/TIMESTAMPS.md` 的周期性任务追踪区 |
| 调度逻辑（SCHEDULER） | 对比当前时间与 `last_*` 时间戳，判断是否到期 | CLAUDE.md H1.1 前置指令 |
| 分发逻辑（DISPATCHER） | 根据任务编号查找对应 Agent，生成 next_prompt，写入待办列表 | `.ctx/PENDING_TASKS.md` |
| 执行闭环 | 规划 → 执行 → 验证 → 更新时间戳 → 记账 | 三步工作流 |

**调度规则**：
- 若 `(now - last_W1) > 7天` → 触发 W1
- 若 `(now - last_M1) > 30天` → 触发 M1
- 若 `(now - last_Q1) > 90天` → 触发 Q1

#### 15.3.2 TIMESTAMPS.md 扩展字段

在 `.ctx/TIMESTAMPS.md` 中维护周期性任务追踪区（见该文件"周期性任务最后执行时间"表）。

#### 15.3.3 唤醒触发方式

| 方式 | 适用 | 实现 |
|------|------|------|
| **会话入口检查** | 每次新对话开始时 | `CLAUDE.md` H1.1 前置指令：读取 TIMESTAMPS.md → 检查到期任务 → 若存在到期任务则优先汇报 |
| **手动检查指令** | 用户主动触发 | `/check-recurring` → 执行 SCHEDULER 逻辑并输出到期列表 |
| **GitHub Actions（远期）** | 全自动月级/季级任务 | cron 触发 workflow → Agent 自主执行 → 更新日志 |

#### 15.3.4 通知策略

| 到期天数 | 级别 | 行为 |
|---------|------|------|
| 到期前 3 天 | 提醒 | 下次 AI 会话开头显示"即将到期" |
| 到期当天 | 警告 | 标记为 ⚠️ overdue pending |
| 到期后 7 天 | 升级 | 在 CLAUDE.md 乙部 中追加为短期规划任务 |
| 到期后 30 天 | 紧急 | 标记为 🔴 管理遗漏——写入存档以便追责追溯 |

### 15.4 维护与演进

- 每次新增周期性任务时，同步更新本节 §15.2 + TIMESTAMPS.md 追踪表
- 每次执行周期性任务后，通过三步工作流闭环更新 `last_*` 时间戳
- 季度审查时评估周期性任务的执行质量和覆盖完整性
