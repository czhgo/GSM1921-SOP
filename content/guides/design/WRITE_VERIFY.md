# 写入数据验证设计思路

> 本文档定义 Org OS 系统中"写入→查看"数据流的完整验证框架。
> 作为 CHECKLIST §七的配套设计文档，明确每种写入操作的数据流向和验证点。

---

## 一、设计原则

### 1.1 写入即验证

每次写入操作后，系统应能在至少一个查看点确认数据已正确持久化。写入和查看构成闭环——如果写入的数据在任何查看点都看不到，则写入失败。

### 1.2 数据流三段模型

```
写入端（谁写入） → 存储层（存哪里） → 查看端（谁看到）
```

每条数据流必须明确这三个端点。缺失任何一端，数据流不完整。

### 1.3 验证粒度

- **字段级**：写入的每个字段在查看端是否有对应展示
- **状态级**：写入后的状态变更是否在查看端正确反映
- **关系级**：写入的关联关系（如活动→考勤）是否在查看端正确解析

### 2.1 活动写入

| 写入端 | 存储层 | 查看端 | 验证点 |
|--------|--------|--------|--------|
| 书记工作台（决策树引导式写入） | mockDB.activities + localStorage | 日历视图（月/周/日/列表） | 新活动标记出现 |
| 书记工作台 | 同上 | 主页统计卡片 | "活动总数"+1 |
| 书记工作台 | 同上 | 主页近期活动列表 | 新活动条目出现 |
| 书记工作台 | 同上 | 工作流可视化面板 | 流程节点图出现 |
| 组长工作台（决策树引导式写入） | 同上 | 日历视图 | 新活动标记出现（仅党小组会/主题党日） |
| 组长工作台 | 同上 | 组长工作台活动列表 | 新活动条目出现 |

**数据流向图**：

```
书记写入活动
  ├→ mockDB.activities（内存）
  ├→ localStorage（持久化）
  ├→ 日历组件 ← 读取 activities 渲染
  ├→ 主页统计 ← 读取 activities 计数
  ├→ 主页活动列表 ← 读取 activities 排序展示
  └→ 工作流面板 ← 读取 activities + sopData 渲染

组长写入活动
  ├→ 同上存储层
  ├→ 日历组件 ← 读取 activities 渲染
  └→ 组长活动列表 ← 读取 activities 过滤展示
```

## 四、验证策略

### 4.1 自动化验证（长期目标）

每个写入操作应配套一个验证函数，写入后自动检查查看端是否正确反映：

```javascript
// 伪代码示例
function verifyWrite(writeOp, expectedView) {
  writeOp.execute();
  const viewData = expectedView.read();
  assert(viewData.contains(writeOp.data));
}
```

### 4.2 手动验证清单（当前方案）

每次实现新写入功能时，在 CHECKLIST §七 中补充对应的验证项，开发完成后逐一勾选。

### 4.3 跨页面验证

部分写入操作的数据需要跨页面可见（如书记写入活动→主页统计更新）。跨页面验证依赖 `CrossPageState` 和 `storage` 事件同步机制，需确保：

1. 写入后触发 `CrossPageState.bumpDataVersion()`
2. 其他页面监听 `storage` 事件并刷新数据
3. 页面切换时通过 `CrossPageState.load()` 恢复上下文
