# 运行标准与操作规范

## 1. YAML Frontmatter规范

所有 `content/` 目录下的 `.md` 文件必须包含以下字段（按顺序）：

```yaml
---
title: "中文标题"
type: <枚举值>
role: "[人]"/"[人机]"/"[AI]"
last_updated: "YYYY-MM-DD"
version: "X.Y"
status: active/archived/suspended
related_files: [...]
---
```

**type 枚举值**（仅限以下值，不得自创）：

| type             | 含义             | 典型位置                         |
| ---------------- | -------------- | ---------------------------- |
| `roadmap`        | 项目路线图与 Harness | 根目录 CLAUDE.md                |
| `architecture`   | 架构设计文档         | 根目录 ARCHITECTURE.md, guides/ |
| `SOP`            | 制度母本           | content/SOP/                 |
| `guide`          | 设计理念与操作指南      | content/guides/              |
| `governance`     | 治理规范           | content/guides/              |
| `design`         | 功能设计方案         | content/guides/              |
| `experience_doc` | 经验沉淀           | content/insights/            |
| `reference`      | 参考模板           | content/references/          |
| `template`       | 可复用模板          | content/references/工作模板/    |
| `index`          | 目录索引           | 各目录 README.md                |
| `log`            | 执行日志           | .ctx/logs/                   |
| `decision_log`   | 决策日志           | .ctx/logs/                   |
| `audit_report`   | 审计报告           | .ctx/logs/                   |
| `snapshot`       | 系统快照           | .ctx/snapshots/              |

**已废弃的 type 值**：`CLAUDE.md`（改为 `roadmap`）、`模板`（改为 `template`）、`导航`（改为 `index`）

## 4. 编码规范

全仓库必须遵守以下编码标准，确保中文内容在所有工具链中正确显示：

1. **文件编码**：所有文本文件（`.md`、`.js`、`.html`、`.css`、`.json`、`.yaml`）必须使用 **UTF-8 无 BOM** 编码
2. **换行符**：统一使用 **LF**（`\n`），禁止 CRLF（`\r\n`）。`.gitattributes` 中应设置 `* text=auto eol=lf`
3. **中文标点**：Markdown 正文中使用**中文标点**（，。：；！？""''），代码和表格内使用英文标点
4. **git 操作编码**：执行 `git show`/`git diff` 等命令时，必须设置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，避免中文乱码
5. **PowerShell 输出**：使用 `Out-File -Encoding utf8` 保存文件，禁止使用默认的 Windows 编码

## 5. 文档关系定义

**CLAUDE.md、guides、insights、logs 之间的关系**：

```
                    CLAUDE.md（甲部 Harness）
                    ┌──────────────────────┐
                    │ 核心原则 + 判例       │  ← 最高权威，定义"是什么"和"为什么"
                    │ 乙部执行事项          │  ← 当前工作上下文
                    └──────────┬───────────┘
                               │ 引用
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │  guides/   │   │ insights/  │   │   logs/    │
     │ 设计理念   │   │ 经验沉淀   │   │ 运行记录   │
     └────────────┘   └────────────┘   └────────────┘
     定义"怎么设计"   提炼"什么经验"   记录"做了什么"
```

**四者职责**：

| 维度         | CLAUDE.md 甲部   | guides/          | insights/   | logs/       |
| ---------- | -------------- | ---------------- | ----------- | ----------- |
| **定位**     | 宪法（原则+判例）      | 法律（详细设计）         | 判例法（经验模式）   | 庭审记录（事实）    |
| **内容**     | 核心原则、关键判例、运行标准 | 完整设计文档、架构方案      | 可复用经验、管理哲学  | 操作步骤、决策过程   |
| **稳定性**    | 最稳定（修改须书记确认）   | 稳定（设计理念始终存在）     | 渐进增长（定期蒸馏）  | 只增不改（归档后冻结） |
| **信息流向** → | ← guides 补充细节  | ← CLAUDE.md 授权原则 | ← logs 蒸馏提炼 | ← 执行过程产生    |
| **信息流向** ↓ | ↓ 乙部规定当前工作     | ↓ 代码实现设计         | ↓ 指导未来决策    | ↓ 归档为历史     |

**关键规则**：

- CLAUDE.md 甲部是 guides 的**摘要和索引**，不是 guides 的副本。甲部保留核心原则+判例，详细设计归 guides
- 当甲部与 guides 内容冲突时，以**甲部为准**（本文件 §7.1 上层优先原则）
- guides 的更新如果涉及甲部引用的原则变更，必须**同步更新甲部**（H2.1 一改具改）
- insights 从 logs 中蒸馏提炼，不直接从 guides 中产生
- logs 是原始记录，insights 是提炼后的知识，两者不可互相替代

## 6. 编号命名规则

### 6.1 甲部 Harness 编号体系

采用**字母+数字**的层级编号，格式为 `H<层>.<节>`：

```
H1   ← 一级章节（大领域）
H1.1 ← 二级章节（具体事项）
H1.1.1 ← 三级章节（细则，仅在必要时使用）
```

**层级约束**：

- 最多**三级**（H1.1.1），不得出现四级（H1.1.1.1）
- 若三级不够用，说明该节应拆分为独立的二级章节
- 新增章节时，在当前同层级末尾追加编号，**不得插队**

**编号预留策略（防数字爆炸）**：

- 一级章节编号按 10 递增预留：H10, H20, H30...（当前 H1\~H10 实际使用 H10\~H100）
- 但为可读性，当前阶段使用连续编号（H1\~H10），当 H10 用满后切换为 H20 递增制
- 二级编号按 1 递增，不预留
- 三级编号按 1 递增，不预留

**编号语义对照**：

| 编号 | 语义   | 当前内容                                             |
| -- | ---- | ------------------------------------------------ |
| H1 | 工作流  | 审查/执行/next\_prompt                                |
| H2 | 一改具改 | 一改具改/母本子本/Guides定位/经验沉淀                           |
| H3 | 检查清单 | 文件修改检查清单                                          |
| H4 | 甲部修改与钩稽 | 甲部修改/钩稽/Snapshot                                  |
| H5 | 乙部与丙部 | 乙部生命周期/丙部待决策                                      |
| H6 | 日志规范 | 日志写入/执行日志/决策日志/分片                                 |
| H7 | 已知陷阱 | 上下文丢失教训                                           |
| H8 | 理论基石 | 双域/视图/专班/双向修改/赋权/扁平化                              |
| H9 | 运行标准 | YAML/术语/角色/编码/文档关系/编号规则（详见本文件 §1-§7）              |
| H10 | 快速导航 | 导航表                                              |

### 6.2 乙部任务编号体系

格式：`T<轮次>-<序号>`

- **轮次**：按工作日递增（T30, T31, T32...），每轮可包含多个任务
- **序号**：同一轮次内的任务序号（1, 2, 3...）
- **跨轮延续**：若某任务未完成，在新轮次中保留原编号，不重新编号

**防数字爆炸策略**：

- 轮次编号与日期绑定，不与任务数量绑定。一个工作日 = 一个轮次，无论当天有多少任务
- 轮次编号不要求连续——T30 之后可以是 T35（中间跳过的轮次编号不回收）
- 序号上限：单轮次内序号原则上不超过 20。若超过，说明该轮次应拆分为多个轮次
- **持续任务**使用 `C-<序号>` 前缀，不占用 T 编号空间
- **待讨论议题**使用 `D.<序号>` 前缀，**暂缓议题**使用 `F.<序号>` 前缀

### 6.3 编号对应关系

乙部任务编号与日志条目之间**必须建立双向可追溯关系**：

```
CLAUDE.md 乙部任务 T30-7  ←→  EXECUTION_LOG 中包含 "T30-7" 的条目
```

**执行日志中的编号规则**：

- 每条日志条目标题格式：`## YYYY-MM-DD | T<轮次> — <一句话摘要>`
- 条目内用 `T<轮次>-<序号>` 标注具体完成的任务
- 若一次工作完成多个任务，在条目内逐项标注

**决策日志中的编号规则**：

- 格式：`D-<序号>`，全局递增，不按月重置
- 若某决策与乙部任务相关，标注对应任务 ID（如 `关联任务: T30-7`）

### 6.4 用户补充工作的流程

用户在对话中直接提出的任务（非乙部已有条目），按以下流程处理：

1. **判断是否涉及决策**：
   - 若涉及方案选择（A vs B）、制度变更、架构调整 → **必须写入决策日志**
   - 若仅为执行性操作（修 bug、补字段）→ 仅写入执行日志
2. **写入乙部**：将用户补充的任务追加到乙部对应优先级分组，分配新编号
3. **执行**：按 H1.2 标准流程执行
4. **完成后**：从乙部删除，写入执行日志

**特殊场景**：用户直接要求"立即做 X"且 X 可在当次工作中完成——先追加到乙部（标注 `🔄 当次`），完成后立即标记 ✅ 并在下次乙部更新时删除。

### 6.5 Guides 文件编号

Guides 文件不使用数字编号，使用**语义化文件名**（大写+下划线），按 MECE 分类归入子目录（见 guides/README.md）。

## 7. 文档权威层级与索引规范

### 7.1 文档权威层级

> **D-218 决策**：SOP（执行细节）和 guides（理念概括）是正交维度，不排先后。
> CLAUDE.md 是最高层上下文入口，承接理念和具体细节。

```
┌──────────────────────────────────────────────────────────┐
│ 上下文层    CLAUDE.md（甲部 Harness）                      │  ← 最高：上下文入口
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ┌─── 理念维度（为什么）────┐  ┌─── 执行维度（怎么做）───┐ │
│  │ guides/                 │  │ content/SOP/            │ │
│  │  设计理念 + 操作规范     │  │  制度母本 + 工作流程     │ │
│  │  回答"为什么这样做"      │  │  回答"具体怎么做"        │ │
│  └─────────────────────────┘  └─────────────────────────┘ │
│                                                          │
├──────────────────────────────────────────────────────────┤
│ 架构层    ARCHITECTURE.md                                 │  ← 技术架构
├──────────────────────────────────────────────────────────┤
│ 参考层    content/references/（工作模板）                  │  ← 可复用资源
├──────────────────────────────────────────────────────────┤
│ 审计层    .ctx/（日志/快照/时间戳）                        │  ← 运行记录
└──────────────────────────────────────────────────────────┘
```

冲突裁决规则：CLAUDE.md > guides/SOP（正交，互不覆盖） > 代码实现。
- guides 和 SOP 是正交维度：guides 回答"为什么"，SOP 回答"怎么做"
- 当两者涉及同一主题时，guides 定义设计理念，SOP 定义执行流程，互不替代

### 7.2 索引规范（README 的职责）

每个目录的 README.md 是该目录的**唯一入口索引**，职责为：

1. **列出所有文件**及其一句话说明
2. **按 MECE 分类**组织（不得有文件不属于任何分类，不得有文件属于多个分类）
3. **标注权威源**：当本目录文件与其他目录存在内容重叠时，标注哪个是权威源
4. **减少 AI token 消耗**：AI 读取 README 即可决定需要深入读取哪些文件，无需逐个扫描

**禁止**：README 中不得重复文件内容，仅做索引和导航。
