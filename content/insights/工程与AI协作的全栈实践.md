# 工程与 AI 协作的全栈实践

> **定位：** 面向系统使用者、产品负责人和维护者的跨层学习文章。先讲通用方法，再用 GSM1921-SOP 的实际结构和判例说明。
> **边界：** 本文解释工程概念和检查思路。制度口径、字段定义、权限规则、测试纪律仍以文末链接的 03/04/05 权威文件为准；发生冲突时回到权威源，不在本文修第二份规则。

## 1. 先从用户任务追数据

一个系统功能不是一张页面。要弄清“某个数字为什么是这个值”，通常需要沿着一条链追：

**用户任务 → 页面与控件 → 页面入口 → 前端服务 → 数据适配器 → API → 服务端路由/业务校验 → 数据库写入或查询 → 汇总读口 → 页面显示。**

并非每个功能都经过所有层；重点是确认每一层做了什么，以及权威结果在哪一层生成。

- **页面（UI）**呈现信息、收集输入并反馈结果。它可以控制“看见什么、点了什么”，不能单独证明“数据正确”或“用户有权做”。
- **服务层**把页面动作变成有名字的业务操作，隐藏数据来自本地 mock 还是服务器的细节。这样页面不必知道存储方式。
- **API**是浏览器与服务器之间约定的请求/响应边界。接口参数只是输入；服务端仍需验证身份、权限和业务条件。
- **数据库**保存可追溯的业务事实。写入记录与从记录计算出的汇总值要区分：汇总最好由同一规则计算，不要让多个页面各自维护一个数字。
- **读模型**是为了列表、报表和工作台组织的数据视图。它可以组合多个权威记录，但应能说明每个值从哪里来。

### 项目例子：活动上报人数

判断活动上报人数时，先确认它要表达“名单人数”还是“实际签到人数”，再检查来源、状态、身份键和重复。名单口径已经明确为：活动分配成员与**已通过且未作废**的报名人按 `personId` 去重；没有 `personId` 的报名不能可靠匹配到人，不计入并集。签到实到数是另一种业务事实，不可沿用名单公式。

这种追法能把“代码里写了什么”和“业务希望数字表达什么”分开。先定口径，再检查实现；否则即使程序运行、SQLite 完整性检查通过，算出来的业务数字仍可能错。

## 2. 先定数据口径，再写代码

改数据库计算前，至少把这几件事写清楚：

1. **身份是什么：** 用稳定的 `userId` / `personId` 连接记录，姓名只是展示值，不能作为可靠去重键。
2. **哪些状态有效：** 待审核、通过、拒绝、取消、作废等状态分别对列表、人数和报表意味着什么。
3. **计算范围是什么：** 按活动、议题、支部还是时间区间计算；边界条件是否相同。
4. **变化如何传播：** 状态变化、撤销、软删除和物理删除会怎样影响派生数字或相关记录。
5. **失败时是什么结果：** 部分写入能否回滚；数据形状不完整或互相矛盾时，是拒绝、待处理还是默认通过。

**事务**把一组必须共同成功的数据库写入合成一个操作：其中一步失败，整组回滚，不能留下“有参与记录但没有票数”的半成品。**迁移**是版本化改变已有数据库结构的程序，应能在失败时回滚或明确停止。**索引**是数据库为常用查询增加的查找结构；它能缩短查询，但会增加写入和维护成本，所以要先看真实查询模式与规模。

删除也要先问生命周期问题。若物理删除一个父记录，哪些子记录必须一起删除？哪些必须为审计保留？这应成为明确的业务规则和原子事务，而非依赖“后来没人查到”。

### 项目例子：匿名表决

投票记录可能只证明“某位有资格的人参与过”，匿名 tally 才保存同意、反对、弃权的合计。参与人数不能当成同意人数。如果可用参与记录数与有效 tally 数不一致，安全的默认是拒绝判定通过，等待修复数据，而不是猜一个对业务有利的结果。这个反例已进入分工提案票决测试。

## 3. 把“可见”与“有权”分开

界面隐藏一个按钮，只是减少误操作；用户仍可能构造请求直接访问 API。**认证**回答“你是谁”，**授权**回答“你能对哪个资源执行什么动作”，两者都应由可信的服务端按当前身份、资源归属和业务规则核验。

权限检查要落在实际写入口。常见遗漏包括：创建有门、修改没门；页面入口有门、直连 API 没门；检查角色但没检查资源归属；一个通用路由承载多种操作却只做统一登录校验。

部署边界也属于权限模型的一部分。如果服务端不按支部过滤读取，就不能仅靠前端过滤声称“支持多支部共用一个实例”。要么服务端补齐隔离并验证，要么诚实地限制为一实例一支部。

## 4. 测试业务结果与失败路径

测试应分层，让每一层回答一个问题：

- **纯逻辑测试：** 输入边界值、重复值、无效状态，核对计算本身。
- **数据库/API 测试：** 核对服务端写入、权限、事务回滚、查询和关联删除。
- **浏览器流程测试：** 核对用户从真实入口完成任务、看见正确反馈，并留意控制台错误。
- **静态守卫：** 快速发现已知结构约束被破坏，例如遗漏时间戳、断链或多个配置源。守卫通过只证明它所检查的约束通过，不证明业务结果正确。

先写能暴露错误的反例，再改实现；修复后保留反例，防止同类错误回来。至少覆盖正常路径、状态变化、空值/重复值、越权请求、并发或失败回滚、删除后残留等与规则相关的情形。

**数据库完整性检查不是业务正确性检查。** `PRAGMA integrity_check` 能发现 SQLite 文件结构损坏，不能判断活动人数或投票结果的业务含义是否正确。

本项目的正常启动默认使用 `server/data.db`。读测试应尽可能使用 `:memory:`；固定端口的写型 E2E 应显式设置 `DB_PATH` 指向专用临时库，并在结束后检查库完整性。这样测试本身不会把日常数据当作测试夹具。

## 5. 合并应减少维护面，且不改变语义

看到两个页面、表、函数或配置长得像，并不足以决定把它们合并。先比较：

- 它们服务的用户任务是否相同？
- 数据来源、稳定身份键和生命周期是否相同？
- 权限边界、制度门槛和失败处理是否相同？
- 变化是否总是一起发生，是否由同一责任域维护？
- 合并后用户会更容易找到、理解和完成任务吗？维护者会少维护几份规则吗？

如果答案不同，强行合并可能只是把不同业务藏进更多条件分支。可以先统一名称、展示读模型或共用底层计算函数，而保留不同的流程入口、表和政策。若答案相同，再以小步重构合并，并加测试保护旧行为。

### 从“重复”到“维护成本”的判断

同一规则在两个入口重复实现，常适合抽出共用服务；两个角色的工作台布局相似，却可能代表不同责任，不应只为减少文件数而合并。项目已把分工提案和专班提案的票决计算归为同一算法，同时保留不同场景的门槛；Help 的章节导航元数据也从两处定义收敛为一处。这类改动减少重复口径，没有改变业务语义。

本轮工作台复核进一步用具体维度检验这条判据：正式会议类型与议程步骤分别表达；活动与专班保留各自记录并关联共同工作组；活动承办范围与报名资格分别判断；工作组成员与系统授权分别记录；角色入口保留，同时允许只读日历共用渲染。候选合并时逐项比较任务、数据来源、身份键、生命周期、权限和失败处理；这些条件一致时合并实现，条件有差异时保留各自对象或责任关系。验证时改变其中一项，检查其余维度的存储值、访问范围和角色入口不发生意外联动。

评估功能体验时，使用设计规范中的**最小三成本**：信息成本（找出要做什么）、操作成本（从入口到完成动作的步骤）、适应学习成本（理解角色分工和使用方式）。对真实高频任务逐条走查，记录用户需要找几次、跳几页、还要问谁；再决定应删除入口、合并入口、改名还是把信息前置。

## 6. 先把部署边界说清

后端服务是项目的一部分，不等于必须再安装一个外部数据库服务。此项目的 Node 服务内置 SQLite 驱动，本地正常启动直接使用仓库中的 `server/data.db`；开发和测试库是隔离测试数据的手段，不代表项目不能在本地跑通。

运行环境还包含 Node 版本、环境变量、静态文件、上传目录、端口、备份与恢复方式。上线前应说明空库如何启动、真实组织数据如何进入、密码和会话怎样管理、如何备份和恢复，以及本地约束和多实例部署是否已验证。**能在一台电脑启动**与**适合多组织生产使用**是两个不同结论。

当前服务端有明确的单支部单实例边界。先把此限制用于安全部署，再按顺序评估服务端支部隔离、个人身份、角色写权限和数据字段索引；这些问题不能靠更换数据库品牌自动解决。

## 7. AI 协作要有闭环

AI 擅长快速搜索、连通调用链、生成测试反例和做重复编辑，但如果任务目标或数据口径不明确，它也会很快把错误假设铺到更多层。一个稳健的协作闭环是：

1. **先读边界：** 工作区现状、项目规则、相关文档、Git 历史和已有实现；区分当前规则、历史记录和待澄清事项。
2. **复述目标与假设：** 把用户任务、业务口径、权限边界和验收方式说清；重要业务定义不靠 AI 猜。
3. **追踪完整数据路径：** 找页面、服务、API、数据库写入、读取汇总和文档；用证据回答“现在发生什么”。
4. **先做最小反例与计划：** 定义需要保留的行为、失败行为、受影响文件和测试，再实施。多个职责不同的改动分开验证。
5. **改后验证并更新归处：** 跑覆盖本批逻辑的测试、检查真实用户路径，核对数据库没有被意外写入，并更新必要的帮助、索引和学习文档。
6. **把经验放回合适位置：** 当前规则进权威文件；可复用的检查方法进 05；给人读的跨层经验进 insights；本次发生的事情进执行记录；不要在多个文件复制同一段规则。

让 AI 提供判断和反例，而不是替使用者承担业务裁定。出现权限变化、统计口径变化、跨角色流程变化时，应该明确展示差异和代价，再由负责者决定。

## 8. 常见工程词语

| 词语 | 人话解释 |
|---|---|
| 前端 / 后端 | 用户在浏览器操作的部分 / 在服务器接收请求、校验规则并访问数据的部分 |
| API | 前后端约定如何传请求和结果的接口 |
| 数据适配器 | 把同一种业务操作连接到本地模拟数据或真实服务器数据的转换层 |
| 事务 | 一组数据库操作“全成功或全失败”，避免只写成一半 |
| 迁移 | 可重复、可追踪地改变数据库结构或版本的程序 |
| 认证 / 授权 | 确认“你是谁” / 判断“你能对哪个资源做什么” |
| 单一事实源 | 一条规则或一个事实只有一个权威维护处，其他视图从它读取或生成 |
| 回归测试 | 修复问题后留下的检查，确认以后改动没有把问题重新带回来 |
| mock | 用于开发或测试的模拟数据/接口；需要检查它与真实 API 是否同一口径 |
