# 多代理独立审查操作手册

> **定位：** `CLAUDE.md` H21「多代理独立审查协议」的详版操作手册。H21 是热层规则（什么时候做、必须守住什么），本文是可直接照做的执行层（每步怎么做、提示词怎么发、结果怎么收、裁定怎么记）。
> **read_strategy：** `on-demand`——只在准备启动一轮多视角审查时读；日常任务不需要常驻上下文。
> **何时读：** 支书要求对同一批页面/代码做多视角批判性审查，或 H20.2 命中「脏乱繁 / 最小三成本 / 功能与美观 / 全栈数据结构设计」前置条件时。
> **读者：** 主代理（组织与汇总）、子代理（独立审查）、支书（裁定与验收）。

---

## 1. 适用与边界

### 1.1 适用

| 场景 | 典型问题 | 建议 lens 数 |
|---|---|---|
| 脏乱繁复审计 | 页面脏、乱、繁，层级与主次失守 | 3 |
| 最小三成本 | 信息成本、操作成本、学习成本过高 | 3 |
| 功能与美观 | 功能完整性、视觉主张、交互手感互相拉扯 | 3 |
| 全栈数据结构设计 | 前端呈现、服务端 API、数据模型边界不清 | 3 |

适用前提：同一个范围存在**多种合理判断**，且单一视角容易一刀切；需要保留真实分歧，再由支书裁定。

### 1.2 不适用

- **单视角任务**：只有一个明确判据（如「补齐 `scope="col"`」），直接执行即可。
- **已有明确结论、只需执行的任务**：裁定已完成，只剩实施与验证；不要再开一轮审查。
- **范围大到一轮做不完**：先按 `OPERATIONS_GUIDE.md` §10.5 分片，一次只审一个可完成的范围。
- **没有可验证证据的纯口味争论**：先补证据，或转为设计讨论，不占用多代理流程。

### 1.3 成本边界

一轮审查的成本 = N 个子代理 × 独立读范围 × 独立出报告 + 主代理汇总 + 支书裁定。代理数默认 3，最多 4；不得为了「更全面」无限加人。同一 skill 不得拆给两个代理。

## 2. 一轮审查的 7 步

> 主流程：**定题 → 选 lens → 并行独立审查 → 证据校验 → 汇总 → 人类裁定 → 落 spec 实施**；**复盘**为收尾环节，不单独占步，但不得省略。

| 步 | 动作 | 主代理产出 | 完成判据 |
|---|---|---|---|
| 1 | 定题 | 范围、页面/文件清单、四个待回答问题、排除项 | 范围能在一轮内完成；四个问题已写死 |
| 2 | 选 lens | 本轮 skill 矩阵（每个代理一个不同 skill） | 无重复 skill；未确认的 skill 不入场 |
| 3 | 并行独立审查 | N 份互不可见的独立报告 | 每个代理只加载自己的 skill，未读他人报告 |
| 4 | 证据校验 | 证据核对结果（可用/待补证/剔除） | 每条发现至少一种可复现证据 |
| 5 | 汇总 | 共识 / 分歧 / 待裁定 | 不平均意见、不选边、不替支书决定 |
| 6 | 人类裁定 | 决策记录（原话 + 日期 + 未选方案处理） | 每个分歧 2–4 个互斥选项，一次一问 |
| 7 | 落 spec 实施 → 复盘 | `spec.md` / `tasks.md` / `checklist.md` + 复盘记录 | 实施并验证完成；AI 假设与人类意图的偏差已记录 |

### 2.1 定题

写清五件事，缺一不可：

1. **范围**：本轮审哪些页面/文件/流程。
2. **环境**：视口（如 1440 / 390）、浏览器、数据状态、是否登录。
3. **四个待回答问题**：见 §3.3。
4. **排除项**：本轮明确不看的区域，防止代理扩散。
5. **完成定义**：什么算本轮结束（如「每个代理至少 3 条带证据发现，主代理完成三分类」）。

一轮只审一个范围。发现新问题先记入下一轮选题池，不中途扩范围。

### 2.2 选 lens

- 默认三路，每路一个 skill；skill 必须与审查主题匹配。
- 同一轮内**禁止重复 skill**；同一 skill 给两个代理会失去独立性。
- 未确认可用的 skill 只留在 skill 矩阵的「待确认」列，不得写死进提示词。
- skill 矩阵见 `.trae/specs/generalize-parallel-skill-audit/spec.md` 附录 A。

### 2.3 并行独立审查

- 同时启动 N 个子代理，各自只拿到：本轮范围 + 自己的 skill + §3 的提示词模板。
- 子代理不得读其他代理报告、不得读主代理汇总、不得共享中间结论。
- 子代理只输出 §4 的 schema，不写完整实现，不改任何文件。

### 2.4 证据校验

主代理逐条核对，不核对就不得进入汇总：

| 证据类型 | 校验动作 | 不合格处理 |
|---|---|---|
| `file:line` | 打开文件确认行号与内容一致 | 行号漂移→修正；内容不存在→剔除 |
| 计算样式 | 在指定环境执行，记录实际返回值 | 无法复现→标「待补证」 |
| 截图 | 确认路径存在、视口尺寸与结论一致 | 缺视口信息→要求补 |
| 运行结果 | 记录命令、退出码、关键输出 | 只有结论无输出→剔除 |

「待补证」条目不能进入共识；只能作为待裁定里的低置信项，并注明缺失证据。

### 2.5 汇总

主代理只做三分类：**共识 / 分歧 / 待裁定**。不得把分歧写成「综合建议」，不得用平均意见抹平差异。模板见 §5。

### 2.6 人类裁定

每个分歧点单独问，给 2–4 个互斥选项与各自代价；记录支书原话选择与日期。规则与记录表见 §6。

### 2.7 落 spec 实施与复盘

- 裁定逐条转成 `spec.md` / `tasks.md` / `checklist.md`，未选方案写「已考虑但未采用」。
- 实施后按 H25 跑相关测试，不以 `GetDiagnostics` 零错误代替运行验证。
- 复盘按 `sample-diff-learning` 记录「AI 假设 vs 人类意图」；可泛化规则写入 `DESIGN_SYSTEM` 或 H21 判例，不造第二套。

## 3. 子代理提示词模板

### 3.1 使用方式

1. 主代理复制 §3.2 代码块，逐项替换 `{占位符}`。
2. 一个代理只填一个 `{skill_name}`；同一轮不得重复。
3. 范围内外都要写；不写「自行判断相关文件」。
4. 发送前检查：是否包含「只加载一个 skill」「不读其他代理报告」「四个问题」「证据格式」「禁止形容词」「输出 schema」六项。

### 3.2 可直接复制的模板

```text
你是本轮「{轮次/主题}」审查的独立子代理 {编号}。你只对自己这一路 lens 负责。

## 一、你唯一可用的 lens
只加载并遵循 skill：`{skill_name}`。
- 只使用该 skill 的判据，不混入其他设计观或经验法则。
- 不得加载其他 skill。
- 不得读取、搜索、引用其他代理的报告或主代理的中间结论（包括 .ctx/、.trae/specs/ 下本轮其他代理的输出）。
- 不得猜测其他 lens 会说什么；你的价值是独立，不是共识。

## 二、审查范围
- 主题：{本轮主题，如「脏乱繁复审计」}
- 页面/文件清单：{逐项列出}
- 运行环境：{视口 1440/390、浏览器、登录角色、数据状态}
- 明确排除：{本轮不看的区域}
- 只审这个范围，不扩散到未列出的页面/文件。

## 三、你只回答四个问题
1. 现象：在这个 lens 下，本范围最严重的 3–5 个问题分别是什么？用一句话说清「哪里、什么表现」。
2. 证据：每个问题的可验证证据是什么？必须能让主代理按你写的路径/命令复现。
3. 影响：每个问题对用户完成任务、可读性、可维护性或性能的具体影响是什么？不要写「体验不好」。
4. 建议方向与代价：每个问题建议往哪个方向改？代价是什么（改动范围、风险、可能牺牲什么）？不要写完整实现。

## 四、证据格式（每条至少一种，且必须可复现）
- 代码位置：`path/to/file.js:123`（行号必须与当前工作区一致）
- 计算样式：`getComputedStyle(document.querySelector('...')).color` 的实际返回值
- 截图：`.ctx/screenshots/{round}/{agent}-{nn}.png`（注明视口尺寸与页面状态）
- 运行结果：完整命令 + 关键输出 + 退出码
- DOM 结构：选择器 + 关键 outerHTML 片段（不超过 5 行）

## 五、禁止
- 禁止只有形容词：「很脏」「不美」「拥挤」「不高级」等不得单独成条，必须落到具体元素与证据。
- 禁止写完整实现、补丁或大段重构代码；只写建议方向。
- 禁止替支书做取舍，禁止写「建议采用某方案」式的最终裁决。
- 禁止读取或引用其他代理报告。
- 禁止修改任何文件、禁止运行会写数据的命令。
- 禁止把未验证的猜测写成事实；不确定就标「待补证」。

## 六、输出格式（只输出这些）
### lens 总评
不超过 100 字：本 lens 下这个范围的核心问题是什么。

### 发现表
| 编号 | 现象 | 证据 | 影响 | 建议方向 | 严重度 | 可能冲突 |
|---|---|---|---|---|---|---|
| {agent}-01 | ... | ... | ... | ... | P0/P1/P2 | 无 / 可能与 {lens} 冲突：{一句话理由} |

严重度定义：
- P0：阻断任务完成、数据错误、关键操作不可达。
- P1：明显损害效率、可读性、一致性，但有绕行办法。
- P2：打磨项，不影响任务完成。

### 待补证
| 编号 | 缺什么证据 | 需要主代理怎么补 |
|---|---|---|
| ... | ... | ... |

只输出以上内容，不要附加寒暄、总结或实施计划。
```

### 3.3 四个待回答问题的固定口径

| 问题 | 对应 schema 列 | 不合格表现 |
|---|---|---|
| 现象是什么 | 现象 | 「整体很乱」 |
| 证据是什么 | 证据 | 「肉眼可见」 |
| 影响是什么 | 影响 | 「体验差」 |
| 建议方向与代价是什么 | 建议方向 / 可能冲突 | 直接给完整代码或替支书拍板 |

四个问题必须原样出现在提示词里，不得只写「请审查」。

## 4. 输出 schema

### 4.1 表格列定义

| 列 | 必填 | 写法 | 反例 |
|---|---|---|---|
| 编号 | 是 | `{agent}-{NN}`，如 `wdg-01` | `1`、`问题一` |
| 现象 | 是 | 哪里 + 什么表现，一句话 | 「很脏」 |
| 证据 | 是 | `file:line` / 计算样式 / 截图路径 / 运行输出 | 「看起来」 |
| 影响 | 是 | 对任务、可读性、可维护性、性能的具体后果 | 「不好用」 |
| 建议方向 | 是 | 方向 + 代价，不写完整实现 | 直接贴补丁 |
| 严重度 | 是 | `P0` / `P1` / `P2` | 「严重」 |
| 可能冲突 | 是 | `无` 或 `可能与 {lens} 冲突：{理由}` | 留空 |

### 4.2 证据格式示例

| 类型 | 示例 | 说明 |
|---|---|---|
| 代码行 | `docs/src/components/ui/data-table.js:123` | 行号必须与当前工作区一致；行号漂移视为无效 |
| 计算样式 | `getComputedStyle(document.querySelector('.btn-accent')).backgroundColor` → `rgb(135, 87, 17)` | 记录实际返回值，不写「偏褐」 |
| 截图 | `.ctx/screenshots/round1/design-with-taste-01.png`（390×844，待办页） | 必须注明视口与页面状态 |
| 运行结果 | `node server/test/module-load.test.mjs` → 退出码 0 | 记录命令、退出码、关键输出 |
| DOM | `document.querySelector('.ws-tab-scroll').scrollWidth > clientWidth` → `true` | 可复现的判定表达式 |

### 4.3 单条发现示例

| 编号 | 现象 | 证据 | 影响 | 建议方向 | 严重度 | 可能冲突 |
|---|---|---|---|---|---|---|
| wdg-02 | 390px 待办表格横向溢出，行尾操作列被推出屏外 | `.ctx/screenshots/round1/web-design-guidelines-02.png`（390×844）；`document.querySelector('.data-table').scrollWidth` 大于容器宽度 | 移动端无法直接处理待办，必须横向拖动 | 窄屏改为卡式行；代价是桌面/移动双形态，需补响应式测试 | P0 | 可能与 design-with-taste 冲突：对方可能主张保留表格密度 |

### 4.4 报告级要求

- 每个代理 3–5 条，少于 3 条需说明「本 lens 下仅发现 N 条」，不得凑数。
- 同一现象只写一条；不要把同一问题拆成多条抬高数量。
- 「待补证」单列，不混入发现表冒充已证实结论。

## 5. 主代理汇总模板

### 5.1 汇总原则

- 只输出三节：共识 / 分歧 / 待裁定。
- 共识 = 两个及以上 lens 独立指向同一现象，且证据可交叉验证；不是「主代理也同意」。
- 分歧 = lens 之间结论相反或代价取舍不同；必须并列两方证据与代价，**不得选边**。
- 待裁定 = 需要支书拍板的事项；每项给 2–4 个互斥选项。

### 5.2 可直接复制的模板

```markdown
# {轮次} 多代理审查汇总

- 范围：{页面/文件/流程}
- 环境：{视口/浏览器/角色/数据状态}
- 参与 lens：{skill 1} / {skill 2} / {skill 3}
- 输入：{N} 份独立报告（{agent 编号清单}）
- 证据校验：{通过 X 条 / 待补证 Y 条 / 剔除 Z 条}

## 一、共识

| # | 现象 | 交叉证据 | 影响 | 涉及 lens | 建议轮次 |
|---|---|---|---|---|---|
| C1 | ... | ... | ... | ... | 本轮 / 下一轮 |

## 二、分歧

### D1 {决策点，一句话}

- **甲方 lens：{skill A}**
  - 主张：...
  - 证据：...
  - 代价：...
- **乙方 lens：{skill B}**
  - 主张：...
  - 证据：...
  - 代价：...
- **主代理：不选边。** 两方成立的前提分别是：{甲前提} / {乙前提}。

### D2 ...

## 三、待裁定

| # | 决策点 | 选项 A | 选项 B | 选项 C（可选） | 选项 D（可选） |
|---|---|---|---|---|---|
| Q1 | ... | ...（代价：...） | ...（代价：...） | ... | — |

> 每个决策点单独提问，选项互斥；不得把多个决策点打包成一个问题。
```

### 5.3 分歧写法要求

- 必须并列：主张、证据、代价、成立前提，四项齐全。
- 不得写「综合来看建议 A」；不得用「多数 lens 认为」替代证据。
- 若一方证据不足，标注「该方待补证」，但仍保留其主张，不替它删除。
- 若两方其实在说不同层面（如视觉密度 vs 任务可达性），先指出层面差异，再交支书裁定。

### 5.4 待裁定写法要求

- 每项 2–4 个**互斥**选项；不能同时选，也不能「都要」。
- 每个选项写代价，不写「更好」。
- 选项必须是可执行的决定，不写「再研究一下」作为唯一选项；确需研究时，把「先做小样验证」作为一个有代价的选项。

## 6. 人类裁定与决策记录

### 6.1 AskUserQuestion 规则

1. **一次一个决策点**：一个提问只包含一个分歧，不打包。
2. **选项互斥**：2–4 个，覆盖真实取舍；不设「都行」。
3. **每个选项写代价**：支书看到的是代价，不是 AI 的偏好。
4. **记录原话**：支书选了什么、原话怎么说、日期是哪天。
5. **未选方案不静默丢弃**：写「已考虑但未采用：{方案}——{理由}」，进 spec 的「已裁定 / 不在本批」。
6. **支书选择优先**：与任何 agent 建议冲突时，以支书选择为准；AI 不得替支书拍板。
7. **答复含糊时继续追问**：如「你决定」，回到选项与代价，请支书明确选一个；不得自行代选。

### 6.2 决策记录表模板

| 决策点 | 选项 A | 选项 B | 支书选择 | 日期 | 未选方案处理 |
|---|---|---|---|---|---|
| {一句话决策点} | {方案 + 代价} | {方案 + 代价} | {原话/明确选择} | YYYY-MM-DD | 已考虑但未采用：{方案}——{理由/归入哪批} |

> 有第三、第四个选项时，在「选项 B」单元格内换行续写 `选项 C：...` / `选项 D：...`，或另起一行同一决策点；不得省略未选方案。

### 6.3 判例填写示例

| 决策点 | 选项 A | 选项 B | 支书选择 | 日期 | 未选方案处理 |
|---|---|---|---|---|---|
| 390px 表格怎么保操作可达 | 卡式行：每行「标签：值 + 行尾动作」；代价是桌面/移动双形态 | 冻结列：保留表格，横向滚动；代价是操作列仍可能滑出屏外 | 卡式行（2026-10-19） | 2026-10-19 | 已考虑但未采用：冻结列——390px 下横向滚动仍损害操作可达性 |

## 7. 反模式清单

| # | 反模式 | 典型表现 | 后果 | 正确做法 |
|---|---|---|---|---|
| 1 | 同一 skill 给两个代理 | 两个代理都加载 `frontend-design`，只换提示词措辞 | 结论高度重合，误当「共识」 | 一轮内每个代理一个不同 skill；矩阵去重 |
| 2 | 代理互读报告 | 主代理把 A 的报告发给 B「参考一下」 | 独立性消失，分歧被提前抹平 | 只发范围 + 自己的 skill；报告在汇总前互不可见 |
| 3 | 主代理平均意见 | 「综合三方，建议折中」 | 真实分歧被掩盖，支书失去选择权 | 只分共识/分歧/待裁定；分歧并列证据与代价 |
| 4 | 无证据的「很脏/不美」 | 只有形容词，没有 `file:line`、计算样式或截图 | 无法复核，无法验收，容易误伤 | 每条必须带可复现证据；无证据进「待补证」 |
| 5 | AI 替支书拍板 | 汇总里直接写「建议采用 A」并开始实施 | 越权，人类意图被替代 | 给互斥选项与代价，等支书选择后再落 spec |
| 6 | 四轮同时开 | 一轮还没裁定，就并行启动后三轮 | 范围爆炸、上下文丢失、裁定互相污染 | 逐轮启动；上一轮裁定并落 spec 后再开下一轮 |
| 7 | 把未确认 skill 写死 | 提示词里写了当前环境不存在的 skill | 代理假装已加载，判据失真 | 只写矩阵中「已验证」的 skill；未确认的留「待确认」 |

补充红线：

- 不得用「多数 lens 同意」代替交叉证据。
- 不得把同一问题拆成多条制造共识。
- 不得在子代理提示词里预埋结论或期望答案。
- 不得跳过证据校验直接汇总。

## 8. 判例：2026-10-19 脏乱繁三路审计

### 8.1 定题与 lens

- **主题**：桌面与 390px 关键页面的脏乱繁复审计。
- **lens**：`web-design-guidelines` / `design-with-taste` / `frontend-design`，三路各一代理，互不读报告。
- **输入**：当前页面实测 + 既有 68 页签审计稿 + `REVIEW_QUEUE` 未闭环项。
- **输出**：三份独立发现表，主代理汇总为共识 / 分歧 / 待裁定。

### 8.2 六项共识

| # | 共识现象 | 证据类型 | 影响 |
|---|---|---|---|
| C1 | 390px 表格失守，操作列被推出屏外 | 390 截图 + 容器 `scrollWidth` 大于可视宽度 | 移动端关键操作不可达 |
| C2 | 1440/390 页签被裁，溢出无提示 | 页签容器滚动宽度大于可视宽度；末项不可见 | 页签不可发现，功能像消失 |
| C3 | 待答复被折叠，首屏看不到 | 待办页首屏截图 | 待办入口失效，任务漏处理 |
| C4 | 指标重复且重心错 | 卡头/卡尾重复计数；「在办」字号最大 | 第一眼抓不到逾期与待我处理 |
| C5 | 选人是假模态 | 焦点可落到遮罩后；body 未锁滚动 | 键盘与移动端操作混乱 |
| C6 | 行内动作等权 | 「设/改」「改名」「解散」同权重并排 | 危险动作易误触 |

> 共识判据：三项发现由两个及以上 lens 独立指向同一元素，且证据可复核；不是主代理的主观合并。详细证据与验收见 `.trae/specs/harden-mobile-and-primary-actions/`。

### 8.3 五项分歧

| # | 决策点 | 甲方主张与代价 | 乙方主张与代价 | 结果 |
|---|---|---|---|---|
| D1 | 390px 表格怎么保操作可达 | 卡式行：操作留在行尾；代价是双形态与响应式测试 | 冻结列：保留表格语义；代价是横向滚动仍可能滑出 | 支书裁定：卡式行 |
| D2 | 待答复首屏露几条 | 默认露 2 条：首屏可见；代价是占用首屏高度 | 全部收起：首屏简洁；代价是待办不可发现 | 支书裁定：默认露 2 条 |
| D3 | 主 CTA 用什么颜色 | 角色色全强度：主次清晰；代价是需处理白字对比度 | 深灰混色：对比度稳；代价是主 CTA 发泥褐、失去角色识别 | 支书裁定：角色色全强度，对比度不足用 `--app-accent-strong` |
| D4 | 活动风采去留 | 保留并改造：白卡 + 类型色；代价是本批范围扩大 | 移出首屏/删除：聚焦待办；代价是首页少一块内容 | 未列入四项裁定，进 Phase 2 观察（去渐变、改名「近期活动」） |
| D5 | 页签溢出怎么提示 | 渐隐 + 箭头：不改变 tab 尺寸；代价是需处理滚动边界 | 「更多」菜单：入口明确；代价是改变现有页签交互 | 支书裁定：渐隐 + 箭头 |

### 8.4 支书四项裁定

| 决策点 | 裁定 | 落点 |
|---|---|---|
| 390px 表格 | 卡式行：≤640px 每行「标签：值 + 行尾动作」，桌面保留表格 | `spec.md`『窄屏表格卡式行』 |
| 主 CTA 颜色 | 角色色全强度，不再与深灰混合；对比度不足用 `--app-accent-strong` | `spec.md`『主 CTA 角色色全强度』 |
| 待答复首屏 | 默认露 2 条，其余与未读通知收起 | `spec.md`『待答复首屏露 2』 |
| 页签溢出 | 渐隐 + 箭头，保留 tab 尺寸与选中态 | `spec.md`『页签溢出可发现』 |

### 8.5 落点与复盘

- **落点**：`.trae/specs/harden-mobile-and-primary-actions/`（`spec.md` / `tasks.md` / `checklist.md`）。
- **未选方案**：已裁定项中的冻结列、全部收起、深灰混色、「更多」菜单均记为「已考虑但未采用」，不静默丢弃；D4 活动风采未裁定，留在 Phase 2 选题池。
- **复盘要点**：
  - AI 容易把分歧折中成「兼顾两方」，人类要的是**明确取舍 + 代价**。
  - AI 容易把 P2 打磨项塞进 P0 批次；支书按「任务可达性优先」截断范围。
  - 可泛化规则回写 `DESIGN_SYSTEM` 或 H21 判例，不新造第二套设计规范。

## 11. 批判性 IA 审查（H21.3 · 2026-10-19 立）

> 判例：`.ctx/logs/archive/2026-10/AUDIT_IA_CRITICAL.md`、`.ctx/logs/archive/2026-10/IA_INVENTORY.md`、`.ctx/logs/archive/2026-10/IA_LINK_TRUTH.md`。
> 起因：支书指出「入口太多、界面太多，没有各尽其责又相互配合；链接还有问题」。上一轮 H21 擅长「页面做得好不好」，不擅长「该不该存在、指向对不对」。

### 11.1 三问（未过不得进入视觉/无障碍评分）

1. **这个 tab 是否必须存在？** 一 tab 一问；同问或 80% 可承接 ⇒ 合并候选；无独有主行动/数据/角色 ⇒ 删除候选。
2. **这张卡是否改变一个决策或触发一个动作？** 纯展示且不影响决策 ⇒ 删除/下沉；每 tab 只留一条主阅读线。
3. **这枚链接是否指向「该角色 + 该对象 + 该步骤」的正确落点？** 目标 page 必须对该角色可达；目标 tab 必须是动作本位；对象 id 必须携带且被消费。

### 11.2 数据适配功能原则

- DB / 枚举 / mock 以页面功能与权限判据为准，不以「旧数据已有」为保留理由。
- mock 数据只是验证辅助，可删、可改、可重写；不得为兼容旧 mock 削足适履。
- 状态集合由 UI 流程反推：页面筛选什么、授权认什么、写口校验什么，就定义什么状态。

### 11.3 sample-diff 学到的 Boolean 规则（项目层）

| 编号 | Boolean 规则 | 证据 |
|---|---|---|
| AP-IA-01 | IF 链接目标是 `workspace/*` 且不属于当前角色本位台 THEN 按角色派生 href 或渲染纯文本交接；禁止一条链接打天下 | 材料闭环四行链接；`bootstrap.js:172-201` |
| AP-IA-02 | IF 某 tab 对该角色是稳定空集 THEN 删除/合并并保留旧 id 别名；不得保留空壳 tab | 纪检/宣传 `tf-view` |
| AP-IA-03 | IF 一张卡同时承载只读决策信息与写 CTA THEN 拆分；写 CTA 移到页头或独立主行动区，每屏最多 1 个 | 六台 `today` 日程卡 |
| AP-IA-04 | IF 交接为 auto-confirm THEN 不为接收方派生可执行待办；改为只读回执，confirm 幂等返回 true | 纪检自动交接 |
| AP-IA-05 | IF 深链携带 `highlight`/对象 id THEN 壳必须先下发 `navTarget` 再清参，目标页必须消费；定位失败必须可见提示 | `review&highlight`；`thought-review&highlight` |
| CTX-01 | IF 审计结论已沉淀到原则 / 方法文档 THEN 原文必须在 `.ctx/logs/archive/YYYY-MM/`；不得继续留在 `.ctx` 顶层 | 2026-10 IA 三件套归档 |
| CTX-02 | IF 产物可由脚本重跑 THEN 不得作为权威常驻 `.ctx` 顶层；守卫读 `archive` 路径或直接跑生成脚本 | `server/scripts/ia-inventory.mjs` → `IA_INVENTORY.md` |
| CTX-03 | IF 内容是可复用契约（逐角色落点 / 深链协议）THEN 进 `content/04_web_design/module/MODULE_UI_DESIGN.md` 一类设计文档，不进审计报告常驻 | `IA_LINK_TRUTH.md` 材料闭环表 → MODULE_UI_DESIGN §五 |
| CTX-04 | IF `.ctx` 顶层新增文件 THEN 必须命中白名单（`logs/`、`evidence/`、`TIMESTAMPS.md`、`SNAPSHOT.md`、`REVIEW_QUEUE.md`、`ACTIVE_RULINGS.md`、`ENGINEERING_ASSESSMENT.md`）；否则先沉淀再归档 | `CLAUDE.md H26.3` |

### 11.4 审查顺序

1. 先做 IA 矩阵（tab / 卡片 / 链接 / 深链参数）。
2. 再过三问；三问未过的 tab/卡片/链接不进入视觉评分。
3. 再做六路批判性 lens：tab 必要性、卡片顺序、链接真值、跨角色交接、最小三成本、数据/路由真值。
4. 汇总共识/分歧/待裁定；只开一次 frontier。
5. 修复 spec 按「删/并 → 链接落点 → 卡片顺序 → 交接」排序。

### 11.5 证据要求

- 每条结论必须有矩阵行或 `文件:行号`；真机读数单独标。
- 不得用「感觉乱」替代「该不该存在」；不得用「看起来多」作为删除唯一理由。
- 跨角色链接必须给分角色落点表，不能只给一个目标页。

## 12. 全局性审查的五问（2026-10-20 立 · 第三轮专项沉淀）

> **判例**：`.ctx/logs/archive/2026-10/UI_AUDIT_R3.md`（浮窗 / 筛选 / 名实）、`.ctx/logs/archive/2026-10/FULLSTACK_AUDIT_R3.md`（数据真值 / 权限 / 迁移）。
> **用途**：单页审查回答「这页好不好」；五问回答「这个对象在全站是否只有一个说法」。**先跑五问，再进入 §11 三问与视觉评分**；任一问为真，暂停逐页修复，按 §12.2 发起专项。

### 12.1 五问与 Boolean 条件

| # | 问 | Boolean 条件（为真＝违规） | 判例路径 |
|---|---|---|---|
| G-1 | **承载面**：同一对象是否只有一个完整内容面？ | 同一对象（活动 / 专班 / 思想汇报 / 待办）在 ≥ 2 处各有完整正文或完整字段清单，且两处都能改写 | `UI_AUDIT_R3.md` 判例③④、§六 重复入口；规则落 `DESIGN_SYSTEM.md` §10.7 |
