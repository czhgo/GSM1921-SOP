# 概念复用性扫描评议·设计文档

## 1. 任务背景

T-116 反论评议·第三轮完成后，书记临时穿插"概念复用性扫描评议"任务——在整个仓库范围内扫描所有孤立概念（零星出现或仅出现 1 次的名词/形容词/动词），逐条判定是表达原因还是 AI 错误扩充/概括原因导致。

本任务属于 T-117 理论复用评议的变体——更聚焦于"孤立概念"的扫描与判定，而非"跨节/跨文件引用"的复用准确性。

## 2. 任务目标

1. **扫描**：在整个仓库范围内（排除 .github/、审计层历史记录）扫描所有 ≤2 次出现的名词/形容词/动词
2. **判定**：对每条孤立概念逐条判定原因（5 类细分）
3. **报告**：写入 `.ctx/REVIEW_QUEUE.md`，供书记决策
4. **不修订**：本阶段仅扫描+判定+报告，不即时修订

## 4. 扫描方法（方案 A：脚本驱动全量扫描）

### 4.1 技术流程

```
阶段1：文本提取
├─ 提取所有 .md 文件纯文本
└─ 提取 .js 文件中的中文注释（// 和 /* */）+ 字符串字面量中的中文

阶段2：候选词提取
├─ 中文 n-gram：2-6 字连续中文字符
└─ 英文单词：连续字母（含驼峰分词）

阶段3：频次统计
├─ 对每个候选词统计全仓库出现次数
└─ 输出频次表

阶段4：筛选
├─ 筛选 ≤2 次的候选词
└─ 按频次升序排列

阶段5：人工分类
├─ 概念性词汇（保留判定）
├─ 技术细节（如变量名、文件路径）
├─ 常见词（如"的"、"是"等功能词）
└─ 英文词（如"localStorage"）

阶段6：判定
└─ 对概念性词汇逐条判定原因（5 类细分）
```

### 4.2 技术实现

使用 PowerShell 脚本：
1. `Get-ChildItem` 递归获取目标文件
2. 正则提取中文连续字符段和英文单词
3. 哈希表统计频次
4. 输出 CSV 或 Markdown 表格

### 4.3 噪声控制

由于"不排除任何词"，扫描结果会包含大量噪声。采用以下策略控制：
1. **n-gram 长度限制**：仅 2-6 字中文（单字噪声大，6 字以上罕见）
2. **频次筛选**：≤2 次
3. **人工分类**：将候选词分为概念性词汇/技术细节/常见词/英文词四类
4. **聚焦判定**：仅对概念性词汇逐条判定原因

## 4.4 "概念性词汇"的判定标准

为避免人工分类阶段的主观性，明确以下标准：

| 类别 | 定义 | 处置 |
|------|------|------|
| **概念性词汇**（聚焦判定） | 表达某种管理理念、组织设计、流程原则的名词/形容词/动词组合（如"赋权链"、"扁平化"、"动态派生"、"按需选择"） | 进入判定流程 |
| **技术细节** | 变量名、文件路径、函数名、CSS类名等代码标识符（如 `localStorage`、`renderTabBar`、`docs/src/`） | 不判定，但记录在报告中备查 |
| **功能词** | 单字功能词（的、是、在、了等）、纯连接词、标点 | 直接过滤 |
| **专有名词** | 人名、地名、机构名、文件名、日期等（如"光华管理学院"、"2026-07-19"） | 不判定 |
| **数字与英文** | 纯数字、英文缩写（如"T1"、"H5"） | 不判定 |

**同义概念处理**：当两个孤立候选词实际指同一概念时（如"赋权链"与"赋权链条"），人工判定时合并频次后重新判定是否仍为孤立。

## 5. 判定维度（5 类细分）

| 维度 | 含义 | 典型特征 | 处置建议 |
|------|------|---------|---------|
| **表达原因·书记原话** | 书记有意使用的特定表达 | 可溯源到书记原话记录 | 保留 |
| **表达原因·特定场景** | 在特定上下文中有意义的孤立概念 | 在某个判例/某次决策中产生 | 保留 |
| **AI 错误扩充** | AI 添加了书记没说过的内容 | 无母本溯源，AI 自行创造 | 删除或改写 |
| **AI 错误概括** | AI 把书记的话概括成不存在的概念 | 书记原话被 AI 提炼为不存在的标签 | 改写为正论 |
| **历史残留** | 曾经使用但现已废弃 | 可溯源到已废弃的术语/概念 | 标注废弃或删除 |

### 5.1 判定流程

每条孤立概念按以下顺序判定：

1. **溯源**：是否能溯源到书记原话/决策记录？
   - 溯源路径：`SECRETARY_PRONOUNCEMENTS.md`（书记论断）→ `.ctx/logs/DECISION_LOG.md`（决策记录）→ `.ctx/logs/*-EXECUTION_LOG.md`（执行日志中书记反馈原文）
   - 找到原话 → 表达原因·书记原话
   - 未找到 → 进入下一步
2. **场景**：是否在特定判例/决策场景中产生？
   - 判定依据：该概念是否在某个具体的 D-XXX 决策、某次书记评议反馈、某个特定 T 编号任务中产生
   - 是 → 表达原因·特定场景
   - 否 → 进入下一步
3. **AI 推导**：是否为 AI 自行创造/概括？
   - **AI 错误扩充**：AI 添加了书记未说过的内容（无母本溯源，AI 自行创造）
   - **AI 错误概括**：AI 把书记原话概括成不存在的概念（书记原话被 AI 提炼为不存在的标签）
   - 区分依据：是否能在书记原话中找到相近表述？有但被 AI 改写 → 错误概括；完全没有 → 错误扩充
   - 是 → AI 错误扩充或 AI 错误概括
   - 否 → 进入下一步
4. **历史**：是否为已废弃的术语/概念？
   - 判定依据：`USAGE_POLICY.md §1.1.2 废弃术语对照`、insights 中的"已被XX条件下的新经验修正"标注
   - 是 → 历史残留
   - 否 → 标记为"待书记判定"

### 6.2 反馈分流

按 H5.4 三层分流：
- **机械性问题**：AI 错误扩充/概括的孤立概念 → 删除或改写
- **设计性问题**：是否保留某概念的判断分歧 → 写入丙部
- **即时小修订**：typo/格式错误 → 当场修复

## 7. 工作流程

```
1. 脚本扫描阶段（AI 执行）
   ├─ 提取候选词
   ├─ 统计频次
   └─ 筛选 ≤2 次

2. 人工筛选阶段（AI 执行）
   ├─ 分类候选词
   └─ 聚焦概念性词汇

3. 判定阶段（AI 执行）
   └─ 逐条判定原因（5 类细分）

4. 报告阶段（AI 执行）
   └─ 写入 REVIEW_QUEUE.md

5. 书记决策阶段（书记执行）
   └─ 在 REVIEW_QUEUE.md 中填写反馈

6. 分流阶段（AI 执行）
   ├─ 机械性问题 → 删除/改写
   ├─ 设计性问题 → 入丙部
   └─ 即时小修订 → 当场修复

7. 收尾阶段（AI 执行）
   ├─ 执行日志写入
   └─ Git commit
```

## 8. 验证标准

按 verification-before-completion skill：
1. **扫描完整性**：所有目标文件均已扫描（`Get-ChildItem` 计数验证）
2. **频次准确性**：抽样验证 5-10 个候选词的频次（`rg -c` 交叉验证）
3. **判定完整性**：每条概念性词汇均有判定（无"待判定"残留，除"待书记判定"外）
4. **报告完整性**：REVIEW_QUEUE.md 包含所有必要字段

## 10. 风险与应对

| 风险 | 应对 |
|------|------|
| n-gram 产生大量噪声 | 人工筛选阶段过滤，仅聚焦概念性词汇 |
| 中文分词不准确 | n-gram 重叠覆盖，人工判定时验证 |
| 代码注释中的概念遗漏 | 阶段 1 文本提取时确保包含 .js 文件中文内容 |
| 判定标准主观 | 5 类维度有明确判定流程（§5.1） |
| 扫描结果过多 | 分批评议，每批 20-30 条孤立概念，避免书记单次审阅负担过重 |
| 代码注释中概念与文档概念混淆 | 报告中按文件来源分组标注（根目录 .md / content/ .md / docs/src/ .js） |
| 跨文件同义概念被分别计为孤立 | 人工判定阶段识别同义关系，合并频次后重新判定 |
