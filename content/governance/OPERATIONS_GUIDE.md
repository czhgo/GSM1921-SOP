# 运行标准与操作规范

## 1. YAML Frontmatter规范

所有 `content/` 目录下的 `.md` 文件必须包含以下字段（按顺序）：

```yaml
---
title: "中文标题"
type: <枚举值>
role: "[用户]"/"[工程师]"/"[AI]"（可用 + 连接形成复合标记）
last_updated: "YYYY-MM-DD"
version: "X.Y"
status: active/archived/suspended
related_files: [...]
---
```

**type 枚举值**（仅限以下值，不得自创）：

| type             | 含义             | 典型位置                         |
| ---------------- | -------------- | ---------------------------- |
| `roadmap`        | 项目路线图与 Harness | 根目录 CLAUDE.md                |
| `architecture`   | 架构设计文档         | 根目录 ARCHITECTURE.md         |
| `SOP`            | 制度母本           | content/sop/                 |
| `guide`          | 设计理念与操作指南      | content/strategy/, content/design/ |
| `governance`     | 治理规范           | content/governance/          |
| `design`         | 功能设计方案         | content/design/              |
| `experience_doc` | 经验沉淀           | content/insights/            |
| `reference`      | 参考模板           | content/references/          |
| `template`       | 可复用模板          | content/references/工作模板/    |
| `index`          | 目录索引           | 各目录 README.md                |
| `log`            | 执行日志           | .ctx/logs/                   |
| `decision_log`   | 决策日志           | .ctx/logs/                   |
| `audit_report`   | 审计报告           | .ctx/logs/                   |
| `snapshot`       | 系统快照           | .ctx/snapshots/              |

**已废弃的 type 值**：`CLAUDE.md`（改为 `roadmap`）、`模板`（改为 `template`）、`导航`（改为 `index`）

## 4. 编码规范

全仓库必须遵守以下编码标准，确保中文内容在所有工具链中正确显示：

1. **文件编码**：所有文本文件（`.md`、`.js`、`.html`、`.css`、`.json`、`.yaml`）必须使用 **UTF-8 无 BOM** 编码
2. **换行符**：统一使用 **LF**（`\n`），禁止 CRLF（`\r\n`）。`.gitattributes` 中应设置 `* text=auto eol=lf`
3. **中文标点**：Markdown 正文中使用**中文标点**（，。：；！？""''），代码和表格内使用英文标点
4. **git 操作编码**：执行 `git show`/`git diff` 等命令时，必须设置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，避免中文乱码
5. **PowerShell 输出**：使用 `Out-File -Encoding utf8` 保存文件，禁止使用默认的 Windows 编码

## 5. 文档关系定义

**CLAUDE.md、guides、insights、logs 之间的关系**：

```
                    CLAUDE.md（甲部 Harness）
                    ┌──────────────────────┐
                    │ 核心原则 + 判例       │  ← 最高权威，定义"是什么"和"为什么"
                    │ 乙部执行事项          │  ← 当前工作上下文
                    └──────────┬───────────┘
                               │ 引用
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │  guides/   │   │ insights/  │   │   logs/    │
     │ 设计理念   │   │ 经验沉淀   │   │ 运行记录   │
     └────────────┘   └────────────┘   └────────────┘
     定义"怎么设计"   提炼"什么经验"   记录"做了什么"
```

**四者职责**：

| 维度         | CLAUDE.md 甲部   | guides/          | insights/   | logs/       |
| ---------- | -------------- | ---------------- | ----------- | ----------- |
| **定位**     | 核心原则（原则+判例）      | 法律（详细设计）         | 案例法（经验模式）   | 庭审记录（事实）    |
| **内容**     | 核心原则、关键判例、运行标准 | 完整设计文档、架构方案      | 可复用经验、管理哲学  | 操作步骤、决策过程   |
| **稳定性**    | 最稳定（修改须书记确认）   | 稳定（设计理念始终存在）     | 渐进增长（定期沉淀）  | 只增不改（归档后冻结） |
| **信息流向** → | ← guides 补充细节  | ← CLAUDE.md 授权原则 | ← logs 沉淀提炼 | ← 执行过程产生    |
| **信息流向** ↓ | ↓ 乙部规定当前工作     | ↓ 代码实现设计         | ↓ 指导未来决策    | ↓ 归档为历史     |

**关键规则**：

- CLAUDE.md 甲部是 guides 的**摘要和索引**，不是 guides 的副本。甲部保留核心原则+判例，详细设计归 guides
- 当甲部与 guides 内容冲突时，以**甲部为准**（本文件 §7.1 上层优先原则）
- guides 的更新如果涉及甲部引用的原则变更，必须**同步更新甲部**（H2.1 一改具改）
- insights 从 logs 中沉淀提炼，不直接从 guides 中产生
- logs 是原始记录，insights 是提炼后的知识，两者不可互相替代

## 6. 编号命名规则

### 6.1 甲部 Harness 编号体系

采用**字母+数字**的层级编号，格式为 `H<层>.<节>`：

```
H1   ← 一级章节（大领域）
H1.1 ← 二级章节（具体事项）
H1.1.1 ← 三级章节（细则，仅在必要时使用）
```

**层级约束**：

- 最多**三级**（H1.1.1），不得出现四级（H1.1.1.1）
- 若三级不够用，说明该节应拆分为独立的二级章节
- 新增章节时，在当前同层级末尾追加编号，**不得插队**

**编号预留策略（防数字爆炸）**：

- 一级章节编号按 10 递增预留：H10, H20, H30...（当前 H1\~H10 实际使用 H10\~H100）
- 但为可读性，当前阶段使用连续编号（H1\~H10），当 H10 用满后切换为 H20 递增制
- 二级编号按 1 递增，不预留
- 三级编号按 1 递增，不预留

**编号语义对照**：

| 编号 | 语义   | 当前内容                                             |
| -- | ---- | ------------------------------------------------ |
| H1 | 工作流  | 审查/执行/next\_prompt                                |
| H2 | 一改具改 | 一改具改/母本子本/Guides定位/经验沉淀                           |
| H3 | 检查清单 | 文件修改检查清单                                          |
| H4 | 甲部修改与钩稽 | 甲部修改/钩稽/Snapshot                                  |
| H5 | 乙部与丙部 | 乙部生命周期/丙部待决策                                      |
| H6 | 日志规范 | 日志写入/执行日志/决策日志/分片                                 |
| H7 | 已知陷阱 | 上下文丢失教训                                           |
| H8 | 理论基石 | 党建与党务/视图/专班/双向修改/赋权/扁平化                              |
| H9 | 运行标准 | YAML/术语/角色/编码/文档关系/编号规则（详见本文件 §1-§7）              |
| H10 | 快速导航 | 导航表                                              |

### 6.2 乙部任务编号体系

格式：`T<轮次>-<序号>`

- **轮次**：按工作日递增（T30, T31, T32...），每轮可包含多个任务
- **序号**：同一轮次内的任务序号（1, 2, 3...）
- **跨轮延续**：若某任务未完成，在新轮次中保留原编号，不重新编号

**防数字爆炸策略**：

- 轮次编号与日期绑定，不与任务数量绑定。一个工作日 = 一个轮次，无论当天有多少任务
- 轮次编号不要求连续——T30 之后可以是 T35（中间跳过的轮次编号不回收）
- 序号上限：单轮次内序号原则上不超过 20。若超过，说明该轮次应拆分为多个轮次
- **持续任务**使用 `C-<序号>` 前缀，不占用 T 编号空间
- **待讨论议题**使用 `D.<序号>` 前缀，**暂缓议题**使用 `F.<序号>` 前缀

### 6.3 编号对应关系

乙部任务编号与日志条目之间**必须建立双向可追溯关系**：

```
CLAUDE.md 乙部任务 T30-7  ←→  EXECUTION_LOG 中包含 "T30-7" 的条目
```

**执行日志中的编号规则**：

- 每条日志条目标题格式：`## YYYY-MM-DD | T<轮次> — <一句话摘要>`
- 条目内用 `T<轮次>-<序号>` 标注具体完成的任务
- 若一次工作完成多个任务，在条目内逐项标注

**决策日志中的编号规则**：

- 格式：`D-<序号>`，全局递增，不按月重置
- 若某决策与乙部任务相关，标注对应任务 ID（如 `关联任务: T30-7`）

### 6.4 用户补充工作的流程

用户在对话中直接提出的任务（非乙部已有条目），按以下流程处理：

1. **判断是否涉及决策**：
   - 若涉及方案选择（A vs B）、制度变更、架构调整 → **必须写入决策日志**
   - 若仅为执行性操作（修 bug、补字段）→ 仅写入执行日志
2. **写入乙部**：将用户补充的任务追加到乙部对应优先级分组，分配新编号
3. **执行**：按 H1.2 标准流程执行
4. **完成后**：从乙部删除，写入执行日志

**特殊场景**：用户直接要求"立即做 X"且 X 可在当次工作中完成——先追加到乙部（标注 `🔄 当次`），完成后立即标记 ✅ 并在下次乙部更新时删除。

### 6.5 Guides 文件编号

Guides 文件不使用数字编号，使用**语义化文件名**（大写+下划线），按 MECE 分类归入子目录（见 guides/README.md）。

## 7. 文档权威层级与索引规范

> **本节为文档权威层级的唯一权威源**。DOC_MAP.md 是本节层级模型的导航图（按目录结构组织，标注每个文件的权威层级），SSOT_INDEX.md 是母本子本关系的完整注册表。三者关系：§7 定义层级→DOC_MAP 标注层级→SSOT_INDEX 注册关系。

### 7.1 文档权威层级（7层模型）

> **D-218 决策**：SOP（执行细节）和 guides（理念概括）是正交维度，不排先后。
> CLAUDE.md 是最高层上下文入口，承接理念和具体细节。

```
┌──────────────────────────────────────────────────────────────────────┐
│ L0 核心层    CLAUDE.md                                                │ ← 最高：核心层权威源（HARNESS）
├──────────────────────────────────────────────────────────────────────┤
│ L1 上下文层  ARCHITECTURE.md / SSOT_INDEX.md /                        │ ← 项目上下文入口
│             SECRETARY_PRONOUNCEMENTS.md                              │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌─── L2 理念维度（为什么）────┐  ┌─── L3 执行维度（怎么做）───┐ │
│  │ content/strategy/           │  │ content/sop/                │ │
│  │ content/design/             │  │  制度母本 + 工作流程        │ │
│  │ content/governance/         │  │  回答"具体怎么做"           │ │
│  │ content/insights/           │  │                             │ │
│  │  设计理念 + 经验沉淀        │  │                             │ │
│  │  回答"为什么这样做"         │  │                             │ │
│  └─────────────────────────────┘  └─────────────────────────────┘ │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│ L4 实现层    docs/src/ + .github/agents/ + .github/skills/           │ ← 代码与配置实现
├──────────────────────────────────────────────────────────────────────┤
│ L5 审计层    .ctx/（日志/快照/时间戳）                                │ ← 运行记录
├──────────────────────────────────────────────────────────────────────┤
│ L6 官方层    content/references/（党章/条例/模板）                    │ ← 外部权威（只读）
└──────────────────────────────────────────────────────────────────────┘
```

**层级定义与裁决规则**：

| 层级 | 名称 | 内容定位 | 裁决优先级 |
|------|------|---------|-----------|
| L0 | 核心层 | 全局系统指令、Agent 协作规则 | 最高（全局约束） |
| L1 | 上下文层 | 项目 Harness、架构说明、母本注册表、战略论断 | 次高（项目内最高） |
| L2 | 理念维度 | 设计理念、操作规范、经验沉淀（回答"为什么"） | 与 L3 正交，互不覆盖 |
| L3 | 执行维度 | 制度母本、工作流程（回答"怎么做"） | 与 L2 正交，互不覆盖 |
| L4 | 实现层 | 代码实现、Agent 配置、Skill 定义 | 跟随 L1-L3（母本优先） |
| L5 | 审计层 | 执行日志、决策日志、快照、时间戳 | 只增不改（归档后冻结） |
| L6 | 官方层 | 党章、条例、规范、工作模板 | 外部合规底线，L2/L3 涉合规内容须溯源 |

**冲突裁决规则**：
1. L0 > L1 > L2/L3（正交，互不覆盖）> L4 > L5
2. L2 与 L3 正交：L2 定义设计理念，L3 定义执行流程，互不替代
3. L4 实现层必须溯源 L1-L3 母本，不得自行创造规则
4. L5 审计层为事实记录，不可回溯修改（D-233 原则）
5. L6 为外部合规底线，L2/L3 涉及合规内容时须溯源 L6

**三个正交维度**：

| 维度 | 回答的问题 | 体现位置 |
|------|-----------|---------|
| 内容分类 | 是什么 / 为什么 / 怎么做 / 实现 | L0-L5 层级划分 |
| 读者分类 | 给谁看（用户/工程师/AI） | DOC_MAP "受众"列 + 文件 YAML role 字段 |
| 使用目的 | 执行指令 / 决策上下文 / 设计参考 / 操作执行 / 审计追溯 | DOC_MAP "内容"列 |

三个分类依据正交：同一文件在三个分类依据各有归属。例如 `content/sop/纪检委员工作流程指南.md` 在内容分类是 L3 执行层，在读者分类是 `[用户]`，在使用目的是"操作执行"。

### 7.2 索引规范（README 的职责）

每个目录的 README.md 是该目录的**唯一入口索引**，职责为：

1. **列出所有文件**及其一句话说明
2. **按 MECE 分类**组织（不得有文件不属于任何分类，不得有文件属于多个分类）
3. **标注权威源**：当本目录文件与其他目录存在内容重叠时，标注哪个是权威源
4. **减少 AI token 消耗**：AI 读取 README 即可决定需要深入读取哪些文件，无需逐个扫描

**禁止**：README 中不得重复文件内容，仅做索引和导航。

### 7.3 仓库分层体系权威源

仓库中存在 7 套独立的分层体系，按性质分为三类：**文档治理类**（管文件怎么归位）——L0-L6 文档权威层级（见 §7.1）、CLAUDE.md 热温冷三层架构、content/ 目录结构层级、insights 卷一/二/三结构；**术语表达类**（管语言怎么用）——T1/T2/T3 术语权威层级（见 USAGE_POLICY.md §1.7）、文件角色分类（用户/工程师/AI，见 §3 与 §8）；**组织架构类**（管工作和角色怎么分）——ARCHITECTURE.md 五层架构。各类详细定义见对应权威源。

> §7.1 定义 L0-L6 层级模型（权威源），§7.4 制定 7 套分层体系的一致性检查规范（梳理源）。两者互补，不重复定义。

### 7.4 一致性检查规范

> 本节为仓库 7 套分层体系的一致性检查权威源，供 Agent 修改涉及分层概念的文件时自检使用。历史冲突记录见 [KNOWN_PITFALLS.md §7](KNOWN_PITFALLS.md#7-分层体系冲突记录)，定期扫描任务见 [§15.2 Q4](#152-周期性任务清单)。

#### 7.4.1 命名规范

每套分层体系有专属命名前缀，**不得混用**：

| 分层体系 | 命名前缀 | 正确用法 | 错误用法 |
|---------|---------|---------|---------|
| 文档权威层级 | L | L0/L1/L2/L3/L4/L5/L6 | ❌ 用 L1 指代术语层级 |
| 术语权威层级 | T | T1/T2/T3 | ❌ 用 T1 指代文档层级 |
| 热温冷三层 | 热/温/冷 | 热层/温层/冷层 | ❌ 用 L1 指代热层 |
| 文件角色分类 | 用户/工程师/AI | [用户]/[工程师]/[AI]（可复合） | ❌ 使用废弃的 [人]/[人机] |
| Agent 职能 | 型 | 协调型/执行型/审查型 | ❌ 用 L 指代 |
| insights 卷 | 卷 | 卷一/卷二/卷三 | ❌ 用 L 指代 |

#### 7.4.2 引用规范

引用某套分层时**必须标明所属体系**：

- ✅ 正确："L2 设计理念层"（标明 L 体系）
- ✅ 正确："T2 约定表达"（标明 T 体系）
- ✅ 正确："热层"（标明热温冷体系）
- ❌ 错误：孤立使用 "L2"（读者不知道指文档层级还是其他）
- ❌ 错误：孤立使用 "[人机]"（已废弃标记，应使用 [用户]+[AI] 或 [工程师]+[AI]）

#### 7.4.3 冲突检测

以下冲突点需在修改文件时重点检查：

| 冲突点 | 涉及体系 | 检查方式 |
|--------|---------|---------|
| L1/L2/L3 与 T1/T2/T3 混淆 | 文档权威层级 vs 术语权威层级 | Grep "L1"/"L2"/"L3" 确认指文档层级而非术语层级 |
| 废弃角色标记残留 | 文件角色分类 | Grep "[人]"/"[人机]" 确认无残留（迁移索引和术语废弃说明除外） |
| 热温冷三层与 L0-L6 混淆 | 文档权威层级 vs 热温冷三层 | 热温冷是 CLAUDE.md 内部分层，不从属于 L0-L6 |
| 目录结构与 L 层级混淆 | 文档权威层级 vs 目录结构 | 目录结构是 L 层级的物理映射，但不是 1:1 对应（如 content/references/ 是 L6 而非 L2） |

**文件角色分类一致性检测项**（2026-07-11 升级后新增，替代原"受众维度与角色三分类混用"检测）：

- 文件 YAML `role:` 字段必须使用新三分类 `[用户]/[工程师]/[AI]` 或复合标记
- 禁止使用废弃的 `[人]`/`[人机]`（迁移索引和术语废弃说明除外）
- DOC_MAP "受众"列与 YAML `role:` 字段保持一致（同一维度）

#### 7.4.4 检查清单

Agent 修改涉及分层概念的文件时，按以下清单自检：

```
□ 1. 使用的分层前缀（L/T/热温冷等）是否正确？
□ 2. 引用分层时是否标明所属体系？
□ 3. 是否存在 L1/L2/L3 与 T1/T2/T3 的混淆？
□ 4. YAML `role:` 字段是否使用新三分类、DOC_MAP 受众列是否与之一致？
□ 5. 目录结构引用是否与 L 层级映射一致？
□ 6. 新建分层概念时是否在 §7.4.5 中注册？
```

#### 7.4.5 新增分层注册规则

当仓库中出现新的分层概念时，按以下 5 步流程注册：

1. **识别**：判断新概念是否为"分层"（有多个层级 + 有划分标准 + 有应用场景）
2. **命名**：选择不与现有 7 套体系冲突的前缀（避免 L/T/热温冷等已用前缀）
3. **注册**：在 §7.3 中新增条目，含层级定义/划分标准/应用案例/与其他体系关系
4. **检查**：在 §7.4.3 中更新冲突检测项，若新分层与既有体系有交叉
5. **同步**：更新本文件 YAML `last_updated`，并在相关文件中引用本节作为权威源

## 8. 文件角色分类操作指南

> **2026-07-11 更新**：本节原为"三类受众规范"（与 ROLE_CLASSIFICATION.md 的角色三分类正交）。
> 升级后，受众维度与 AI 权限维度合并为单一维度。本节现为"文件角色分类的操作指南"，
> 即 ROLE_CLASSIFICATION.md 的操作补充。受众定义见 ROLE_CLASSIFICATION.md §一。

> **确立日期**：2026-07-01 | **确立背景**：书记指出"给用户看、给系统工程师看和给 AI 看的部分区分开了吗？我们之前只区分给人和给 AI，但是给用户和系统工程师的部分，表述和内容未必是一样的，不能一刀切"

### 8.1 三类文件角色定义

文档按 `[用户]` / `[工程师]` / `[AI]` 三类标记文件角色（可用 `+` 连接形成复合标记，如 `[用户]+[AI]`）。定义见 ROLE_CLASSIFICATION.md §一。

| 角色标记 | 语义 | 典型读者 |
|---------|------|---------|
| `[用户]` | 党支部具体建设相关内容 | 党支书、党小组组长、支委、党员 |
| `[工程师]` | 编程系统设计相关内容 | 系统维护者、开发者 |
| `[AI]` | AI Agent 专用执行指令 | AI Agent |

**复合标记示例**：`党小组组长工作手册.md` 标记为 `[用户]+[AI]`——既面向党小组组长本人的操作指南（用户），又供 AI Agent 共读执行（AI）。

**适用位置**：文件角色分类同时用于 DOC_MAP.md 的"受众"列和各文件 YAML `role:` 字段（同一维度，保持一致）。

### 8.2 读者画像

| 受众 | 读者画像 | 典型角色 |
|------|---------|---------|
| `[用户]` | 要熟悉内容，但可以不熟悉系统的前端设计。读者可能是党支书、党小组组长、支委，他们关心"做什么、怎么用"，而非"系统怎么实现的" | 党支书、党小组组长、支委、党员 |
| `[工程师]` | 可以不熟悉书记的路线部署，但要熟悉为什么要设计一些功能，这些功能要实现什么。读者可能是系统维护者、开发者，他们关心"为什么这么设计、要实现什么、与其他模块的关系" | 系统维护者、开发者 |
| `[AI]` | 执行指令。读者是 AI Agent，需要明确的执行指令、规则约束、检查清单 | AI Agent |

### 8.3 信息需求

| 受众 | 应该看到 | 不应该看到 |
|------|---------|-----------|
| `[用户]` | 执行流程、操作步骤、职责分工、规则要求、反馈渠道 | 技术变量名、文件路径、架构决策理由、代码实现细节 |
| `[工程师]` | 设计理念、架构决策理由、模块间关系、数据流、权限模型、技术实现方案 | （无限制，但应避免重复用户视角的执行流程） |
| `[AI]` | 执行指令、规则约束、检查清单、触发条件、输出格式 | （保持现有 AI 指令风格，无需调整） |

### 8.4 表述风格

| 受众 | 表述风格 | 禁止事项 |
|------|---------|---------|
| `[用户]` | 用人话说明"做什么、怎么做"；以动词开头的操作步骤；可用流程图/表格辅助理解 | 禁止使用技术变量名（如 `canWriteActivity()`）；禁止出现文件路径（如 `docs/src/core/state.js`）；禁止假设读者熟悉 CSS/SVG/JS |
| `[工程师]` | 用设计语言说明"为什么这么设计、要实现什么"；可包含文件路径、技术变量名、架构决策理由；模块间关系用引用图表达 | 禁止重复用户视角已覆盖的执行流程；禁止空泛表述（如"做好管理"） |
| `[AI]` | 用指令语言说明"执行什么、检查什么"；以 `MUST`/`SHALL`/`禁止` 等明确约束词表达；检查清单用 checkbox 格式 | 禁止模糊表述（如"酌情处理"）；禁止缺少触发条件的规则 |

### 8.5 如何重写指南

当某文件需要从"一刀切"表述拆分为多受众表述时，按以下流程执行：

1. **判断当前受众归属**：阅读文件内容，判断主要面向用户还是工程师（参照 §8.2 读者画像）
2. **标记受众**：在 DOC_MAP.md 中将"受众"列标记为对应类别
3. **检查表述一致性**：
   - 若标记为 `[用户]`：检查是否包含技术变量名/文件路径/架构决策理由 → 若有，移至 `[工程师]` 文件或在文件内独立章节标注"工程师参考"
   - 若标记为 `[工程师]`：检查是否包含用户视角的执行流程 → 若有，确认是否与 `[用户]` 文件重复，重复则删除（以 `[用户]` 文件为权威源）
4. **分章节处理**（仅当文件同时面向多受众时）：在文件内用 `> [用户]` / `> [工程师]` 标注分隔，但优先拆分为独立文件
5. **避免范围爆炸**：若重写工作量超过 200 行修改，仅修订 DOC_MAP 标记 + 留"实际重写"为后续任务

**判断优先级**：用户视角 > 工程师视角。当不确定时，先确保用户视角清晰，工程师视角的补充留作后续。

## 9. 文件命名规范

> **确立日期**：2026-07-08 | **确立背景**：部分文件命名过长（如"关于支部大会时间调整的改革说明（征求意见稿·修订版）.md" 64 字符），导致管理与阅读困难

### 9.1 适用范围

本规范适用于 `content/` 目录下所有 `.md` 文件的命名。根目录文件（`CLAUDE.md`、`ARCHITECTURE.md`、`SSOT_INDEX.md`、`SECRETARY_PRONOUNCEMENTS.md`、`README.md`）和 `.ctx/` 下日志文件遵循既有约定，不强制适用本规范。

### 9.2 命名标准

| 文件名类型 | 命名风格 | 字符上限 | 示例 |
|----------|---------|---------|------|
| 英文文件名 | 大写蛇形（UPPER_SNAKE_CASE） | ≤ 30 字符 | `PARTICIPANT_DATAFLOW.md`、`LOGIN_SYSTEM_DESIGN.md` |
| 中文文件名 | 简洁中文，无特殊符号 | ≤ 20 字符 | `党小组组长工作手册.md`、`常见工作场景快速指南.md` |

**禁止事项**：
- 禁止使用空格、连字符（`-`）以外的特殊符号
- 禁止使用中文标点（顿号、书名号、全角括号等），但历史档案除外
- 禁止缩写过度导致语义丢失（如 `PD.md` 代替 `PARTICIPANT_DATAFLOW.md`）

### 9.3 超长文件名处理原则

对超长文件名（英文 > 30 字符 / 中文 > 20 字符），按以下优先级选择处理策略：

1. **保留原名+索引简称**（首选，适用于历史档案）：文件保留原始命名，在目录 README 中建立简称映射。适用于 `content/references/历史会议材料/` 下的文件
2. **缩写**（适用于内部文档）：在保留核心语义前提下简化命名。如"支委与党小组定人定责定岗说明"在边界 20 字符，语义清晰，可不改
3. **拆分**（适用于内容可分离）：当文件内容可合理分为多个独立部分时，拆分为若干短文件

### 9.4 历史档案例外条款

`content/references/历史会议材料/` 下的文件保留原有命名方式，不强制改名。这些文件是历史档案，改名会破坏引用链路且无实际收益。

### 9.5 新建文件命名检查清单

```
□ 1. 文件名是否清晰描述文档内容？
□ 2. 英文文件名是否 ≤ 30 字符且为大写蛇形？
□ 3. 中文文件名是否 ≤ 20 字符且无特殊符号？
□ 4. 是否避免使用中文标点（历史档案除外）？
□ 5. 是否避免缩写过度导致语义丢失？
```

## 10. 反论表述审核标准

> **确立日期**：2026-07-08 | **确立背景**：insights 文件中存在"为什么不是加法关系""为什么不是乘积关系"等缺乏上下文、易产生歧义的反论表述

### 10.1 什么是反论

反论是指用"为什么不是 X"形式表达的否定性对比论述，目的是通过否定一个错误方向来凸显正确方向。

### 10.2 应该用反论的情况

满足以下**全部条件**时，适合用反论：

- 被否定项 X 是读者**可能合理误选**的方向（读者真的会想到 X）
- 否定 X 后能**凸显正确方向**（对比有教学价值）
- 被否定项 X 是读者**熟悉的具体概念**（而非生造概念）

**正面案例**：`扁平化≠无分工，而是无上下级` — 读者确实可能误以为扁平化就是无分工，否定有教学价值

### 10.3 不应该用反论的情况

出现以下**任一情况**时，不适合用反论：

- 被否定项是读者**不熟悉的抽象概念**（如"为什么不是加法关系"——读者不知道"加法关系"指什么）
- 被否定项是**生造概念**或无对照价值（如"为什么不是乘积关系"——"乘积关系"是为反论而生造的术语）
- **缺乏上下文**导致反论无意义（未说明在讨论什么，直接抛出"为什么不是 X"）
- 存在**术语冲突风险**（被否定项与既有术语同名，造成混淆）

### 10.4 反论成立三要素

一个合格的反论必须同时具备：

1. **明确的上下文**：读者知道在讨论什么问题
2. **被否定项的简要说明**：读者知道被否定的是什么（一句话解释 X 是什么）
3. **否定理由与正确方向的关联**：读者理解为什么正确方向更好（不只是"X 不对"，还要说"Y 对在哪里"）

### 10.5 改写策略

对不达标的反论，按以下优先级改写：

1. **首选：改写为正面表述**。直接说"是什么"，而非"不是什么"。如"为什么不是加法关系" → "两者是乘积关系而非简单堆叠"
2. **次选：补充上下文后保留对比**。若对比有教学价值，先说明上下文，再否定。如"有人可能以为是简单堆叠（加法关系），但实际上..."
3. **避免：术语冲突**。若被否定项与既有术语同名，必须改写，不得保留

### 10.6 自检清单

写反论前自检：

```
□ 1. 读者真的会想到被否定项 X 吗？（若不会，改正面表述）
□ 2. 被否定项 X 是读者熟悉的概念吗？（若不是，改正面表述）
□ 3. 上下文是否明确？（若不明确，先补上下文）
□ 4. 否定后是否说明了正确方向？（若没有，补关联）
□ 5. 被否定项是否与既有术语冲突？（若冲突，必须改写）
```

## 11. 面向用户表述规范

> **确立日期**：2026-07-09 | **确立背景**：面向用户的阐述性文档中存在设问句、主观预设、生硬排比等表述，影响客观性与可读性

### 11.1 适用范围

本规范适用于面向用户的阐述性文档，包括：

- `SECRETARY_PRONOUNCEMENTS.md`（书记重要论断汇编）
- `content/strategy/*.md`（战略路线文档）
- `content/sop/*.md`（制度母本与工作流程）
- `content/insights/*.md`（经验沉淀文档）

### 11.2 规范要点

| 要点 | 含义 | 识别标准 |
|------|------|---------|
| 段落化叙述 | 用自然段落展开论述，而非条目罗列 | 检查是否过度依赖列表/表格替代叙述 |
| 加粗重点 | 关键结论用**加粗**标注 | 检查核心命题是否有加粗标识 |
| 禁止设问句 | 不得用"为什么X？"引出论述，改为陈述句 | 含"？"且非引用书记原话、非表格表头 |
| 客观书面语 | 用客观陈述句，避免口语化、戏剧化表达 | 检查"点破了""一出口就清楚了"等主观评价词 |
| 禁止主观预设 | 不得预设读者的心理状态或反应 | 检查"你可能会想""你可能会觉得"等预设句式 |

### 11.3 修订示例

| 违规表述 | 修订后 | 违规类型 |
|---------|--------|---------|
| "这句话点破了支部存在的一个常见误解" | "组织性常被误解为排他门槛" | 主观预设（"点破了"为主观评价） |
| "为什么在当下强调这一点？" | "在当下强调这一点的原因在于..." | 设问句 |
| "你可能会想..." | （删除预设，直接陈述） | 主观预设 |
| "这个比喻一出口，分工的本质就清楚了" | "这个比喻明确了分工的本质" | 戏剧化表达 |

### 11.4 自检清单

```
□ 1. 是否存在设问句（含"？"且非引用/非表头）？
□ 2. 是否存在主观预设（"你可能会想""读者可能觉得"等）？
□ 3. 是否存在主观评价词（"点破了""一针见血"等）？
□ 4. 是否存在戏剧化表达（"一出口就清楚了""看似简单但..."）？
□ 5. 核心命题是否用加粗标注？
□ 6. 是否用段落化叙述而非纯条目罗列？
```

### 11.5 表达方式分类原则

> **确立日期**：2026-07-15 | **确立背景**：书记指出"涉及结构化的内容（比如程序、制度），用列表式、表格等结构化方式展示的方式是重要的。涉及非结构化的内容（比如书记论断、故事叙述），段落化的表达式最重要的"
> **权威定义源**：[USAGE_POLICY.md §1.8](USAGE_POLICY.md) — 本节为同步索引，完整定义见权威源

#### 11.5.1 核心原则

| 内容性质 | 表达方式 | 典型场景 |
|---------|---------|---------|
| **结构化内容** | 列表式、表格等结构化方式 | 程序、制度、流程步骤、权限矩阵 |
| **非结构化内容** | 段落化表达 | 书记论断、故事叙述、设计理念讲解 |

**判定要点**：内容本身是否具有"可枚举、可步骤化、可矩阵化"的内在结构——若有，用结构化；若无（如论断展开、叙事递进、理念阐释），用段落化。两者不可错配。

#### 11.5.2 文档与表达方式的对应

| 文档 | 受众 | 内容性质 | 主表达方式 |
|------|------|---------|-----------|
| `content/strategy/DEVELOPMENT_PATH.md` | [用户] | 故事叙述 | **段落化**（全仓库唯一需要"故事完整"的文档） |
| `SECRETARY_PRONOUNCEMENTS.md` | [用户] | 书记论断 | 段落化为主，元数据用 `<details>` 折叠 |
| `content/sop/*.md` | [用户] | 制度流程 | 结构化为主（表格/列表），why 讲解用段落化 |
| `content/governance/*.md` | [工程师]+[AI] | 治理规范 | 结构化为主 |
| `content/insights/*.md` | [用户]+[AI] | 经验沉淀 | 混合——道层用段落化，术器层用结构化 |
| `content/strategy/*.md`（除 DEVELOPMENT_PATH） | [工程师]+[AI] | 设计理念 | 段落化为主，表格辅助 |

#### 11.5.3 "故事完整"的唯一性

**全仓库中需要"故事完整"的文档只有 `DEVELOPMENT_PATH.md` 一个**——承载"从入党申请人到正式党员"的完整叙事（CLAUDE.md H7 项目产出声明标注）。其他【用户】文档只需"用词严谨、尽可能言简意赅"，不要求"故事完整"。

### 11.6 AI 展开原则——"吃透精神后写出，而非标注边界"

> **确立日期**：2026-07-16 | **权威定义源**：[USAGE_POLICY.md §1.9](USAGE_POLICY.md) — 本节为同步索引，完整定义见权威源

**核心原则**：AI 对书记原话的展开，目标是吃透书记精神后用自己的语言把原话讲透，而非复读原话或标注"这段是 AI 写的"。吃透后的展开与书记原话在精神上应无张力。

## 12. 甲部修改流程

> **本节为 CLAUDE.md 原 H4 内容的外移归位**。定义甲部修改的标准工作流、钩稽联动、Snapshot 更新规则。

### 12.1 甲部修改工作流

> 🔴 **当用户对甲部提出修改意见时，必须按以下 5 步执行，不得跳过任何步骤。**

**Step 1 — 修改甲部**：将用户的新看法准确写入甲部对应章节

**Step 2 — 影响评估**：识别修改波及的范围（甲部内部/guides/insights/SOP/代码）

**Step 3 — 写入乙部**：将同步更新任务写入乙部，作为甲部修改的衍生任务链

**Step 4 — 逐项执行**：按乙部中的任务链顺序执行

**Step 5 — 全局验证**：Grep 确认全仓库无旧版表述残留

**禁止**：仅修改甲部而不写入乙部衍生任务。

### 12.2 钩稽联动

> 🟡 **修改任何文件前触发。**

修改任何文件前，必须检查 CLAUDE.md 及 guides 中是否存在对该文件的钩稽声明并按要求联动更新。

### 12.3 Snapshot 更新规则

> 🟢 **仅在特定触发条件下执行。**

`.ctx/SNAPSHOT.md` **不再每次执行更新**。仅在以下触发条件满足时更新：

- (a) 大版本升级（v3→v4），如架构重大变更、角色体系迭代
- (b) 用户显式指令触发（如"/snapshot"或"生成快照"）
- (c) 项目阶段性收官（Phase 1/2/3 完成）

日常变更仅由 `EXECUTION_LOG` + `DECISION_LOG` + `TIMESTAMPS` 承载。

## 13. 日志规范

> **本节为 CLAUDE.md 原 H6 内容的外移归位**。定义执行日志与决策日志的权责划分、写入铁律、模板、编号与分片规则。

### 13.1 执行日志与决策日志的权责划分

| 维度       | 执行日志（EXECUTION\_LOG） | 决策日志（DECISION\_LOG）     |
| -------- | -------------------- | ----------------------- |
| **定位**   | 做了什么                 | 为什么这样做                  |
| **写入时机** | 每次工作结束后**必须写入**      | 仅在做出**非显而易见的决策**时写入     |
| **读者**   | 下次接手的 Agent（恢复上下文）   | 书记/支委（理解为什么）、经验沉淀（提炼模式） |
| **沉淀去向** | → insights/（经验沉淀）    | → insights/（管理哲学）       |

### 13.2 日志写入铁律

1. **条目排列**：时间正序，新条目追加到文件末尾
2. **归档标准**：按沉淀状态，不按时间。`[经验沉淀: 是]` 的条目方可归档
3. **写入后验证**：确认新条目出现在文件末尾

### 13.3 执行日志模板

```markdown
## YYYY-MM-DD | YYYY-MM-T<序号> — <一句话摘要>

- **来源**: <用户指示 / Agent 执行 / 周期性唤醒>
- **变更文件**: <文件1>, <文件2>, ...
- **关键动作**: YYYY-MM-T<序号>-<子序号> ✅ / YYYY-MM-T<序号>-<子序号> ✅
- **变更详情**:
  - <紧凑表述：每个变更点一行，用动词开头，不展开实现细节>
  - ⚠️ 排除Harness固定动作（更新YAML、记录日志、乙部更新等），只记录实质性内容变更
- **设计决策**: <仅非显而易见的选择，关联 D-<序号>>
- **结果**: <完成情况>
- **沉淀标签**: [经验沉淀: 否 — <一句话>]（🔴 初次写入只能标[否]，经正式沉淀写入insights后改为[是]）
```

### 13.4 决策日志模板

```markdown
## D-<序号> <日期> — <决策标题>

### 背景 / 选项 / 决定 / 理由 / 影响范围 / 一改具改检查
```

### 13.5 编号与分片规则

**编号规则**（D-188）：执行日志按月重置编号，格式为 `YYYY-MM-T<序号>`（如2026-05-T1、2026-06-T1）。跨月引用需加月份前缀。小任务（可一次性完成、不涉及3+文件或制度变更）不分配T编号，直接写日志。

**分片规则**：大任务（5+文件或200+行修改）必须提前分片：预估→拆分→写入乙部→顺序执行→上下文传递
```

## 14. 吸收外部输入操作流程

> **本节为原 `content/governance/SYNC_EXTERNAL.md` 的合并归位**（2026-07-11 合并）。定义"外部输入→内部知识"的完整操作流程，作为 CLAUDE.md H2.1 吸收外部输入原则的配套指南。

### 14.1 适用场景

当以下外部输入到达时，触发本流程：

1. **书记评议**：书记对现有制度/代码的修正意见
2. **外部文档**：书记上传的官方文件、评议文档、制度更新
3. **人类自行更新**：书记直接修改了仓库中的文件（非AI操作）

### 14.2 操作流程

#### 第一步：识别变更范围

收到外部输入后，首先识别变更涉及的范围：

- **术语变更**：概念的增删改、定义的修正
- **制度变更**：流程/规则/权限的调整
- **设计变更**：架构/数据模型/交互逻辑的修改
- **纯增量**：新增内容，不涉及既有条目的修改

#### 第二步：归位到权威源

根据 H2.2 母本子本表，将变更归位到对应的权威源：

| 变更类型 | 权威源 | 操作 |
|---------|--------|------|
| 术语变更 | USAGE_POLICY.md | 更新术语定义，触发全仓一改具改 |
| 制度变更 | content/sop/*.md | 先改SOP母本，再改代码 |
| 设计变更 | content/{strategy,design,governance}/*.md | 先改设计理念/治理母本，再改代码 |
| 原则变更 | CLAUDE.md 甲部 | 按H4.1甲部修改工作流执行 |

#### 第三步：触发一改具改

变更写入权威源后，按 H2.1 执行标准执行一改具改：

1. **修改前**：全仓库搜索所有引用位置
2. **修改中**：逐一替换，每处替换记录到执行日志
3. **修改后**：再次全仓搜索确认零残留

#### 第四步：验证与记录

1. 运行 GetDiagnostics 确认代码无错误
2. 写入执行日志
3. 更新乙部（如有衍生任务）

### 14.3 AI生成过程中的HARNESS清单

> 书记明确：不需要references模板，而是AI在生成过程中自检的HARNESS清单。

AI在执行任何写入操作时，必须自检以下清单（对应H3检查清单的生成时版本）：

```
□ 1. 本次写入是否涉及外部输入？→ 是则触发本流程
□ 2. 变更范围是否已识别？→ 术语/制度/设计/原则
□ 3. 权威源是否已确定？→ 按H2.2母本子本表归位
□ 4. 一改具改是否已执行？→ 全仓搜索+逐一替换+零残留确认
□ 5. YAML是否已更新？→ last_updated字段
□ 6. 执行日志是否已写入？
□ 7. 乙部是否已更新？
```

### 14.4 与H2.1一改具改的关系

- **H2.1一改具改**：覆盖"内部变更"流程（修改前→修改中→修改后）
- **本节**：覆盖"外部输入→内部知识"的吸收流程（识别→归位→一改具改→验证）
- 两者是互补关系：外部输入触发本流程，本流程的第三步调用H2.1

## 15. 周期性任务与自动唤醒机制（原 RECURRING_TASKS.md）

### 15.3 自动唤醒机制设计

#### 15.3.1 架构

唤醒机制由三个层次组成：时间戳注册表 → 调度逻辑 → 分发逻辑，最终汇入三步工作流闭环执行。

| 层次 | 职责 | 实现位置 |
|------|------|---------|
| 时间戳注册表 | 记录每个周期性任务的最后执行时间 | `.ctx/TIMESTAMPS.md` 的周期性任务追踪区 |
| 调度逻辑（SCHEDULER） | 对比当前时间与 `last_*` 时间戳，判断是否到期 | CLAUDE.md H1.1 前置指令 |
| 分发逻辑（DISPATCHER） | 根据任务编号查找对应 Agent，生成 next_prompt，写入待办列表 | `.ctx/PENDING_TASKS.md` |
| 执行闭环 | 规划 → 执行 → 验证 → 更新时间戳 → 记账 | 三步工作流 |

**调度规则**：
- 若 `(now - last_W1) > 7天` → 触发 W1
- 若 `(now - last_M1) > 30天` → 触发 M1
- 若 `(now - last_Q1) > 90天` → 触发 Q1

#### 15.3.2 TIMESTAMPS.md 扩展字段

在 `.ctx/TIMESTAMPS.md` 中维护周期性任务追踪区（见该文件"周期性任务最后执行时间"表）。

#### 15.3.3 唤醒触发方式

| 方式 | 适用 | 实现 |
|------|------|------|
| **会话入口检查** | 每次新对话开始时 | `CLAUDE.md` H1.1 前置指令：读取 TIMESTAMPS.md → 检查到期任务 → 若存在到期任务则优先汇报 |
| **手动检查指令** | 用户主动触发 | `/check-recurring` → 执行 SCHEDULER 逻辑并输出到期列表 |
| **GitHub Actions（远期）** | 全自动月级/季级任务 | cron 触发 workflow → Agent 自主执行 → 更新日志 |

#### 15.3.4 通知策略

| 到期天数 | 级别 | 行为 |
|---------|------|------|
| 到期前 3 天 | 提醒 | 下次 AI 会话开头显示"即将到期" |
| 到期当天 | 警告 | 标记为 ⚠️ overdue pending |
| 到期后 7 天 | 升级 | 在 CLAUDE.md 乙部 中追加为短期规划任务 |
| 到期后 30 天 | 紧急 | 标记为 🔴 管理漏——写入存档以便追责追溯 |

### 15.4 维护与演进

- 每次新增周期性任务时，同步更新本节 §15.2 + TIMESTAMPS.md 追踪表
- 每次执行周期性任务后，通过三步工作流闭环更新 `last_*` 时间戳
- 季度审查时评估周期性任务的执行质量和覆盖完整性
