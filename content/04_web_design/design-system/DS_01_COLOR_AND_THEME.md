# 第一编 色彩与主题

> **回答什么问题**：颜色怎么选（品牌 / 主题 / 功能 / 中性 / 表面五层）、主题色板与令牌怎么取、深色模式怎么定、暗色下哪些色不能借。
> **不回答什么**：组件长什么样、状态徽章怎么排 → [DS_03_COMPONENTS.md](DS_03_COMPONENTS.md)；焦点环用什么颜色 → [DS_04_INTERACTION_AND_RESPONSIVE.md](DS_04_INTERACTION_AND_RESPONSIVE.md) §5.8；判例与边界 → [CASES.md](CASES.md)。
> **谁什么时候读**：[工程师]+[AI]；新增页面选色、加状态色 / 类别色、改主题、做暗色适配之前读本篇；配色审查时按 §2.10 颜色四问逐条核。

## 二、色彩系统

### 2.1 色盘总览

```
┌─────────────────────────────────────────────────────────────┐
│                    色彩系统架构                              │
│                                                             │
│  品牌统一层（Brand）    主色（Primary）                      │
│  ┌────────────────┐   ┌────────────────┐                    │
│  │ 党徽金 FFD700   │   │ 党建红 CE1126   │ ← 不可变合规底线   │
│  │ tab/强调边框/   │   │ 红系渐变 9 阶   │ ← 品牌语义         │
│  │ 主题党日/徽章   │   │ 主CTA/标题装饰  │                    │
│  └────────────────┘   └────────────────┘                    │
│                                                             │
│  角色识别层（Role/Accent）  状态层（Functional）              │
│  ┌────────────────┐   ┌──────────────┐                     │
│  │ 主题色（可自选） │   │ 完成绿/待处理琥珀/告警红/进行中蓝 │   │
│  │ 色条/标签/chips │   │ API青         │ ← 状态指示          │
│  └────────────────┘   └──────────────┘                     │
│                                                             │
│  中性色（Neutral）     表面色（Surface）                      │
│  ┌────────────────┐   ┌──────────────┐                     │
│  │ 白→黑 11阶灰度  │   │ 页面/卡片/浮层 │ ← 组件层级深度       │
│  │ 文字+边框+分割线 │   │ 悬停/激活态   │                     │
│  └────────────────┘   └──────────────┘                     │
└─────────────────────────────────────────────────────────────┘
```

> **主题色 / 功能色 / 品牌色三色区别（2026-08-14 裁决明确定义）**：
>
> | 层 | 名称 | 驱动 | 是否随用户自选 | 用途 |
> |----|------|------|--------------|------|
> | 品牌统一层 | **品牌色**（党徽金 `#FFD700` + 党建红 `#CE1126`） | 固定常量 | ❌ 不随 | 党徽、主 CTA、党务标签、标题装饰——横跨全站的身份/合规底线 |
> | 角色识别层 | **主题色**（各角色可自选） | `getAccentColors(role)` / 侧边栏「主题选择」 | ✅ 随（个性化覆盖） | 身份归属 + 个人偏好：tab 激活态、色条、角色标签、chips、主按钮、选中项、工作台内强调色 |
> | 状态层 | **功能色**（成功绿/警告琥珀/告警红/信息蓝） | 固定常量 | ❌ 不随 | 只表语义状态：完成/待处理/错误/信息提示——绝不用于身份或装饰 |
> | 中性层 | 灰度 + 表面色 | 固定常量 | ❌ 不随 | 文字层级、边框、分割线、卡片层级 |
>
> **使用铁律**：四层各司其职禁止混用——状态红、品牌红、主题红三者语义各异；同色相不同层按语境区分（§2.8 判例）。身份不再绑定固定色值（2026-08-14 裁决），角色识别一律走主题色体系。

> **四层职责（2026-08-08 裁决）**：品牌统一层（金色）横跨全站、不受主题色制约；角色识别层（主题色）可个性化、只管身份归属与个人偏好；状态层（功能色）只表语义状态；中性层只做层级。**四层各司其职，禁止混用**——这也是"金色/蓝色/主题色并存"问题的规范答案（详见 §2.8）。

> **主题色取值判据（2026-10-01 支书评议批立）**：① **随支部主题色的只有三类**——主操作、选中态、本人标识；**成功 / 警告 / 危险 / 信息 / 活动类别色一律固定**，两者不得互串。② **颜色是最好的信息载体**——并列分类须用**小胶囊标注类别色**，不得用中性灰糊过去。

### 2.3 辅助色（Accent）— 党徽黄系 + 角色识别色

#### 2.3.1 品牌统一层（党徽金）— 横跨全站、不受主题色制约

> **定义（2026-08-08 三审修正）**：金色是党建合规色（`--party-gold` 定义于 `:root`，不经角色派生链路），用于**全站统一视觉**场景。**但金不强制充当"主题色"**——主题色语义（tab 激活态、选中项、chips）回归角色识别层（§2.3.2/§2.8 ②），因金是品牌合规色、含义多、受对比度牵制反复变色（半透明偏淡→实色偏艳，均不被接受）。金色仅保留于：强调卡边框、主题党日类别、待办行动按钮、通知徽章。

| Token | 色值 | 色块 | 用途 |
|-------|------|------|------|
| `--party-gold` | `#FFD700` | ██ | **党徽金 · 品牌统一层基准** |
| `--party-gold-light` | `#FDE68A` | ██ | 党徽金浅调 |
| `--accent-gold` | `var(--party-gold)` | ██ | 别名（SVG 着色、装饰线） |
| 金黄文字 | `#A16207` | ██ | 金浅底/金底上的文字（2026-08-10 裁定"再黄一点"，对比度达标） |
| 金浅底 | `rgba(255,215,0,0.12~0.14)` | ██ | 浅金色背景（类型徽章、图标底、待办次要按钮） |
| 金边框 | `rgba(255,215,0,0.35~0.45)` | ██ | 金色边框（强调卡、待办行动按钮、类型徽章） |

> **焦点不再用党徽金（2026-10-28）**：焦点色统一取主题色 `--app-accent`，固定党徽金退场；顶栏深红底的白色焦点环属唯一例外，见 §5.7。

> **G3 裁定（2026-08-08 实测）**：金色按钮一律用**金浅底** `rgba(255,215,0,0.12)`，**禁用纯亮金实底** `#FFD700`——实测「去处理」纯亮金实底「过于艳丽，饱和度太高」，而 tab 的金浅底「因为有透明度，黄色非常舒服」。金浅底与 tab 激活态同源。
> **G3 裁定（边框）**：金色作为主题色时，普通按钮/标签**不加边框**，与其他主题色结构完全一致（「别的有他也有，别的没有他也必须没有」）；仅 visitor 品牌金待办行动按钮保留金边框（与详情按钮同页一致）。

**应用范围（固定，不得私自扩增）**：
1. **可交互强调卡边框**：inspector 品牌活动卡 `border-left:3px solid var(--party-gold)`（品牌金边框，档位 1 卡片，见 §4.2「五档语义表」档位 1；实现中 inspector.js 内联 `#EAB308` 为历史存量、不入权威色板，待收敛至 `var(--party-gold)`）
2. **主题党日系**：类别色（`ACTIVITY_CAT_COLOR['theme-party']`）
3. **待办行动按钮**：visitor「去处理/处理」金底
4. **通知/紧急徽章**：header 未读数、badge--gold

**约束**：金色仅用于上述品牌统一场景；不得用于角色识别（色条/标签）、状态指示（完成/告警）、正文文字、以及任何"个人可选的强调/选中语义"（tab 激活态、选中项、chips 等一律用主题色）。

#### 2.3.2 角色识别色系（红橙黄绿蓝紫系统化）

> **设计原则**：每个角色一个独立色相，按职能分工分配色相，确保 8 种角色在关系网络图、角色卡片、日历图例等场景中可快速辨识。
>
> **色相分配逻辑**（按职能分工归类）：
> - 红色系（最深）→ 领导核心（党支书）
> - 石灰绿系 → 执行层（党小组组长，与支委分工配合）
> - 紫/蓝/琥珀系 → 支委三类（组织/宣传/纪检，横向协作）
> - 青/绿/灰系 → 项目执行层（组织者/深度参与者/普通参与者）
>
> ⚠️ **本表是身份标识场景的默认识别色，不是"主题色硬编码"**（2026-08-10 补充）：主题色已演进为一套**可选择的色盘**——侧边栏「主题选择」中所有角色均可从色盘自选主题色（2026-08-06 起），`resolveAccentRole` 优先读 localStorage 个性化覆盖（`docs/src/core/domain/constants.js`）。本表仅约束**身份标识场景**（关系网络节点/角色卡片/日历图例的辨识色）；**主题色场景**（tab 激活态/按钮/标签/选中项/chips 等强调色）由个人自选色盘决定（见 §2.7 规则 + §2.8 ② 角色识别层）。2026-08-14 裁决强化：身份不再保留既有固定颜色设定——本表色值为默认识别色，任何角色均可经侧边栏「主题选择」自选覆盖，工作台强调一律走主题色。

### 2.5 功能色（Functional）— 状态层（只表语义状态）

> **2026-10-26 Task 4：token 改名 `--functional-*` → `--status-*`**。组件只允许读 `--status-*`；
> `--functional-*` 仅作短期兼容别名（`var(--status-*)`），**禁止新增消费**。语义与色值不变。

| Token（唯一可消费名） | 兼容别名 | 亮色值 | 暗色值 | 用途 |
|-------|------|------|------|------|
| `--status-success` | `--functional-success` | `#10B981` | `#34D399` | 成功 / 已完成 |
| `--status-warning` | `--functional-warning` | `#F59E0B` | `#FBBF24` | 待处理 / 提醒 / 逾期 |

| `--status-info` | `--functional-info` | `#3B82F6` | `#60A5FA` | 信息 / 提示（白名单见 §12.14） |

**使用约束**：
- 仅用于 Badge、状态指示器、表单验证提示、圆点 / 提示条 / 左条
- 不可用作大面积背景色或装饰色
- **状态层与品牌层/角色层互不混用**：状态蓝（进行中/信息）与角色蓝（组织委员/宣传委员）相区分；状态红（告警/超期）与品牌红（党建红主 CTA）相区分；状态琥珀（待处理）与品牌金（党徽金）相区分。同色相不同层按"语境"区分（见 §2.8 判例）。
- 组件（`docs/src/**/*.js` 与 `styles.css` 组件段）只写 `--status-*`；`--functional-*` 只出现在 `:root` 别名定义处。

**2026-10-18 改准（逾期 / 超期归 warning）**：上表 `--functional-error` 的用途中「已逾期」**改归** `--functional-warning`（琥珀）；`--functional-error` 只保留给**阻断 / 失败 / 删除 / 驳回**。上表原文保留为历史表述，现行口径以 §2.10「颜色四问与明暗档」为准。

### 2.7 主体色配色规则（给定主体主题色 X）— 打样样板

> **⚠ 2026-10-23 批次 505 起，本节规则 1 的「三件套公式」已由 §2.11 取代**：浅底 / 边框 / 深字不再由
> `rgba(X, 0.10~0.12)` + `rgba(X,0.30)` + X 文字运行时派生，而是每个主题 × 亮/暗各 8 个手选 token
> （`softBg/softBorder/softText/strongBg/strongInk/hoverBg/activeBg`）。本节保留为历史样板与
> 「品牌金做统一层 / 状态色全局统一 / 暖白底 / 灰只做中性」四条的出处；取色一律以 §2.11 为准。

> **来源：**普通参与者界面视觉重设计打样（2026-08-01，批准）。本规则是"给定主体主题色 X 时如何搭配全页色彩"的可复用样板，其他角色改版按此规则推广。

**配色规则五条**：

1. **X 做工作台强调**：主按钮、标题装饰条、主要标签、**tab 激活态**均用主体色 X。tab 统一渲染方案即主题色三件套：浅底 `rgba(X,0.10~0.12)` + 边框 `rgba(X,0.30)` + X 文字（`tab-bar.js` 消费调用方 `accentColor`；2026-08-08 三审定稿）。
2. **品牌金做统一层**：可交互强调卡边框、主题党日、待办行动按钮、通知徽章用党徽金，全站一致、不受 X 制约。
3. **状态色全局统一**：完成绿 `#10B981` / 提醒琥珀 `#F59E0B` / 告警红 `#EF4444`，所有角色一致。

### 2.8 颜色分类规则（品牌统一层 / 角色识别层 / 状态层 / 中性层）

> **依据（2026-08-08）**："金色/蓝色/主题色并存"看似无规律，实因全仓并存两套体系且未成文：一套是活动类别语义色（红/金），一套是功能/状态色（蓝/绿/琥珀/青）大量硬编码。裁定：**颜色必须有更合理的分类规则，四层各司其职**。

**四层分类总表**：

| 层 | 驱动 | 是否受主题色制约 | 代表色 | 职责 |
|----|------|----------------|--------|------|
| ① 品牌统一层 | `--party-*`（:root 常量） | ❌ 不受 | 党徽金 `#FFD700`、党建红 `#CE1126` | 全站统一视觉：强调卡边框、主题党日、待办行动按钮、主 CTA、党务标签、通知徽章 |
| ② 角色识别层 | `getAccentColors(role)` / 侧边栏「主题选择」 | ✅ 受（可个性化） | 各角色主题色 | 身份归属 + 个人偏好：**tab 激活态（2026-08-08 三审回归）**、色条、角色标签、人员 chips、左侧边线、主按钮、选中项、chips、工作台内强调色 |
| ③ 状态层 | `--functional-*` + 语义 Tailwind 类 | ❌ 不受 | 完成绿/待处理琥珀/告警红/进行中蓝/API 青 | 只表语义状态：完成、待办、告警、进行中、API 模式 |
| ④ 中性层 | `--neutral-*` | ❌ 不受 | 灰阶 | 文字层级、边框、分割线 |

**判定规则（遇到"这个边框该用什么色"时的决策路径）**：
1. 是**状态指示**（完成/待处理/告警/进行中/API）？→ 状态层 ③
2. 是**个人可选的强调/选中语义**（tab 激活态、下拉选中项、chips 选中态、主按钮、标签）？→ 角色识别层 ②（主题色）
3. 是**全站统一品牌视觉**（强调卡边框、主题党日、待办行动按钮、通知徽章、主 CTA）？→ 品牌统一层 ①（金）
4. 都不是 → 中性层 ④

**同色相跨层判例**（解决"颜色到底有没有规律"的困惑）：

| 色相 | 品牌统一层 | 角色识别层 | 状态层 |
|------|-----------|-----------|--------|
| 红 | `#CE1126` 党建红（主 CTA/党务标签） | 支书/副书主题色 `#B91C1C`（tab 激活态） | `#EF4444` 告警/超期/删除 |
| 金/琥珀 | `#FFD700` 党徽金（品牌） | 纪检委员 `#C2410C` | `#F59E0B` 待处理/提醒 |
| 蓝 | `--accent-blue`（一般装饰） | 组织委员 `#0EA5E9` / 宣传委员 `#2563EB` | `#3B82F6` 进行中/信息/高亮 |
| 绿 | — | 党小组组长 `#22C55E` | `#10B981` 完成/成功 |
| 青 | — | 组织者 `#7DD3FC` | teal API 模式 |

**归档决策**：
- **首页 dashboard 定位为功能/状态色体系**（蓝=数据/进行中、红=主操作、金=主题党日、琥珀=待处理），**不接入个人主题色**（2026-08-08 确认）——首页是全局总览，状态色传达信息更准确。
- **首页统计卡四相语义色·定稿**（2026-08-10 两次裁定，最终版）：本月活动用蓝 `#3B82F6`（信息/载体）、活跃专班用亮金 `#F59E0B`（琥珀金，**参考工作台 tab 亮色呈现——底色必须是亮的：浅金底+亮金字**）、未读通知用红 `#DC2626`（待处理/告警语义）、我的考勤用绿/琥珀/红（状态语义，考勤三色称"很好"保留）——红蓝亮金三原色 + 考勤状态色的平衡组合。
- **主题色应用范围在工作台内可适当放宽**（2026-08-08）：工作台内 tab 激活态与强调色挂靠主题色；侧边栏选择器统一命名「**主题选择**」（浅色/深色模式与颜色选择同一排）。**每个角色 tab 各有各的主题色渲染**（`bootstrapPage → resolveAccentRole` 支持自选覆盖，2026-08-08 三审强调）。
- **「金」主题色即主题党日胶囊**（2026-08-08 四审定稿，原话"金色就应该和主题党日的胶囊颜色一致，那个我觉得很漂亮！"）：`ACCENT_COLORS.participant` 增配 `bg/border` 覆盖字段（亮金底 `rgba(255,215,0,0.12)` + 金黄字 `#A16207` + 亮金边框 `rgba(255,215,0,0.35)`），`getAccentColors` 优先消费覆盖；侧边栏色板「金」色块显示亮金 `#FFD700`。文字色仍守金黄 `#A16207` 保对比度（2026-08-10 裁定"再黄一点"），金不再因对比度牵制而变色。
- **存量收敛**：状态层现存约 69 处硬编码 Tailwind 类（`bg-green-50 border-green-200` / `bg-amber-50` / `bg-blue-50` / `#3B82F6` 等）本期**不动**，后续按本表逐项收敛，新增代码必须按四层分类取色。**硬编码 hex 的回归防线**＝守卫 `server/test/hex-hardcode-guard.test.mjs`：现存项按「文件 × 值」进基线（`server/test/style-baseline.mjs`），**新增即红**；删存量后同批收基线（删值 / 减计数），进度自动前进。

**语义动作类与颜色对应法则（2026-08-08 指令 #1/#4）**：

**按钮颜色三层（什么按钮用什么颜色）**：

### 2.9 颜色角色 → 令牌 映射（2026-09-28 立 · 补「标准缺档」）

> **为什么要立这一节（诊断依据，非凭空新增）**：§2.8 给了**四层分类**与「遇到某边框该用什么色」的**决策路径**，
> 但**没有一份「哪种角色在哪种组件里用哪个令牌」的映射**——于是 §2.8 的四层语义在**实现层落不到具体令牌名**上，
> 新写的组件各自解读，同一角色出现多种令牌（同一「危险」既有 `--functional-error`、又有 `red-600`、又有裸 hex）。
> 实读证据（2026-09-28 全站扫描 `docs/src/**/*.js`）：`style="…"` 内含色值的写法 **180 处 / 60 文件**、
> 形如 `var(--tok, <硬编码兜底>)` 的兜底 **84 处**；其中**近期新写的 div 组件**（`committee-meeting-tab.js` /
> `assign-tab.js` / `group-progress-tab.js`）出现**新造硬编码**（如内联 `#C8102E`、`rgba(185,28,28,0.45)`），
> 而早期按本规范落地的样板组件（`.btn-accent*` / `.chip-accent-on` / `.sel-accent-on` / `tab-bar.js`）
> **零新造硬编码**——支书 2026-09-28 判「新组件很没有自觉」的技术根因即此。
> ⇒ **「不统一」的根不在实现者手滑，而在标准没有给「角色 → 令牌」**。本节把它写成表。

### 2.9.1 U1「选中态卡片底色档」（2026-09-28 立 · 据既有合规样本归纳）

> **⚠ 2026-10-23 批次 505 起「0.10 / 0.30 公式」由 §2.11 取代**：选中态改用显式 `softBg` +
> `softBorder` + `softText`（每主题手选 hex），不再由主题色乘透明度得到；`--app-accent-bg/-border/-text`
> 仅作为批次 506 前的一轮兼容别名存在。本条保留为「选中态一律三件套、不许自写 rgba」的出处。

> **为什么要立（诊断依据，非凭空）**：§2.7 规则 1 只写「主题色浅底 `rgba(X,0.10~0.12)`」——**给的是区间、不是一档**；
> 实现层于是 3 种不透明度并存：`--app-accent-bg`（**0.10**）· Tailwind `bg-red-50/50` 类（**≈0.12**，alpha 由 Tailwind 生成）·
> 新写组件里的 `rgba(185,28,28,0.45)`（**0.45**，`entries/tabs/secretary/group-progress-tab.js`，2026-09-28 前批已改走 `var(--app-accent-*)`）。
> 同一个「选中卡」在不同文件三种底 ⇒ 深浅不一。

**判据（从既有「合规样本」归纳 —— 不凭空定）**：本仓**早已合规范**的选中 / 强调组件，底与边**清一色用同一对**（`docs/src/styles.css`）：

| 合规样本 | 底 | 边 |
|---|---|---|
| `.chip-accent-on`（chip 选中） | `--app-accent-bg` | `--app-accent-border` |
| `.sel-accent-on`（列表行选中） | `--app-accent-bg` | （无边框） |
| `.btn-accent-soft`（次级按钮） | `--app-accent-bg` | `--app-accent-border` |
| `.accent-avatar`（主题色首字块） | `--app-accent-bg` | （无边框） |

而 `--app-accent-bg` 在 `:root` 的正式默认值 ＝ `rgba(185, 28, 28, 0.1)`（**0.10**）、`--app-accent-border` ＝ `rgba(185, 28, 28, 0.3)`（**0.30**）
——即「合规样本」实际用的就是 **0.10 / 0.30**。⇒ **选中态底档定成 0.10、边档 0.30**（＝既有合规样本值，非新造）。

**规则（选中态一律三件套，不许自写 rgba）**：凡「选中 / 强调 / 激活」的卡片 · 列表行 · chip · 面板，一律用
`--app-accent-bg`（底）＋ `--app-accent-border`（边框）＋ `--app-accent`（字 / 描边）三件套，或直接用上表语义类：

- **不许**自写 `rgba(<主题色>, <任意 alpha>)`——0.45 这类「加浓」是未定档期的一次性写法；
- **不许**用 Tailwind `bg-red-50/50` 一类类代替「主题色底」——那是一套与主题色**无关**的固定红（用户切到「金 / 蓝」主题时不跟）；
- 日 / 夜两套由三件套的 `html.theme-dark` 派生自动完成（§7.1），**不许**为选中态另写深色覆盖。

（判据口径可核：`grep` 全站「选中卡」类底——用 `--app-accent-bg` 的即是合规样本；出现自写 `rgba(x,0.45)` 或 `bg-<color>-50/5x` 的即违例。）

### 2.9.2 U4「合法状态色类清单」（2026-09-28 立 · 白名单 ＋ 禁例）

> **为什么要立（诊断依据）**：§2.8 只写「存量约 69 处状态层硬编码本期不动、新增按四层取色」——**没列哪些 Tailwind 色类算合法状态类**；
> 于是「危险 / 报错红」在实现层出现 **五套并存**（支书 2026-09-28 逐字）：`#EF4444`（＝`--functional-error` 值）·
> `#DC2626`（red-600 值）· `#F87171`（深色提亮值）· `red-600` 类 · `#C8102E`（党务红误用）。本节把「什么类合法、什么档禁止」写成可判清单。

**合法状态色类白名单**（状态层；色相限 `red / amber / green / blue` ＝ 四个功能色，逐档给用途）：

| 类 | 档 | 用途 | 深色映射（`docs/src/styles.css`，**已登记**） |
|---|---|---|---|
| `bg-<c>-50` | 50 | Badge / 提示条 / 行内状态块的**浅底** | `html.theme-dark .bg-<c>-50`（4474–4483） |
| `bg-<c>-100` | 100 | 强一档的浅底（徽章 `bg-red-100` 等） | `html.theme-dark .bg-<c>-100` |
| `border-<c>-200` | 200 | 状态块 / 徽章的**边框**（唯一允许的 200 档——深色映射即按 200 登记，故列白名单） | `html.theme-dark .border-<c>-200`（4810–4813） |
| `text-<c>-600` | 600 | 状态**字**（与 `bg-*-50` 成对） | `html.theme-dark .text-<c>-600`（4495–4499） |
| `text-<c>-700` | 700 | 深一档的状态字 | `html.theme-dark .text-<c>-700`（4797–4801） |
| `bg-<c>-600` | 600 | **危险 / 破坏性操作的实底按钮**（`bg-red-600 text-white`，如「删除 / 撤销并删除 / 采纳生效」） | 无（实底色已够深，深色下不需提亮） |

其中 `<c> ∈ {red, amber, green, blue}`：**red＝错误 / 驳回 / 超期 / 危险** · **amber＝待处理 / 提醒** · **green＝成功 / 完成** · **blue＝进行中 / 信息**。

**禁例（可判）**：

1. **禁用色相**：`rose` / `pink` / `violet` / `orange` 作**状态**——四功能色无此四者（`orange` 曾在早期当「警告」用，现统一归 `amber`）；
   现存 `orange-*` / `rose-*` 为**存量**、逐批收敛、**新增即红**。
2. **禁用档**：`bg / text / border-<c>-300/400/500/800/900`——档位内无这些「中间 / 最深档」（`border-*-200` 已在白名单、属唯一例外）。
3. **禁混色相**：同一状态块内不得混用两种色相（如 `bg-blue-50 text-red-700`）——状态＝一个语义＝一个色相。
4. **禁裸 hex / 内联 rgba 表状态**：状态色一律走 Token（`--functional-*`）或上列白名单类；`#DC2626`（red-600 值）· `#F87171`（深色提亮值）·
   `#EF4444`（token 值）**不得再写死**——`--functional-error` 已含日 / 夜两值（§7.2），深色提亮由 `html.theme-dark` 映射完成。

（判据口径可核：扫描 `docs/src/**` 的 `(bg|text|border)-(red|amber|green|blue|rose|pink|violet|orange)-\d+`，命中白名单外的 (色相, 档) 即违例；深色映射段（4474–4813）即本清单的镜像、两者须同集。）

### 2.9.3 U3「同色相共存规则」（2026-09-28 立 · 主题色与功能色同色相时）

> **为什么要立（诊断依据）**：§2.8 给了「同色相跨层判例」表（红 ＝ 品牌 `#CE1126` / 角色 `#B91C1C` / 状态 `#EF4444`），
> 但**没给「同屏同色相怎么区分」的判据**——支书 2026-09-28 逐字问「是否禁止『主题色＝红 ＋ 同块用告警红』并存」。**不禁止**（红主题用户全站都会碰到红 ＋ 红），但**须有区分规则**。

**判据（从既有合规样本归纳）**：本仓**状态色**（§2.5）的规范用法**从来不是「一块纯色」**，而是**带形状 / 图标 / 文案的 Badge / 提示条 / 状态点**
（`bg-*-50 text-*-700` 胶囊 · `w-2 h-2 rounded-full` 状态点 · 「已逾期」「驳回」文案）；而**主题色**则走 tab 激活态 / 按钮 / 标签 / 选中底 / 首字块。⇒ 两者形态本就不同。

**规则**：

1. **形状 / 图标 / 文案承担语义，颜色只作辅助**——状态的存在感由其**形态**（徽章轮廓 / 状态点 / 警示图标 / 「已逾期」「驳回」等文案）提供，色相只是加重。
2. **同屏时状态色一律走 Badge / 提示条（或状态点）形态**，主题色一律走 tab / 按钮 / 标签 / 选中底 / 首字块——**不得让状态色退化成一块与主题色同形的纯色块**（那才会「红红不分」）。
3. **同一元素内不得混用**：一个元素要么是主题色强调（走 `--app-accent-*` / 语义类），要么是状态（走 `--functional-*` / U4 白名单类）；**不得**一个底一种、一个字另一种地混搭（如主题红底 ＋ 告警红字）。

（判据口径可核：真机——红主题工作台内，凡同时出现主题红与状态红者，状态红必为「带轮廓或图标的 Badge / 提示条 / 状态点」；出现「与主按钮同形的纯红状态块」即违例。）

### 2.10 颜色四问与明暗档（2026-10-18 立 · 颜色语义单一源）

> **为什么单立**：§2.8 / §2.9 已给出四层色与「角色 → 令牌」，但「这一处该用实底还是淡底」仍靠手感；
> 逾期与错误同屏时也常被写成同一种红。本节把取色收成两步：**先答四问，再选明暗档**。
> §2.5 / §2.9 中「逾期 / 超期」的口径以本节为准。

**第一步：颜色四问**（按顺序问，任一问答「是」即停）

1. **是行动**（用户要点的）→ 用**主题色**：主 CTA 实底白字，次级行动淡底深字。
2. **是状态**（完成 / 待处理 / 逾期 / 进行中 / 失败）→ 用**功能色**：徽章 / 提示条淡底深字；只有危险确认可用实底白字。
3. **是身份**（角色 / 归属）→ 用**角色识别色**：只做色条 / 徽章 / 图例，不进按钮与状态。
4. **是结构**（文字 / 边框 / 分割线 / 禁用）→ 用**中性色**。
5. 四问全「否」⇒ **不加颜色**；颜色不是装饰。

**「别的颜色」的边界**：品牌色（党徽金 / 党建红）只用于品牌合规与主题党日；活动类别色只用于活动类型图例；角色识别色只用于身份色条 / 徽章 / 图例。三类都**不得**充当主按钮、状态徽章或页面大面积底色。

**第二步：明暗档**

| 用途 | 形态 | 允许 | 禁止 |
|---|---|---|---|
| 主 CTA | 实底 | 主题色实底 + 白字（`.btn-accent`） | 功能色实底、渐变、整圈彩色边框 |
| 次级行动 | 淡底 | 主题色约 10% 底 + 主题色深字（`.btn-accent-soft` / `.text-accent`） | 与主 CTA 同等权重的实底 |
| 状态 | 淡底 | 功能色约 12% 底 + 功能色深字（`.state-badge--*`） | 用主题色做状态；大面积实底铺色 |
| 危险确认 | 实底 | `--functional-error` 实底 + 白字，且只在确认动作出现 | 页面常驻红底；用整圈红边表示强调 |
| 身份 | 标识 | 角色色只做色条 / 徽章 / 图例 | 角色色进按钮、进状态徽章 |
| 结构 | 中性 | `--neutral-*` 文字 / 边框 / 分割线 | 中性色承担强调或状态语义 |

**逾期与错误分色（2026-10-18 改准）**

- **逾期 / 超期 = `--functional-warning`（琥珀）**，用淡底深字徽章或数字着色。
- **阻断 / 失败 / 删除 / 驳回 = `--functional-error`（红）**；需要二次确认时用实底白字。
- **主题色为红时，逾期仍用琥珀**；红色只出现在错误 / 危险确认。状态与主题同色相时的区分规则见 §2.9.3（形状 / 图标 / 文案承担语义）。

**三个反例（看到即判违例）**

1. **整圈红边**：卡片 / 会议卡用整圈彩色边框表示「重要」——同时像主题色、错误色和选中态，用户无法判断语义；改用章节头计数、左侧 2px 单色规则或状态徽章。
2. **功能色主按钮**：用 `--functional-success` / `--functional-error` 做实底主按钮——功能色只表状态，主行动归主题色。
3. **主题色状态徽章**：用 `--app-accent-*` 做「在任 / 待召开 / 已留存」等状态——身份色与状态色混层，状态一律走 `--functional-*`。

### 2.11 主题色板：7 主题 × 亮/暗 × 8 显式 token（2026-10-23 批次 506 立 · **取代 §2.7 / §2.9.1 的三件套公式**）

> **单一源**：`docs/src/core/domain/constants.js → ACCENT_COLORS`（数据）+ `getAccentColors` / `accentButtonColors` /
> `solidAccentStyle`（查表 API）+ `docs/src/core/boot/theme.js → accentThemeTokenVars / applyAccentThemeTokens`（注入）
> + `docs/src/styles.css`（`--app-accent-*-light/-dark` 原始变量与 8 个别名）。改色只改这张表，别处不得写主题色 hex。

**三条设计原则**

1. **党徽金 ≠ 主题金**。党徽金 `#FFD700`、党建红 `#CE1126`、主题党日亮金 + 金黄字 `#A16207` 是**固定语义色 / 合规底线**，
   走 `_C.partyGold / _C.partyRedBrand / _C.yellow700` 与 `--party-gold / --party-red`；主题金是另一档更沉稳的琥珀金
   （亮 `#A97A12`、暗 `#E0B24C`）。两者同屏时**不要求同值**。
2. **活动类别色固定**。`ACTIVITY_CAT_COLOR` / `ACTIVITY_CLASSIFICATION` / `_ACTIVITY_TYPE_BASE` 只消费固定常量，
   **不读任何主题 token**——用户把主题从红切到蓝，三会一课徽章仍是党建红、主题党日仍是亮金（spec SD-19）。
   只用于徽章 / 圆点 / 左条等小面积标记，不整卡铺色。
3. **沉稳但是鲜活**。大面积表面保持中性或低彩度 `softBg`（与白 1.11–1.15）；正文深墨；每个视图最多一个高强调
   （主 CTA 或一个语义徽章）；高饱和只允许出现在按钮 / 徽章 / 圆点 / 左条等小面积元素。

**为什么要削到 7 个（10 → 7）**

原色板 10 项里有 3 个重复色相（天蓝 / 亮蓝同蓝、雾紫 / 紫同紫），而**浅底/深字由一条公式生成**：
浅底 `rgba(X,0.10)`、边框 `rgba(X,0.30)`、深字 `color-mix(X 45%, neutral-900 55%)`。公式的后果是可测的：
origin 的「主题色字」在绿 / 天蓝 / 雾紫 / 亮蓝上只有 2.09 / 2.51 / 2.49 / 1.59:1（不可读）；现行 deep 虽过 4.5，
但饱和度从 92% 跌到 28–58%（橙变褐、绿变灰绿、亮蓝变钢蓝）——这就是「灰度太高、太脏」的根因。
⇒ 删除天蓝、雾紫、亮蓝；**紫只留一个、蓝只留一个**；每个主题的每一部分改为**手选 hex**，不再派生。
旧值回落：`sky` / `light-blue` → `blue`，`deep` → `purple`（`ACCENT_KEY_ALIASES`，`normalizeAccentKey()` 使用）。

## 七、深色模式设计规范

> **确立背景（2026-08-09 指令）**："每一个色块的设计，请都要考虑【深色模式】。只要是主题色，每一个颜色都必须平行——如果一个在深色模式下是淡色的底深色的字，别的也应该是淡色的底深色的字（总之是一致的，且易用的）。对于功能色，因为不随主题色变化而变化，也要记得去做好深色模式下可见度、可分辨率的评估。"
> **实现机制**：[theme.js](../../../docs/src/core/boot/theme.js) — `<html class="theme-dark">` 前缀驱动三态（浅色/深色/跟随系统，默认跟随系统）；CSS 侧深色规则统一 `html.theme-dark` 前缀（2026-08-07 替代 @media prefers-color-scheme）。
> **分层覆盖**：CSS 变量反向 + 高频 Tailwind 类 `!important` 提权 + 硬编码组件逐一覆盖；`--party-red` 系不变 / `--surface-header` 深红保持 / 角色识别色不变。

### 7.1 色块平行性总则（主题色）

> **色值权威源见 §2.3**；本节只记深色模式下的使用约定，不重复定义色值。

**总则**：深色模式下，所有主题色色块必须使用**同一套明暗关系**——统一「深底浅字」或统一「淡底深字」，禁止出现"这个色块淡底深字、那个色块深底浅字"的单独反转。
