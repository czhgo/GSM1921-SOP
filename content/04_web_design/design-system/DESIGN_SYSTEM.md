## 一、设计哲学

### 核心原则

> 原则按场景灵活选用，不锁定数量。下表为基础参考集，可按页面特性增补（如探索页可加"叙事性"、表单页可加"反馈清晰"）。

1. **清洁优先（Clean First）**：能用纯色解决的，不用渐变；能用扁平解决的，不用阴影；能用留白解决的，不用分割线
2. **最小三成本（Min Cost First）**：任务流默认直接展示在工作台，不要求用户额外操作才能看到"我需要做什么"。包含三个维度：①**信息成本**——用户获取"我需要做什么"所需的信息搜寻成本，任务流默认直接展示；②**操作成本**——从"进入工作台"到"看到可执行事项"的点击/操作次数，进入即见，系统主动推送；③**适应学习成本**——新用户理解工作分工、工作任务、信息流运作方式的学习成本，通过系统设计本身自解释。适用于全系统所有角色工作台。
   - **知情权优先（裁定 2026-08-08）**：无职责不代表没有知情权。支委/角色即便业务上不负责活动/专班的操作（如纪检无专班职责、组织无活动 tab），仍有权查看其详情。凡首页跳转携带 `activityId`/`taskforceId`/`view=activities` 参数，各角色工作台均须有对应「查看」承载（激活相关 tab 或复用活动/专班查看组件），不得因"无职责"而丢弃参数、让用户信息成本升高。
3. **哑光质感（Matte Aesthetic）**：背景采用低饱和中性色，拒绝高光/镜面反射/玻璃拟态
4. **色彩克制（Color Restraint）**：每个页面主色 ≤ 2 种，功能色仅用于状态指示。**点缀色**（图标浅底 / 笔触 / 关键数值，每屏 1–2 处）不计入主色数量，也不承担状态语义；页面以素净为主，不等于禁止彩色点缀（判例：CASE-DESIGN-030）
5. **动效适度（Motion Modesty）**：过渡动画 150-250ms，仅使用 opacity/transform（GPU 加速）
6. **渐进增强（Progressive Enhancement）**：基础体验不依赖 backdrop-filter（低端设备友好）
7. **同一套数据（One Source, Multi Entry）**：能够顺路产生的数据，尽可能不要单独填写，但可以保留多个入口——只要做到读取、写入、写出的数据是同一套数据。例如活动数据必然携带诸多副产物字段，赋权这类副产物应整合进活动数据流，而非另起一套与活动数据割裂的记录。可验证条件：`has_parent(entity, byproduct)` 且 `parent_record[byproduct] == 所有入口读取值` 视为通过；存在独立表/独立数组承载同类副产物数据 → 违反。（2026-08-02 确立）
8. **降低填写负担（Low Friction Filling）**：降低每一个功能的填写负担，让填写者愿意填写、有正向反馈（确实完成了某项工作，且启动不那么困难）。三个可验证条件：① `field_derivable(field)` → 必须自动填充/预填，不得要求手填；② `action_completed` → 必须有正向反馈（toast / 状态流转 / 记录可见）；③ 从待办/列表到可操作状态 ≤ 2 跳，启动直达。（2026-08-02 确立，呼应原则 2 最小三成本）
9. **信息密度精确原则（Precision of Information Density）（2026-08-10 确立，战略级）**："执行委托与知情监督是对应的，统一的。统筹是最大的管理！"——赋权链（执行委托的操作边界）与按人视图（知情监督的信息边界）对应统一，是同一枚硬币的两面；"一个尽可能降低管理摩擦的方向是任何角色的信息可见范围，应精确等于其职责空间所需的最小充分信息"——**信息可见性是职责空间的投影**。信息密度分层：**L0 个人视角**（自己）/ **L1 条线视角**（上级看下级的条线在办：谁在干什么、有无异常）/ **L2 全局视角**（支书看全部条线+块块）。向上越层需职责依据（赋权链），向下缩层是对他人职责空间的保护。**看与做相区分**：做与看是分工运行保障的一环（[P-012 分工的运行保障](../../01_strategy/SECRETARY_DIRECTIVES.md#p-012-分工的运行保障执行委托与知情监督的统一)）——监督停留在"方向把握"（P-027②），不沉入"细节干预"；内控失效的常见入口是"知情过载"（看到他人操作细节→越过职责边界干预/代劳）。可验证条件：某角色可见信息超出其职责空间所需（可见他人操作细节但无监督关系）→ 违反；按人视图按赋权链投影、不含操作细节 → 通过。设计落点：支书工作台全局概况以统一待处理主队列为先，待决定/确认与异常/督办分开；责任线、指标和趋势按需展开，按人视图仍按赋权链投影、异常可直达。
10. **高频零跳转（High-Frequency Zero-Jump）（2026-08-10 确立）**：最小三成本的最终验收标准落在「**完成一个高频工作，需要操作多少次？信息的展示是否和操作在同一个地方，便于参考？**」。①**答复类置顶待办**：汇报答复是支书最高频动作，待办 tab 顶部内建「待答复」收件箱（问题优先排序、行内填写即发、零跳转），而非藏在全局概况→按人→汇报区多层之下；②**答复回路全角色化**：信息流畅是双向的——其他角色同样有答复机制（组长可答复本组组员，支书仍全局可见，P-012 做与看不破坏）；③**工作概况三区总览**：全部角色新增「工作概况」tab，汇报（待我行动，信息展示与操作同屏）/卡点（我的超期+条线缺口）/在办（我的聚合+条线态势）三区上下排布、问题优先，让"看到"与"操作"在同一可视区域。可验证条件：① 完成任一高频工作的点击/跳转次数 > 2 → 违反（呼应原则 2 操作成本）；② 某数据与其操作入口不在同一可视区域（需滚动/跳转才能从看到变为操作）→ 违反；③ 某角色存在单向汇报却无答复回路 → 违反；④ 待办列表顶部存在比"答复类"更高频的动作类型 → 违反。孤零零数据行（不属于任何卡片的裸 `div` 字段，数值与结论与卡片冗余）属信息成本冗余，须整合进卡片或直接删除。
11. **工作进度指标设计（Progress Indicator Design）（2026-08-10 确立，战略级）**：工作进度的指标设计与显示必须谨慎——**"已完成 N"是无信息量的存量统计**，只可作为归档统计信息存在于归档库；面向"要完成的工作"，进度指标必须指向"进行时与未完成"（待办/待完成/超期/缺口/进行中），并提供信息增量与操作入口。①**只显未完成类**：工作界面（工作台 tab、概况、详情）不得出现"已完成 N/总数"式无差异存量统计；"已完成"仅在归档库/归档统计中出现；②**可下钻**：进度数字/聚合须可点击进入具体任务清单或详情（信息展示与操作同地，呼应原则 10）；③**从"看"到"做"**：概况"在办"区列出具体可点击条目（待办→定位工作台待办 tab 对应任务；活动/专班→下钻只读详情视图），杜绝"只有数字没有入口"。可验证条件：① 工作界面出现"已完成 N/总数"类存量统计（归档库除外）→ 违反；② 进度数字聚合不可点击、无下钻入口 → 违反；③ 概况在办区仅显示聚合数字、无具体条目 → 违反。
12. **工作台集成制（Workspace Integration）（2026-08-10 确立）**：角色单页制后，**视图切换（header 工作台切换 / sidebar 切换）已失去作用——每个人就是每个人**；组织者与深度参与者的所有信息均集成在工作台中，任务来了就都在工作台内完成，不再依赖任何"切换到某角色视角"的入口。可验证条件：出现需"切换到某角色/视角"才能完成的操作路径 → 违反；信息展示或操作入口越出工作台边界（依赖别的页面）→ 违反。
13. **文件流外发确认闭环（External Dispatch Confirmation）（2026-08-10 确立，战略级）**：任务流/信息流均可通过系统实现，**唯一缺口是"文件流"——文件本体暂靠微信传输**。当任务/材料需微信外发给对方确认时，系统不得静默——发送方须在系统中标记「已通过微信发送给 XX」（外发确认），接收方在系统内「确认收到」，形成可审计闭环（谁 / 何时 / 发给谁 / 何时确认）。**"总是有内控设计的方法的！！"**——内控设计的必然要求就是：外部依赖（微信）发生时，系统内必须有状态记录兜底。面向支书目标（低成本小程序/服务号与微信原生协同），记录模型保持简单可迁移——"标记已发送"演进为"发送到对方微信"，"确认收到"保持同构。可验证条件：① 存在需微信外发文件的工作环节但系统无外发标记/确认入口 → 违反；② 外发记录缺发送方/接收方/时间任一要素 → 违反；③ 接收方确认后记录未闭环（审计时间线不完整）→ 违反。设计落点：宣传材料上传后「文件外发确认」模态（标记已微信外发+选择接收方）；接收方工作台卡点区/异常队列「文件待确认 → 确认收到」。
14. **KPI 行为异化防御（KPI Behavioral Integrity）（2026-08-10 确立，战略级）**：**指标设定必须考虑行为激励——"完成率 100%"类指标会诱导凑数提交，目标即异化**（例：复盘率设 100% → 大家随意提交凑数，违背"从最初设定上我们就只是希望大家提交真问题"的初衷）。面向"要完成的工作"，指标应指向工作的真实意图而非形式完成：复盘要的是"真问题"（问题导向）而非"完成率"；承诺要的是"兑现质量"而非"次数"。可验证条件：① 某指标为百分比/计数类"完成率"且目标设为 100%（或接近）→ 须审查是否诱导凑数；② 指标计量对象与工作真实意图（产出真问题/真成果）不一致 → 违反；③ 指标被形式达成但对工作无信息增量 → 违反。设计落点：复盘 KPI 由「复盘完成率 目标100%」改为「复盘问题 真问题导向」（计量活跃活动复盘中提出的真问题数量，复盘表单内建"提出的真问题"填写）。

### 工作台信息秩序检查（页面“脏”的可验证判据）

“脏”不是卡片或 `div` 数量多，而是用户无法快速看懂当前对象、责任、状态和下一步。审查工作台时按以下顺序检查：

1. **任务层级**：首屏是否明确当前组织/业务范围、最重要的待办或问题、责任人、状态和下一步动作？说明是否先于任务、操作是否被趋势或重复指标遮挡？
2. **对象与责任边界**：页面主对象是什么，谁负责读、写、审批和收尾？角色、支部范围、业务能力包、活动/工作组等概念是否混在同一层？看与做的权限是否分别表达并由服务端验证？
3. **数据形状与载体**：单条对象用详情，有限同类记录用列表，待办用队列，横向比较用表格/矩阵，时间变化用时间线，比例/阶段分布才用图形。不得把关系数据压成互不相关的小卡，也不得为追求紧凑而隐藏必要关系。
4. **信息与动作同地**：每项高频信息旁应有对应操作或明确下钻；操作完成后要看得到状态变化、决定与回传结果。无真实数据源或无明确处理人的数字不进入待办队列。
5. **组件与排版节奏**：标题、对象范围、主任务、状态、次级信息和辅助说明有稳定字号/字重/间距；同一层级组件用同一语义样式。仅在容器承担清楚分组职责时使用卡片，避免重复标题、说明、边框、底色和嵌套容器。

**评审记录最小证据**：页面入口 → 用户任务 → 服务/API/数据源 → 可执行动作 → 成功/失败反馈；另记角色与支部范围、数据形状、桌面/窄屏差异。视觉判断要记录 DOM/布局或交互证据；业务错位要给出服务端或状态流证据。一次评审要检查代表性反例，不能因为一张页面“卡片少”就推导全站规则。

**2026-10-18 全仓深审补充**：① 同一任务只保留一个权威处理位；今天、概况只做摘要、异常与跳转，待办、我的处置承担处理，其他入口不得再长一套行内表单。② 同一实体只用一套空值词表；空串、缺失、未填写、未分组在数据层区分，在展示层统一。③ 结构索引不等于审阅；审阅记录必须有用户任务、主对象、数据形状、主动作、五类问题、结论与证据。
