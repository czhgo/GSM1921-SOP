# 部署与对外对接目录索引（04/deploy/）

> 目录定位见 [DOC_MAP.md §五 目录作用表](../../03_doc_system/DOC_MAP.md#五目录作用表2026-10-24-立)。

## 作用

本目录回答**「系统部署到哪、怎么登录与门控、怎么和学校/党校/微信对接」**，是部署决策与对外叙事的权威入口。

## 不负责什么

- 不写服务器逐键操作步骤——那部分由本目录《服务器部署操作手册》承接。
- 不写安装 / 更新 / 打包脚本的实现——脚本在根 [`deploy/`](../../../deploy/README.md)。
- 不写视觉、组件与数据模型——归 `design-system/`、`data/`。
- 不写业务制度、权限矩阵与代码实现。

## 权威源与派生

- **权威源**：`DEPLOYMENT_GUIDE.md`——部署形态选择、认证与登录门控、对外对接边界都以它为准；附录 A.2 / A.2.1 是安装与更新的步骤母本。
- **派生**：`SERVER_DEPLOY_MANUAL.md` 是面向执行人的操作派生；根 `deploy/` 脚本是自动化派生；包内自动生成的 `DEPLOY.md` 来自同一口径。
- **与 `DESIGN_SYSTEM` 的关系**：本目录**不承担视觉规范**。部署后的页面外观、登录页视觉与组件样式仍以 [DESIGN_SYSTEM.md](../design-system/DESIGN_SYSTEM.md) 为唯一权威；本目录只决定「部署形态、谁能登录、对外怎么接」。

## 知识流向

学校 / 党校的对接诉求与部署踩坑 → 在 `DEPLOYMENT_GUIDE.md` 形成路径选择与门控模型 → 派生操作手册与根 `deploy/` 脚本 → 实测结果与日志回写附录与手册；视觉问题不在此沉淀，回 `design-system/`。

## 是否保留原始材料

不保留。真机截图、读数与日志在 `.ctx/evidence/` 与实例自身的 `server/logs` / `backups`；本目录只存决策与操作结论。

## 维护触发器

- 新增、删除或重命名本目录文件；
- 部署路径、认证方式、门控规则或对接对象变化；
- `server/` 启动约束（端口、生产必设口令、数据落点）变化；
- `DESIGN_SYSTEM` 或 `DATA_MODEL` 的边界变化导致本目录引用失效。
