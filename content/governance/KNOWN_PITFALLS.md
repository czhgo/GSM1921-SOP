# 已知陷阱与上下文丢失教训

> **本文件聚焦 AI 工具使用陷阱**——记录 AI 在上下文丢失后反复犯过的工具使用错误及其纠正，供 Agent 集群按需读取。
> **分工边界**：本文件 = AI 工具使用陷阱；[insights §10](../insights/党支部管理与实务经验沉淀.md) = 业务/制度教训判例。
> OPERATIONS_GUIDE.md §7 保留原则级提醒，本文件提供判例级细节。

## 1. 文件修改持久化陷阱（Edit 虚假成功 → Write 整体覆写）

**原则**：修改关键文件后必须验证磁盘持久化，不能仅依赖编辑器返回值。大文件关键区域优先用 Write 整体覆写。

**判例**：2026-05-20，Edit 工具报告修改 CLAUDE.md 成功（返回 diff 显示正确），但 PowerShell 读取磁盘文件发现修改未持久化。连续 3 次 Edit 均报告成功但实际未写入。最终使用 Python 脚本 `fs.writeFileSync` 才成功持久化。

**虚假确认闭环**：Edit 工具对 CLAUDE.md 等大文件报告"成功"但实际未写入磁盘，与 Read 工具的缓存内容叠加形成**虚假确认闭环**——Edit 报告成功 → Read 返回缓存中的"已修改"内容 → AI 误以为修改已持久化。丙部 P.8/P.9 曾在一次会话中被 Edit 工具报告为写入成功，但下次会话磁盘上仍是"当前无丙部待决策事项"。

**根因**：Edit 工具对大文件（CLAUDE.md 约 500+ 行）的修改可能因缓冲区未刷新而丢失。AI 在写入后未执行 H7 #9 要求的 Python 验证，仅依赖 Edit 的返回值和 Read 工具的缓存内容确认。Edit 的"成功"是工具层面的返回值，不是文件系统的确认——这是 AI 工具链的固有缺陷，不是偶发事件。

**纠正（分层策略）**：

| 文件规模 / 区域 | 推荐方式 | 验证方式 |
|---|---|---|
| 大文件（500+ 行）关键区域（YAML / 乙部 / 丙部 / 日志条目） | **Write 整体覆写** | `Select-String` 验证关键字符串 |
| 小文件（<200 行）或非关键区域 | Edit + 验证 | Python `open()` 读回确认 |

**为什么 Write 整体覆写优于 Edit + Python 验证？** 因为"检测"是事后发现，"预防"是事前规避。Edit + Python 验证的流程是"修改→验证→发现失败→重试"，每次失败消耗一轮工具调用。Write 整体覆写的流程是"构造完整内容→一次写入→`Select-String` 验证"，将"可能失败"的环节从"写入"前移到"构造内容"，而构造内容是 AI 的强项（不会"虚假成功"）。

**为什么不是"所有文件都用 Write"？** 因为小文件（<200 行）的 Edit 失败概率低，整体覆写的成本（重新构造全部内容）高于 Edit + 验证的成本。Write 覆写仅在大文件关键区域（YAML / 乙部 / 丙部 / 日志条目等"虚假成功"高发区）才必要。

**为什么不是"Edit 成功就够了"？** 因为 Edit 的"成功"是工具层面的返回值，不是文件系统的确认。工具返回值和磁盘状态之间可能存在不一致。

**生效条件**：仅在大文件（500+ 行）的关键区域修改时成立。小文件或非关键区域仍可用 Edit + `Select-String` 验证。

## 2. 一改具改执行陷阱

**原则**：术语或制度变更后，必须全仓库搜索确认零残留，不能只改"最明显的几处"。

**判例**：ROADMAP→CLAUDE.md 更名时，仅修改了文件名和部分引用，遗漏了 guides/insights/SOP 中的引用。书记批评"一改具改执行不令人满意"。

**纠正**：修改前用 Grep + SearchCodebase 全仓搜索，修改后再搜索确认零残留。搜索时使用多种模式（精确匹配+模糊匹配+上下文搜索）。

**反面论证**：为什么不每次都全仓搜索？因为简单修改（如修 typo）不需要全仓搜索。判断标准：涉及术语/制度/编号变更 → 必须全仓搜索。

## 3. 临时文件遗留陷阱

**原则**：每次 session 结束前必须清理所有临时文件（.bak/.py 等），零容忍。

**判例**：2026-05 期间，修复乱码时创建了 28 个 .bak 文件和 8 个一次性 Python 脚本，session 结束后未清理。书记批评"这是 Harness 的极大失误，会让我们的文件越来越脏"。

**纠正**：D-0182 确立文件卫生铁律——临时文件用完即删，可复用工具归入 .tools/ 目录。

**反面论证**：为什么允许 .tools/ 目录存在？因为 3 个可复用工具（diagnose_garbled.py/audit_yaml_headers.py/verify_content_safety.py）确实需要持久化存放。

## 4. 上下文丢失后制度推断陷阱

**原则**：上下文丢失后，不得自行推断制度安排，必须读取 CLAUDE.md 和对应 guides 确认。

**判例**：赋权关系链修正了三轮——第一轮遗漏了组织委员的专班赋权，第二轮混淆了管理者只读和成员只读的区别，第三轮才与 COMMISSIONER_FRAMEWORK.md 对齐。

**纠正**：遇到权限/角色/制度相关问题时，先读取对应 guides 文件确认，再动手修改代码。

**反面论证**：为什么不每次都读取所有 guides？因为 token 有限，按需读取更高效。判断标准：涉及角色/权限/制度 → 必须读取对应 guide。

## 5. 经验沉淀位置陷阱

**原则**：经验沉淀写入 insights 前必须比对既有结构，兼容则追加，不兼容则写入丙部。

**判例**：曾将 AI 运行规则（上下文连续、Harness 工程）写入 insights 的"管理哲学"章节，与"专供人类阅读"的定位产生张力。后经书记决策，insights 保留管理哲学，AI 行为规范可写入 CLAUDE.md。

**纠正**：写入前检查目标文件的结构定位，确认内容与定位匹配。

**反面论证**：为什么不全写入 CLAUDE.md？因为 CLAUDE.md 是"怎么做"（执行规则），insights 是"为什么"（管理哲学），两者不可混同。

## 6. 工具选择陷阱

**原则**：选择最合适的工具，不要默认用 Python 脚本处理所有问题。

**判例**：修复乱码时，先用 11 个 Python 硬编码脚本处理简单模式，但复杂问题（如"党支"→"党支书"的上下文推断）无法用硬编码解决。书记批评"不是所有修复工作都需要 py 脚本来实现"。

**纠正**：D-0182 确立工具选择层级——MCP 工具（Read/Edit/Grep）> LLM 推理 > Python 脚本（仅用于批量操作）。

**反面论证**：为什么还需要 Python 脚本？因为批量操作（如全仓 YAML 修复 22 个文件）用 MCP 工具逐个修改效率太低。

## 9. 对话总结虚假完成陷阱

**原则**：接续会话开始新工作前，必须用 Grep 验证前序会话的"对话总结"描述与实际代码状态一致，不得仅凭总结描述就认为某项修改已完成。

**判例**：T94 权限系统第 4 轮成果补强时，前序会话的对话总结声称"11 个 entry 已添加 storageKey 参数"，但接续会话 Grep 验证发现实际只有 6 个 entry 添加了 storageKey，5 个 entry（party-disc/party-org/party-secretary/ws-prop-commissioner/ws-disc-commissioner）完全未添加；另有 2 个 entry（ws-deep/ws-leader）虽有 storageKey 但 activate 仍为硬编码未改为 activeTab。总共 7 处遗漏。

**根因**：AI 在生成长会话的对话总结时，可能基于"应该完成"的预期而非"实际完成"的证据描述工作成果。特别是在多轮工具调用、多文件修改的长会话中，AI 可能将"计划中的修改"误记为"已执行的修改"。这与 §1 的"Edit 虚假成功"不同——§1 是工具返回值与磁盘状态不符，本节是 AI 总结描述与磁盘状态不符。

**纠正（验证策略）**：

| 场景 | 验证方式 |
|---|---|
| 接续会话开始前 | Grep 验证前序总结声称的"已修改文件清单"与代码实际状态一致 |
| 会话结束前 | verification-before-completion（Grep 零残留 + GetDiagnostics） |
| 对话总结生成时 | "已修改文件清单"必须附 Grep 验证证据，不得仅描述"已添加/已修改" |

**为什么必须 Grep 验证而非信任总结？** 因为总结是 AI 生成的内容，可能包含"应该完成"的预期描述。Grep 是对磁盘状态的直接查询，不受 AI 记忆影响。信任总结等同于信任一个可能基于错误前提的描述。

**为什么不是"每次会话都重新审计所有文件"？** 因为接续会话只需验证"前序总结声称的修改清单"，不需要全仓库审计。判断标准：前序总结提到的每个"已修改文件"都应用 Grep 验证关键标识符是否存在。

**为什么不是"Edit 失败"问题？** 因为如果 Edit 工具报告失败，前序会话会立即重试或换用 Write。本次问题是 Edit 可能成功执行了部分修改（tab-bar.js 组件改造），但 entry 调用方的修改（添加 storageKey 参数）未执行——AI 在总结时将"计划"误记为"已完成"。这是 AI 认知层面的问题，不是工具执行层面的问题。

**与 §1 的区别**：§1 是"Edit 报告成功但磁盘未持久化"（工具层面），纠正措施是改用 Write。§9 是"AI 总结声称完成但磁盘未执行"（认知层面），纠正措施是 Grep 验证。两者可能叠加——Edit 虚假成功 + AI 总结虚假完成，但根因不同，纠正措施也不同。

**生效条件**：仅适用于"接续会话"场景——前序会话留下对话总结，接续会话基于总结继续工作。同一会话内不适用（因为 AI 清楚知道自己刚做了什么）。

**防范措施三层**：
1. 会话内：每次"完成一批修改"后立即运行 Grep 验证，不等到会话结束
2. 会话末：verification-before-completion（Grep 零残留 + GetDiagnostics）作为强制出口
3. 接续会话首：Grep 验证前序总结声称的修改清单与代码实际状态一致后再开始新工作
